Si tira, non si inietta. Successo e staleness di recollect vengono esposti per un giudizio umano — non diventano mai termini di score silenziosi né auto-cancellazioni. Se una vista live a metà sessione e la capture non coincidono, vince sempre la capture.

Memoria curata

Remember/recall funzionano solo su corpus con memory_scope = "global" o "project" in kb.toml (oppure creati dal plugin Claude kb-memory + /kb-setup). Un corpus di soli artefatti non basta.

# minimal memory corpus (then restart the daemon)
# [kb.memory]
# path = "/home/you/kb-memory"
# memory_scope = "global"

kb remember "We pin arrow and lance to the same version" \
  --title "Arrow/lance pin" --salience 0.9 --tags "invariant,build"

kb recall "arrow lance version"
kb recall "arrow lance version" --explain
kb forget <id>

Verificare con kb recall "test" / kb status. Risultati vuoti o in errore di solito significano che non è montato alcun corpus con memory scope.

Recall fa fan-out sui corpus di memoria in scope e ordina con una formula fissa: rank-position × salience × decay. Supersede è un tombstone applicato al momento del recall (la cronologia resta ispezionabile). Forget elimina fisicamente il file dell’artefatto di memoria. Pin tiene una memoria sopra il pavimento del decay. Promote (SPA) copia una memoria in una kb ordinaria (non di memoria) e rimuove i meta di memoria (salience/decay/pin/supersedes) — non è un passaggio project→global dentro i corpus di memoria, e non esiste il verbo CLI kb promote.

Per un gate umano invece della scrittura immediata: kb propose → kb proposals list|approve|reject. L’approvazione usa lo stesso percorso di scrittura di kb remember.

Sessioni episodiche

# Why is this file the way it is? (path → sessions + decisions + commits)
kb why path/to/file.rs

# Have we done something like this before? (semantic over session digests)
kb recollect "federated search fan-out"
# sessions similar to another session's digest (session id, not a file path):
kb recollect --similar-to <session_id>

kb sessions list
kb sessions show <session_id>
kb sessions read <session_id>
kb sessions by-commit <sha>
  • kb why — ricostruisce le sessioni passate che hanno toccato un path, con prompt, decisioni e commit (confidence etichettata).
  • kb recollect — ricerca semantic sui digest di sessione; espone recency, errori e commit così si può decidere quanto fidarsi di un hit.
  • Id di sessione canonico — recuperato dal sessionId del transcript stesso (ground truth), non da un nome file troncato.

La superficie indicizzata è un digest deterministico, non il JSONL grezzo. Il testo completo del transcript è evidenza da tirare on demand; la ricerca predefinita resta pulita.

Capture e hook

Claude Code (e gli adapter di harness affini) catturano allo Stop (e agli hook correlati). Una sessione lunga può produrre molte righe di capture; gli strumenti list/show limitano le letture alla capture più recente, così i conteggi non si raddoppiano.

Setup per Claude Code: marketplace + plugin kb-memory + /kb-setup. Per altri agent: invocare gli stessi verbi kb da shell; mettere il protocollo in AGENTS.md / nelle istruzioni.

kb sessions capture …     # explicit capture when needed
kb import claude-history  # bulk import historical transcripts

Verificare la capture: dopo un hook Stop di sessione, kb sessions list dovrebbe mostrare una riga. Una lista vuota di solito indica che il daemon è spento, che mancano plugin/hook, o che l’adapter dell’harness non è installato. kb why / kb recollect richiedono almeno una capture con digest indicizzato. Le capture sono solo pull — il daemon non le auto-inietta mai nei prompt.

Progresso di lettura per gli agent

Prima di rivedere un documento lungo, controllare cosa ha effettivamente letto un umano:

kb reading <artifact-id> --json

Il progresso è cumulativo (max-merge), seminato all’apertura, senza rumore SSE. Alimenta anche lo stato di lettura derivato sulle liste di lettura.
