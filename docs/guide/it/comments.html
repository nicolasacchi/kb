Commenti

Umani e agenti lasciano note a margine sugli artefatti renderizzati. Il daemon possiede i file di review; la CLI è l'unica via di mutazione sicura per gli agenti.

Nell'interfaccia

Apri un artefatto e attiva l'annotazione (dock commenti / sheet di ispezione). Clic su un blocco: una selezione di testo diventa un'ancora Selection, un'intestazione un Chapter, un elemento con id una Section. I thread vivono nei file .review/<id>.json di proprietà del daemon (kb-comments/1) — non modificarli a mano; la SPA ascolta gli aggiornamenti in tempo reale via SSE.

Ancore e obsolescenza

A ogni reindex il daemon ri-risolve le ancore aperte. Se un target si è spostato troppo, il commento viene marcato come stale (obsoleto) (badge + dashboard delle ancore stale/obsolete). Il resolver è solo di rilevazione — non riscrive mai in silenzio l'ancora congelata. Quando si sposta intenzionalmente una sezione, si ripunta con l'ancora corretta:

kb comments reanchor <comment_id> --path <artifact> --anchor section:<new-id>

Gli id stabili delle intestazioni nell'HTML di origine sono ciò che mantiene sane le ancore Section tra una rigenerazione e l'altra. Evitare id basati su UUID o timestamp.

Ciclo dell'agente

Turno tipico di un agente:

kb find <path-or-name> --json
kb comments list --path <artifact> --json
# edit the source file on disk (watcher reindexes)
kb comments reply <comment_id> --path <artifact> --body "What changed."
# resolve one comment (kb + artifact id + comment id as positionals):
kb comments resolve <kb> <artifact_id> <comment_id>
# or resolve every open comment on an artifact:
kb comments resolve --path <artifact> --all

Regola di triage

  • Fix chiaro e piccolo (typo, formulazione) → modifica + reply + resolve.
  • Ambiguo o ampio → reply con una domanda o delle opzioni; lasciare aperto.
  • Incerto → reply piuttosto che risolvere in silenzio.

Ciclo in tempo reale da terminale: kb comments watch. Esportare un thread intero con kb comments export; incorporare i commenti in una copia HTML portabile con --embed e rileggerli con import.

Applicare in blocco

Quando un turno di review produce molte mutazioni, inviarle in modo atomico:

kb comments apply --path <artifact> --ops-json '[
  {"op":"add_reply","comment_id":"c_aaa","author":"claude","body":"fixed in §2"},
  {"op":"set_anchor","comment_id":"c_bbb","anchor":{"kind":"section","id":"overview"}},
  {"op":"resolve","comment_id":"c_ccc"}
]'

Tutte le operazioni atterrano o nessuna; un solo aggiornamento SSE. Un batch non può fare reply a un commento che crea nello stesso batch (gli id sono assegnati dal server).

Identità (attribuzione, non autorizzazione)

kb può registrare chi ha agito — identità dal bordo della rete (es. Authelia Remote-User su un hop fidato), token API per utente, o l'operatore loopback configurato — e associa per utente lo stato di lettura e l'autorialità dei commenti.

Ciò che non fa: password, ruoli, token di sola lettura o ACL. Ogni identità ammessa è un co-operatore a pieno titolo. L'unica eccezione di igiene: modificare o eliminare il body di un commento è riservato al proprietario (altrimenti 403). Resolve, reply, attach e reanchor restano aperti a tutti i collaboratori.

author: you|claude è la distinzione di ruolo umano↔agente; il campo user è la stringa di identità.
