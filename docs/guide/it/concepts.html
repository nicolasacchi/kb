Cinque sostantivi

SostantivoCos'èDove viveVerbo principale
artefatto (artifact) Un deliverable HTML o Markdown — l'atomo che kb indicizza e serve Una cartella sorgente (un corpus) kb search / kb get
nota (note) Un artefatto Markdown con [[wikilinks]] e checklist GFM Dentro una kb (kb-category: note) kb notes
lista (list) Una lista di lettura ordinata e consapevole delle sezioni; lo stato di lettura è derivato Documento kb-list/1 per-kb kb list
memoria (memory) Un fatto curato ed esplicito per l'agente, richiamato in modo deterministico Un corpus di memoria (globale o di progetto) kb remember / kb recall
sessione (session) Un transcript episodico di un agente, indicizzato come digest, solo in pull Store delle sessioni accanto a ogni kb kb why / kb recollect
Memoria ≠ sessione. La memoria è ciò che si è scelto di conservare (curata). Una sessione è ciò che è successo (episodica). kb recall risponde a «cosa sappiamo?»; kb why / kb recollect rispondono a «cosa abbiamo fatto, e possiamo fidarci?».

Daemon e kb

Un daemon è un processo in esecuzione (default http://127.0.0.1:4000). Se ne possono far girare diversi in parallelo su porte diverse. Ogni daemon monta una o più kb — una kb è semplicemente una cartella nominata di artefatti dichiarata in ~/.config/kb/kb.toml (o aggiunta con kb add).

Un solo processo può federare ricerca, recall, sessioni, liste e note su ogni kb montata. È multi-kb su un daemon — non un proxy multi-daemon. Il tooling di flotta (kb fleet status, SPA Settings) osserva molti daemon; non unisce i loro corpus in un'unica ricerca.

Come funziona l'indicizzazione

Per il lavoro quotidiano non serve un job di «indice» separato. Il daemon osserva le cartelle sorgente e mantiene l'indice aggiornato.

source folders │ file watcher (~400ms debounce) ▼ parser → title · headings · tags · category · prompt · link edges │ per-kb back-pressured ingest ▼ indexer → storage → lance (vectors + body) + sqlite (metadata) │ ▲ └── embedder sidecar (out-of-process) ──┘ │ axum server ◄─┘ REST /api/* · SSE events · SPA · artifact subdomains
  • Gate su content-hash — i byte invariati non vengono riparsati né ri-embedded.
  • Quarantena — i file non parsabili compaiono nell'API di quarantena invece di sparire.
  • Percorsi forzati — kb reindex ri-percorre; kb reset --kb NAME azzera lo stato dell'indice (i commenti in .review/ restano salvo con --all).

Gli id degli artefatti sono un digest esadecimale stabile di 12 caratteri del path relativo alla sorgente. Rinominare cambia l'id; modificare il contenuto no. Preferire il motore di relocate (kb mv / API move) agli spostamenti grezzi sul filesystem quando contano commenti e history.

Cosa kb rifiuta (decisioni registrate)

Questi sono confini di scope, non funzionalità mancanti:

  • Niente LLM nel daemon — ranking e digest restano deterministici; i passi LLM vivono nelle skill/comandi dell'agente.
  • Niente editor CRDT / multiplayer — commenti e file .review sono la superficie di collaborazione.
  • L'identità è attribuzione, non autorizzazione — kb può nominare chi ha agito (identità dal bordo / token / operatore loopback) ma non gestisce password, ruoli o ACL. Ogni identità ammessa è un co-operatore.
  • Il mount del corpus è l'ACL — ciò che il daemon monta è ciò che serve. La condivisione oltre un confine di trust è kb share oppure un daemon pubblico dedicato.
  • Il mobile è un reader + slot di cattura, non un editor.
  • Niente server MCP ancora — la CLI è il protocollo finché un harness non può fare shell out.
