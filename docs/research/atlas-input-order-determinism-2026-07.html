The atlas that could mirror across machines

determinism at the algorithm vs the pipeline · Fable frontier run #6 · 2026-07-07 15:40–17:10 CEST · isolated daemon, 40-doc corpus · Rust permutation probe + adversarial verification (0 fatal flaws) · severity: low · status: finding, no code changed

Verdict. kb's atlas layout is reproducible on one machine — bit-identical across four from-scratch rebuilds, and identical whether the corpus is 40 fragments or 1. But the layout function compute_layout is severely order-sensitive (a reverse-permutation of the input moves all 40/40 points, up to 0.81 on a [0,1] scale; k-means seeds centroids by array position, so any reorder can flip cluster colours wholesale), and the pipeline feeds it a non-canonical, filesystem/ingest-dependent input order (unsorted WalkDir → merge_insert insertion order → unordered lance scan — all verified in code). The function's invariant #3 ("same inputs → bit-identical across machines") is correct and golden-tested — order is part of "the input." What is unpinned is the pipeline that produces that order, so the operator-facing expectation "same corpus → same atlas everywhere" is not guaranteed across machines. The atlas is a non-load-bearing visualisation, so this is a latent, low-severity gap — with a one-line fix.

1 · Closing run #5's open gap

Run #5 audited search determinism and left one surface explicitly untested: the atlas, because its coordinate endpoint looked SPA-only. It is not — GET /api/kb/{kb}/docs?include=atlas returns atlas_x/atlas_y/atlas_cluster (lance.rs:1232). Run #5's static hypothesis was that the atlas input (list_embeddings, no ORDER BY) rides an unpinned scan order and could be non-reproducible. This run tests it empirically, and settles the mechanism.

The surprising part is the scan order: deterministic across rebuilds, yet neither id-sorted nor filename-sorted. 3 · But the layout is order-sensitive — proven

Does the input order actually matter? I injected a permutation probe into atlas.rs (run, then reverted — the tree is clean), calling compute_layout on 40 embeddings and on their reverse permutation, matching each permuted output back to its original doc by index:

FABLE_PROBE order-sensitivity: 40/40 points moved, max coord delta 0.810392

Every point moved, by up to 0.81 on the normalised [0,1] canvas — a near-total re-layout. The mechanism is in committed code: UMAP init draws RNG per input in array order (atlas.rs:253), and k-means seeds centroids by index into the input slice (atlas.rs:414, empty-cluster reseed at :454). An f32 check confirms the same values summed in different orders diverge at single precision (−5.5996265 vs −5.5996256), which the power-iteration accumulates. Reverse is a worst case — but note k-means is positional, so even a single-file reorder changes the centroid seed set and can renumber clusters, flipping colours wholesale while geometry barely moves. At the invariant's own bit-identical bar, any reorder is a divergence.

4 · The pipeline that leaves order unpinned

Verified end to end against the source:

unsorted WalkDir (indexer.rs:303, watcher.rs:278 — no .sort_by)
        ↓  readdir order — filesystem-dependent (ext4 htree ≠ xfs ≠ tmpfs ≠ apfs)
merge_insert on "id" (lance.rs:526) — insertion/fragment order, NOT id-sorted
        ↓
list_embeddings (lance.rs:1392) — select/execute, NO ORDER BY, returns scan order
        ↓  order-preserving .unzip()
compute_layout(&embeddings, k, DEFAULT_SEED) (atlas.rs:648) — order-SENSITIVE
The precise framing (the verification's sharpest correction). Invariant #3 is scoped to compute_layout(embeddings, k, seed) "for the same inputs," and it holds: the function is IEEE-754-deterministic for a fixed input order, and the golden test pca_layout_golden_coords_pin_cross_libc_determinism pins its bits across glibc/musl/macOS. A permuted slice is a different input, so the function does not break its literal contract. The gap is one level up: recompute_for_kb_with never canonicalises input order before calling the order-sensitive function. CI never catches it because no test permutes the input — every determinism test passes the same slice twice. The invariant is right; the pipeline around it is unpinned.

5 · The synthesis with run #5

Runs #5 and #6 are one finding seen twice. kb pins determinism at the algorithm boundary — a fixed seed, IEEE-754 bit-stability, a cross-libc golden test — but leaves the pipeline input order to an unsorted lance scan. Search surfaces it as the missing tie-break (tied BM25 scores resolve by physical order); the atlas surfaces it as the cross-machine input-order gap (an order-sensitive layout fed a readdir-ordered input). Same root, and the same family of one-line fix: pin the order with an explicit sort.

6 · The fix

One line, kb-controlled, robust. In recompute_for_kb_with, right after let pairs = list_embeddings().await? (atlas.rs:609): pairs.sort_by(|a, b| a.0.cmp(&b.0));. Artifact ids are source-relative path hashes (root invariant #27) — machine-independent — so sorting by id canonicalises the layout input regardless of readdir or lance scan order, making invariant #3's "across machines" promise hold end-to-end. (Sorting the WalkDir is weaker: it fixes ingest order but still trusts lance to preserve insertion order into an unordered scan, which is lance-internal and undocumented — do the sort at the atlas boundary.) The reverted probe should land as a permanent test: compute_layout(emb) vs a permuted emb, matched by id, asserting equal coords + clusters — which today would fail, and after the fix would pass.

7 · Honest bounds

  • Severity is low. The atlas is a visualisation, not search/recall/integrity; each kb computes its own atlas on its own store; cross-machine atlas comparison is rare. This is latent under-enforcement, not an active bug.
  • Cross-machine divergence is a code-grounded inference, not 2nd-machine data. I ran on one machine; "readdir is filesystem-dependent" is well-established (the project already treats this class as first-class — invariant #3 bans HashMap-iteration order, and a prior cross-libc fix exists), but I did not reproduce on a second machine.
  • Two candidate causes for the stable order, not isolated. The scan order could be governed by readdir or by the async back-pressured ingest/embed scheduling — both are unpinned across machines, both point the same way, and the id-sort fixes either, so the conclusion is robust while the exact mechanism is one of two.
  • Local reproducibility is code-predicted + observed, not "proven." The daemon restart lifecycle was flaky; I wiped state and confirmed a fresh 0→40 index before each capture, and the deterministic-compute + stable-on-disk-scan code predicts the identical results I saw — but treat it as strongly-observed, not a formal proof.
  • 0.81 is a ceiling. Reverse permutation is worst case; a small real reorder moves continuous coords less — the more likely visible symptom of a small reorder is cluster-colour renumbering, not big coordinate jumps.
