The briefing invites three challenges. We do all seven. Each names the decision being pushed back on, the specific evidence, and a concrete alternative position. Some recommend kept-as-is; some recommend changed. The most substantive bug caught is push-back #3 — the proposed iframe sandbox is storage-broken without a subdomain-per-artifact serving model.

Headline pushbacks

#3 — The proposed iframe sandbox is storage-broken. allow-scripts allow-popups + own origin = no localStorage at all. Fix: subdomain-per-artifact + tighter flags. #4 — The SSE event taxonomy needs a published JSON Schema; the proposal mentions one envelope shape but no formal contract. #1 — Plugin / extension alternatives to the daemon were considered and rejected — Obsidian, Karakeep-fork, TiddlyWiki — each fails on at least one load-bearing requirement (observability, agent-ingest HTTP API, headless self-host, HTML-as-primary-unit). #7 — The "no MCP" decision is defensible but worth re-examining once kb's HTTP API exists; an MCP wrapper is small.

  1. Challenge #1 · Architecture · alternatives to the daemon

    Plugin / extension reframings considered and rejected — daemon is the right path

    The briefing locks in "one daemon + thin clients" with HIGH confidence. Three alternative paths were evaluated against that — each promising fewer lines of code by reusing an existing tool — and each rejected on the same set of load-bearing requirements:

    1. kb-as-Obsidian-plugin. Register .html as first-class, render in a sandboxed iframe pane, store prompt metadata in YAML frontmatter, lean on Smart Connections for vector search. Fails on: Obsidian plugins can't expose an HTTP API for other Claude Code sessions to ingest into; can't run headless on a self-host server; the markdown-vault model fights HTML-as-primary-unit; and there is no streaming surface a TUI can subscribe to for live observability.
    2. kb-as-Karakeep-fork. Karakeep ships self-host + FTS + AI tagging + multi-client. Add an "artifact ingest" endpoint accepting inline HTML + prompt instead of a URL. Fails on: Karakeep's data model is "URL + captured snapshot," not "authored artifact + prompt"; reshaping it is invasive. No SSE event stream for a TUI. Long-term fork-maintenance burden owns the merge conflicts forever.
    3. kb-as-TiddlyWiki-extension. TiddlyWiki takes "everything in HTML" seriously; a plugin could treat each artifact as a tiddler. Fails on: TiddlyWiki's quine architecture (one self-modifying file = the whole stack) is incompatible with kb's external-indexer + thin-clients model. No daemon, no agent ingest, no remote thin clients.

    The four load-bearing requirements that decide it:

    • Observability surface. Ratatui TUI live-watching SSE during indexing/generation is part of the product.
    • Programmatic agent ingest. kb's HTTP API hit by other Claude Code sessions and external tools.
    • Headless server-side use. Self-host on a personal server with thin browser/CLI/TUI clients hitting it remotely.
    • HTML files on disk as primary unit. One self-contained .html per artifact — not markdown-with-html-guest, not capture-snapshot, not single-file-quine.

    Verdict: the daemon path is confirmed. The plugin / extension alternatives stay documented in topic 08 as "considered, rejected" — they shouldn't be reopened without new evidence that one of these requirements has changed. The fact that all four exist together is precisely the wedge that justifies the bespoke daemon.

  2. Challenge #2 · Storage · alternatives not considered

    FAUST / FoundationDB-style "one log, many materialised views" was missing

    The briefing considered lance vs sqlite vs surrealdb vs duckdb-vss vs sqlite-vec — all state stores. None of the alternatives consider append-only event-log architecture: every ingest is an event, all state derived deterministically by replaying. In Rust, this would be:

    • fjall (LSM kv store, 2024–2026 active) — appendable log + secondary indexes by reduce.
    • redb (1.x stable, BSL-then-Apache, single-file ACID) — pair with tantivy for FTS and a flat-file vector store.
    • SlateDB + S3 — overkill for single-user, but interesting for the self-hosting roadmap.

    Why this matters for kb specifically: the briefing says "every cross-store write is idempotent. retries are safe." That's hard with a lance + sqlite split (two stores, two transaction boundaries). Trivial with an event-log: each event is the only source of truth; the rebuild is deterministic. And it solves the schema-versioning question (replay with new code → new schema, no migrations).

    Honest counter: event-sourcing for a 50k-doc personal app is over-engineering. The bytes-on-disk argument also evaporates — sqlite-vec gets you to ~3–8 MB binary, an event log doesn't beat that. The only reason to pursue this is if you want "deterministic rebuild from disk" as a principle, which is a luxury for kb's scale.

    Recommended action: note the pattern, defer to v2 unless schema migrations become painful. Topic 01's recommendation to spike sqlite-vec first stands.

  3. Challenge #3 · Iframe sandbox · the proposed flags are storage-broken

    "allow-scripts allow-popups" without same-origin = SecurityError on every storage call

    Topic 06's research is unambiguous: without allow-same-origin, the iframe is treated as an opaque origin. localStorage.setItem(), indexedDB.open(), document.cookie all throw SecurityError. The proposed flag string would silently break any artifact that tries to persist anything.

    Adding allow-same-origin is the trap: combined with same-origin serving, the iframe sandbox is trivially escapable (parent.document.querySelector('iframe').removeAttribute('sandbox')). MDN, WHATWG, the W3C HTML validator all warn.

    The right answer is the CodePen / Observable / Claude pattern: serve each artifact from a separate subdomain (<id>.artifacts.localhost, wildcard DNS+TLS). Then allow-scripts without allow-same-origin still leaves the artifact with a real, persistent, isolated origin. Storage works. Sandbox-removal attack is neutered (subdomain ≠ parent).

    When shadow DOM IS the right call: for the JS-free artifact subclass — pure HTML/CSS/SVG, no <script>, no external libraries. Detect at ingest. Render those without the iframe overhead. Everything else: iframe. Topic 07's grep of all 20 reference artifacts confirms ~6/20 are JS-free and would benefit from shadow-DOM rendering.

    Recommended action: adopt topic 06's recipe. Subdomain serving is non-negotiable.

  4. Challenge #4 · SSE event taxonomy · no published schema

    The brief mentions "structured events" but ships no JSON Schema

    Two clients (TUI, SPA) plus the CLI all subscribe to SSE. The current proposal: dotted event names (index.progress, file.added, etc.) and an envelope shape. No JSON Schema, no field-level docs, no version semantics. Fragile contract.

    Topic 04's research lands on a baseline envelope: {v, id, type, ts, payload}. That's the right shape. The work that's missing:

    1. Per-type JSON Schema files. Author once, validate on producer (server) and consumers (TUI/SPA).
    2. Public schema endpoint: /events/schema/{type}/v1.json. Schemas served from the running server are the source of truth, not in-repo files (those are dev-time mirrors).
    3. Versioning rules: v bump only on breaking change. Renames/removals run ?v=1 and ?v=2 side by side through a deprecation window.
    4. A kb events introspect CLI subcommand that returns the live schema set, so external agents can self-describe.

    Anti-pattern to avoid: splitting endpoints by domain (/events/index, /events/files) or by direction (the dual-endpoint trap MCP rolled back in 2025). Keep one firehose /events with a server-side glob filter ?types=index.*,error.*.

    Recommended action: author events.schema.json as part of the v0.0.1 vertical slice — before the TUI subscribes to anything. Treat the schema as a public API.

  5. Challenge #5 · Language · is Rust really the right call?

    Honestly evaluated: Go is closer than the briefing implies; Rust still wins on net

    The briefing flags "rust as primary language" with HIGH confidence and forbids language switches without evidence. Here's the honest evidence comparing the three plausible alternatives:

    • Go: almost every reference in the prior-art scan is Go (Syncthing, Tailscale, Karakeep deps, k9s, lazygit, gh-dash, readeck). Faster compile, simpler concurrency story (goroutines vs tokio), single-binary distribution is the language norm, far more ecosystem for the daemon-and-clients shape. Real cost: no fastembed-rs equivalent (would need to call Python or use onnxruntime-go directly); ratatui equivalent is tcell/tview/bubbletea — usable but each smaller than ratatui's ecosystem in 2026; LanceDB has a Go client but the embedded story is Rust-first.
    • Zig: no embedded vector store, no ratatui equivalent, no axum equivalent, file watcher story would be hand-rolled. Fast, fun, wrong tool.
    • OCaml: dream + ocaml-tui-rs-equiv-doesnt-exist + … nope. Also slower compile.

    The strongest case against Rust is the binary size hit from lance + Arrow + DataFusion (40–80 MB stripped — see topic 01). A Go equivalent shipping just sqlite-vec + tantivy-go + ratatui-go-stub would land at ~15–25 MB. That's a real loss.

    The strongest case for Rust is the embedding stack: fastembed-rs is the most mature single-process embedding library in any language right now (topic 02). Go's onnxruntime-go needs hand-written tokenisers; Python integration adds a second runtime; the convenience gap is real.

    Verdict: Rust still wins on net given the embedding requirement. If kb dropped vector search and shipped pure BM25 (topic 02 confirms BM25-alone is competitive for code-heavy corpora), Go would be the better call.

  6. Challenge #6 · Packaging · single binary vs workspace

    Single binary is right for distribution. Workspace is right for source. They're not mutually exclusive.

    The briefing conflates "one binary for users" with "one crate for developers." These are separate decisions:

    • Distribution: single kb binary with subcommands (kb serve, kb tui, kb search, kb add, …). Confirmed correct — matches Tailscale, kubectl, gh, etc.
    • Source layout: a Cargo workspace with kb-core (lib), kb-server (binary), kb-cli (binary), kb-tui (binary), kb-spa (web bundle, separately built and embedded via rust-embed). Each crate has tight scope and tests against kb-core only. Then a single top-level kb binary that depends on the binary crates and dispatches subcommands.

    Why workspace: compile-time guard against business logic leaking into the TUI/CLI. kb-core doesn't depend on tokio::sync::broadcast; only kb-server does. kb-tui doesn't depend on lancedb; it depends on kb-client (a thin HTTP wrapper around the kb daemon API). The dependency arrows are the architecture diagram.

    The trick: bundling many binary crates into one ship-able binary. Use cargo build --release --bin kb where kb is the top-level dispatcher. The workspace lets you also cargo build --release --bin kb-server for users who want only the server (e.g. a self-host appliance). Best of both.

    Recommended action: workspace with kb-core + 4 binary crates + 1 top-level dispatcher. Single binary in the GitHub releases page.

  7. Challenge #7 · MCP · the "no MCP, only CLI" decision

    The briefing says HIGH-confidence "no MCP." Defensible — but worth revisiting once the HTTP API exists

    The briefing's reasoning: "transparency over magic." Claude Code calls kb search as a shell command, the operator sees it. MCP would hide the same call behind a tool-use wrapper.

    Three counter-arguments to keep in mind:

    1. MCP servers are often thinner than the briefing assumes. If kb has an HTTP API (it does — the SSE topic 04 confirms this), a stdio MCP wrapper is ~150 LOC of tokio + serde_json. The cost of also offering MCP is low.
    2. Streaming results are hard via shell. kb search "x" returns N rows. Claude Code parses them. But what about "watch this folder for new artifacts and tell me when one matches my open thread"? CLI wants exit codes; MCP wants tool-use streaming. The briefing's "no MCP" precludes that flow.
    3. Other agents. Cursor, Cline, Windsurf, Aider all support MCP. CLI-only locks kb to Claude Code's specific shell affordance. If kb wants to be agent-agnostic, MCP is the lingua franca.

    The case for CLI-only stays strong: for the operator's specific workflow (single-user, transparent agent calls), CLI gives the better mental model. The user sees what the agent is doing, can intervene, can run the same command by hand.

    Recommended action: CLI-only in v0.0.1 as proposed. Add MCP wrapper in v0.2 once the HTTP API is stable. Treat MCP as a thin shim, not a re-architecture. Cost low, optionality high.
