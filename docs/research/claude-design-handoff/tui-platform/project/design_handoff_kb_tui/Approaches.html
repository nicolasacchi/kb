kb tui — 5 alternate approaches

The original kb tui.html is a four-panel ratatui dashboard in the k9s/lazygit lineage. Here are five other answers to the same brief, each committing hard to a different premise about what an operator wants from this tool. They're static — the question is which paradigm to invest interactivity in next.

approach · 01

Dense ops console

No sidebar, no activity panel — a single full-screen table, like k9s. Every row is one source across all kbs; columns are the truth. Maximum information per scanline; chrome stripped to a one-line key bar. The activity log is folded into a footer ticker. For operators who want raw signal, no decoration.

approach · 02

REPL / notebook

The session itself is the UI. You type queries, commands, and questions; outputs render below as immutable cells. Status lives in the prompt itself (server pulse, indexing badge, active kb). Closer to jq+jupyter than to a dashboard. Best when the operator is exploring rather than monitoring.

approach · 03

Spatial minimap

Treat the corpus as terrain. Each kb is a block; each cell is one document. Color encodes freshness (saturated = recently re-indexed, faded = old, red = errored, dark = paused). One look reveals where the system is alive vs. stale. Hover/select reveals doc detail in the side rail.

approach · 04

Ambient status board

Designed to live on a second monitor or wall display. Big numbers, sparklines, no input expected. Tokyo-Night palette so it doesn't blow out a dim room. One screen tells you in two seconds: is the system alive, what is it working on, has anything broken. Run with kb tui --board.

approach · 05

Swim-lane timeline

Promotes the activity log to the hero. Each kb is a horizontal lane; events render as colored runs across a time axis. You see when things happened, not just what. Indexing runs are bars; queries are dots; errors are red ticks. Scrub the cursor to read off the moment.
