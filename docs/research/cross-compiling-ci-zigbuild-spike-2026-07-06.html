Cross-compiling kb — the zigbuild spike and the release-CI design

An empirical answer, not a literature review: the full kb binary was actually cross-built on this machine to musl-static and to a pinned glibc-2.31 floor — and the embedder was proven un-cross-linkable. The CI design follows from the measurements.

2026-07-06 · status:open · project:kb · companion: distribution-channel landscape

Thesis

kb's two binaries sit at opposite extremes of cross-compilability, and that asymmetry — measured on real hardware, below — dictates the whole release-CI shape. The main kb binary (daemon + CLI, no ONNX Runtime) cross-compiles under cargo-zigbuild to both fully-static musl and a pinned-old-glibc target, blocked today by exactly one upstream lance build defect. The kb-embedder sidecar can never be zig-linked at all: the failure is a C++ standard-library ABI wall, not a version problem. Therefore: keep the native-runner matrix as the trunk; add zigbuild only as an additive, kb-only "universal Linux" lane; harden the trunk with provenance attestations and a properly multi-arch image.

The spike — setup

Run 2026-07-06, 07:58–09:33 CEST on the development machine: Arch Linux x86_64, 8 cores, glibc 2.43, no AVX-512 (AVX2 present) — a detail that turned out to be load-bearing. Toolchain: zig 0.15.2, cargo-zigbuild 0.23.0 (v0.23.0 released 2026-06-18; README supports zig 0.15+), rustc 1.96.0 (the repo's pinned toolchain). All builds: --locked --profile fast, dedicated CARGO_TARGET_DIR, nice -n 20 ionice -c 3. Full logs: /tmp/kb-distrib-research/spike.md + s1.log/s2.log/s3.log.

S1 — musl-static kb: one lance defect away (link_failure, 29.2 min)

cargo zigbuild --locked --profile fast -p kb-cli --bin kb --target x86_64-unknown-linux-musl

Every crate compiled cleanly for musl under zig cc — rusqlite's bundled sqlite amalgamation, zstd-sys, lz4-sys, ring, blake3, onig_sys, and the whole lance/datafusion/arrow/tantivy graph. The build failed only at the final link:

ld.lld: error: undefined symbol: sum_4bit_dist_table_32bytes_batch_avx512
>>> referenced by FlatIndex/IvfSubIndex::search in liblance-*.rlib

Root cause — fully diagnosed, and it is not musl's fault

lance-linalg 4.0.0's build.rs compiles two AVX-512 C kernels and both emit the same cargo:rustc-cfg=kernel_support="avx512":

  • f16.c — built with an explicit -march=sapphirerapids -mavx512fp16; pragma-vectorised, compiles on any host.
  • dist_table.c — built with -march=native; uses explicit _mm512_* intrinsics that clang gates on evex512. On a non-AVX512 build host, -march=native omits AVX-512 → the compile fails → the object is silently never emitted.

The f16 kernel still sets the shared cfg, Rust code references the extern symbol, and the link dies. Proven with direct probes: zig cc -target x86_64-linux-musl -march=sapphirerapids dist_table.c compiles and defines the symbol (rc=0); -march=native fails on this host. The defect is host-CPU-dependent, not musl/zig-specific — a native gnu build on the same machine would hit it too. Fixes, in order of correctness: (a) upstream lance patch — give dist_table.c an explicit AVX-512 -march like its sibling, and/or stop sharing one cfg across two independently-compiled kernels; (b) build on an AVX-512-capable host; (c) CFLAGS=-march=sapphirerapids — links, but poisons all C with AVX-512 (SIGILL on older CPUs), so it is a diagnostic tool, not a shipping fix.

VerdictFully-static musl kb — a universal Linux binary that kills the glibc floor for the daemon/CLI — is viable and one small upstream fix away. File the lance issue with the probe evidence.

S2 — glibc-floor pinning works end-to-end (success, 27.5 min)

cargo zigbuild --locked --profile fast -p kb-cli --bin kb --target x86_64-unknown-linux-gnu.2.31, run with the one-line CFLAGS=-march=sapphirerapids workaround so lance's dist_table.c compiles (see S1).

  • Linked, rc=0. 175 MB (fast profile, effectively unstripped), ELF 64-bit PIE.
  • Max glibc symbol referenced: GLIBC_2.30 (objdump -T tail: 2.28 / 2.29 / 2.30) — comfortably under the requested 2.31 pin.
  • NEEDED: libm, libpthread, libc, libdl, ld-linux only. No libstdc++ (zero GLIBCXX symbols), no libgomp — the main binary carries no C++ runtime at all.
  • Runs on this host: kb --version → kb 0.22-31-g9279de1c-dirty, exit 0; --help exit 0. (Version/help paths don't execute AVX-512 kernels; this specific binary is not runtime-safe on non-AVX512 CPUs — an artifact of the workaround, not of glibc pinning. A build on an AVX-512 host, or post-lance-fix, has no such poisoning.)
VerdictA GLIBC_2.30-floored kb — Debian 10 / Ubuntu 20.04 / RHEL 8 era, four releases below today's documented Debian 13 / Ubuntu 24.04 floor — is achievable from a single x86_64 runner, gated on the same lance fix as S1.

S3 — the embedder hits a C++ ABI wall, not a glibc floor (link_failure, 20.9 min)

cargo zigbuild --locked --profile fast -p kb-embedder --bin kb-embedder --target x86_64-unknown-linux-gnu.2.31

ort-sys downloaded the pyke prebuilt ORT for the target; ort, fastembed, and tokenizers all compiled. The link then failed on ~40 undefined GNU libstdc++ symbols referenced from inside the prebuilt archive — std::__cxx11::basic_string::_M_append, std::_Rb_tree_rebalance_for_erase, vtable for std::ostream, std::istream::read (referenced by inference_session.cc.o). The link line passes -lstdc++, but zig's cross toolchain provides LLVM libc++, not GNU libstdc++ — the C++11-string-ABI symbols are unresolvable by construction. The planned .2.39 retry was skipped: this failure fires before any glibc version check and is independent of the suffix.

Verdictcargo-zigbuild is a permanent non-starter for kb-embedder while it links pyke's GCC-built prebuilt ORT. The embedder stays on native ubuntu-24.04 runners. Invariant #26's two-binary split is exactly what makes the rest of this design possible.

The ORT constraint, precisely

kb pins ort/ort-sys 2.0.0-rc.12 (via fastembed 5.13.4), which ships ONNX Runtime ms@1.24.2 from pyke's CDN. The authoritative target list (ort-sys/build/download/dist.txt at the tag):

Three findings that go beyond the target list:

  • The glibc-2.39 floor is pyke's choice, not ORT's. pyke builds Linux prebuilts on ubuntu-24.04 with no manylinux sysroot, baking in glibc-2.38 C23 symbols (__isoc23_strtol) and GCC-12 GLIBCXX_3.4.30. Microsoft's own onnxruntime 1.24 wheels are manylinux_2_28 (glibc ≥ 2.28). A CI-built ORT in a manylinux_2_28 container, fed to ort-sys via ORT_LIB_PATH, would lower the embedder floor to 2.28 — at the cost of owning an ORT build (~30–60 min/target; ort-sys expects the full cmake build tree with split onnxruntime_* + _deps/ archives, not one .a). Demand-gated.
  • A second, undocumented floor: x86-64-v3. Since rc.11 the x86_64 prebuilt targets Haswell/Zen1+ (AVX2/BMI2/FMA); older CPUs SIGILL at first inference with no warning from any current kb check. Also from rc.11: ORT is compiled --client_package_build — inter/intra-op spinning off by default, tuned for edge not server throughput. Latent perf regression worth a kb bench pass; not a distribution blocker.
  • Doc correction to land: ORT_STRATEGY does not exist in ort 2.x (kb's Cargo.toml comment, CLAUDE.md, and self-host.md all reference it). The mechanism is ORT_LIB_PATH (deprecated alias ORT_LIB_LOCATION) plus disabling the download feature / ORT_SKIP_DOWNLOAD.

Pure-Rust fallback backends exist (ort-tract, ort-candle) but are a contingency, not a plan: candle measured roughly an order of magnitude slower for BGE on CPU, tract's ort API coverage is partial, Burn can't import bge — and kb calls fastembed, which exposes no hook for alternative backends, so any of them means reimplementing the embed pipeline.

cargo-zigbuild assessment for kb's dependency set

Mechanism: zigbuild substitutes zig cc/zig c++ (bundled clang + lld + multi-version glibc/musl headers and stubs) as the C compiler for cc-crate build scripts and as the Rust linker. The glibc suffix (--target x86_64-unknown-linux-gnu.2.31) pins the minimum version; un-suffixed -gnu already defaults to ~2.28 (varies by zig release). Known sharp edges that matter here: an invalid suffix fails silently to a fallback; version gating is imperfect near the host's own glibc; static glibc (crt-static) is unsupported (musl is the static path); always verify the real floor post-build (objdump -T | grep GLIBC_ — as the spike did).

kb dependencyNative codeMeasured/assessed risk
ring (rustls crypto)C + per-arch asm, target-list-gated build.rsbuilt cleanly in S1/S2 (musl + gnu). Nuance from the verify pass: historical ring×zig failures include genuine zig bugs (e.g. zig 0.16's ar wrapper), not only cc-crate regressions — pin zig + zigbuild versions
libsqlite3-sys (bundled), zstd-sys, lz4-sys, onig_sysvendored C via ccbuilt cleanly — no system headers needed, so zigbuild's -nostdinc never bites

prost-build (lance transitive)needs host protochost tool, orthogonal to the target — install on the runner as today
ort-sys (embedder only)prebuilt GCC-built static ORTpermanent blocker (S3) — GNU libstdc++ ABI vs zig's libc++

The crates that dominate zigbuild's issue tracker — aws-lc-sys, openssl-sys, opencv, linkme — are all absent from kb's Cargo.lock (rustls+ring is the single biggest enabler; keep it). Comparisons: cross-rs (container per target, real GNU sysroot) is the more reliable fallback for heavy C++ and the only option that runs tests under QEMU, at the cost of Docker and per-target images; plain gcc-cross toolchains offer no glibc pinning and per-target host setup. Real-world zigbuild shippers at kb's dependency weight: Cargo Lambda (default engine), Polars (maturin --zig), Astral's uv/ruff/ty (linux-cross + musllinux-cross legs). Maintenance note: zigbuild tracks pre-1.0 zig and the 0.15 transition needed explicit fixes — pin both tools by version/SHA. macOS-from-Linux cross is rejected outright: it needs a redistributed Apple SDK (license gray area for a public MIT repo) and per-arch ORT anyway. Windows targets: zigbuild doesn't support them (moot — non-goal).

The recommended release-CI design

on: push tag v*

job 1  create-release                  (unchanged: gh release create --verify-tag)

job 2  binaries — native matrix        [contents:write, id-token:write, attestations:write]
  x86_64-unknown-linux-gnu   → ubuntu-24.04        (pinned; glibc-2.39 embedder floor)
  aarch64-unknown-linux-gnu  → ubuntu-24.04-arm    (ORT prebuilt confirmed in dist.txt)
  aarch64-apple-darwin       → macos-14            (no strip — ad-hoc signature)
  [optional] x86_64-apple-darwin → macos-15-intel  (kb-only until ort ships x64-mac ORT;
                                                    sunset ~Aug 2027)
  per leg: free disk · protoc · rust-toolchain@1.96.0 · rust-cache key=release-<target>
    · cargo build --release --locked -p kb-cli --bin kb            (no ORT)
    · cargo build --release --locked -p kb-embedder --bin kb-embedder  (static ORT)
    · package + sha256 sidecar
    · NEW actions/attest-build-provenance (subject = archive)     → SLSA Build L2
    · gh release upload

job 3  universal-kb — zigbuild lane    [GATED on the lance-linalg fix]
  one ubuntu-24.04 runner; setup-zig + cargo-zigbuild (both SHA/version-pinned)
    · cargo zigbuild --locked --release -p kb-cli --bin kb --target x86_64-unknown-linux-musl
    · cargo zigbuild --locked --release -p kb-cli --bin kb --target x86_64-unknown-linux-gnu.2.28
    · (later, same runner: aarch64 variants of both)
    · CI assertion: objdump -T | grep GLIBC_ ceiling ≤ pinned floor   (spike-proven check)
    · package as kb-only assets (no embedder; keyword-only degradation documented)
    · attest + upload

job 4  docker — multi-arch             [packages:write, id-token:write]
  matrix: linux/amd64 → ubuntu-24.04 · linux/arm64 → ubuntu-24.04-arm
    each: buildx push-by-digest, oci-mediatypes=true
    Dockerfile: TWO cargo build RUNs (restore invariant #26) · model-fetch stage
    COPY --link'd into runtime (dedupes the 1.34 GB layer across arches) · :slim variant
  merge: buildx imagetools create (tags: X.Y.Z, X.Y, latest, sha; annotations on the INDEX)
    · cosign keyless sign the index digest + cosign attest SBOM
    · attest-build-provenance (subject-digest = index)

Design notes: fail-fast: false throughout so one leg never sinks the others; every expression through env: (the existing injection-safe pattern); per-target rust-cache keys (the two-invocation split compiles kb-core twice per target with different feature sets — both cache correctly under one target key). The zigbuild lane is additive: the combined tarball's floor is always max(kb, embedder) = 2.39, so low-floor assets must ship as kb-only artifacts with the split floor stated plainly. If SLSA L3 is ever wanted, the per-target build moves into a reusable workflow that holds the attestation permissions itself; L2 is the pragmatic target now.

What would change this design

  • lance-linalg fix lands (the gate on job 3) — file the issue now; the spike's zig cc probes are the reproduction. Also unblocks native builds on non-AVX512 hosts generally.
  • ort ships an x86_64-apple-darwin prebuilt (main's platform table lists it) → the optional Intel leg gains its embedder; decide native macos-15-intel vs cross-compiling from arm64 (same SDK) before the ~Aug 2027 runner sunset.
  • ort ships a musl prebuilt (none today, verified in dist.txt) or kb adopts a manylinux_2_28/musl ORT source build via ORT_LIB_PATH → the embedder joins the universal lane and the split floor collapses.
  • The next ort bump (main targets ONNX Runtime 1.27) → re-verify dist.txt, the glibc floor, x86-64-v3, and the --client_package_build throughput posture; pyke changes build environments between rcs.
  • zig/zigbuild churn — both pinned; a zig 0.16-era regression (e.g. the ar-wrapper ring breakage) is contained by the pins and the lane's additive nature.

Verification plan

  1. rc1 smoke (after the public flip): throwaway v0.0.0-rc1 tag; watch all binary legs (the aarch64 ORT download especially), the ghcr multi-arch push, gh attestation verify on one tarball and the image, and an end-to-end install.sh run against the real release.
  2. zigbuild lane, when gated in: the objdump -T GLIBC ceiling assertion (≤ 2.28); run the musl kb inside alpine:latest (kb daemon + a keyword search against a canon corpus); run the gnu.2.28 kb inside ubuntu:20.04; confirm no AVX-512 poisoning (objdump -d | grep -c zmm on the C-kernel objects, or run on a non-AVX512 host — this spike's machine is exactly that).
  3. musl allocator: before shipping musl assets, benchmark the daemon under concurrent indexing with musl malloc vs a jemalloc/mimalloc global-allocator swap (musl's allocator measured up to ~7–13× futex contention in multithreaded workloads).
  4. Embedder throughput follow-up (orthogonal): kb bench before/after re-enabling ORT's inter/intra-op spinning, since rc.11+ prebuilts default to edge-tuned --client_package_build.
