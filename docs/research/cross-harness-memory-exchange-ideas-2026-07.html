Cross-harness memory exchange — codex ⇆ Claude Code through kb

Once a capture adapter translates a foreign transcript into Claude-shaped JSONL, every kb memory surface — why, recollect, sessions, recall — works across harnesses unchanged. That was proven on this machine today; this board maps what it opens up.

2026-07-06· status:open· companion to the foreign-harness evaluation artifact

The unlock, in one paragraph

kb’s episodic pipeline has a narrow waist: everything downstream of parse_session_activity (crates/kb-core/src/sessions.rs:472) — the R1 digest, the five sqlite tables, kb why, kb recollect, the SPA session panels, cross-kb fan-out — reads derived rows, never the raw transcript. So the only Claude-specific piece is the JSONL shape the parser consumes. The codex adapter (plugins/kb-memory/hooks/kb-capture-codex.sh, ~150 lines of bash+jq, deterministic, LLM-free) translates an OpenAI Codex rollout into that shape at capture time. Verified end-to-end on a scratch daemon on 2026-07-06: three real rollouts in, kb sessions show printed 49 commits with SHAs and subjects, 63 edited files, 18 web-research rows, model gpt-5.5, 4,793 tool calls; kb why renderer.ts answered with the codex session that created the file; kb recollect ranked all three with staleness and error signals. Nothing in the daemon changed.

VerifiedCross-harness episodic memory is an adapter problem, not a daemon feature. The daemon stayed at v0.20-50-g838eaa1e throughout; every result below that says “verified” ran against unmodified kb.

The ideas

I1 — One episodic plane: kb why answers across harnesses

Shipped today. With codex captures in the sessions corpus, kb why <file> reconstructs provenance regardless of which harness did the work. Claude, about to refactor renderer.ts, learns codex wrote it, from which prompt, through which 49 commits — before touching it. The inverse holds once codex is taught to call kb (I3): codex sees Claude’s decisions and commit trail for the file it’s editing.

Evidence: kb why renderer.ts against the scratch daemon returned the codex simcity session with prompt + commits. Effort: zero — backfill + hook registration only. Risk: none; R0 keeps transcripts out of default search/recall.

I2 — Ambient recall injection into codex turns

Codex’s UserPromptSubmit hook carries prompt and accepts additionalContext output — the same contract kb-recall.sh already speaks (both names confirmed in the codex binary’s hook schema). A kb-recall-codex.sh is kb-recall.sh with the payload field names checked and the daemon URL passed explicitly. Every codex turn then starts with the same top-k curated memories a Claude turn gets: one memory store, two harnesses, no divergence in what the user’s agents “know.”

Evidence: hook event + field names in /usr/bin/codex strings (user_prompt_submit, additionalContext), confirmed against the official codex hooks docs — the output JSON is deliberately Claude-Code-wire-compatible, config in ~/.codex/hooks.json, stable + default-on since v0.124. And it generalises: opencode’s chat.message plugin hook and gemini-cli’s BeforeAgent → additionalContext give every harness a first-party injection point. Effort: ~1 hour incl. hook registration.

I3 — The AGENTS.md memory protocol, generated by kb tools

kb already ships the teaching surface: kb tools emits a prompt-ready markdown manifest of every verb. A trimmed “memory protocol” block — kb recall before re-deriving, kb remember after decisions, kb why before rewriting, kb recollect before re-doing — dropped into a project’s AGENTS.md gives codex (and opencode, and gemini via GEMINI.md) the same discipline CLAUDE.memory.md gives Claude. The protocol is harness-neutral prose; only the file name differs per harness.

Evidence: kb tools exists (CLI v0.20); CLAUDE.memory.md is the proven template. Effort: an afternoon — write once, symlink or generate per harness. Guardrail: sandbox note per harness (codex needs network_access = true or approval-escalation for agent-initiated calls).

I4 — Resume-in-the-right-harness dispatch

The adapter stamps every capture with <meta name="kb-harness" content="codex"> and an adapter-meta JSONL line carrying rollout_path. kb sessions resume today shells claude -r <session_id> unconditionally; with the harness meta it can dispatch — codex resume <uuid> for codex sessions (the verb exists: codex resume / fork --last), claude -r otherwise. “Continue that Tuesday session” then works from one command regardless of where the session happened, from recollect hit to live prompt in the right tool.

Evidence: adapter-meta line verified in captures; codex resume in codex --help. Effort: small kb-cli patch (read kb-harness from the artifact meta or sessions row) — the one idea on this board that touches kb code. Alternative without code: print the right command as a hint.

I5 — Second opinions with provenance

The user already runs multi-model reviews (the 2026-07-06 code-craft review was dual-model by design). Cross-harness memory upgrades this: ask codex to review what Claude shipped with the episodic record in hand — kb recollect "the milestone" surfaces the sessions, kb sessions show yields the decision log and commit list, kb why explains each contested file. The reviewer critiques the reasoning trail, not just the diff. Symmetrically, Claude can audit codex’s 180-error marathon session and say why it went sideways.

Evidence: all query surfaces verified on codex captures today; decision rows populate once codex’s request_user_input tool is mapped (seen in one rollout — a natural adapter v2). Effort: zero infra; a prompt pattern. This is agent-layer LLM work, exactly where the non-goals put it.

I6 — Bridge codex’s native memories — carefully, one-way

Codex is growing its own memory (memories_1.sqlite: stage1_outputs.raw_memory / rollout_summary per thread, a phase-2 selection pass — an LLM distillation pipeline, currently empty here). When it populates, a read-only exporter could mirror selected summaries into kb as kb remember --tags harness:codex,distilled facts, making them recallable in Claude turns and inspectable in the SPA. The inverse direction (writing kb facts into codex’s store) should be refused: kb is the canonical, deterministic, operator-inspectable store; feeding a second opaque store creates split-brain memory.

Evidence: schema read from ~/.codex/memories_1.sqlite (0 rows today). Effort: blocked until the feature activates; revisit when stage1_outputs is non-empty. Decision to record now: one-way, codex→kb, provenance-tagged.

I7 — Watcher-pull capture for hookless or flaky-hook harnesses

Push capture needs a hook, and all three harnesses now have one (codex Stop, opencode session.status, gemini AfterAgent — gemini’s SessionEnd is explicitly not awaited, and its transcripts self-delete after 30 days by default, so a pull sweep doubles as the backfill/retention escape). Hooks also regress. The pull alternative: a systemd path unit (or a 5-minute timer) watching ~/.codex/sessions/** and running the adapter in CLI mode on changed rollouts. The adapter is already idempotent — one file per session id, overwritten on re-capture, atomic mv — so pull and push can coexist as belt-and-suspenders. The same pattern generalises: any harness that persists transcripts anywhere becomes capturable by pointing a unit at its directory and writing one translator.

Evidence: adapter CLI mode processed 39 MB of rollouts in 2.3 s; overwrite semantics inherited from kb-capture.sh (the 47 GB lance-bloat lesson of 2026-07-03). Effort: a 10-line unit file. Trade-off: pull captures mid-session snapshots only as often as it runs; the Stop hook stays the primary path where hooks exist.

I8 — The opencode adapter: plugin event, not file watcher

opencode 1.17 stores sessions in sqlite (opencode.db: session / message / part tables, JSON in data columns — 482 sessions here), so there is no transcript file to watch. But its plugin API is richer than a hook: a JS plugin in ~/.config/opencode/plugin gets lifecycle events plus an SDK client and can read the full session, then either shell out to the same envelope logic or POST the translated capture itself. Message/part JSON is closer to Claude’s shape than codex’s (roles, typed parts with text/tool types), so the translation is thinner. Alternative zero-plugin path: opencode export <sessionID> emits session JSON — a cron sweep over recently-updated sessions works like I7.

Evidence: schema + @opencode-ai/plugin Hooks interface read locally (event, chat.message, tool.execute.after…); opencode export --help. Effort: ~half day. Priority: low until opencode re-enters real use here (444 of its 482 sessions were a March experiment).

I9 — Comparative harness telemetry from the funnel

Sessions rows already carry message_count, tool_calls, error_count, token_total, model, and commit counts per session; with kb-harness attribution the existing per-project rollups become comparative: commits-per-session, errors-per-kilotoken, decision density by harness on the same repo. Not a benchmark arms race (recorded non-goal) — an operator’s own telemetry over their own work, answering “which tool do I actually ship with?” with provenance instead of vibes. The simcity data point is already spicy: 393 M input tokens, 180 errors, 49 commits in one codex session.

Evidence: effort line in kb sessions show (verified on codex capture). Effort: needs harness attribution in the sessions row first (I10); then it’s a query, maybe a kb sessions stats --by harness flag. Guardrail: stays descriptive; no leaderboard scoring in the daemon.

I10 — Harness-tagged provenance in list/show/SPA

Small, load-bearing plumbing: teach the sessions enrichment to surface which harness produced a capture — either parse the adapter-meta first line, or (zero-parse) read the kb-harness meta already in parser::Fields reach. Then kb sessions list grows a harness column, kb recollect hits show [codex] badges, and the SPA session panel says whose transcript it renders (its Claude-shaped renderer currently shows translated codex sessions without saying so). This is the one schema-adjacent change on the board; everything else rides existing columns.

Evidence: kb-harness meta already written by the adapter; unknown metas are ignored today (verified — captures indexed cleanly). Effort: small kb-core patch + one migration or a computed field. Sequencing: do this before I4/I9; both dispatch on it.

Guardrails — what this board must not become

  • No in-daemon LLM. Every translation above is deterministic (jq mappings); every distillation (I5, I6’s upstream) happens in the agent layer or in codex’s own pipeline. The daemon indexes what adapters write — nothing more.
  • One daemon, one operator. Cross-harness is many tools, one human. Nothing here introduces a second identity; codex uses the same bearer, same mounts, same authority as Claude. (A colleague’s codex is their daemon’s problem.)
  • Adapters live in plugins/, not crates/. The daemon’s contract is the capture envelope + Claude-shaped JSONL; if a third harness needs a fourth adapter, that’s a new script, not a new parser branch — until real usage justifies a parse_session_activity dialect (the codex adapter deliberately chose translation over a parser fork to honour this).
  • Lossy is fine, silent isn’t. The adapter caps tool outputs at 2,000 chars and drops reasoning traces; the raw rollout stays in ~/.codex/sessions and its path rides adapter-meta. Any future adapter must keep a pointer to its ground truth.

Sequencing, if this gets pulled

  1. Now (zero code): register the codex Stop hook + backfill 30 rollouts (I1); add the AGENTS.md protocol block to one shared project (I3); use I5 as a prompt pattern on the next review.
  2. Next (hours): kb-recall-codex.sh (I2); watcher-pull unit as backstop (I7).
  3. Then (small kb patches, only after a week of real dual-harness data): harness attribution (I10) → resume dispatch (I4) → comparative stats (I9).
  4. Later / trigger-gated: opencode adapter when opencode re-enters real use (I8); codex-memories bridge when stage1_outputs populates (I6).
NoteThe MCP question is deliberately absent from this board: none of these ideas need it. The formal trigger evaluation lives in the companion artifact kb as memory for non-Claude harnesses.
