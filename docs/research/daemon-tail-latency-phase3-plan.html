kb daemon tail-latency Phase 3 — read bypass, embed IPC timeout, query-priority lanes

Three code-level changes that remove the daemon's remaining multi-second tail: reads that no longer queue behind compaction, embeds that can time out instead of hanging the shared mutex, and queries that jump the indexer's embed batches.

2026-07-03 · status:open · project:kb

Status — 2026-07-10

Implemented Fix 1 (embedder IPC timeout) and Fix 2 (query-priority embed lane) are implemented and tested. Fix 3 (compaction off the read path) was superseded before this plan was executed: the perf(kb-core): ingest + storage engine sweep (PS1) commit (26619b54, 2026-07-10) added compact_off_loop (storage/actor.rs), which runs Table::optimize on a spawned task and keeps servicing reads (and non-lance writes) inline while parking only lance mutations — the plan's goal, achieved without the riskier full read-bypass (a second lance handle + a read-only !Sync sqlite connection + version-refresh). Its test compact_in_flight_defers_writes_and_serves_reads proves reads are served during a compaction.

What changed relative to this plan's original design:

  • Fix 1 landed env-tuned (KB_EMBED_TIMEOUT_SECS, default 60 s) rather than a [indexer] TOML key — mirroring the existing KB_EMBEDDER_HANDSHAKE_TIMEOUT_SECS sibling and keeping the change inside embed_ipc.rs (no config-struct plumbing).
  • Fix 2 uses a process-global, per-model pending-query counter keyed on the &'static str model name (crate::embed::QueryLaneGuard / pending_query_count), instead of wrapping the shared Arc<Mutex<Embedder>> in a new type at its ~15 call sites. Same behaviour, far smaller blast radius. The indexer embeds chunk vectors in INDEX_EMBED_MINI_BATCH-sized mini-batches and yields the mutex between them while a query is waiting (bounded so a query storm never indefinitely starves indexing).
  • Fix 3 — the broader "route all reads off the actor" ambition is deferred as unnecessary: the measured problem was compaction (now off-loop), and post-ops-fix latency is already 0.24–0.43 s. Reopen only if /api/metrics shows read queue-wait climbing behind non-compaction write bursts.

Context — the 2026-07-03 incident

kb.example.com intermittently answered in multiple seconds (occasionally >10 s — the per-turn memory-recall hook blew its 15 s budget). The investigation found a three-layer feedback loop; the ops layers were fixed the same day (Phases 0–2), and this plan is the third, code-level layer.

Why Phase 3 still mattersThe ops fixes shrank the frequency of contention windows. The mechanisms remain: any large corpus edit, operator reindex, or slow embed still serializes reads behind writes and queries behind indexer embeds. Phase 3 removes the mechanisms.

The three mechanisms, with code anchors

1. Compaction blocks reads for its whole duration

Each kb has a single-writer storage actor (crates/kb-core/src/storage/actor.rs, run loop ~line 871) that processes one message at a time; reads serialize through the same queue as writes — the module doc says "v0.1+ may add bypass-for-read handles if query latency requires it". compact_all is handled inline in the actor (~line 1059); crates/kb-server/src/lib.rs (~line 825) documents plainly that "a compaction pass briefly blocks search for this kb while it runs", and records a prior pathology of 5–10 s hybrid queries at 2,592 fragments. Compaction fires at startup and on every reconcile tick once a corpus crosses 32 small fragments.

2. Embed IPC has no per-request timeout

crates/kb-core/src/embed_ipc.rs send_recv (~line 346) does a blocking read_line on the kb-embedder subprocess with no timeout — only the spawn handshake is bounded (line 128, 300 s). The 1 Hz liveness probe (lib.rs:648) only catches a subprocess that exited. A wedged-but-alive embedder (swap stall, ONNX hang) blocks forever while holding the shared per-model mutex — every embed-dependent query on that model hangs with it.

3. Indexer and queries embed through one mutex

All kbs on the same model share one Arc<Mutex<Embedder>> and one subprocess (crates/kb-server/src/lib.rs:300). The query path locks it in embed_cache.rs (~line 227); the indexer locks the same mutex for doc vectors (indexer.rs:1153) and whole chunk batches (indexer.rs:1217). During a reindex burst, an uncached query waits behind arbitrarily large indexer batches. This is why slowness tracked cache misses — cached queries never touched the mutex.

Design decisions

Order: smallest blast radius first

IPC timeout (localized, pure win) → query-priority lane (small, no architectural change) → read bypass (touches the storage invariant). Each lands as an independent, revertable commit.

IPC timeout: reader thread + recv_timeout, then kill-and-respawn

The stdout pipe read moves to a dedicated reader thread per subprocess feeding an mpsc; send_recv waits with recv_timeout (default 60 s; config [indexer] embed_timeout_secs). On timeout the client kills the child and marks the transport dead — the existing respawn-on-transport-death path recovers, and embedder_respawn_count records it. Rejected: async pipes (kb-embedder IPC is deliberately sync/blocking under spawn_blocking; converting the transport to tokio is a bigger change for no additional safety).

Query priority: a fairness gate, not a second subprocess

Default fix is an AtomicUsize pending-queries counter beside the mutex: queries increment before locking; indexer embed work splits into mini-batches of ≤8 texts and yields between mini-batches whenever the counter is non-zero. Worst-case query wait becomes one mini-batch (≈8 × ~50–170 ms) instead of a whole document. Rejected as default: a dedicated query-lane subprocess per model — bge-large costs ~1.3 GB on disk and comparable RSS per process; doubling that for every model is too heavy for the 12 GiB container cap. It can be offered later as an opt-in (dedicated_query_embedder = true) for RAM-rich hosts. Note the ops layer already achieves subprocess isolation per corpus where it matters most: the high-churn sessions corpus runs its own bge-small embedder as of 2026-07-03.

Read bypass: reads leave the actor; writes and compaction stay

Lance is MVCC — the Lance format versions every commit, so concurrent readers against the last committed version are safe while a writer commits; sqlite in WAL mode supports concurrent readers alongside one writer. So the fix is a ReadHandle owning read-only lance Dataset handles (refreshed on version bump) plus a read-only sqlite connection, serving vector_query, bm25_query, and doc/list reads. Writes, index-ensure, and compact_all remain serialized on the actor — lance still wants a single writer, and that invariant is load-bearing (docs/architecture-invariants.md #2, which this change must update, not silently break). Rejected: moving compaction off the actor to a side task — it is a writer, so it belongs on the writer lane; once reads bypass the actor, an inline 10 s compaction is harmless to queries and merely delays queued writes, which are already asynchronous to users.

Invariant disciplineThe single-writer actor is a deliberate design recorded in crates/kb-core/CLAUDE.md and docs/architecture-invariants.md (invariant #2: "embed work serialises through the actor on purpose"). Step 3 must land with the invariant text updated to describe the read/write split — a code change that contradicts the invariant doc is worse than no change.

Steps

The executable step list — each with its verify command — lives in this artifact's kb-prompt (the handoff contract). Summary:

  1. Embedder IPC timeout — embed_ipc.rs: reader thread + recv_timeout, kill-and-respawn on expiry, config knob, mock-embedder hang test.
  2. Query-priority lane — embed_cache.rs + indexer.rs: pending-query counter, ≤8-text indexer mini-batches, saturation test asserting query p95 < 500 ms during a 500-chunk ingest.
  3. Storage read bypass — actor.rs + lance.rs: ReadHandle for query/list reads, version-bump refresh, invariant-doc update, e2e test asserting search p95 < 300 ms during a ≥2 s compaction.
  4. Gate — cargo test --workspace + clippy clean (remember: cargo test regenerates the ts-rs bindings in web/src/api/gen).
  5. Deploy — run the deploy script; no state wipe (no id-scheme or index-format change).

Verification after deploy

Detailed metrics are already enabled in prod ([server] metrics = true since 2026-07-03). Watch GET /api/metrics / kb metrics for:

  • storage-actor queue-wait for reads ≈ 0 while maintenance.compact.* events fire (fix 3 proof);
  • search/recall p95 < 1 s during an operator kb reindex --kb platform (fix 2 proof — platform is the 791-doc bge-large corpus);
  • embedder_respawn_count incrementing instead of latency flat-lining if an embed ever stalls past the timeout (fix 1 proof);
  • the per-turn recall hook (15 s budget) producing zero timeout warnings across a week of normal use — the original user-visible symptom.

Rollback

Three independent commits; git revert individually. The read bypass keeps the actor's read API routed rather than removed, so reverting restores full serialization with no data migration. State volumes are untouched by all three fixes.
