Each topic frames the question, lists tradeoffs, and ends with a recommended default plus dissent. These are the negotiations the operator should have before the v0.0.1 vertical slice begins. Some have clear defaults; some genuinely depend on the operator's preference.

  1. 1 · Workflow · claude-code ↔ kb integration loop

    What does "look up before producing new" actually look like?

    Frame: the briefing wants Claude Code to consult kb before generating new artifacts. Two flows are possible:

    • Pull (operator-initiated): CLAUDE.md instructs "before generating an artifact, run kb search '<topic>'." The operator sees the search; can correct.
    • Push (automatic): a hook in .claude/settings.json intercepts artifact generation and pre-injects search results. Cleaner UX, less transparent.

    Tradeoff: pull respects "transparency over magic" (briefing's HIGH-confidence stance, ties into challenge #7); push reduces friction but creates a black-box feel.

    Where do new artifacts land? Three options: (a) _staging/ folder watched by kb, auto-added on debounce settle (matches topic 03's file watcher recipe); (b) explicit kb add <path>; (c) Claude Code skill that calls kb add programmatically when finishing a generation. Recommendation: watched _staging/ by default, kb add for explicit ingest from anywhere else. Skill option as v0.2 polish.

    Default: pull-style search, watched staging folder.

  2. 2 · Provenance · prompt-as-comment in artifacts

    Format, reproducibility, privacy

    Topic 07 ran the analysis. Recommendation: <template id="kb-prompt"> for the prompt body + <meta name="kb-*"> for structured fields (kb-id, kb-model, kb-model-version, kb-temperature, kb-created, kb-category, kb-tags, kb-sandbox). <template> wins because it's parser-visible, doesn't render, multi-line, survives minifiers.

    Privacy scrub pass mandatory: strip system prompt by default; regex-redact known secret formats (AWS keys, GitHub PATs, Anthropic sk-ant-*, JWT-like, generic high-entropy 32+ char tokens); path-normalise /Users/<name> → ~/; confirmation gate when prompt > 1000 chars. Audit log under ~/.kb/audit.log.

    Reproducibility fields beyond the prompt: kb-skill (which generation skill, e.g. html-artifacts), kb-tool-version, kb-source-files (hashes of inputs that informed the artifact). Useful for "regenerate when the source diff changes" flows.

    Default: <template> + <meta>, scrub-on by default, opt-out per-artifact via kb add --no-scrub (with a confirmation prompt).

  3. 3 · Multi-kb · visual identity

    Accent color? Subdomain? Glyph?

    Frame: kb is namespace-not-federation — one daemon serves multiple kbs (per the briefing's HIGH-confidence stance). The risk is the operator getting confused about which kb they're in.

    Three signals worth combining:

    • Accent colour per kb. Cheap, instantly recognisable. Pulled from a fixed palette of ~8 colours (avoid AI-aesthetic gradients — see dogum/html-artifacts ruleset).
    • Glyph / icon per kb. A single Unicode character (📚, 🛠, 🧪, 📐) or a short emoji. Less subtle but works in tight TUI rows.
    • Subdomain in SPA: code.localhost, research.localhost. Most rigorous, requires wildcard cert + DNS work for self-hosting.

    Default: accent colour + glyph, both stored in kb config. Subdomain SPA scoped is a self-hosting v0.2 — not v0.0.1 (single user on localhost).

    Where the colour appears: top-nav stripe in the SPA, status-line accent in the TUI, prefix in CLI output ([code], [research] tags).

  4. 4 · Schema versioning + migration

    How does the schema evolve?

    Frame: schemas always change. lance + sqlite split (topic 01) means two schemas to evolve.

    • SQLite: standard schema_migrations table (Rails convention) tracking sequential migration IDs. Tools: refinery, sqlx::migrate!, rusqlite-migration. Pick one, never write hand-rolled ALTER TABLE in prod code.
    • Lance: add_columns, alter_columns, drop_columns are exposed (topic 01). Bug #3136 (2026-03) on schema evolution past embedding columns is live — pin known-good. Dimension changes (384 → 768) are not a compatible cast; require add-new + drop-old + rename.
    • Full reindex on schema bump: the brutalist option. Acceptable at <50k docs (a few minutes), unacceptable past 1M.

    Export format for portability: kb export --format=tar produces artifacts/*.html + kb.db (sqlite) + lance/ dir. Tar/untar across machines works (lance uses relative paths). Schema migrations on import: re-apply sqlite migrations idempotently; lance schema is the source of truth from the dataset itself.

    Default: refinery for sqlite migrations + lance schema captured in dataset itself. Full reindex acceptable in v1; revisit at 1M+ scale.

  5. 5 · Self-hosting story

    Smallest delta from local to remote

    Frame: on the briefing's roadmap, not v0.0.1. But planning the seam now is cheap.

    • Tier 0 — localhost only. Bind to 127.0.0.1:7000. v0.0.1 default.
    • Tier 1 — Tailscale + LAN. Bind to 0.0.0.0:7000, rely on Tailscale ACLs for access. Zero auth required, but the daemon must trust the network. The simplest "self-hosting" path; matches Syncthing's ergonomics.
    • Tier 2 — public VPS with auth. TLS via Caddy (auto-issuance), basic auth or oauth-proxy in front. Requires schema for users + sessions; meaningful surface area.

    The seam to design now: auth middleware. Design kb-server's axum middleware so authentication is pluggable (no-op locally, Tailscale-auth-key check on Tier 1, oauth-proxy header on Tier 2). Every endpoint requires RequireAuth extractor; the no-op extractor is a development convenience that doesn't ship in release builds without an explicit flag.

    Default for v0.0.1: localhost only. Plan auth middleware seam. Document Tailscale path; defer oauth to v0.2+.

  6. 6 · Observability of the daemon itself

    Logs, metrics, traces — what's actually load-bearing?

    Frame: kb's TUI is the user-facing observability surface. But the daemon also needs internal observability for debugging.

    • Structured logs (tracing crate): mandatory. Default: info to stderr, debug to ~/.local/state/kb/log rotating (tracing-appender). Spans per request, per indexer-batch.
    • Metrics: Prometheus-format /metrics endpoint behind a feature flag. Useful only for self-hosting tier; don't ship enabled by default. Cardinality cheap (counters per event type, gauges for queue depths).
    • Traces: overkill for v0.0.1. opentelemetry is heavy; defer.

    Reading observability state from sqlite (briefing suggestion): good for "indexer state at a point in time" via kb status CLI. Don't conflate with metrics — sqlite is for state, Prometheus is for time-series.

    Default: tracing structured logs, sqlite-backed kb status, metrics endpoint behind feature flag. No tracing/OTLP in v1.

  7. 7 · Release packaging

    How does the operator actually install kb?

    Frame: distribution is downstream of "single binary" (challenge #6 confirms). The question is which channels.

    • cargo install — for Rust developers. Free with the workspace. Default for first-mile testing.
    • GitHub Releases prebuilt binaries — macOS arm64/x86_64, Linux x86_64/arm64. Use cargo-dist to automate. Mandatory for non-Rust users.
    • Homebrew tap — brew install kb-app/kb. Half a day to set up, biggest UX win for Mac users.
    • AUR package — for Arch users (relevant since the dev environment here is a Linux desktop). Trivial maintenance: kb-bin PKGBUILD pointing at GH releases.
    • Snap / Flatpak — heavy ceremony; defer.
    • Deb / RPM — defer to v0.2 unless a user asks.

    Auto-update: kb self-update via self-update crate (downloads from GH releases). Check on startup with a --check-update flag, never auto-install. Don't use cargo-install upgrade as the canonical path — it's slow and Rust-only.

    Default: cargo-dist for releases, GH releases first, Homebrew + AUR within a week of v0.0.1, kb self-update opt-in.

  8. 8 · Artifact thumbnails (gallery cards)

    Synthetic vs real screenshots vs DOM-painted

    Topic 07 lands on the answer: real screenshots via headless Chromium as default, synthetic icon-collage as fallback.

    • Synthetic icon-collage — fast, lightweight (no browser dependency), informative for kind (has-svg, has-form, has-drag) but poor for content. Two flowcharts look identical.
    • Real headless screenshot — Playwright/Puppeteer dependency adds ~150 MB runtime. Generate at write-time, cache as 320×240 WebP (~20 KB each). For 10k artifacts: ~200 MB cache. Acceptable.
    • DOM-painted client-side (html2canvas) — slower than synthetic, less accurate than headless, no extra runtime. Worth shipping in the SPA as a degraded-mode fallback.

    Lazy capture: synthetic immediately on ingest (free, runs in-process). Headless screenshot in the background queue. Show synthetic first, swap to screenshot when ready. UX: thumbnails appear instantly; refine on second visit.

    Default: synthetic-immediate + headless-background, --no-screenshots flag for users without Playwright.

  9. 9 · SSE event schema (formal contract)

    JSON Schema, where to publish, versioning rules

    Topic 04 + challenge #4 cover this. Summary:

    • Single envelope: {v, id, type, ts, payload}. id mirrors SSE id: field for free Last-Event-ID. type mirrors SSE event: field for browser addEventListener("index.progress").
    • Reserved top-level type namespaces: index.*, file.*, query.*, error.*, system.*.
    • Per-type JSON Schema files in repo (events/v1/index.progress.json, etc.); served live at /events/schema/{type}/v1.json.
    • Publishing rule: schemas in repo are dev-time mirrors; the running daemon's schema endpoint is canonical. CI checks the two match.
    • Versioning: bump v on breaking change only. Add fields freely (consumers ignore unknown). Renames/removals run two endpoints side-by-side through a deprecation window.
    • One firehose /events with ?types=index.*,error.* filter. Don't split by domain or by direction.

    Default: author events.schema.json as part of the v0.0.1 vertical slice, before any client subscribes. Treat as public API.

  10. 10 · Error budget for indexing

    Skip + log + continue, or hard-fail?

    Frame: the briefing asks: if a single HTML file fails to parse, do we skip / log / hard-fail?

    • Hard-fail the run: wrong. One malformed artifact shouldn't break ingest of 999 healthy ones. Rejected.
    • Skip + log + continue: right default. Failed files emit an error.parse event with file path + parser error. The TUI surfaces these in the Errors tab.
    • Quarantine: move failed file to ~/.local/state/kb/quarantine/ with a .error.txt sidecar. Optional; nice for debugging without re-tripping every reindex.

    Retry policy: retry on next index run (cheap, idempotent). Never retry inside one run — if the parser failed once, it'll fail again. Track retry count per file in sqlite; after 3 consecutive failures, demote to quarantine.

    Bad-artifact poisoning: sqlite errors table per file, scoped by content hash. If the file's content changes (hash differs), the error is cleared. Index is never poisoned — failed files are absent from the search index, present in the errors view.

    Default: skip + log + continue + retry-on-next-run + quarantine after 3.

  11. 11 · Backup model · "HTML is source, rebuild the rest"

    The principle is right for derived data, incomplete for user-authored state

    Frame: the operator proposed: HTML files on disk are the source of truth; everything else (lance index, sqlite tables, vector embeddings) can be rebuilt by re-indexing. Sound architectural instinct — aligns with the briefing's "html as source of truth, never markdown" stance. The question is how far the principle extends.

    What's right (derivable from HTML alone):

    • BM25 / FTS index (lance native or sqlite-FTS5 per topic 01)
    • Vector embeddings (re-embed body chunks with the same model per topic 02)
    • Title / heading path / first-paragraph / code-block extraction
    • Facets — has_svg, has_form, has_drag, has_animation, js_loc bucket, kb_category (full list in topic 07 §D)
    • All kb-* meta tags (kb-id, kb-model, kb-tags, kb-prompt — they live in the HTML by design per topic 07)
    • Edges of kind "link" and "embed" (extracted from <a> / <img> / <iframe>)

    An HTML-only backup is sufficient to rebuild the entire retrieval surface.

    What's lost on an HTML-only restore:

    1. Comments (topic 09). Sqlite-stored; anchored by selector + context. Not in HTML.
    2. Sources config — which folders kb watches, multi-kb names + accent colours (topic 3). Not in HTML.
    3. Audit log (topic 07's ~/.kb/audit.log for scrub events). Lost.
    4. Manually-curated tags / aliases / edges — if added via kb UI rather than embedded as kb-tags in HTML. Lost.
    5. Errors table (topic 10) — per-file retry counts, quarantine flags. Re-runnable but transient state is gone.
    6. Index_runs metadata — when each run happened. Fine to lose.
    7. View counts / last-opened (briefing's open question). If implemented, lost.
    8. Regen history at .kb/history/<id>/<timestamp>.html (topic 07). These are HTML files but they're an archive set — whether to back them up is a policy choice.

    Other concerns:

    • Rebuild cost. 50k artifacts × 5 chunks × ~30 ms embed ≈ 2 hours on CPU (per topic 02's latency numbers). Acceptable for disaster recovery; painful for casual sync between machines.
    • Atomicity. A regen in progress at backup time could capture half-written HTML. Mitigate by writing artifacts via tmp + rename (matches topic 03's debouncer pattern); back up during a quiescent moment.
    • Sensitive content. If kb-prompt is embedded per topic 07, the operator's prompts (potentially including secrets the scrub regex missed) are now in every backup copy. Encrypt at rest if kb-prompt is preserved verbatim.
    • Anchor stability. Comments anchor to selectors / ranges in the artifact body. A fresh rebuild produces the same kb-id (it's the ULID from the meta tag) but selector positions are byte-identical only if the HTML was restored byte-for-byte. Comment anchors survive iff the HTML round-trips exactly.

    Recommendation — two backup modes, named explicitly:

    • Minimal (HTML-only): tar czf kb-min.tgz artifacts/*.html. Restore = drop in place + kb reindex. You lose comments, sources config, manually-curated tags, audit log, view stats. Acceptable for "I just want my artifacts back."
    • Complete (default): kb export produces a tarball with artifacts/*.html + kb.toml (config) + comments.jsonl + sources.jsonl + tags.jsonl (manually-curated tags only — embedded kb-tags live in HTML) + optionally .kb/history/. Restore = kb import + reindex. Everything user-authored is preserved. Sidecars are KB-class, not GB-class — overhead is negligible.

    Optional third mode: include the lance index too (just files) to skip the ~2-hour rebuild on sync-across-machines. Trade ~GB of storage at destination for a no-wait restore.

    Default: ship kb export in complete mode (opt down to --mode=minimal). The operator's HTML-as-source principle stands as the minimum; the doc names the gap so they pick consciously rather than discovering at restore-time that comments are gone.

    Cross-refs: topic 4 (schema migration) covers the existing kb export mention — this topic adds the minimal-vs-complete distinction; topic 5 (self-hosting) for backup placement on a Tailscale or VPS-hosted instance.
