The pull nobody makes

adoption telemetry for kb's episodic-memory verbs · Fable frontier run #4 · 2026-07-07 09:52–11:05 CEST · 4,793 real transcripts, one operator's machine · independently recounted + adversarially reviewed (survives) · status: finding, no code changed

Verdict. kb's deliberate episodic-pull surface — kb why <file> ("why is this the way it is") and kb recollect "<task>" ("has this been done before"), invariant #11's central "pulled on demand" bet — sees near-zero spontaneous adoption outside the repo that builds it. Across 4,793 transcripts: 12 real invocations, 6 sessions, 2 projects, ~75% inside kb itself. Post-ship, non-kb adoption is 1 of 13 human sessions and 0 of ~4,600 non-kb subagent runs. But the sharper finding is why: the surface is out-competed, not undiscovered. The agent knows it exists and is well-designed; for repo-local work the file-read reflex and the always-on recall block already answer "how was this done here?" more cheaply. The pull verb only wins for cross-project, no-code-trace questions — a narrow slice — and its one advertisement is fragile. This is a case study of one machine, not a population.

1 · A number that had to be corrected twice

This finding is only as good as "did an agent actually run the verb," and that turned out to be genuinely hard to count. Three passes:

  1. Raw grep said kb why appears in 394 files — meaningless: the SessionStart wake hook prints "kb why <file>" as protocol text into nearly every session. That measures hook presence, not use.
  2. Segment-head parsing (split each Bash command on ;|&&, match the verb at a segment's head) cut it to 25 pull calls — still inflated: a git commit heredoc or a kb remember "…" body that documents the feature has lines that begin "kb why…", and they were counted as invocations.
  3. An independent recount with a quote/heredoc-aware shell tokenizer, auditing all 45 candidate commands by hand, gave the honest number: 12 real invocations, 6 sessions, 75% kb. My "25 / 88%" reproduced exactly as a mentions count — 22 of 25 were kb-repo commit messages and remember-bodies describing the work.

The through-line of this whole frontier program keeps repeating: the hardest part of measuring a memory system is telling the instruction-text about a verb from an invocation of it. Runs #2 and #3 hit the same wall at the title and payload level; here it bit the telemetry itself. The corrected numbers are used throughout below.

Segmenting the pull surface honestly:

  • Ship-date denominator. The pull verbs shipped ~2026-06-26; 58 of the 102 top-level sessions predate them and could not have used them. The fair base is the 44 post-ship sessions, so overall adoption is ~14%, not 6% — I keep the corrected denominator. (An earlier draft's "recall-injection is same-era, and it got used constantly" rebuttal is false: recall-injection predates the pull verbs and fired in 20 pre-ship sessions, so the 57-vs-12 gap is an older automatic feature vs a young manual one, not a clean comparison.)
  • Outside kb, it rounds to zero. Post-ship non-kb human adoption is 1 of 13 sessions (~3 genuine work-pulls, all in one other project). Of ~4,600 non-kb subagent transcripts: zero pull invocations.
  • The subagent pulls are kb evaluating itself. Subagents did pull ~78 times — but every one is in the kb repo, and they are benchmark and review harness calls: latency probes with nonsense queries (kb recollect "zanzibar hovercraft pineapple lattice"), the session-memory audit's own deep-review agents. That is dogfooding and self-evaluation, not adoption. (So the tempting claim "explicit prompting is the only driver" is unsupported — there is no cross-project case where prompting drove pull use at all.)

3 · Why a well-designed surface goes unused

A reader agent worked through four non-kb sessions where the recall block was injected but no pull happened. Its verdict: out-competed, not undiscovered.

Two of the four were textbook episodic situations — adding Komga, then huddle, behind Traefik + Authelia is a repeated pattern (kb, authelia, huddle all added the same way), so kb recollect "add a service to the traefik stack with authelia + cname" would have surfaced the exact playbook. The agent instead reverse-engineered it by reading the kb service block in docker-compose.yml — and then wrote a new memory rather than pulling the existing one. The mechanism, ranked:

  1. Substitution by the file-read reflex (strongest). "How is this done here?" is answered by opening the self-documenting source (docker-compose.yml, CLAUDE.md) that the agent opens by instinct anyway — plus the always-on recall block already surfaced the relevant deploy facts. Episodic recall returns the same knowledge with more latency. It only wins when the answer is not in the working tree — cross-project priors, decisions that left no code trace — and none of these tasks pressed that hard.
  2. Habit, not ignorance. The agents demonstrably know the memory system (kb remember, kb get, kb recall all appear); "read the file to understand the code" is an ingrained reflex, "query an external episodic store first" is not.
  3. A fragile advertisement. Two concrete, fixable defects surfaced: in one 5,600-message opensim session the SessionStart wake hook was hook_cancelled, so the why/recollect advert never appeared; and the per-turn recall block re-surfaces kb get (via each hit's id) but never re-mentions why/recollect — so after its single SessionStart mention, the episodic verbs fade from context for the rest of a long session.

4 · Where this sits in the memory story

Four frontier runs now triangulate kb's memory system from four sides, and they converge:

RunSurfaceFinding
#1recall rankingsalience inverts it — right memory buried below top-5 for ~half of on-topic queries
#2recall injectiona pointer, not a payload — transmits little at turn zero; production ≈ no injection
#3the memory channelan unmitigated injection vector; only guard is model judgment
#4episodic pullthe deliberate alternative to auto-push is ~unused outside its own repo

The push surface fires constantly but ranks wrong (#1), barely lands (#2), and is unsafe (#3); the pull surface is safe and well-shaped but out-competed by a cheaper reflex (#4). One root runs under all four: kb's memory is architecturally rich and behaviorally thin — the system does far more than agents actually exercise. The value is not "tear it out"; it is that the next investment should go to behavioral footprint, not more capability.

5 · What would move the needle (proposals — triage-gated)

  1. Re-surface the episodic verbs contextually. The per-turn recall block should add a one-line why/recollect nudge when the prompt smells episodic — "add another…", "like the other services here", "why is…", "publish/export vN", "same as…" — instead of a single static SessionStart paragraph that fades. This is a kb-recall.sh change, deterministic, no daemon LLM.
  2. Make the advert resilient. One cancelled SessionStart hook blinded the verbs for a 5,600-message session; the protocol should survive hook cancellation and context compaction (re-inject on compaction, or carry a compact reminder in the recall block).
  3. Position for the slice where it wins. Episodic recall's real edge is the cross-project / no-code-trace question. Adoption will stay low as long as it competes with the file read on repo-local tasks; surface it where the working tree can't answer.
  4. Don't over-invest in pull ranking yet. Run #1's ranking fix matters for the push surface that actually fires; the pull surface's problem is reach, not ranking. Sequence accordingly.

6 · Honest bounds

  • One machine, n=1. This is a case study of one operator's transcripts, not a population. Every rate is descriptive of this deployment; "adoption is low" generalizes no further than "here."
  • Unused ≠ useless. Non-use is consistent with both under-adoption of a useful surface and tasks that genuinely didn't need episodic recall. The reader judged ~2.5 of 4 sampled sessions as plausible missed opportunities, but the true base rate — "sessions where episodic recall would have helped" — was not measured, so even the post-ship 14% is a floor on would-have-helped adoption, not the adoption rate of a needed feature.
  • Recency is real. A ~2-week-old feature with low adoption is partly just young; the finding is "as of the first two weeks on this machine," and the trend, not the level, is what a re-run would test.
  • Counting is noisy at the edges. The independent recount (12) is quote-aware and hand-audited, but heredocs and $()/xargs forms remain hard; the kb-vs-non-kb direction is robust, the last digit is not.
  • Dropped as unsound: an "injection→pull funnel" (7 of 57) — the semantic recall store and the episodic session store are orthogonal, so their overlap is not a drop-off.
