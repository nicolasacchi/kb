v0.1 commits to lancedb + sqlite split per cluster 3 decision (§Decisions). Lance holds docs/vectors/BM25, sqlite holds relational tables (sources, errors, runs, edges, schema versions). The original "spike sqlite-vec + FTS5 first" recommendation in §F below is preserved as historical context; if a kb crosses ~50 k docs and the binary-size / single-backup pressure reverses, re-run the spike then.

Confirmation · SPA exposes three search modes (2026-05-11)

The Web Gallery handoff (topic 10 §H)'s Cmd+K cycles three modes: hybrid (k+v) default, keyword (k), semantic (v). Both backends are reachable from one query plan via the committed lance + sqlite split: lance-native FTS for BM25, lance vector cosine for semantic. hybrid default uses RRF (Reciprocal Rank Fusion) with k=60 per topic 02 §Decisions — score-agnostic, no alpha to tune (the original "hybrid_alpha" knob is replaced by hybrid_k in kb.toml, defaults to 60).

Decisions · 2026-05-11 (cluster 3: storage — amended post deep-review)

Open-points cluster 3 of 4 landed. Storage decision committed without further spike. Post-review: fixed the hybrid_alpha/RRF inconsistency with topic 02; spec'd the atomic backup mechanism; added on-disk layout.

  • Commit: lancedb + sqlite split for v0.1. Briefing default wins. Battle-tested IVF-PQ, columnar artifact storage, mature migration story. Trade-off accepted: larger binary, two stores to back up.
  • sqlite-vec + FTS5 spike → downgraded to a regression test, not a v0.1 gate. Re-run if a kb crosses ~50k docs and the operational-simplicity / scaling tradeoff inverts.
  • On-disk layout. Per kb: ~/.local/state/kb/<daemon-name>/<kb-name>/lance/ (vectors + BM25 + artifact columns) + …/<kb-name>/index.db (sqlite). Single writer per kb (daemon serializes via a tokio actor). kb backup <kb>: (1) issue BEGIN IMMEDIATE on sqlite, then PRAGMA wal_checkpoint(TRUNCATE); (2) read lance's _versions/<latest>.manifest + tar the fragments it references (lance manifests are atomic — referenced fragments are immutable); (3) COMMIT sqlite. The indexer is paused during steps 1-3 (typically <500 ms). True atomic-without-quiesce is a v0.2 follow-up.
  • BM25 field-aware indexing. The lance-native FTS index carries five fields: title (extracted from <title> or first <h1>), body (DOM walk excluding <script>, <style>, <template> per topic 07 §D), headings (all <h1>–<h6> + <details><summary> outline tokens), code (<pre><code> blocks), prompt (the <template id="kb-prompt"> contents, capped at 8 k tokens). The prompt template is indexed as its own filterable field (kb search "claude-code" field:prompt) so prompts are searchable when wanted, isolatable when not. Privacy rationale: see topic 07 Decisions.
  • Hybrid scoring: RRF k=60 (matches topic 02 §Decisions and topic 10 §H). Reciprocal Rank Fusion is score-agnostic — no hybrid_alpha weight to tune; the k parameter (default 60, Cormack et al. 2009) controls how aggressively tail-rank results are penalized. Exposed in kb.toml as [kb.<name>] hybrid_k = 60. Pure-keyword and pure-semantic modes are query-time overrides (Cmd+K's mode toggle).
  • Schema versions. sqlite schema_migrations table; lance dataset metadata carries a kb_schema_version field. Mismatch on daemon start triggers a re-index of touched docs (lazy backfill, not full re-index).
TL;DR

v0.1 commits to lancedb + sqlite split (cluster 3 — see §Decisions). Lance holds vectors + native-BM25 + columnar doc rows; sqlite holds sources / errors / runs / edges / schema_migrations. Hybrid scoring: RRF k=60 per topic 02. The historical recommendation was "spike rusqlite + sqlite-vec + FTS5 first (1–2 days); collapse if within 5% nDCG" — that spike is downgraded to a regression test triggered when a kb crosses ~50k docs. Rejected for v1: DuckDB-VSS (experimental), SurrealDB (BSL + heavy), Turso DB (beta), three-store tantivy paths.

A. LanceDB Rust crate · current state

Active, capable, still 0.x

Crate lancedb on crates.io, license Apache-2.0. Latest is 0.27.2 (2026-03-31); recent cadence: 0.27.0 (2026-03-16), 0.26.0 (2026-02-06), 0.23.1 (May 2025). A minor every 4–6 weeks — clearly active, still 0.x so breaking-change semantics under cargo. The older vectordb crate is superseded.

Single-table vector + FTS + scalar

Yes. The Rust Index enum (lancedb::index::Index) exposes Auto, BTree, Bitmap, LabelList, FTS(FtsIndexBuilder), plus IVF-PQ / IVF-HNSW vector variants — all on the same table. A FixedSizeList<Float32, 384> column gets an IVF-PQ index by default; scalar columns get BTree. Hybrid search is built in (query_type="hybrid" plus rerankers RRF/linear/Cohere/ColBERT).

FTS specifics

As of 2025 LanceDB has a native Rust FTS ("No more Tantivy"). It still re-uses tantivy's tokenizer enum for compat (tantivy::tokenizer::Language::English). Supports BM25 scoring, term, phrase (needs with_position=true), prefix, fuzzy (Levenshtein), boolean (MatchQuery/PhraseQuery/BooleanQuery/BoostQuery).

Important caveat: "Lance-based FTS doesn't support queries using boolean operators OR, AND in the search string" — you build them programmatically via the query types, not in a single string. CJK tokenisation is a known gap (issue #2329); third-party tantivy-jieba/cang-jie not directly supported. For an English-language kb, this is fine.

Indexing types

IVF-PQ (default vector), IVF-HNSW-SQ/PQ, scalar BTree/Bitmap/LabelList, FTS. Optimise after writes: tbl.optimize(OptimizeAction::All).execute().await? — recommended every ~100k row changes or 20 ops.

Concurrency

MVCC. Readers never block. Single writer is the safe default on a local filesystem; concurrent writers on object storage need an external commit handler (S3 + DynamoDB). For kb (one daemon = one writer) this is a non-issue.

Embedded mode

Confirmed. lancedb::connect("/path/to/db").execute().await? opens a directory on local disk — same model as SQLite. Continue.dev, OpenClaw, and the wider local-RAG ecosystem use exactly this configuration.

Binary size

No public benchmark surfaced, but the dependency surface is large: full Apache Arrow stack (arrow-array, arrow-cast, arrow-data, arrow-ipc, arrow-ord, arrow-schema), Apache DataFusion (datafusion-physical-plan and friends), object_store, tokio, plus optional candle/HF features. Realistic expectation for a release build: 40–80 MB stripped. cargo bloat --crates will give the real number; budget for it. Static link lzma-sys via the static feature for distribution.

Schema migrations

add_columns, alter_columns, drop_columns are exposed in Rust. Changing a FixedSizeList dimension (e.g. 384 → 768) is not a compatible cast — must add-new + drop-old + rename. Lance file format 2.2 (2025) added nested schema evolution. Live bug as of 2026-03 (#3136): adding columns past an embedding column caused CastError on insert — watch the changelog.

Spike update · 2026-05-11 · spike-lance exercised the schema-evolution path against lance 4.0.0 with NewColumnTransform::SqlExpressions(vec![("kb_category".into(), "CAST(NULL AS STRING)".into())]) — add_columns succeeded; bug #3136 NOT observed. The "live bug" warning above appears resolved in 4.0.0; production planning can drop the defensive workaround. Full context: docs/spike-findings.md.

Arrow version alignment

Lance 4.0.0 transitively depends on arrow = 57.3.1 (and matching arrow-array, arrow-schema). If kb-core's direct dependencies pin a different Arrow major (e.g. arrow = "55" or "56"), two distinct arrow crate versions coexist in the dependency graph and RecordBatch types from arrow::array vs arrow_array::record_batch don't unify — Connection::create_table::<T: Scannable> fails to type-check. Production kb-core/Cargo.toml must pin arrow = "=57.3.1" (and arrow-array, arrow-schema) exactly, matching lance's transitive version. CI invariant: cargo metadata --format-version 1 | jq '[.packages[] | select(.name | startswith("arrow")) | .version] | unique | length == 1'. lance-index must also be a direct dep (pinned =4.0.0) because FullTextSearchQuery lives there, not in lancedb's public exports. Disable lancedb's cloud features (default-features = false) — aws/gcs/azure/dynamodb/oss are dead weight for a local-only daemon.

Spike update · 2026-05-11 · spike-lance initially used arrow = "55"; the resulting dual-version graph blocked create_table for an hour before exact-pinning unblocked it. Vec<RecordBatch> is the simplest Scannable input and is what kb's per-watch-event indexing should use. Full context: docs/spike-findings.md.

Backup / portability

Lance datasets use relative paths. tar -czf backup.tgz data/lance/ and extract elsewhere works. Capture _versions/, _indices/, _transactions/ and the fragment files — those are what the manifest references.

Cold-start latency

No published numbers for 10k rows specifically. Lance is mmap-friendly columnar with lazy index loading. The 2025 native-FTS work targeted "reducing index file size to reduce cold latency". Expect tens of ms for 10k rows; worth a 50-line spike.

B. Alternatives

One real challenger, several non-starters

  1. Turso / libSQL · vector + FTS in one file

    Strong shape, beta tax

    Crates: libsql (production), turso (the Rust rewrite — beta, not for production per their own docs). Native vector type with DiskANN built into libSQL, no extension needed. FTS5/BM25 inherited from SQLite; Turso DB adds Tantivy-backed FTS with fts_score() SQL function — but only in the beta engine.

    Risk: DiskANN index size — one user reported 30k × 1024-dim vectors (~117 MiB raw) producing a 5 GiB index (turso #3778). At 384-dim/50k rows it's more workable, but verify with a spike. Use this if you want one binary, one .db file, and accept the libSQL FTS5 BM25 limit (or pin the Turso-DB beta).

  2. SurrealDB embedded · graph-native

    Wrong model for kb

    Crate surrealdb v2.x. License: BSL 1.1 — embedded use is permitted, only commercial DBaaS is restricted; converts to Apache-2.0 four years after release. In-memory HNSW index, DEFINE INDEX … HNSW DIMENSION 384. FTS / BM25 exists but the BM25 tuning surface isn't documented — maturity gap vs lance/tantivy. Binary heavy, SurrealQL is its own thing.

    Use this if you want graph/edges inside the same store and accept BSL.

  3. DuckDB + VSS · analytics-grade SQL

    Skip

    HNSW vector index via vss extension. VSS is officially experimental, not recommended for production (DuckDB docs). HNSW persistence requires hnsw_enable_experimental_persistence=true; index not buffer-managed (must fit in RAM, full re-serialise on checkpoint), WAL recovery incomplete, deletes are tombstones. FTS extension is BM25-lite.

  4. rusqlite + sqlite-vec + FTS5 · the strongest one-store path

    Spike this before committing

    sqlite-vec is the successor to sqlite-vss (deprecated). Mozilla Builders project, sponsored by Fly/Turso/SQLite Cloud. Pure C, no deps, runs everywhere SQLite runs. KNN brute-force and IVF-style index in a vec0 virtual table with MATCH operator.

    Vectors via vec0, FTS5 with BM25 (built into SQLite), scalar/relational with normal SQL — everything in one .db file. Hybrid via RRF in plain SQL is documented.

    Risks: sqlite-vec is still 0.x; ANN quality has improved through 2025 but lance's IVF-PQ is more mature past 1M. FTS5's BM25 less tunable than Tantivy/lance-FTS (no per-language pipeline, fewer tokenisers). C extension means an extra .so/.dylib unless you use the vendored sqlite-vec crate.

    Use this if at ≤50k rows the FTS5 quality is "good enough" — you want the smallest binary, smallest dependency surface, easiest backup. This is the strongest alternative to the proposed split.

  5. Tantivy + sqlite-vec + sqlite · three stores

    Three sets of consistency to manage

    Tantivy 0.25.0 (latest), MIT, by Quickwit. ~2× faster than Lucene per benchmarks. Pair with lance-the-format (no DB layer), qdrant_client (network), qdrant-edge (embedded), or sqlite-vec.

    Use this only if lance's FTS proves insufficient (richer query DSL, non-English tokenisers).

  6. qdrant-edge · vector-only embedded

    New, no native BM25

    Crate qdrant-edge v0.6.0 (Feb 2026), public after a 2025 private beta. In-process via EdgeShard, synchronous, no background threads, reads server-format snapshots. Best-in-class vector search with HNSW + scalar/binary/PQ quantisation. No native BM25/FTS — Qdrant's full-text is a simpler text-match index, not Tantivy-grade BM25 ranking.

    Use this if vector recall is the first-order concern and you'd add tantivy or sqlite-FTS5 alongside. Don't conflate with qdrant-client (gRPC-only, not embedded).

Could kb collapse to ONE store?

Yes — two viable paths:

  • rusqlite + sqlite-vec + FTS5 — strongest "collapse" candidate. Smallest binary, easiest backup (cp file.db), edges/sources/index_runs/errors are just tables alongside docs. Against: BM25/FTS5 less tunable than Tantivy/lance-FTS; sqlite-vec ANN fine ≤50k rows but lance's IVF-PQ scales better past 1M.
  • lancedb alone — lance can hold the relational tables too (scalar BTree/Bitmap, LanceTableProvider exposes DataFusion SQL). Against: lance is columnar/append-oriented; row-level updates to index_runs/errors work but heavier than SQLite. You also lose SQL ergonomics. Doable, not idiomatic.

Argument for the split (proposed)

  • Each store does what it's best at — lance for vec/FTS at scale, sqlite for transactional row updates, edges, history.
  • SQLite's WAL semantics + ergonomic transactions are a better fit for index_runs / errors than lance manifests.
  • Backup story stays simple: tar the lance dir + copy the sqlite file.
  • Schema evolution lives in two well-trodden tools.

Argument against the split

  • Two query paths, two transaction boundaries, two on-disk layouts to back up consistently (a snapshot of one without the other = inconsistency).
  • Slightly larger binary than sqlite-only (mostly Arrow + DataFusion).
  • For 10k–50k docs sqlite-vec + FTS5 would work and yield a far smaller binary.
Recommendation Confidence · HIGH (cluster 3 committed) historical recipe below — preserved as regression-test trigger

v0.1 commits to lancedb + sqlite split per §Decisions. The block below preserves the historical "spike sqlite-vec + FTS5 first" recipe — it is now the regression-test trigger: re-run if a kb crosses ~50k docs and the operational-simplicity / scaling tradeoff inverts. Hybrid scoring is RRF k=60 (not hybrid_alpha); see topic 02 §Decisions.

Historical (superseded by §Decisions — kept as regression-test trigger): the proposed split is the well-trodden path; lance gives IVF-PQ + native BM25 + scalar indexes in one table, hybrid search and built-in rerankers, all from Rust. At 10k–50k docs and 384-dim vectors it is genuinely overkill in the safe direction. Schema evolution, backups, embedded story all solved.

Historical: the spike for rusqlite + sqlite-vec + FTS5 would collapse to one file, one binary 5–10× smaller, one backup command — material wins for a single-user daemon if relevance survives.

Regression-test recipe (run only if >50k docs)

  1. Index 5–10k real HTML docs into both stacks. Measure index time, on-disk size, binary size (cargo bloat --crates --release).
  2. Run a 50-query relevance set (mix of keyword-only, semantic-only, hybrid). Compare nDCG@10 between (lance hybrid + RRF) and (sqlite-vec KNN + FTS5 + RRF in SQL).
  3. Cold-open latency: kill the process, reopen, time the first query.
  4. If sqlite-vec is within ~5% relevance and meets latency targets, collapse to one store. Otherwise ship the lance + sqlite split.
Open questions / risks
  • Lance FTS in Rust: confirmed exposed (Index::FTS(FtsIndexBuilder), query.full_text_search()). Not Python-only.
  • Boolean operators in query strings not supported in lance FTS — must compose BooleanQuery programmatically. If kb's HTTP/SSE API accepts Lucene-style strings, write the parser yourself or use tantivy.
  • Schema migration risk: active bug #3136 on schema evolution past embedding columns. Pin to a known-good patch and re-test before 0.28+. Resolved — spike-lance (2026-05-11) confirmed add_columns works in lance 4.0.0; see §Schema migrations spike update.
  • Backup atomicity: lance dir + sqlite file aren't snapshot-consistent unless you stop the daemon. For a single-user kb, "stop, tar, restart" is fine; document it. Resolved cluster 3 — see §Decisions: indexer paused <500 ms while sqlite WAL-checkpoints and lance manifest is read + fragments tar'd. True atomic-without-quiesce is v0.2.
  • Cold-start latency: unmeasured for this size — spike it.
  • Binary size: assume 50 MB+ stripped Linux release. If distribution cares about size (Homebrew, single-file), real cost vs sqlite-only.
  • API churn: lancedb is 0.x with breaking minors every 1–2 months. Pin tightly, expect to rev.
