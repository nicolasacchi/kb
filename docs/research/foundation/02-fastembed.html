Topic 02 · Embeddings stack · Confidence MEDIUM → HIGH

verdictKeep fastembed-rs + bge-small.
Plan the dynamic-link path now.

The proposed stack — fastembed-rs with bge-small-en-v1.5 (384-dim) — is the right default for kb's 10k–50k single-user corpus. The risks are not in model quality. They are in onnxruntime's ~15 MB shared-library bundle and fastembed's first-run download UX in air-gapped installs. Both are solvable today.

Decisions · 2026-05-11 (cluster 3: embeddings — amended post deep-review)

Open-points cluster 3 of 4 landed. Embedding stack confirmed with multi-model support shipping from v0.1. Post-review additions: dimension-migration sequence (lance bug #3136), model registry source, kb.toml schema consolidation, edge cases for the CLI.

  • Default model: bge-small-en-v1.5 (384-dim, MIT). Prose-tuned, the right baseline for the canon.
  • Multi-model from v0.1 — CLI surface:
    • kb model list — installed + downloadable from the compiled-in fastembed enum (OSS-licensed subset: bge-*, gte-*, mxbai-*, nomic-v1.5, jina-v2-base-code, MiniLM/mpnet).
    • kb model download <name> [--from <path-or-url>] — fetches to XDG cache; --from accepts a local .tar.gz sidecar for air-gapped installs.
    • kb model set <name> [--kb <kb>] — per-kb selection. Refuses if the named model is not installed unless --yes (then auto-downloads). Refuses if the daemon is mid-index. On dimension change, prints re-embed cost estimate (single-digit minutes per 10 k docs, scaling with chunk count × model latency) and requires explicit confirmation.
    • kb model rm <name> — exits non-zero if any kb's embedding_model references it (use --force to break that reference; affected kbs refuse to start until reconfigured).
    CLI-only in v0.1 — writes ~/.config/kb/kb.toml directly; daemon picks up changes via file-watcher (topic 03) and either restarts the affected kb's indexer or signals reload. HTTP surfacing (read + switch via SPA Settings) deferred to v0.2.
  • Model registry source. v0.1: compiled-in via the fastembed::EmbeddingModel enum, filtered to the OSS-licensed subset. Custom HuggingFace models via [models.custom] in kb.toml deferred to v0.2.
  • Documented switch candidate: jina-embeddings-v2-base-code (768-dim, Apache 2.0). For code-heavy kbs.
  • Dimension migration sequence (lance #3136 workaround). Changing model dimension is not a column type cast in lance; bug #3136 reports CastError when adding columns past an embedding column. Sequence: (1) refuse to start re-embed if the daemon's lance version is in the #3136 affected range; (2) build chunks_v<n+1> as a sibling table at the new dimension (avoid add_columns on the old table); (3) re-embed in batches, emit index.file events for progress; (4) atomic manifest swap to the new table; (5) drop the old table. Documented as a v0.1 deliverable when kb model set is invoked with a dim-changing target.
  • XDG cache: ~/.cache/kb/models/<model-name>/<hf-revision>/ (revision-keyed so two daemons pinned to different revisions coexist). $KB_MODELS_DIR overrides the root. Concurrent downloads use a flock'd .lock file; a second daemon waiting on a partial download tails it.
  • Resumable downloads. Partial files keep a .part suffix; kb model download --resume picks up where it stopped.
  • onnxruntime via load-dynamic: use system libonnxruntime.so when present; bundled fallback.
  • Embedding input excludes <template id="kb-prompt">. DOM walk extraction: see topic 07 §D. Excluded tags: <script>, <style>, <template> — the kb-prompt template falls under the last exclusion automatically. BM25 still indexes the prompt as a separate filterable field (topic 01 Decisions).

Two TOML files, two roles. kb.toml is read by the daemon and SPA — daemon-side config + per-kb settings + SPA preferences served via /api/settings. daemons.toml is read only by the TUI — the user's list of daemons across machines they want to switch between via D. The SPA's federated-daemon registry lives in kb.toml [ui.daemons.<name>] (per topic 10 §O″) because the SPA inherits its server from the daemon hosting it; the TUI runs as a separate process and needs its own list.

TL;DR

Keep fastembed-rs 5.12 + bge-small-en-v1.5 (MIT, 384-dim, 33M params). Use ort with load-dynamic so the kb binary doesn't statically link onnxruntime. Cache models in ~/.cache/kb/models/. Add a kb model download subcommand for air-gapped pre-fetch. Implement BM25 + vector + RRF (k=60) hybrid from day one. Two switch candidates worth a config flag: nomic-embed-text-v1.5 (matryoshka, 8k context) and jina-embeddings-v2-base-code (768, 30 languages). Avoid jina-v3 (CC BY-NC) and EmbeddingGemma (Gemma Terms — non-OSI).

A. fastembed-rs · current state

Healthy crate, dual backend, primary is ort

fastembed-rs is maintained by Anush008. Latest stable is 5.12.0 (2026-03-05), with releases roughly every 2–4 weeks through 2025/early 2026 (5.0.0 in July 2025, 5.5.0 December 2025, 5.10.0 February 2026). Cadence is healthy and Qdrant uses it as their reference Rust embedding library, which is the closest the ecosystem has to a bus-factor signal.

Backend

Until 2024 it was a pure ONNX wrapper. In 2025 it became hybrid:

  • Primary: ort = 2.0.0-rc.11 (pykeio/ort, the maintained ONNX Runtime Rust binding). Used for BGE, MiniLM, MPNet, GTE, MXBai, Nomic v1/v1.5, E5, Jina v2, EmbeddingGemma — i.e. everything kb is likely to consider.
  • Optional Candle backend (feature-gated): candle-core = 0.9.1, used only for architectures ONNX can't faithfully export — nomic-embed-text-v2-moe (MoE gating layer can't be JIT-traced) and Qwen3-Embedding-{0.6B, 4B}. Enabled via features = ["nomic-v2-moe"] or ["qwen3"].

For kb with bge-small, only ort is involved; you don't pay the Candle compile cost.

CPU latency (bge-small-en-v1.5, 384-dim, ~33M params)

The web doesn't publish a project-specific fastembed-rs M-series benchmark. Bracketing numbers from comparable setups:

  • TEI on a 4-core CPU matches hosted-API latency for bge-base-v1.5 (Milvus 2025 benchmark).
  • Comparable models (e5-small, all-MiniLM-L6-v2, mpnet-base-v2) clock <30 ms per embed in real-time benchmarks.
  • For bge-small specifically, expect ~5–15 ms per embed at 512 tokens on M-series Apple silicon (CoreML EP) and ~15–40 ms on modern x86 CPU (AVX2/AVX-512). Batched throughput on CPU lands near 300–800 embeddings/sec for short inputs.
  • bge-base-v1.5 (110M) and mxbai-large (335M) are roughly 3× and 10× slower respectively.
Action: these should be re-measured with criterion once the daemon exists. Do not ship without a project-local benchmark — published numbers vary 2–5× by tokenizer config and runtime.
Spike update · 2026-05-11 · spike-fastembed measured bge-small-en-v1.5 on Intel i7-7700 Kaby Lake (4c/8t, no AVX-VNNI, x86_64 Arch Linux, system onnxruntime 1.24.4 via ort-load-dynamic): single-embed p50 = 169 ms for ~500-token input (3.4× over the 15–40 ms x86 prediction), and batched throughput collapses to ~5.6 emb/sec regardless of batch size (50–100× under the 300–800 emb/sec prediction — batching gives no benefit on this hardware). Per-doc time at batch 8 (189 ms) ≈ batch 32 (177 ms) ≈ single-embed (169 ms). Batch 128 was killed at 30 min wallclock (cache-thrash). Cold-start (model cached) 3.36 s — within the 5 s ceiling. Read: the research's x86 bounds are aspirational and assume Ice Lake / Tiger Lake or newer (AVX-VNNI). On older hardware, production must plan for slow embedding: a 50k-artifact full reindex ≈ 140 min, not 1–3 min. Incremental indexing + SSE progress UI are essential. Cap production batch size at 32 max. Full context: docs/spike-findings.md.

Model download / first-run UX

fastembed downloads from HuggingFace (or a Qdrant-mirrored GCS bucket as fallback). The Rust crate stores files in a cache dir controllable via the cache_dir builder field; default is local_cache in CWD — this is bad; kb should set it to ~/.cache/kb/models/ explicitly. Known offline issues:

Spike update · 2026-05-11 · spike-fastembed confirmed the bad default in stronger terms: the actual directory name is <cwd>/.fastembed_cache/ (not local_cache as the docs imply, and decidedly not ~/.cache/huggingface/hub/). Models silently land wherever the daemon happens to be invoked from. Production must pass InitOptions::new(...).with_cache_dir(xdg::cache_home("kb/models")) at every construction site — there is no global override. Full context: docs/spike-findings.md.
  • Issue #30 (still partially open): cached model is re-validated against HuggingFace on each load even when offline, blocking startup.
  • HF_HUB_OFFLINE=1 falls through to a GCS download attempt instead of using the local cache (qdrant/fastembed #615).
  • Workaround: kb should pre-download via its installer/init step, then set HF_HUB_OFFLINE=1 and point cache_dir directly at the snapshot folder, and accept that first-run requires network.

Bundled binary size impact

ort/ONNX Runtime CPU shared lib is ~10–20 MB for Release builds (Linux .so, macOS .dylib); CUDA/TensorRT EPs blow this past 100 MB but are irrelevant here. With ort features default-features = false plus minimal-build, you can shave further. With load-dynamic you skip the link dependency entirely and dlopen at runtime — recommended for kb so the binary can ship without onnxruntime and pull it from a sidecar dir.

Default model and quantized variants

Confirmed: BAAI/bge-small-en-v1.5 is still the default. Quantized variants are available — append Q to the enum (EmbeddingModel::BGESmallENV15Q). Currently 6 models have dynamic quantization: gte-base/large-en-v1.5, mxbai-embed-large-v1, nomic-embed-text-v1.5, all-MiniLM-L12-v2, all-MiniLM-L6-v2.

Spike update · 2026-05-11 · spike-fastembed measured BGESmallENV15Q against BGESmallENV15 on Intel i7-7700 Kaby Lake (no AVX-VNNI): quantised is slower — 199 ms p50 vs 169 ms p50 for the same ~500-token input. The fp32 model is 127 MB on disk; the "quantised" (bge-small-en-v1.5-onnx-Q) is 64 MB — closer to mixed-precision than pure int8. On pre-VNNI CPUs (anything before Ice Lake / Tiger Lake / Zen 4), quantised is a memory-footprint win only, not a latency win. Production kb model {download,set} CLI should default to fp32 and document the quant variant as memory-constrained-host-only. Full context: docs/spike-findings.md.
B. Direct alternatives

Three serious, two non-starters

  1. Candle · pure-rust ML

    Smaller, slower, defer

    Native Rust ML framework from HuggingFace. Loads safetensors directly, supports BERT/JinaBERT/T5 (covers BGE, MiniLM, mpnet, jina-v2, mxbai). Optimised CPU backend with optional MKL / Accelerate.

    Pros: pure Rust, no onnxruntime shared lib (binary stays small — Candle compiles into the crate), can use any HF model without ONNX export, smaller surface area. Cons: 3–5× slower than ONNX Runtime in published benchmarks; less production-hardened. The sentence-transformers-rs crate (jwnz) wraps it with 15+ pre-built BGE/MiniLM/mpnet models if you want a higher-level API.

    For kb's "10k–50k docs, indexed once, queried daily" profile, Candle's slower indexing is acceptable. If you anticipate re-indexing churn, ort wins.

  2. ort directly · skip the wrapper

    Save 200 LOC, lose model registry

    Skip fastembed-rs and call ort yourself with a manually downloaded ONNX model. ~150–300 LOC of glue (tokenizer config parse, attention mask, mean-pool + L2 norm), and you reinvent fastembed's model registry. ort 2.0.0-rc.12 (March 2026) is stable enough.

    Verdict: start with fastembed-rs; drop to ort only if fastembed's first-run UX or model registry becomes a constraint.

  3. ollama-rs · subprocess Ollama

    Decisively wrong for kb

    ollama-rs wraps the Ollama HTTP API; you'd call nomic-embed-text via http://localhost:11434/api/embed.

    Pros: zero ONNX in the kb binary, model management delegated. Cons: requires the user to install and run Ollama — a heavy external dep for a "single-user app." Adds 200 MB+ of process memory always-on, 2-process architecture, network hop adds 5–15 ms per query, breaks the "self-contained daemon" pitch. Decisively worse.

  4. OpenAI / Voyage / Cohere · paid API

    Out of scope, with one footnote

    The brief is "self-contained, offline-friendly, single-user." Sending document text to a paid API per index/query violates the offline goal and the privacy story. Confirmed exclusion.

    Footnote worth keeping: Voyage's voyage-code-3 is the current SOTA for code retrieval (beats OpenAI v3-large by ~14% on 32 code datasets). If a "cloud sync / cloud index" mode appears later, this is a strong rerank-pass option for opt-in users — but never the default offline path.

  5. rust-bert · old guard

    Skip

    Recent issues from April/May 2025 sit open without resolution; commit cadence is slow. Has ONNX support via the same ort crate. No advantage over fastembed-rs, plus a heavier/slower API.

C. Model selection

The 384 vs 768 question is a quality choice, not a storage one

For 50k docs at 5 chunks each = 250k vectors, even fp32 1024-dim only costs ~1 GB raw. With LanceDB IVF-PQ it's sub-100 MB. Pick the model on quality.

Storage impact: 384 vs 768 in lancedb

For 50,000 documents with 5 chunks each = 250,000 vectors:

  • fp32 384-dim: 250k × 384 × 4 B = ~366 MB raw vectors.
  • fp32 768-dim: 250k × 768 × 4 B = ~732 MB raw vectors.
  • int8 PQ-compressed (16 sub-vectors): ~4 MB for 384, ~8 MB for 768.

LanceDB's columnar Lance format plus IVF-PQ pushes both well under raw figures. Distance computation is O(dim) — 384 vs 768 is roughly 2× faster brute-force, sub-millisecond at this scale either way. Verdict: at 10k–50k docs, storage is irrelevant (sub-GB even at 1024-dim). Pick the model on quality.

Practical recommendation

  1. Default: bge-small-en-v1.5 (384). Solid baseline, fast, English-only is fine for the common case, MIT.
  2. Config option for higher quality: nomic-embed-text-v1.5 with matryoshka truncation. Embed at 768, store at 768 in lancedb, expose a "fast" query path that truncates to 256 with F.layer_norm. Apache-2.0, 8k context.
  3. Code-heavy corpora: jina-embeddings-v2-base-code (768, Apache-2.0, 8k context, 30 programming languages). Best open-source code-retrieval option fastembed-rs already supports.
  4. Avoid by default: jina-v3 (license), EmbeddingGemma (Gemma Terms — non-OSI), nomic-embed-code (7B is absurd for desktop), large/x-large generic models (10× cost for ~1 MTEB point).
D. Bundling strategy

Download on first run, cache in XDG, dlopen onnxruntime

Option 1 (recommended) · download on first run

  • Model files in $XDG_CACHE_HOME/kb/models/ (default ~/.cache/kb/models/).
  • kb init or kb index triggers download with a progress bar.
  • Daemon refuses to start if model missing and offline; kb model download <name> for explicit pre-fetch.
  • 130 MB (bge-small) is fine to download — users tolerate this for ollama pull-style flows.
  • Air-gapped install: ship a kb-models.tar.gz sidecar that extracts to the cache path; document the layout.

Option 2 · bundle ONNX in the binary

  • include_bytes!("model.onnx") adds 130 MB (or 33 MB for int8/Q variant) to the binary.
  • Pros: single-file install, fully offline by default. Cons: every architecture change forces re-download; users who want to swap models lose; 130 MB binary is ugly.
  • Acceptable only if the int8/Q variant is bundled — that's 33 MB which is tolerable.

Option 3 · split tier (defer to v2)

Bundle a tiny fallback (e.g. Model2Vec static distillation of bge-base — ~30 MB, near-instant inference, slightly lower MTEB) so the daemon works immediately. First-run downloads the full model in the background, swaps in once ready. Most polished UX, most engineering work.

onnxruntime distribution

  • Use ort with load-dynamic feature → kb binary doesn't link onnxruntime at compile time.
  • kb install-runtime downloads libonnxruntime.{so,dylib} (15–20 MB) for the host platform from the official ONNX Runtime release tarball into ~/.local/share/kb/lib/.
  • macOS arm64 + x86_64 + Linux x86_64 + Linux arm64 are the standard four. ONNX Runtime publishes signed binaries for all of them; macOS signing has been a recurring issue (microsoft/onnxruntime#16168) so verify before shipping.
  • Static linking is possible (ORT_STRATEGY=system + ORT_LIB_PATH to a from-source build with --no-build_shared_lib) but adds 30+ minute build times and Microsoft does not officially support it. Skip.
E. Open questions

Three live debates, three confident defaults

E.1 Is bge-small the right base for Claude-generated artifacts?

Claude artifacts are mixed prose + code + ASCII diagrams. bge-small was trained on web text and is biased toward natural language; it'll handle prose well, treat code reasonably (BERT tokenisers don't choke on it but don't model it either), and do poorly on ASCII art (token-level meaningless). Options:

  • For the default: bge-small is fine. Code blocks are usually a minority of an artifact's volume; BM25 catches the exact-symbol queries vector search misses.
  • For code-heavy corpora: switch to jina-embeddings-v2-base-code. Same family fastembed-rs already supports, just a different model enum. Apache-2.0.
  • For mixed corpora at scale: chunk by content type (prose vs. code-block) and embed each with the appropriate model. Adds complexity; defer.

E.2 Is matryoshka worth using?

Yes, for the "fast filter / accurate rerank" pattern, but only if you'd use it.

  • nomic-embed-text-v1.5 lets you embed at 768 and query at 256 by truncating + F.layer_norm. MTEB drops 1.24 points. 3× distance-compute speedup for 2% quality loss.
  • LanceDB IVF-PQ already provides a coarse-fine pattern on a single embedding, so matryoshka's win is marginal at 50k vectors. It becomes valuable above ~500k vectors where the brute-force fallback dominates.
  • For kb v1: don't bother. Use a single 384-dim or 768-dim embedding throughout. Revisit if the corpus grows.

E.3 BM25 + vector with RRF — actually better than BM25 alone?

For prose-heavy retrieval: yes, broadly confirmed. For code/identifier-heavy retrieval: BM25 alone often wins on exact-name queries, and vector adds noise. Hybrid with RRF (Cormack et al. CIKM 2009; canonical formula score = 1/(rank + k), k=60) is the right default because:

  • Score-agnostic (no normalisation headaches between unbounded BM25 and bounded cosine).
  • Degrades gracefully when one signal is wrong: if vector retrieval surfaces noise, BM25's high-precision results dominate, and vice versa.
  • The 2024 ACM TIS paper "An Analysis of Fusion Functions for Hybrid Retrieval" (Bruch et al.) shows weighted linear combination can beat RRF with corpus-specific tuning, but RRF is the safer default.
  • OpenSearch shipped RRF as default hybrid scoring in 2.19 (Feb 2025); Azure AI Search uses it for hybrid + multi-vector queries. Industry-standard choice.

For kb: BM25 (tantivy, or LanceDB-via-tantivy) + vector (lancedb) + RRF fusion (k=60). Skip cross-encoder reranking in v1 — at 50k docs the top-20 RRF results are good enough and rerankers add another model dependency. Add bge-reranker-base as an optional v2 quality knob.

Recommendation Confidence · HIGH

Pin fastembed = "5.12" with default-features. No qwen3 / nomic-v2-moe needed.

Use ort with load-dynamic so onnxruntime is dlopened from ~/.local/share/kb/lib/ rather than statically linked. Ship kb install-runtime that downloads the platform-appropriate shared lib (15–20 MB).

Set cache_dir = ~/.cache/kb/models/ explicitly — do not accept the local_cache default in CWD. Add kb model download <name> for pre-fetching; require it in air-gapped installs.

Expose --embedding-model config with at minimum bge-small-en-v1.5 (default), nomic-embed-text-v1.5, jina-embeddings-v2-base-code. Hard-code the dimension per model; re-create the lancedb index on switch — you can't mix dimensions in one table.

Implement BM25 + vector + RRF fusion (k=60) for hybrid query. Defer matryoshka, cross-encoder rerankers, and EmbeddingGemma/jina-v3 (license issues) to a v2 conversation.

Add criterion benchmarks from day one: (a) embed latency for a 500-token chunk, (b) batched throughput at batch=32, (c) end-to-end query p50/p95.

What would change this recommendation
  • If kb grows past ~500k vectors → switch to nomic-embed-text-v1.5 with matryoshka, query at 256-dim and rerank top-100 at 768-dim.
  • If the corpus is dominated by source code → make jina-embeddings-v2-base-code the default.
  • If a "cloud sync / cloud index" mode appears → add Voyage voyage-code-3 as an optional backend for opt-in users.
