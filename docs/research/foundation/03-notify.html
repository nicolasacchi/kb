Topic 03 · File watcher · Confidence HIGH

verdictnotify + debouncer-full,
400 ms window, ENOSPC fallback.

The proposed 250 ms debounce was a guess. The right number for "Claude Code drops a finished .html" + occasional cp -r bursts is closer to 400 ms. notify + notify-debouncer-full ≥ 0.7.0 is the canonical primitive — every comparable Rust project uses it.

TL;DR

notify 8.2.0 + notify-debouncer-full 0.7.0. Don't roll your own debouncer — rename-stitching alone justifies it. Pin ≥ 0.7.0 (older versions had a real dedup bug, fixed in #711). 400 ms debounce window, configurable via KB_DEBOUNCE_MS. RecommendedWatcher first; on ENOSPC (errno 28), log an actionable message and fall back to PollWatcher (2 s interval). Initial directory walk is your responsibility — neither inotify nor FSEvents replays history. Skip watchexec as a library — solves a different problem (process supervision).

Decision · HIGH Crate maturity · HIGH Cross-OS coverage · HIGH (linux+macos)
A. notify · current state

Stable, multi-maintainer, broadly adopted

Repo: notify-rs/notify. Versions: 8.0.0 (2025-01-10) → 8.1.0 (2025-07-03) → 8.2.0 (2025-08-03, latest stable). 9.0.0-rc.1/2/4 shipped Jan–Apr 2026; debouncer-full 0.8.0-rc tracks it. Wait for 9.0 GA before considering.

Default backends, confirmed: Linux/Android → inotify; macOS → FSEvents (kqueue behind macos_kqueue feature); Windows → ReadDirectoryChangesW; BSDs/iOS → kqueue. RecommendedWatcher is a compile-time alias resolving to the platform native impl. PollWatcher is the universal fallback — works everywhere, no kernel limits, but burns CPU.

Fall back to PollWatcher when

  • inotify ENOSPC
  • NFS / SMB mounts (events silently not delivered)
  • WSL on Windows paths
  • Docker on Apple Silicon (FSEvents unavailable inside Rosetta — "os error 38")
  • macOS files you don't own
Cross-OS event consistency is not clean. Modify(Name(Both)) is the cross-platform "rename" signal but only when notify can pair From/To. Linux pairs via inotify cookies; macOS by path; Windows via file IDs. Linux monitors inodes, macOS monitors paths. Linux has Access(Close(Write)) (CLOSE_WRITE); macOS does not. Renaming a watched directory on macOS emits no event; renaming a file does. Net: don't consume raw notify::Event — use the debouncer.
B. notify-debouncer-full

What it adds over raw notify

Latest 0.7.0 (2026-01-23). 0.8.0-rc.2 (2026-05-02) tracks notify 9.x RC. The value-add over raw notify:

  • Pairs Rename From/To across OSes — emits a single Modify(Name(Both)) with both paths.
  • Tracks file-system IDs (inode on Linux/macOS, fileId on Windows) via FileIdCache so renames stitch even when the OS misses the cookie.
  • Updates queued event paths when an enqueued path is renamed before flush.
  • Collapses duplicate Create and post-Create Modify events.
  • Emits a single Remove when a directory is recursively deleted (inotify otherwise spams one per child).

API

new_debouncer(timeout: Duration, tick_rate: Option<Duration>, handler: F). Timeout is global, not per-path. new_debouncer_opt lets you swap the file-id cache. Handler receives DebounceEventResult = Result<Vec<DebouncedEvent>, Vec<Error>>.

-mini vs -full

The mini variant is simpler — no rename stitching, no file-id tracking. Fine for "rerun a build on any change", insufficient for kb because batch reindexing wants to know "this path moved" vs "this is a new file".

Notable fixes in recent versions

  • 0.6.0 (2025-08-03): skips Modify events fired immediately after Create (#701) — directly improves atomic-write handling.
  • 0.7.0 (2026-01-23): fixed deduplication so events within the timeout actually merge (#711). Before this, the handler could be called multiple times for one save — pin ≥ 0.7.
  • 0.8.0-rc: perf for large watch sets, futures/tokio handler impls, Debouncer::watched_paths, emits Remove even after Create+Remove inside one window.

Window for kb

Docs example uses 2 s; community guidance is 100–500 ms for editor reload, 500 ms for "any save settles". For Claude Code dropping a finished .html (single atomic rename) plus occasional cp -r bursts, 400 ms balances responsiveness with batching. Below ~150 ms you risk re-firing inside one editor save sequence; above ~1 s the user notices lag.

C. Atomic writes & rename semantics

The cases that actually fire in production

Linux tmpfile + rename(tmp, target)

Raw inotify yields, in order: IN_CREATE (tmp) → IN_MODIFY/IN_CLOSE_WRITE (tmp) → IN_MOVED_FROM (tmp) + IN_MOVED_TO (target) sharing one cookie. Notify maps these to Create(File), Modify(Data), Access(Close(Write)), Modify(Name(From)), Modify(Name(To)). If both ends fall in the watch tree, debouncer-full collapses to one Modify(Name(Both)) with paths = [tmp, target].

macOS via FSEvents

Typically just a Modify(Name) on the target with file-event flags; FSEvents may not surface the tmp file individually. The debouncer's file-id (inode) stitching covers this.

Editor "save = rename" (neovim, Helix, IntelliJ)

Same atomic-rename dance. Debouncer-full coalesces correctly as long as timeout exceeds the editor's save sequence (a few tens of ms). 400 ms is generous. Some editors unlink-then-write instead → Remove + Create with no rename pairing; with debouncer 0.6.0+'s "skip Modify after Create" plus file-id tracking, it still ends up as one logical "file at this path changed" event.

Symlink target swaps

notify does not follow symlinks recursively — it watches the link path. ln -sfn newtarget link shows up as Modify(Name) on the link itself, not on what it points to. To react to swaps of a symlinked html directory, watch the real target.

mv from outside the watched dir

Linux yields a single Create (no MOVED_FROM was visible since source wasn't watched); debouncer v6+ relabels as rename-to. macOS yields Create too. kb should treat these as "new file, index it"; debouncer does not invent a phantom From-side.

cp -r of 100 files

Linux inotify yields ~3–5 events per file (CREATE/OPEN/MODIFY/CLOSE_WRITE) → ~300–500 raw events streamed; with a 400 ms window debouncer-full collapses to ~100 DebouncedEvents, one per final path. macOS FSEvents already coalesces in-kernel. Either way kb should treat the debounced flush as "here is a batch — index every path".

D. Linux inotify limits

Per-directory, not per-file — kb won't hit it

  • fs.inotify.max_user_watches: Arch 524288 (since 2018, confirmed default — relevant on a Linux desktop). Ubuntu/Debian 524288 (Linux 5.11+ auto-tunes by RAM, often ~1048576). Fedora same.
  • fs.inotify.max_user_instances: 128 across all distros. Per-user limit on inotify FDs (one per inotify_init()). kb only needs one — never your problem.
  • fs.inotify.max_queued_events: 16384. Burst overflow surfaces as a notify error.
  • inotify is per-directory: recursive watching adds one watch per subdirectory. 10k files in one folder = 1 watch. 1k files in 10 nested folders = 10 watches. 100k subdirs = 100k watches → trips the limit. kb's flat-ish html corpus will not hit this organically.

Detecting the limit

notify surfaces as notify::Error with kind = ErrorKind::Io(io) where io.raw_os_error() == Some(28) (ENOSPC). The default OS message says "No space left on device" — translate it.

User-facing log when fallback triggers: inotify watch budget exhausted (errno 28). Falling back to polling. To restore native watching, run sudo sysctl fs.inotify.max_user_watches=1048576.

Workarounds, in order

  1. Helpful error + auto-fallback to PollWatcher (poll interval 2 s, no compare_contents unless missed writes are observed on tmpfs/network mounts).
  2. Document sysctl tuning in README.
  3. Advise non-recursive watching if a corpus grows pathological.
E. macOS FSEvents quirks

Path-level, leading vs trailing edge, no historical replay

  • Coalescing window = the FSEvents latency parameter. notify exposes via Config::with_latency; default ≈ 0 (deliver ASAP). For kb, leave default and let debouncer-full's timeout do all coalescing — single source of truth.
  • Leading vs trailing edge: notify defaults to trailing (no kFSEventStreamCreateFlagNoDefer) — what you want for a debouncer.
  • Historical events replay: FSEvents can replay from before stream start using event IDs and the on-disk .fseventsd log. notify does not expose this — always a fresh stream. kb must do its own initial directory walk on startup. Matches Linux (inotify has no replay either).
  • Path-level vs inode-level: FSEvents tracks paths; inotify tracks inodes. Don't rename the watch root while the daemon runs.
  • Known FSEvents+notify bug (#240): in some configs, events for a continuously-written file aren't delivered until close; may delay up to 10 s. Claude Code closes its file before the rename, so this is fine for kb.
F. Production patterns

Everyone uses notify directly

  • notify is the default primitive, used by alacritty, deno, mdBook, rust-analyzer, watchexec, zed, dioxus, and (formerly) cargo-watch.
  • cargo-watch was archived January 2025. The maintainer points to bacon as the successor — bacon uses notify directly. Strongest production signal.
  • watchexec library is split into watchexec (orchestrator), -events, -signals, -supervisor, -filterer-*. Wraps notify and adds Tokio runtime, glob/gitignore filterers, signal handling, process supervisor. Default debounce 50 ms, trailing edge. Don't use it for kb: optimised for "watch files, run a process"; you want "watch files, call an in-process function". Overkill, ties you to Tokio + miette.
  • dioxus dev server and mdBook serve both use notify directly.
  • No newer general-purpose crate has displaced notify.
Recommendation Confidence · HIGH

Architecture

  1. Initial walk first. On startup, walkdir the watch root, index every .html, record (path, mtime, size, content_hash). Neither notify nor the debouncer replays history.
  2. Construct the debouncer next, then re-walk once after it's armed (cheap; deduplicates by content hash). Closes the race between initial walk and watcher arming.
  3. Dispatch on DebouncedEvent.kind for each batch:
    • Create(_) or Modify(Name(To|Both)) → reindex destination path.
    • Modify(Data(_)) or Modify(Metadata(_)) → reindex path.
    • Remove(_) or unmatched Modify(Name(From)) → drop from index.
    • Modify(Name(Both)) with two paths → rename in-index by file-id, no re-read.
  4. Fsync the index after each batch. The debounce window already gave you "burst settled".
use notify::RecursiveMode;
use notify_debouncer_full::new_debouncer;
use std::time::Duration;

let (tx, rx) = std::sync::mpsc::channel();
let mut debouncer = new_debouncer(Duration::from_millis(400), None, tx)?;
debouncer.watch(&kb_root, RecursiveMode::Recursive)
    .or_else(|e| if is_enospc(&e) { fallback_poll(...) } else { Err(e) })?;

Configuration knobs

  • KB_DEBOUNCE_MS — default 400. Lower (~150) for snappier reload; higher (~1000) for noisy network mounts.
  • KB_WATCHER_MODE — auto (default: native + ENOSPC fallback), native, poll.
  • KB_POLL_INTERVAL_MS — default 2000 in poll mode.

Verification (for the executor)

  • Burst test: for i in $(seq 1 100); do echo '<p>hi</p>' > /tmp/kb/$i.html; done → expect one index batch flush logged, not 100.
  • Atomic-rename: small Python snippet using os.replace(tmp, target) → expect a single Modify(Name(Both)) debounced event with both paths.
  • ENOSPC: sudo sysctl fs.inotify.max_user_watches=8 then start kb on a tree with >8 directories → expect actionable error message and successful poll-mode operation.
  • macOS smoke: same atomic-rename test → equivalent single-event behaviour.
