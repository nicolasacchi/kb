TL;DR

SSE on axum is the right transport for kb. Pattern: one broadcast::Sender<Arc<KbEvent>> in AppState, per-connection BroadcastStream wrapping a fresh subscribe(), returned via Sse::new(stream).keep_alive(...). Browser EventSource handles reconnection; VecDeque ring keyed by monotonic u64 makes Last-Event-ID replay work. Schema: single envelope {v, id, type, ts, payload}, one firehose /events with ?types= filter — do not split endpoints by domain or by direction (the dual-endpoint trap MCP rolled back in 2025). WebSockets buy nothing here. §G traces the disk-change → browser-reload flow that artifact.indexed drives; the SPA recreates the iframe on each event using topic 06's iframe-recreate pattern.

0. What SSE is (plain English)

One HTTP connection that never closes — server pushes, browser listens

Server-Sent Events is a one-way pipe from the daemon to the browser. The browser opens a normal HTTP request to /events; the daemon never finishes the response. Instead, every time something happens that the browser should know about — a file was indexed, indexing reached 47%, a comment was added, an error occurred — the daemon writes a few more lines into the open response. The browser parses each chunk as it arrives. The connection lives as long as the browser tab is open.

What the bytes look like

The wire format is plain text. Each event is a few lines, separated by blank lines. This is exactly what curl sees if you run curl -N http://localhost:4000/api/events:

id: 42
event: artifact.indexed
data: {"artifact_id":"a-9f3...","kb":"work","path":"draft.html","hash":"a3b1...","mtime":1715...,"change_kind":"updated"}

id: 43
event: index.file
data: {"run":"r-2c1","kb":"work","path":"draft.html","ms":188,"edges":5,"ok":true}

: heartbeat                ← lines starting with ":" are comments
                             (keepalive only; browser ignores them)

That's it — no framing protocol, no handshake, no JSON envelope outside the data: field. The id: field is how reconnection / replay works (see §B); the event: field is how the browser dispatches to listeners.

How the three pieces fit together

kb daemon                              your browser
─────────                              ────────────
broadcaster.send(event)                EventSource('/events')
         │                                      ▲
         ▼                                      │
SSE broadcast channel ────── HTTP stream ───────┘
         │                  (chunked, never closes)
         ▼
axum Sse response → bytes on the wire
  1. Producer side: kb's indexer, watcher, query handler, etc. all call broadcaster.send(event) when something interesting happens.
  2. Broadcast channel: a single tokio broadcast fans the event out to every connected client (see §A). Slow clients lag; the channel drops oldest events for them and tells them they fell behind.
  3. Browser side: new EventSource('/events') opens the connection and dispatches each event: line to a listener. Built into every browser. No client library.

Why SSE and not WebSockets

  • One-way is correct for kb. The daemon pushes; the browser doesn't push back. Search queries are normal REST. WebSockets give bidirectional communication kb doesn't need.
  • Plain HTTP. Same auth as the rest of kb's API. No handshake protocol. Reverse proxies (nginx, Caddy) just work — with one footgun about buffering, called out in §D.
  • Browser-native. new EventSource(url) handles reconnection, replay (Last-Event-ID), and parsing. No third-party JS dependency. Auto-reconnects on network drops.
Reader shortcut: The rest of this page is technical implementation — broadcast channels, ring buffers, reverse-proxy tuning, performance budgets. Skip to §G — Live-reload if you only want to know how "edit a file on disk, see the change in the browser" works.
A. Axum SSE basics

broadcast + BroadcastStream + keep_alive

axum 0.8.9 (current 2026-05). Pin axum = { version = "0.8", features = ["macros", "tokio"] }. SSE under axum::response::sse; KeepAlive needs the tokio feature. BroadcastStream is in tokio-stream.

Idiomatic broadcast pattern

use std::{convert::Infallible, sync::Arc, time::Duration};
use axum::{extract::State, response::sse::{Event, KeepAlive, Sse}, routing::get, Router};
use futures_util::Stream;
use tokio::sync::broadcast;
use tokio_stream::{wrappers::BroadcastStream, StreamExt};

#[derive(Clone)]
pub struct AppState {
    pub tx: broadcast::Sender<Arc<KbEvent>>, // Arc keeps slot pointer-sized
}

pub async fn sse_handler(
    State(state): State<AppState>,
) -> Sse<impl Stream<Item = Result<Event, Infallible>>> {
    let rx = state.tx.subscribe();
    let stream = BroadcastStream::new(rx).filter_map(|msg| match msg {
        Ok(ev) => Some(Ok(Event::default()
            .id(ev.id.to_string())
            .event(ev.kind.as_str())
            .json_data(&*ev).unwrap())),
        Err(BroadcastStreamRecvError::Lagged(_n)) => {
            // surface a synthetic event so the client knows to refetch
            Some(Ok(Event::default().event("lag").data("reconnect-recommended")))
        }
    });
    Sse::new(stream).keep_alive(
        KeepAlive::new().interval(Duration::from_secs(15)).text(":heartbeat"),
    )
}

KeepAlive defaults to a 15 s : comment; timer resets on every real event so heartbeats only fire during idle.

watch vs broadcast

Use broadcast — events are discrete and every client must see every one. watch collapses to "latest value only" and only fits current state (e.g. IndexerStatus). kb may end up with one broadcast for the event log plus one watch for current indexer state, merged in the handler.

Backpressure

broadcast::Sender::send never blocks. When full, the oldest message is dropped and slow receivers get RecvError::Lagged(n) on next recv(). Buffer rounds up to next power of two (capacity 100 actually holds 128). For kb: capacity 256, surface Lagged as a synthetic event: lag and let the client refetch state via REST. Don't treat Lagged as fatal — broadcast drops by design.

Closed-connection detection

Free: dropped HTTP connection → dropped response body → dropped stream → dropped Receiver. Slot reclaimed automatically. For cleanup hooks, use a Drop guard struct held inside the stream.

B. Last-Event-ID replay

No maintained crate. Write the ring yourself.

Ecosystem (2026): no production-ready axum crate packages Last-Event-ID replay. HTML5 spec is clear (browser sets Last-Event-ID on reconnect, server replays id:-tagged events); axum doesn't ship it. Build it yourself.

Pattern: ring buffer + monotonic id

pub struct EventLog {
    next_id: AtomicU64,
    ring: Mutex<VecDeque<Arc<KbEvent>>>, // last N events, capped (e.g. 1024)
    tx: broadcast::Sender<Arc<KbEvent>>,
}

impl EventLog {
    pub fn publish(&self, mut ev: KbEvent) {
        ev.id = self.next_id.fetch_add(1, Ordering::Relaxed);
        let arc = Arc::new(ev);
        {
            let mut ring = self.ring.lock().unwrap();
            if ring.len() == ring.capacity() { ring.pop_front(); }
            ring.push_back(arc.clone());
        }
        let _ = self.tx.send(arc); // ignore "no receivers"
    }
}

async fn sse_handler(
    State(log): State<Arc<EventLog>>,
    headers: HeaderMap,
) -> Sse<impl Stream<Item = Result<Event, Infallible>>> {
    let last_id: Option<u64> = headers.get("last-event-id")
        .and_then(|h| h.to_str().ok())
        .and_then(|s| s.parse().ok());
    let rx = log.tx.subscribe();
    let replay: Vec<Arc<KbEvent>> = {
        let ring = log.ring.lock().unwrap();
        match last_id {
            Some(id) => ring.iter().filter(|e| e.id > id).cloned().collect(),
            None => Vec::new(),
        }
    };
    let replay_stream = futures_util::stream::iter(replay.into_iter().map(Ok));
    let live = BroadcastStream::new(rx).filter_map(/* ... */);
    let stream = replay_stream.chain(live).map(/* to sse::Event */);
    Sse::new(stream).keep_alive(KeepAlive::default())
}
Caveat: subscribe-then-snapshot can deliver duplicates. Subscribe before snapshotting and filter live items with id <= ring.back().id, or de-dup by id client-side.

SQLite alternative

Persist events to events(id INTEGER PRIMARY KEY, ...) and SELECT WHERE id > ? on reconnect. Only worth it for replay across server restart; for "tab paused 30 s" cases, in-memory ring is enough.

C. Reconnection semantics

Browser auto-reconnects. Rust client picks reqwest-eventsource.

Browser EventSource auto-reconnects with ~3 s default backoff (Chrome ~3 s, Firefox ~5 s, grows on repeated failure). Override via the SSE retry: field — Event::default().retry(Duration::from_secs(5)). Event::retry panics if called twice on one event.

Rust client crates

  • reqwest-eventsource (158k dl/mo, MIT/Apache, ~400 LOC): wrapper over reqwest + eventsource-stream. Tracks Last-Event-ID automatically (handle_response calls stream.set_last_event_id(...)) and retries with backoff. Best fit for kb CLI/TUI.
  • eventsource-client (302k dl/mo, Apache-2.0, hyper v1, pluggable transport): heavier, fuller protocol impl. Also handles Last-Event-ID and reconnect.

Edge cases

Mid-event disconnect: SSE parser is line-based, incomplete events are discarded, Last-Event-ID retains the last complete id. Server restart: client reconnects with Last-Event-ID; if the ring was cleared, server returns a synthetic event: gap so the client knows to refetch.

D. SSE vs WebSockets for kb

One-way wins. Auth wins. Proxy is the footgun.

One-way wins. kb does not need bidirectional streaming — queries are REST. The "6 connection per origin" objection is a 2026 non-issue: HTTP/2 multiplexes ~100 streams (default SETTINGS_MAX_CONCURRENT_STREAMS) over one TCP connection.

Auth. SSE is vanilla HTTP — Authorization: Bearer, cookies, mTLS all work unchanged. WebSocket auth requires URL tokens (logged), custom subprotocols, or post-upgrade handshakes. SSE wins on "same auth as the rest of the API".

Reverse-proxy belt-and-suspenders

  • App: set X-Accel-Buffering: no and Cache-Control: no-cache, no-transform.
  • nginx: proxy_buffering off; proxy_cache off; proxy_http_version 1.1; chunked_transfer_encoding off; proxy_read_timeout 86400s; and disable gzip on the route.
  • Caddy: no X-Accel-Buffering support — use flush_interval -1 in reverse_proxy.
  • Cloudflare-class CDNs: may force-close ~100 s. Use retry: so recovery is transparent.

Keepalives. 15 s : comment is correct. LB idle timeouts fire 60–120 s; 15 s is well under.

E. Event schema design

One envelope, one firehose, glob filter

Recommended envelope

FieldNotes

Event types — watch.* vs artifact.*

The taxonomy distinguishes raw disk signal from pipeline-complete signal. They fire at different times and have different consumers. (Renamed post deep-review: the body previously used file.* + index.progress + error.parse/io/embed; the canonical taxonomy at §canonical-taxonomy supersedes those.)

  • watch.create, watch.modify, watch.delete — fire from the watcher (topic 03) the moment the debouncer settles. Payload {kb, path}. Useful for the TUI watcher pane and debugging. The browser SPA does not subscribe to these — the index is not yet consistent.
  • artifact.indexed — fires from the indexer when the pipeline completes for a file. Payload {artifact_id, kb, path, hash, mtime, change_kind: 'created' | 'updated' | 'reindexed'}. This is the reload trigger for the SPA — see §G.
  • artifact.removed — fires when an artifact leaves the index (file deleted on disk, or explicit kb rm). Payload {artifact_id, kb, path}. SPA shows a "removed from disk" placeholder if the artifact was currently being viewed.
  • index.start, index.file, index.complete — run-level progress: start (with total file count), per-file completion, end-of-run summary. TUI shows a gauge; SPA shows a header progress bar.
  • comment.created, comment.exported, comment.resolved, comment.anchor_stale — per-comment lifecycle (drives the inline comments panel). comments.updated — aggregate debounced summary (drives the status-pill unread badge). See topic 09.
  • atlas.recompute.start, atlas.recompute.complete — UMAP re-projection lifecycle (auto on +10 % artifact delta or manual via TUI/SPA).
  • error — flat event with kind ∈ parse|io|embed|... as a discriminator, not separate error.parse/error.io/error.embed namespaces. Payload {id, kind, kb, path, msg, fix?}; the id field added post deep-review so clients can address POST /api/kb/{kb}/errors/{err}/dismiss. TUI Errors tab.
Why split watch.* from artifact.*? The watcher signals "a file changed on disk." The indexer signals "the index now reflects that change." A browser that reloads on watch.modify would fetch via kb's API before kb's index is consistent — racing the pipeline. Reloading on artifact.indexed is correct because by then the pipeline has finished and a fetch from kb sees fresh content. The SPA filters for artifact.* via GET /api/events?types=artifact.*,comment.*,comments.*,index.*.

ID strategy

Monotonic u64 per process — cheap, sortable, replay-friendly. UUIDs are wrong (unsortable, larger). If kb ever shards, prefix with process-id ({pid}-{seq}) à la Firehose's {partition}-{offset}.

Versioning

Treat the event log as a public API. Add fields freely (consumers ignore unknown — keep #[serde(deny_unknown_fields)] off on clients). Renames/removals bump v; run /events?v=1 and /events?v=2 side by side through a deprecation window. Publish JSON Schemas in-repo, serve from the server.

Multiplexing — single firehose with query filter

  • GET /events — all event types (default for SPA/CLI/TUI).
  • GET /events?types=index.*,error.* — server-side glob filter for narrow consumers.
  • Don't create separate hand-written endpoints (/events/index, /events/files) — they fragment the schema and complicate ring buffer ownership.

Anti-pattern: do not split endpoints by direction (the dual-endpoint trap MCP rolled back in 2025). kb's REST handles client→server; pair that with one SSE direction.

Heartbeat semantics. KeepAlive injects bare : comments — invisible to listeners. Don't model heartbeats as system.heartbeat envelope events; pollutes the log and bloats replay buffers.

F. Performance & limits

Wildly overprovisioned at 1–5 clients

Three rings, three sizes (post-review disambiguation).

  • Broadcast channel capacity = 256 — live-fanout slot count. When a slow consumer falls 256 events behind, BroadcastStreamRecvError::Lagged fires (handled per §A: emit synthetic lag event). Memory: 256 × 8 B (Arc pointers) = 2 KB.
  • Replay ring = 1024 — daemon-side VecDeque<Arc<KbEvent>> for Last-Event-ID gap-fill. With Arc sharing, N subscribers cost only cursor state (~64 B each), not N × ring size. Memory of events themselves (avg payload ~350-500 B post-review remeasure; artifact.indexed + envelope can approach 600 B; outlier error events with fix.patch can reach 1-2 KB but are rare): worst-case 1024 × 1 KB = 1 MB resident. Typical: ~400 KB. Negligible.
  • TUI display ring = 200 — client-side, lives in topic 05 §F (App.activity: VecDeque<Event>). The TUI keeps the most recent 200 events for the activity-log panel display; it does not mirror the daemon's full replay ring. Mis-attribution in earlier drafts of topic 05 corrected post deep-review.

Per-client cost. BroadcastStream cursor (~64 B) + Notify waker. Each connection adds one hyper body task and a kernel TCP send buffer (~64 KB). With Arc<KbEvent>, the replay ring is shared across subscribers — N subscribers do NOT pay N × ring memory; only the per-cursor cost. Round to ~128 KB per connected client, dominated by the kernel TCP buffer. Multi-tab single-user: 4 SPA tabs + 1 TUI = 5 subscribers ≈ 640 KB.

1000 concurrent clients is comfortably feasible: 128 MB resident. Tokio handles 10k+ idle SSE connections per process. For kb's actual user base (1–5 clients) this is wildly overprovisioned — design for correctness, not scale.

G. Live-reload — disk change → browser refresh

The end-to-end flow, traced

The operator's question: "if I save a file, can the browser refresh by itself?" Yes — and the architecture for it already exists in topics 03 (file watcher), 04 (this page, SSE), and 06 (iframe-recreate). This section traces the flow end-to-end and pins down the single new event type (artifact.indexed, from §E) that wires it together.

The step-by-step trace

  1. Something writes a new HTML body to disk inside a watched source folder. Could be Claude Code finishing a generation, the operator hand-editing the artifact in an editor, or kb regen <id> running.
  2. Topic 03's notify-debouncer-full settles 400 ms after the last write event. This collapses tmp+rename pairs, multi-write bursts, editor save sequences — into a single logical "this file changed" event.
  3. The indexer wakes up. It re-parses the file with scraper, re-extracts the kb-* meta tags (topic 07's convention), re-embeds the body chunks with bge-small (topic 02), and updates the lance + sqlite stores (topic 01).
  4. When the pipeline completes, the indexer publishes artifact.indexed to the SSE broadcaster with the new payload: {artifact_id, path, hash, mtime, change_kind}.
  5. The broadcast channel fans the event out to every connected client — CLI subscribers, the TUI, every open SPA tab — with no extra effort from the indexer.
  6. In the browser SPA, a single EventSource connection (opened once on page load) receives the event. The event: field is artifact.indexed, so a previously-registered listener fires.
  7. The SPA branches on which artifact changed:
    • If it's the artifact currently being viewed → save the iframe's scroll position; recreate the iframe element (topic 06's §G "iframe-recreate-per-render" pattern); on the new iframe's load event, restore the scroll position; show a brief ↻ updated toast.
    • If it's in the sidebar list but not the active view → update the card's title / excerpt / mtime in place; flash an "updated" badge that fades after a few seconds.
    • If it isn't on screen anywhere → do nothing. The next time the operator opens that artifact, kb serves fresh content from disk; the SPA has no reason to act now.
  8. Concurrently with step 3, kb runs the comment-anchor stability pass (topic 09's §C). Any comments whose anchors lost confidence emit comment.anchor_stale events. The SPA surfaces these in the comments sidebar with a "needs review" pill — so the operator notices that the regen made some comments un-anchored.

Browser-side code (the listener)

// In the kb SPA, set up once on page load:
const es = new EventSource('/events?types=artifact.indexed,artifact.removed,comment.*');

es.addEventListener('artifact.indexed', (e) => {
  const ev = JSON.parse(e.data);
  const id = ev.payload.artifact_id;

  if (id === currentArtifactId) {
    // Currently viewing — reload the iframe in place.
    const scrollY = iframe.contentWindow?.scrollY ?? 0;
    recreateIframe(id);                    // topic 06 pattern
    iframe.addEventListener('load', () => {
      const maxY = Math.max(0,
        iframe.contentDocument.documentElement.scrollHeight
          - iframe.contentWindow.innerHeight);
      iframe.contentWindow.scrollTo(0, Math.min(scrollY, maxY));
    }, { once: true });
    toast('↻ updated');
  } else if (sidebar.has(id)) {
    // In the visible list — update the card in place.
    sidebar.flashUpdate(id, ev.payload);
  }
  // Otherwise: ignore. Next open shows fresh content.
});

es.addEventListener('artifact.removed', (e) => {
  const id = JSON.parse(e.data).payload.artifact_id;
  if (id === currentArtifactId) showDeletedPlaceholder();
  sidebar.remove(id);
});

es.addEventListener('comment.anchor_stale', (e) => {
  const { id, fuzzy_score } = JSON.parse(e.data).payload;
  commentsSidebar.flagStale(id, fuzzy_score);  // yellow border + "needs review"
});

Why this design works

The live-reload feature is the natural composition of three existing pieces. Nothing is being invented — only wired together with one new event type:

PieceFromRole in live-reload
File watcher + 400 ms debounceTopic 03Detects disk change; collapses bursts into one signal
artifact.indexed SSE event§E (new this update)Pipeline-complete signal — fires when kb's index is consistent
Iframe-recreate-per-renderTopic 06 §GThe actual reload mechanism — drops the old iframe, mounts a new one

Edge cases & what to handle

  • Rapid edits. The 400 ms debouncer collapses bursts at the daemon side, so the browser sees one artifact.indexed per settled save sequence — not ten. If the daemon is somehow chatty anyway, add a 100 ms browser-side debounce on the reload action (defer to v2).
  • Scroll restore on a shorter document. Clamp the restored scrollY to scrollHeight − viewport. Otherwise a shorter regen leaves the viewport in empty space below the new content. (Shown in the code above.)
  • Comment popover open during reload. Dismiss the popover before recreating the iframe — its anchor in the iframe is about to disappear. The operator can re-select after the reload completes.
  • Comment input draft. If the operator was typing a comment when the reload fired, preserve the draft in the parent SPA's state (the input lives in the parent, not the iframe) and re-render after reload. Never lose a typed draft to an auto-reload.
  • Artifact deleted. Separate artifact.removed event. SPA shows a "removed from disk" placeholder with an affordance to navigate away. Orphaned comments stay in kb's store; topic 09's "orphaned" view lists them.
  • Multi-tab. Each open SPA tab has its own EventSource; each reloads independently if it's viewing the changed artifact. No cross-tab coordination needed — every tab does the right thing locally.
  • Mid-reload, another change lands. A second artifact.indexed arrives while the first reload is still mounting. Idempotent: just recreate again. Slightly chatty in pathological cases; usually invisible.
  • Off-screen reload. If the artifact isn't on screen at all, the SPA does nothing — saves CPU. The next open fetches fresh from kb; no stale render.
  • Operator preference: "pause auto-reload." A toggle in the chrome that mutes artifact.indexed handling for the active artifact. Useful when annotating heavily and a sudden reload would jump the page. v2 polish; not strictly required for v1.

The reload trigger, conceptually

Worth stating plainly: kb does not push the new artifact body over SSE. The event payload is small (just an id + hash + change_kind). When the browser receives artifact.indexed, it knows the index is fresh; it then re-fetches the artifact via the normal iframe-recreate path (which loads from https://<id>.artifacts.localhost/... per topic 06). The split keeps the SSE channel low-volume (fixed event sizes, not body-sized) and lets browser HTTP caching do its job on the actual artifact bytes.

Open questions specific to live-reload
  • Pause-while-annotating mode. Should the SPA expose a per-artifact "don't auto-reload" toggle, so heavy commenting isn't interrupted? Default off (auto-reload is the feature). UX TBD.
  • Diff highlight on reload. Could the SPA briefly highlight changed regions (line-level diff between old and new body)? Adds implementation cost; nice-to-have. Defer.
  • Browser-side coalescing window. If the daemon ever emits multiple artifact.indexed for the same artifact within a few hundred ms, should the SPA coalesce to one reload? Default: yes, with a 100 ms client-side debounce. Tune in production.
  • Scroll-restore fidelity. Pixel-perfect scrollY across two different documents is approximate. For large regens, scrolling to "the heading you were near" (anchor-based) would be more useful than pixel-based. Out of v1 scope.
  • "Stale anchor — but did the regen address the comment?" See topic 09's analogous open question. Same answer: V1 unconditional auto-resolve; V2 LLM-judge.
