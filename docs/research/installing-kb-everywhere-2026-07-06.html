Installing kb everywhere — the distribution-channel landscape

Every install path for kb across Linux, macOS, and Windows (WSL2) — package managers, containers, init systems, and updaters — ranked by leverage-per-maintenance-hour, and grounded in the one constraint that shapes them all: the embedder's prebuilt ONNX Runtime.

2026-07-06 · status:open · project:kb · companion: cross-compiling CI + zigbuild spike

The question, and how this was researched

kb ships two binaries that must land side-by-side: kb (CLI + daemon, links no ONNX Runtime) and kb-embedder (statically links a prebuilt ONNX Runtime fetched from pyke's CDN at build time — architecture invariant #26 keeps them in separate cargo invocations, and the daemon finds the embedder as a sibling of the running kb). The question: what is the full space of ways to install this on every OS, which are worth a solo maintainer's hours, and in what order?

Method: a 26-agent research workflow (2026-07-06, run wf_c511c0f9-3ea) — 2 repo-grounding agents, 9 web-research agents (one per distribution dimension), an empirical cargo-zigbuild build spike on real hardware, and 16 adversarial fact-checkers that confirmed or refuted every decision-critical claim against primary sources. Numbers below carry their evidence inline; the cross-compilation half (spike results, CI design) lives in the companion artifact cross-compiling CI + zigbuild spike.

The concrete gaps, all cheap to close within the existing hand-rolled workflow:

  • Tarball has no SPA — and resolve_spa_dist() has no next-to-binary fallback (only $KB_SPA_DIST or ./web/dist relative to cwd), so a tarball or brew install serves no web UI without manual steps. A code fix (check a sibling web/dist / share dir next to current_exe()) or bundling the ~2 MB dist in the tarball closes it.
  • No update mechanism anywhere — no self-update verb, no version check; every channel is manual re-install.
  • Integrity is checksum-only, hosted beside the artifact on the same release (integrity, not authenticity), and install.sh treats a missing checksum tool as a pass.
  • No service files shipped — the systemd unit exists only as a docs snippet; no launchd plist, no brew service block.
  • Single-arch image, even though the same workflow already proves arm64 builds on ubuntu-24.04-arm.
  • The target set is hardcoded in four unsynchronized places — release.yml matrix, install.sh (two separate case-gates), the formula's on_* blocks, and the Dockerfile. Any new target must touch all four.
Highest-value zero-code actionPush the already-documented throwaway v0.0.0-rc1 tag the moment the repo is public. It exercises all three binary legs, the ghcr push, and install.sh's real GitHub path — before the real tag. packaging/README.md step 1 already prescribes this; it has never run.

The two floors — who is excluded, and why it's a choice

Everything in this landscape bends around two runtime floors, both carried only by kb-embedder:

  1. glibc ≥ 2.39 + GLIBCXX_3.4.30 (measured 2026-07-03; confirmed against pyke's own platform docs). Passes: Debian 13, Ubuntu 24.04+, Fedora 40+, Arch. Fails: Debian 12, Ubuntu 22.04, RHEL 9, Alpine (musl). Root cause: pyke builds its ORT prebuilts on ubuntu-24.04 with no manylinux sysroot, baking in the C23 __isoc23_strtol family (versioned GLIBC_2.38) and GCC-12 libstdc++. This is pyke's build choice, not an ONNX Runtime law — Microsoft's own onnxruntime 1.24 wheels are manylinux_2_28 (glibc ≥ 2.28). Building ORT once per target in a manylinux_2_28 container and feeding ORT_LIB_PATH would lower the floor to 2.28 if demand ever justifies owning an ORT build.
  2. x86-64-v3 (AVX2/BMI2/FMA — Intel Haswell 2013+/any AMD Zen). Since ort 2.0.0-rc.11 the x86_64 prebuilt targets v3; a pre-Haswell CPU SIGILLs at first inference — with a working glibc, past every install-time check kb has today. This floor is currently undocumented in kb.

The main kb binary has neither floor — the empirical spike (companion artifact) measured its intrinsic requirement at GLIBC_2.30 when cross-compiled with a pinned floor, and full musl-static is one upstream lance fix away. Without a working embedder the daemon degrades to keyword-only BM25 search (disable_embedder_fallback governs whether that is allowed). That makes a split floor the coherent long-term story: a universal kb that runs anywhere, an embedder that needs 2026-era glibc — or the Docker image, which carries everything.

Doc bug found while researchingkb's Cargo.toml comments, CLAUDE.md, and self-host.md all say ORT_STRATEGY=system + ORT_LIB_LOCATION. ORT_STRATEGY does not exist in ort 2.x. The current mechanism is ORT_LIB_PATH (with ORT_LIB_LOCATION as a deprecated alias slated for removal) plus disabling the download feature (or ORT_SKIP_DOWNLOAD). Fix the three docs before they mislead a from-source user.

Linux

install.sh — harden to the 2026 bar

The de-facto standard among rustup/uv/deno installers is exactly what kb has: a SHA-256 sidecar. Four upgrades close the remaining gap:

  • Fail closed on checksum: today both missing-sidecar and missing-sha-tool paths return success. Error instead (opt-out via KB_SKIP_VERIFY=1).
  • Transport hardening: add --proto '=https' --tlsv1.2 to every curl — table stakes, uv and rustup both do it.
  • Optional attestation verify: once release.yml runs actions/attest-build-provenance (SLSA Build L2, keyless Sigstore), install.sh can run gh attestation verify when gh is present — bonus check, never a hard dependency. minisign sidecars (~200 KB verifier, no infra) are the only way to add authenticity without gh; optional escalation.
  • Install-time doctor: promote the tail checks into a named check that catches the silent degraders — glibc floor and musl up front (not a cryptic loader error), the x86-64-v3 CPU check (via /proc/cpuinfo avx2/bmi2/fma — today an old CPU passes install and SIGILLs at first inference), sibling kb-embedder runnable, PATH, port 4000 free, and the missing-SPA warning. A version short-circuit (skip download when kb --version already matches) makes re-runs cheap; a "restart your daemon after upgrade" note covers the replaced-inode case.

AUR — kb-bin first, source PKGBUILD as community follow-up

kb-bin repackages the release tarball: the tarball is a checksummed source= entry (the sanctioned offline path — network in build() is forbidden), and package() installs both binaries side-by-side into /usr/bin. Arch's rolling glibc makes the floor a non-issue. Per-release upkeep is a scripted pkgver + two-sha256 bump. A source kb PKGBUILD is possible today because Arch's extra/onnxruntime is 1.24.4 and ort 2.0 targets ONNX Runtime 1.24 — link the system lib via ORT_LIB_PATH, two cargo invocations, depends=(onnxruntime) — but it owns a recurring soname-bump failure mode; accept it as a community contribution rather than driving it.

.deb / .rpm without ever rebuilding — nfpm

Because CI already produces finished binaries, the cheapest packages post-process them: nfpm (GoReleaser's packager) takes one YAML and emits both .deb and .rpm — the two binaries, the systemd unit, and a postinstall that runs useradd --system kb. Attach both to the GitHub Release (zero hosting). This never touches the ORT-download-in-a-sandbox problem because nothing is compiled. Only offer them for distros above the floor (Debian 13, Ubuntu 24.04+, Fedora 40+); the package should depend on libgomp1 (ORT's OpenMP). cargo-deb/cargo-generate-rpm work too but are built around building; nfpm fits prebuilt assets best.

Fedora COPR — free auto-update channel

COPR forbids network in %build but allows it in the SRPM phase — the established pattern is a wrapper SRPM that fetches the official prebuilt tarball there. Fedora users then get dnf copr enable + automatic updates. Free, official-adjacent, low upkeep.

Nix — flake in-repo, with one carefully-scoped feature swap

The Nix sandbox has no build-time network, so ort-download-binaries cannot run. The community-proven recipe (the Minne project, Nov 2025) is: build with the ort-load-dynamic feature, add pkgs.onnxruntime (nixpkgs tracks 1.24, matching ort 2.0's ABI), and makeWrapper the embedder with ORT_DYLIB_PATH. Invariant #26 bans load-dynamic because dlopen deadlocks on macOS — a Linux-only Nix overlay is fine, but the swap must never reach the default workspace build. The alternative — a fixed-output derivation pinning pyke's exact tarball hash — keeps static linking but churns on every ort bump. Flake first; a nixpkgs submission only after the derivation is proven (no in-tree ort-consumer precedent exists yet — kb would be early).

What to skip on Linux, and why

  • snap — the only store built for daemons, but corpus-anywhere inotify watching is exactly what strict confinement resists; classic confinement requires a manual Canonical review. The core24 base doesn't widen compatibility either (it is glibc-2.39-era). Defer indefinitely.
  • flatpak — upstream's own FAQ: not a good match for servers. A headless indexing daemon has no place here.
  • AppImage — bundles libraries but not glibc/the loader, so the floor survives; the one-binary model fights the sibling contract; FUSE friction on headless hosts. Doesn't beat the tarball at anything.
  • PPA / OBS — source-only services with no build network; Launchpad explicitly rejects prebuilt binaries. Structurally incompatible with the ORT blob.
  • Hosted apt/dnf repo — not a skip, a defer: Cloudsmith's free OSS tier (≥50 GB storage / 200 GB month, attribution required) is the turnkey option over GitHub-Pages+reprepro (1 GB file cap, GPG self-managed, racy metadata) — when deb/rpm auto-update demand materializes.
musl noteIf the static-musl kb lane ships (companion artifact), swap the global allocator to jemalloc/mimalloc first — musl's default malloc serializes multithreaded allocation (measured up to ~7–13× futex contention), and kb's daemon is heavily concurrent. This is the standard ripgrep-pattern one-liner.

macOS

Gatekeeper reality: kb's current posture is already correct

Gatekeeper keys on the com.apple.quarantine xattr, set by the downloading application. The paths kb ships never set it:

PathQuarantined?Outcome for kb's ad-hoc-signed arm64 binaries
curl | sh + tar (install.sh)noruns cleanly — no prompt
Homebrew formulanoruns cleanly — no signing needed, even under Homebrew 5.x's 2026 cask crackdown (formulae + own taps unaffected)
Browser download, extracted in Terminal (tar xzf)archive yes, CLI tar doesn't propagateruns cleanly
Browser download, extracted with Archive Utilityyes, propagatedblocked ("developer cannot be verified"); Sequoia removed the Control-click bypass — System Settings "Open Anyway" or xattr -dr com.apple.quarantine

So: keep the un-stripped, ad-hoc-signed binaries (release.yml already skips strip on macOS — strip invalidates the signature and the binary dies with "Killed: 9"), document the browser-download caveat, and treat signing + notarization as optional polish: $99/yr (Individual), Developer ID Application cert, codesign --options runtime → notarytool submit --wait in CI. A bare binary can't be stapled (no Mach-O slot) — either accept the online first-run check or wrap in a stapled .pkg. Only browser-download users benefit.

Intel Macs: a runner exists, but the embedder doesn't

Two facts, pulling opposite directions. (1) The adversarial verify pass refuted the assumption that Intel-mac CI is gone: macos-15-intel is GA (2025-09-19) and supported through ~Aug 2027, so a native Intel leg is one matrix row away. (2) But ort 2.0.0-rc.12 ships no x86_64-apple-darwin ORT prebuilt (dropped in rc.11), and the Homebrew-onnxruntime system-link path has a reported failure — so an Intel asset today would be kb-only (keyword-only search). macOS Tahoe 26 is the last Intel macOS; the cohort is a shrinking tail. Keep the current stance (installer refuses Intel, points at source), and revisit when ort ships the x64-mac prebuilt — its main-branch platform table already lists it, so it is coming.

Service integration

Ship both, matched to channel: a packaging/launchd/kb.daemon.plist LaunchAgent template for tarball/curl users (RunAtLoad; KeepAlive as a dict with SuccessfulExit=false so a deliberate kb daemon stop — exit 0 — stays stopped while crashes restart; StandardOutPath under ~/Library/Logs/kb/; an explicit PATH including the install dir), and a service do block in the formula so brew services start kb just works (run [opt_bin/"kb", "daemon"], keep_alive crashed: true, environment_variables PATH: std_service_path_env). Every macOS doc must carry the existing dnsmasq /etc/resolver/localhost caveat — Safari and the system resolver don't map *.localhost, so artifact subdomains silently 404 outside Chrome. Skip MacPorts: source-based buildbots would have to compile ONNX Runtime for a fraction of Homebrew's reach.

Windows = WSL2 (and what native would cost)

The best news in the whole landscape: the Linux release is the Windows release. wsl --install yields Ubuntu 24.04 LTS on WSL2 (26.04 has no Store image until ~2026-08-06) — glibc 2.39, GLIBCXX_3.4.32 — which clears the embedder floor. install.sh runs unmodified. 127.0.0.1:4000 is reachable from the Windows browser out of the box (localhostForwarding defaults on under NAT). The docs work is one "Windows (WSL2)" quickstart block: admin-PowerShell wsl --install, run install.sh in the Ubuntu shell, keep corpora on ext4 (~/corpus — the 9P bridge to /mnt/c silently kills inotify and is ~10× slower; watch_mode = "poll" is the documented fallback), systemctl --user unit + loginctl enable-linger for persistence, with two WSL caveats: the VM stops when the last shell exits (Task Scheduler → wsl -d Ubuntu at logon), and WSLg can clear /run/user/<uid> (fix: guiApplications=false).

Windows-side package (winget/scoop/choco)? The verify pass refuted the claim that WSL-bootstrapper packages are unheard of — Docker Desktop's winget package provisions WSL2, Podman's declares a hard Microsoft.WSL dependency, and Chocolatey ships dedicated wsl packages. Prior art exists; it is still not worth kb owning a Windows package channel to wrap a documented one-liner. Ship the PowerShell one-liner in docs, optionally a convenience .ps1 in the repo. For containers on Windows: any WSL2-backed runtime — Docker Desktop (licensed for orgs >250 employees / >$10M revenue), or free Rancher/Podman Desktop.

Native-port cost (recorded non-goal, kept informed): the dep graph is already Windows-clean — rustls+ring (zero openssl/aws-lc), windows-sys transitively present, notify → ReadDirectoryChangesW, directories → Known Folders, and pyke ships a green x86_64-pc-windows-msvc ORT prebuilt (VS 2022 ≥ 17.11). The actual blockers are three Unix-only SignalKind::terminate() sites needing cfg-gates, *.localhost resolution UX, the script(1) pty CI smoke, and a whole new msvc CI leg to validate — a scope/maintenance decision, not a technical wall.

Containers

  • Multi-arch (amd64+arm64) via the canonical native-runner pattern: each arch builds on its own runner (ubuntu-24.04 / ubuntu-24.04-arm — already provisioned for the binary matrix), pushes by digest (push-by-digest=true,oci-mediatypes=true), and a merge job stitches the manifest list with docker buildx imagetools create. QEMU is rejected on measured numbers (a comparable Rust project: ~50 min emulated vs ~13 min cross — kb's 20+ min native link would land at 60–90+ min); the zigbuild-then-COPY pattern is rejected for the image because the embedder cannot be zig-linked at all (companion artifact, spike S3).
  • Fix invariant #26 inside the Dockerfile while touching it: the current single cargo build -p kb-cli -p kb-embedder unifies the local-embedder feature and links ORT into the image's kb. Split into two RUN cargo build steps.
  • Dedupe the model layer: the ~1.34 GB bge-large weights are arch-independent, but two native builds produce two distinct layers (~2.7 GB in ghcr). Fetch the model in one single-platform stage and COPY --link it into both runtimes so the registry stores one blob.
  • Ship a :slim tag (no baked model, ~350–450 MB; downloads into the cache volume on first run; degrades to keyword-only if offline) beside the full default — the -slim suffix convention from Docker official images: X.Y.Z-slim, :slim.
  • Base image stays debian:trixie-slim (glibc 2.41 clears the floor). The verify pass corrected the research here: Google distroless debian12 (glibc 2.36) fails the floor, but cc-debian13 (glibc 2.41) exists since Aug 2025 and is now the distroless default — so a distroless posture has two viable routes (distroless-debian13, chiseled Ubuntu 24.04) if ever wanted; both cost the debug shell. libssl3 in the runtime is likely vestigial (rustls stack) — confirm with ldd and drop. git (version timelines), curl (healthcheck), and tar (backup/restore shells out to it, no code fallback) are the deliberate extras.
  • Ship docker-compose.yml in-repo: loopback-only publish, config/state/cache named volumes, :ro corpus bind, /healthz healthcheck, restart: unless-stopped, and — load-bearing, from the recorded 2026-07-02 production outage — ulimits: nofile 262144.
  • Ship a rootless Podman Quadlet kb.container (AutoUpdate=registry + the auto-update timer, Volume=…:U for userns ownership, PodmanArgs=--ulimit nofile=262144:262144, loginctl enable-linger documented). Quadlet is the current recommended path; podman generate systemd is deprecated.
  • Kubernetes: record the refusal. kb is single-writer, stateful, spawns a sibling subprocess, and does not horizontally scale — replicas > 1 corrupts the index. One 1-replica StatefulSet example in docs at most; no Helm chart, no operator. This mirrors the cargo-dist and MCP rulings.
  • Registry hygiene: cosign keyless-sign the index digest (covers all arches) + cosign attest an SBOM — one tool, since GHCR still lacks the OCI Referrers API that GitHub-native attestation discovery leans on. Tag policy via metadata-action: X.Y.Z, X.Y, latest (never on pre-releases), sha-; no bare major while 0.x. Annotations must go on the manifest index, not just per-arch labels.

Running kb as a service

  • systemd user unit is the documented default (personal single-operator daemon: no root, no kb user, real XDG paths; loginctl enable-linger once) — the Syncthing pattern. Keep the existing User=kb system unit as the shared-server recipe. Ship both as files: packaging/systemd/kb-user.service + kb.service.
  • LimitNOFILE=65536 in every unit — systemd ignores limits.conf, and production already hit fd exhaustion at the 1024 default (lance segments + inotify + sqlite + SSE + the embedder pipe).
  • Restart=on-failure, never always — kb exits 0 on SIGTERM, so both systemctl stop and kb daemon stop genuinely stop it while crashes restart. The pidfile is advisory; omit PIDFile= and ExecStop= (systemd tracks by cgroup; a second SIGTERM would race). After=network.target only — never network-online.target for a loopback binder.
  • Type=notify is worth an optional Linux-only feature: "ready" for kb is listener-bound and embedder model loaded (seconds for the 1.34 GB model), not process-started. The sd-notify crate is pure-Rust, zero-dep, current — fits kb's dependency discipline behind #[cfg(target_os = "linux")]. Type=simple is correct until then. Socket activation is a recorded non-fit (two self-bound loopback sockets + a supervised sidecar).
  • No kb service install verb for now — Tailscale self-installs its unit, but Ollama/Caddy/Syncthing all ship unit files + docs, and that gets 90% of the ergonomics with none of the cross-platform verb surface. Optional middle ground: install.sh offers to drop the user unit and run systemctl --user enable --now kb when it detects systemd.
  • Logs stay stdout-only — journald (journalctl --user -u kb), launchd (StandardOutPath), and brew (log_path) each wrap stdout; a file-log mode would duplicate the init's job and invite logrotate bugs.
  • Other inits are one doc paragraph each — OpenRC/runit/dinit matter only if the musl kb ships; FreeBSD is rust+lance-viable but has no ORT prebuilt (keyword-only curiosity, wrap with /usr/sbin/daemon).

Updates, installers, and the trust chain

kb self-update — with the uv-proven channel stamp

The single biggest UX gap is updating. The recommended shape: a kb self-update verb that reuses install.sh's exact logic (fetch → verify → replace both siblings), gated on a build-time install-channel stamp baked into the binary (source | release-tarball | docker | distro — install.sh builds carry release-tarball; brew/AUR/nfpm builds carry distro). A package-manager-installed kb must refuse to self-update over the manager's file — uv proves this pattern works by printing the channel in --version and refusing with "update via your package manager". The self_update crate could do it in-process (rustls feature, MoveAll atomic multi-file replace), but reusing install.sh is less code to keep consistent, and the crate's one unique advantage — no shell dependency — matters only on native Windows, which is a non-goal.

Why crates.io + cargo-binstall is a skip

Three independent blockers. (1) cargo install/binstall install only the target crate's binaries — never a dependency's — so a one-command install can never deliver the kb+kb-embedder sibling pair, and merging them into one crate is exactly what invariant #26 forbids (feature unification links ORT into kb). (2) The kb-core crate name is taken by an actively published crate (zornfeuer, May 2026), forcing a workspace-wide rename of an internal path-dep just to publish; kb itself is squatted by a 2020 BASIC interpreter. (3) The audience overlaps install.sh's almost entirely. The verify pass sharpened one nuance: binstall can work without crates.io (--git --strategies crate-meta-data), but that invocation is undiscoverable — it rescues nothing. Document cargo install --git … kb-cli + … kb-embedder (two runs — which happens to match invariant #26; protoc required; ~20 min cold) as a from-source footnote only.

Generic installers and version managers

ubi/eget already work against kb's releases (auto-verify the .sha256; one binary per run → two commands) — mention, maintain nothing. mise: the ubi: backend is deprecated for new registry entries; the modern path is an aqua-registry PR, which lights up both aqua: and mise use kb, and aqua YAML can declare both files: from one asset (though the verify pass notes Homebrew does multi-binary equally natively — aqua's edge is covering aqua+mise in one PR, not exclusivity). Caveat before advertising: under mise's shim layout, confirm the daemon's sibling-embedder lookup resolves (both real binaries land in the same install dir — plausible, untested). asdf is the only channel whose bin/install natively nails the two-sibling layout, but it's a separate repo to maintain for a shrinking ecosystem. All of these are demand-gated, not roadmap.

Provenance for everything

One pinned action — actions/attest-build-provenance with id-token: write — gives every tarball and the image keyless SLSA Build L2 provenance, verifiable with gh attestation verify and interoperable with cosign (v2.4+). This is the highest-leverage trust upgrade available to the hand-rolled workflow, and it requires no installer changes.

The ranked roadmap

  1. Before the public flip (code + CI, hours): fail-closed checksums + TLS flags in install.sh; actions/attest-build-provenance on tarballs + image; split the Dockerfile's cargo build (invariant #26); multi-arch image (digest matrix + imagetools merge + COPY --link model stage); ship packaging/systemd/ units (user + system, LimitNOFILE=65536, Restart=on-failure), packaging/launchd/ plist, compose + Quadlet files; fix the stale ORT_STRATEGY docs; document the x86-64-v3 floor + add the CPU check.
  2. Flip day: repo public → v0.0.0-rc1 throwaway tag → watch all legs → fill the Homebrew formula's three sha256s → create the tap → brew audit/test → real tag.
  3. First channel wave (each ≤ a day, minutes per release after): AUR kb-bin; nfpm .deb/.rpm attached to Releases; WSL2 quickstart + macOS browser-download caveat in docs; :slim image tag.
  4. Second wave: kb self-update + channel stamp; COPR; Nix flake (Linux-only ort-load-dynamic overlay); cosign sign+attest on the image; SPA-in-tarball or resolve_spa_dist sibling fallback.
  5. Demand-gated / deferred: the musl/low-glibc kb lane (gated on the lance-linalg fix — see the companion artifact); aqua-registry PR; minisign sidecars; macOS notarization; Cloudsmith apt/dnf repo; Intel-mac asset (gated on ort's x64-mac prebuilt); manylinux_2_28 ORT source build for Debian-12/RHEL-9 support. When to revisit

  • ort ships an x86_64-apple-darwin prebuilt (main's platform table already lists it) → add the Intel-mac leg on macos-15-intel (native runner exists through ~Aug 2027).
  • ort ships a musl prebuilt, or the lance-linalg AVX-512 defect is fixed upstream → the universal static kb tarball becomes a first-class asset.
  • The next ort bump (main already targets ONNX Runtime 1.27) → re-check dist.txt targets, the glibc floor, and the x86-64-v3 posture; pyke changes build environments between release candidates.
  • Real Debian-12 / RHEL-9 / Alpine demand → the manylinux_2_28 (glibc 2.28) ORT source build via ORT_LIB_PATH is the known, costed escape hatch (~30–60 min/target compile, plus owning an ORT build tree).
  • ubuntu-latest floats to 26.04 (migration underway) — kb already pins ubuntu-24.04; keep it pinned or the floor silently rises.
