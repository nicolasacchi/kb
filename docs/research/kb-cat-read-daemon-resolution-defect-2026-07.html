kb cat / kb read can't resolve artifacts on a shared-daemon topology

status: fixed fixed a8dd891f 2026-07-11 (GC-B5) found 2026-07-06 during the /kb-distill acceptance run · kb-cli · severity: medium (silent capability gap + misleading errors)

Symptom

Against the live shared daemon (docker, 127.0.0.1:4000 — the documented default for the memory rig), id resolution disagrees between verbs for the same artifact:

$ kb cat ad8dfcf6576d --kb sessions
Error: artifact ad8dfcf6576d not found in kb sessions   # exit 1

$ kb cat ad8dfcf6576d
Error: must specify --kb when multiple kbs are configured   # zero kbs configured locally!

$ kb find ad8dfcf6576d --kb sessions
ad8dfcf6576d                                            # daemon lookup: exists

$ kb get ad8dfcf6576d --kb sessions --format html | wc -c
1757635                                                 # daemon fetch: works

kb read fails identically (same resolution path). Memory-corpus ids (kb cat <id> --kb memory-kb) fail the same way.

Root cause

kb cat and kb read are local-state-only: they load kb.toml (or an empty default when none exists) and open the host's lance state dir directly — they never talk to the daemon and accept no --daemon flag.

SiteWhat it does
crates/kb-cli/src/commands/cat.rs:34Storage::open(&paths.kb_lance(&kb_name), …) — host XDG state (~/.local/state/kb/default/…), which is empty when the daemon runs in docker with its own bind-mounted state.
cat.rs:17-25 (and the same match in read.rs)kb-name resolution reads the local config; with no local kb.toml the zero-kb case falls into the "multiple kbs configured" error arm — misleading twice over.
crates/kb-cli/src/commands/read.rs:26Same local KbPaths/Storage::open pattern.

The intended behaviour exists elsewhere: search.rs:1-3 documents the canonical ladder — "try the daemon first, fall back to a lance read-only open if the daemon isn't reachable; --offline forces lance, --daemon URL forces HTTP" — via http::detect_daemon. cat/read simply predate it and were never ported.

Blast radius

  • On any docker / shared-daemon setup (the default in plugins/kb-memory/hooks/README.md), kb cat and kb read are dead verbs — every id the daemon serves is invisible to them.
  • Agent workflows inherit the confusion: /kb-reflect Step 3 claimed kb cat <artifact_id> dumps the session digest — wrong on both counts (it can't resolve, and it dumps raw source bytes, not the digest). Corrected to kb get --format html|md in the same commit as this report.
  • The composability promise in the CLI docs (kb find … | xargs kb cat) breaks exactly where kb find works, since find resolves via the daemon.

Needed fix

Port the search.rs ladder to both verbs:

  1. kb cat — add --daemon/--offline; default = http::detect_daemon, then GET /api/kb/{kb}/artifact/{id} raw bytes (the same route kb get --format html uses) → stdout; unreachable daemon → existing local-lance path (keep the offline promise in the module doc).
  2. kb read — same detection; in daemon mode open the artifact's served URL (SPA permalink or artifact-subdomain URL) in the browser instead of the local file path; offline mode unchanged.
  3. Error copy — the no---kb arm must distinguish zero kbs configured ("no local kb.toml — pass --kb and let the daemon resolve, or --config") from many; and the not-found error should say which store was consulted ("not found in LOCAL lance state for kb X; daemon not consulted — pass --daemon or check kb.toml") so the failure is self-diagnosing.
Non-goal guard: this is CLI plumbing only — no daemon route changes needed; both HTTP endpoints already exist and are what kb get uses today.

Acceptance

  • On this host (docker daemon, no local kb.toml): kb find <file> --kb sessions | xargs -I{} kb cat {} --kb sessions streams the artifact; kb read opens it.
  • With the daemon stopped and a local single-kb kb.toml: both verbs still work offline (regression guard for the original design).
  • kb cat <id> with zero local kbs produces the zero-kb error message, not "multiple kbs configured".
