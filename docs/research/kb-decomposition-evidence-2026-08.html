2. kb-core coupling map

crates/kb-core/src/lib.rs declares 59 public modules. Lance's artifacts schema declares 50 Field::new columns on Doc; sqlite carries 31 CREATE TABLE names across 36 refinery migrations. The brief's assumed names search, boards, and timeline/daycard are not pub mod entries — search is composed from query.rs+fusion.rs+docs_query.rs+actor query methods; "boards" is two unrelated things (corkboard in kb-core, canvas boards as a kb-server sidecar file); timeline/daycard are kb-server read-only views with no kb-core module at all.

2.1 Shared kernel — assumed by every subsystem

  1. Storage actor is the only writer — one lance Storage + one sqlite Db per kb, single-writer via mpsc (CHANNEL_CAPACITY = 1024), not a mutex; per-process only, no filesystem lock on index.db/lance/.
  2. Index generation memo — bumped only on row-set/edge mutations (UpsertDoc(s), DeleteDoc, CascadeDeleteDoc, RelocateDoc, SweepOrphans if rows removed, RecordEdges if changed, DropKbData); chunks/code_refs/lists/reading/atlas-coords/snapshots/compaction do not bump it.
  3. Artifact ids — 12-hex SHA-256 prefix of the source-relative path; relocate is the only sanctioned id change.
  4. EventBus — envelope {v,id,type,ts,payload}, ring 1024, live 1024, Last-Event-ID resume. The storage actor has no bus of its own.
  5. Config — one TOML file, daemon-wide sections plus per-kb [kb.<name>].
  6. Paths — KB_HOME/KB_STATE_DIR/KB_CONFIG_DIR/ KB_CACHE_DIR over XDG; per-kb state at <state>/<kb>/.
  7. Three lifecycle registries, not one — see §2.2; a table missing from any strands rows under a dead id.
  8. Enrichment is in-process — after upsert_docs, indexer::finish_indexed_doc runs enrich::default_hooks(); hooks are best-effort, ordered by registration.

3.3 SPA closed sets a feature cannot grow on its own

  • NAV_ITEMS — closed 10-entry list: grid, list, atlas, press, search, memory, lists, notes, sessions, history. Settings/inbox/replay/ambient/anchors are chrome or deep-links.
  • Inspector rail (invariant #30) — closed 6 tabs: all (About), meta, links, folder, sessions, story. Session replay deliberately kept off it.
  • One SSE connection per daemon per browser (invariant #24) — a SharedWorker hosts the connection; tabs are MessagePort clients. Subscriptions to existing kinds are free; a second /api/events stream is not allowed.

A plugin UI can call sse.subscribeEvent("my.kind", ...) on the existing facade. It cannot: open a second stream, add a 7th inspector tab, register a new router path, add a nav tab, or skip the TanStack invalidation bridge without becoming a new hand-written invariant #23 exception (sessions/note/stale-anchors/doclens are the only four so far).

3.5 The embedder IPC protocol (pattern 2, in detail)

kb-embedder is the only crate linking ONNX Runtime; daemon and CLI stay ORT-free. Spawn lifecycle: locate the binary ($KB_EMBEDDER_BIN → sibling of current_exe() → PATH); spawn with piped stdio, Unix nice in pre_exec; a bounded Ready handshake (default 60s, KB_EMBEDDER_HANDSHAKE_TIMEOUT_SECS) where the child must echo the model name or get killed; one NDJSON line per request, correlated by req_id; a 1 Hz ensure_alive probe respawns a dead/wedged child in place (falls back to keyword-only search on failed respawn).

Request  = Embed { req_id, texts } | Rerank { req_id, query, documents } | Shutdown
Response = Ready { model, dim } | EmbedOk { req_id, vectors } | RerankOk { req_id, scores } | Error { req_id, msg }

NDJSON framing; Rerank returns scores in input order, daemon sorts/top-n's. Embedding dim must match the lance vector column or the call fails Err, never panics — "one bad plugin can't kill the storage actor." Generalising into a reusable plugin_ipc module is deferred until a second concrete subprocess use case demands it.

No split avoids this

5. Measured incremental builds

Machine: 8 cores, 62GiB RAM. Profile fast (release-derived, lto=false, codegen-units=16, incremental). Real stopwatch measurements, not estimates.

Table 5.1 — measured touch-and-rebuild wall time
ActionWall timeWhat recompiled
Warm two-crate build (kb-core+kb-server, deps prebuilt)2m 22s full kb-core + kb-server
touch kb-core/src/memory.rs (3,220 LOC)19.73s kb-core, then kb-server
touch kb-core/src/storage/mod.rs (11-line re-export)16.63s kb-core, then kb-server
touch kb-server/src/routes/memory.rs (2,250 LOC, kb-server only) 9.65skb-server only — the fixed floor

The 9.65s floor is unavoidable regardless of any kb-core split — kb-server's own recompile + relink against the prebuilt lance/arrow/datafusion tree. The crate-boundary tax is not proportional to touched-file size: an 11-line non-logic file cost ~6.98s of kb-core recompile, a 3,220-line file cost only ~3s more (~10.08s). Touching any kb-core file pays a largely fixed ~7–10s tax dominated by whole-crate metadata/codegen bookkeeping, not code volume — exactly what a crate split fixes structurally, since cargo's recompile unit is the crate, not the file. Today's incremental cache already amortizes ~85–90% of a full rebuild; the dev inner loop is not currently broken.

Extrapolating, a split's per-edit cost would be one small feature crate (est. 1–3s for ~3k LOC) + the 9.65s kb-server relink floor ≈ 10–12s, down from ~17–20s today — a 35–50% cut (6–10s saved per edit). Real, but modest against an already sub-20s baseline.

Cold and CI builds mostly don't benefit

Cold builds (fresh checkout, cargo clean, branch switch, CI) pay close to the full 2m22s regardless of crate boundaries, unless cargo parallelizes the independent feature crates across free cores. CI is memory-capped — cargo -j2 was capped this month (commit 10890afc) specifically because higher parallelism OOM'd the image build. More crates building in parallel means more concurrent memory pressure on an already-throttled build — the CI benefit is speculative, plausibly a net regression.

6.2 The storage-actor DTO cycle — the hardest blocker

Genuine cycle, not just an inversion

The storage kernel bakes feature DTOs into its message enum: reading::{ReadingSectionRow, VisitRollup, ReadRollup} (actor.rs:636-699,4064-4155 — 12 hits; sqlite.rs:1348-1732 — 17 hits); lists::{ImportMode, NewListEntry, Patch, PositionSpec, ResolutionUpdate, ReadState} (actor.rs:18,5470-5488 — 11 hits; sqlite.rs:12,1731 — 8 hits); sessions::ProjectFilter (actor.rs:1023,1053,4683,4733 — 4 hits). Meanwhile lists.rs itself imports storage::sqlite::ListEntryRow + StorageHandle — storage → lists and lists → storage simultaneously, an actual cycle Cargo will refuse to compile. Same shape for reading and sessions. Sits inside kb-core's two largest files: storage/actor.rs (6,295 LOC), storage/sqlite.rs (12,404 LOC) — home of the CASCADE_STEPS/SWEEP_TABLES registries. The only clean fix is pulling each feature's plain wire-DTOs into a shared kernel types crate — the classic "DTO crate" pattern.

6.3 enrich.rs — right pattern, wrong placement

Invariant #5 documents a real trait EnrichmentHook + default_hooks() registry (enrich.rs:102-132), called from indexer.rs:2175 — the registration mechanism a split needs already exists in production. The concrete hooks live inline and call directly into feature modules: SessionCaptureHook → crate::sessions:: (enrich.rs:98,173-2391, many refs); EdgeRecordHook → crate::links:: (833-866); CodeRefHook → crate::coderefs:: (922-1032); review-related hooks → crate::review:: (1169-1175); ListAnchorHook → crate::lists:: (1180-1202). A split needs each hook relocated into its owning feature crate, registered by a composition root instead of a hardcoded vec![...].

6.4 The pre-upsert indexer gap

prepare_doc (indexer.rs:1558), at lines 1747-1791, calls sessions::{parse_session_html_full, session_digest, session_digest_excerpt, truncate_code_field} to compute body/body_text_excerpt/code before the row is written — earlier than any EnrichmentHook, which only fires post-upsert. Splitting sessions out needs a new pre-upsert FieldDerivationHook, not just code motion. Separately, finish_indexed_doc (indexer.rs:2069), lines 2235-2381, directly calls review::{migrate_legacy_id, load, fuzzy_resolve_anchor_with}, sessions::view::*, and anchors::{...} — ~150 lines of bespoke, never-hookified review-anchor resolution next to the enrich::default_hooks() loop, structurally identical to the existing ListAnchorHook but never migrated into that pattern.

6.5 parser.rs:845 — a real kernel→feature inversion

crate::share::percent_decode is called from parse_artifact_link (parser.rs:836, call site parser.rs:845) — a real production kernel-depends-on-feature edge. Percent-decoding is generic and misplaced inside share; the cheap fix is moving it to the existing strutil.rs. notes::checklist_counts (parser.rs:1260) and session render helpers (parser.rs:1546-1591) are test-only (#[cfg(test)], from parser.rs:1142) — not build-blocking, but the kernel parser's own test suite would need dev-deps on notes/sessions.

6.6 The zero-inbound pilot candidate

Cleanest split candidate found

atlas.rs+atlas_field.rs+atlas_labels.rs+procrustes.rs — 4,756 LOC (4.9% of kb-core) — zero inbound refs, no appearance in enrich.rs or indexer.rs, no storage-actor DTO entanglement. Essentially a free split, ~1–2 days of work, that would validate the DAG/registration/CI-leg mechanics before the much harder sessions/lists/reading/ storage cycle. Sessions (~13,600 LOC, 14% of kb-core, largest single feature) would capture the biggest per-edit win if split, but is also the worst-coupled candidate — it should follow the atlas pilot, not lead it.

7.1 State of in-process Rust ABI, 2026

Rust Reference: "The Rust ABI offers no stability guarantees" for extern "Rust"; only extern "C" is stable. abi_stable is stale at crates.io v0.11.3 (2023-10-12), no unloading support. stabby uses rustc-version/opt-level/target "canary" markers to fail closed on a layout mismatch. WASI 0.2.0 (2024-01-25) established a pin-able stable WIT world underpinning Extism and Zed's own wasip2 stack. crABI remains an unshipped RFC proposal.

7.2 Cross-cutting observations

  1. Every shipped Rust tool that added plugins did so without a stable Rust ABI — subprocess (nushell, cargo, rust-analyzer) or Wasm (Zellij, Zed).
  2. Compile-time composition is the other proven pattern (Vector, Caddy) — "plugin" = "crate linked into this binary," not a runtime file drop.
  3. Every runtime plugin system paid a real versioning tax: Nushell's Hello + registry rewrite, Zed's target migration, rust-analyzer's JSON skew, SQLite's thunk.
  4. In-process Rust dylib plugins remain research-grade in 2026 — Helix's own maintainer abandoned a C-ABI attempt.
  5. In-process JS ergonomics are a property of already-being-a-JS-host — porting means embedding Wasm or JS as a second runtime.

Primary sources include nushell plugin protocol, "Life of a Zed Extension", Helix PR #8675, SQLite loadext.html, rust-analyzer 2021 recap, VS Code Extension Host docs.

8. Deploy and operational record

8.1 kb ↔ kb-code integration inventory

Service discovery is exactly two hand-edited TOML keys — no registry, mDNS, or /api/siblings: kb's [kb.*] code_url is inert, browser-facing only (kb-core's own comment: "kb NEVER opens an HTTP client to it"); kb-code's [kb_daemon] carries enabled, url (daemon-to-daemon), token_file, public_url. kb-code makes 9 HTTP calls to kb, 8 via a pooled KbClient (1.5s timeout, optional bearer): /api/sessions/by-commit, /{id}/commits, /{id}, /commit-map, /api/why, /api/kb/{kb}/docs/{doc}/code-refs, /api/kb/{kb}/code-refs, /docs/by-path/{*path}, /api/sessions/recollect. No handshake precedes any call; failures degrade to unavailable_reason. GET /api/identity today carries name/version/repos/started_at/ kb_public_url but no build_sha, protocol id, or schema epoch — KbClient never queries it before use.

8.2 The 13.5-hour kbc.example.com outage — corrected root cause

Intra-service, not cross-daemon

Refinery migrations apply forward-only at boot for both kb and kb-code. A deploy rollback retagged kb-code-server's own binary alone back to a pre-DCB build, while its own volume had already forward-migrated. /healthz is liveness-only and stayed green through the multi-minute on-boot backfill, so a naive health check declared victory. This is an intra-service deploy-safety bug — not a cross-daemon kb-to-kb-code protocol-version-skew bug. A version handshake would not have caught this specific incident; the missing check was "may this binary open this volume" (schema-epoch), not "same git sha" (already pinned via main-<sha12>).

Post-outage fixes: redeploy-kbc.sh has no auto-rollback branch at all (stop-and-ask); redeploy-kb.sh kept its rollback but added a migration-advance guard (refuses to retag back to an old sha if refinery_schema_history.version rose during the attempt); kbc-state backups switched from gzip -t to tar tzf (a truncated backup once passed gzip -t on 2026-08-15); deploy now waits for "on-boot backfill complete" log lines (20-min budget) instead of trusting /healthz. There is no script that deploys kb and kb-code atomically — they share only the main-<sha12> tagging convention.

8.3 Proposed kb-sibling/1 handshake spec

Extend GET /api/identity on both daemons with: build_sha (humans/deploy scripts only, never a compat gate); sibling_protocol (literal "kb-sibling/1", exact match — unknown ⇒ refuse the peer); sibling_major (integer, must match — nushell's differing-major rule); schema_epoch (persisted on the volume after migration) vs schema_epoch_min (on the binary): if volume epoch exceeds the binary's max, refuse to boot — the exact gap the outage exposed. /healthz stays unauthenticated pure liveness and must never double as readiness/compat. A sibling client's first request must be GET /api/identity, cached for process lifetime, failing closed on mismatch — distinct from degrade-to-unavailable (genuinely unreachable peers). Precedent for mandatory-not-advisory: rust-analyzer's handshake was only advisory ("expansion will not work," cargo build still succeeded, editor stayed red for days) — the same "process up, contract dead" shape as the kbc outage.

  • kb-code ↔ kb: 6.2% — of 129 commits touching kb-code-server/kb-code-cli/web-code, only 8 also touch kb-core/kb-server/kb-cli/kb-embedder/web, clustered in two episodes: the v0.34 identity-ladder work (44b9a83a, 4d0ff78d) and the DCB milestone (b70d165e, c9a03075, 5a9eca7a, b4be9e60, 41d65321, e67bc6d6) — not steady-state coupling.

Counter-evidence for keeping things together

Red-team spot-checked b0ef6f34 ("W1.B review follow-ups"): a genuinely atomic single-intent bugfix (never_scanned semantics) landed simultaneously in kb-core/src/enrich.rs, kb-server/src/routes/coderefs.rs, kb-cli/src/commands/refs.rs, and a web/ TS fixture — exactly the kind of change that would become an awkward multi-repo staged rollout if those areas were split.

9.2 Prior rulings — already asked and answered in-repo

docs/extending.md: "kb deliberately has no generic plugin SDK. It is a single-author / small-fleet daemon whose value rests on three correctness invariants — single-writer-per-kb storage, a deterministic atlas, and a fail-closed security stack — that a generic framework would fight." Four named, already-shipping mechanisms ranked by isolation: subprocess IPC (the embedder), event-bus/webhook, declarative <meta>/config, in-process enrichment hook (first-party only).

WASM — DEFERRED. "kb has no untrusted-code threat model, and a WASM runtime is a heavy dependency on top of the already-pinned arrow/lance graph. Subprocess IPC gives ~90% of the isolation for ~5% of the complexity, and kb already runs it."
Dynamic native .so — REJECTED. "Rust has no stable ABI, and the exact arrow = 57.3.1 pin means a plugin built against a different arrow is undefined behaviour, not a load error... Both reasons are disqualifying."

The RFC (kb-plugins-extensibility-rfc.html, 2026-05-31): do not build a generic plugin framework; ADOPT the three existing mechanisms + a formalized hook registry + webhook bridge + generic meta registry; DEFER WASM; REJECT dylib; ADOPT Claude-Code packaging; MCP server merely optional. Predates kb-code-server (born 2026-07-18) — its "sibling daemon" reasoning was written before kb had a live example.

README non-goals reinforcing the same posture: no in-daemon LLM ever; one trust tier (no ACLs); no in-daemon visibility ("the corpus mount is the ACL... a live public mirror is a dedicated daemon"); the TUI retired once every data source it rendered had an SPA/CLI home; the desktop app archived as a git tag; no MCP server yet, with three explicit trigger conditions and a stated preference for "a thin facade over the existing HTTP API... never in-daemon."

CLAUDE.md: "Invariant budget — 35 is the cap... Adding a new architecture invariant requires retiring or merging an existing one." Practiced twice — slot #2 opened at kb-tui's retirement (v0.24), refilled by v0.34 (kb-users), then merged into #4 during DCB. Commit f6071d7a performed that merge; a follow-up commit 1fca43d2 had to repair stale bookkeeping about the merge itself — evidence the constraint is real and its own tracking has already drifted once.

9.3 spikes/ as the disposable-crate precedent

Six spike crates (walker, fastembed, sse, iframe, ratatui, lance) were built outside the main workspace, proved a library choice, then were deleted entirely once captured in docs/spike-findings.md — "the architecture decisions in docs/research/*.html are never edited; this file is the delta." A lightweight existing precedent for a disposable, never-workspace-member crate.

Cross-checked by red-team's resample (§9.1, §10).

10.1 Amendments the red-team lane recommends adopting

  1. Correct the outage citation (§8.2) — don't cite it as proof a handshake is "the missing piece"; justify any handshake independently.
  2. Name the kb-cli split concretely: split kb-core into types/wire vs. lance-linked storage first, then promote the ~50-of-61 already-thin kb-cli modules to kb-<verb> binaries on PATH.
  3. Stop calling kb-code-server's kb-server coupling "one call direction, formalized" — it's a path-dependency library reuse on the security surface, a deliberate accepted tradeoff, not yet a loosely-coupled sibling.
  4. Extend SSE schema discipline to kb-code-server; consider a machine-checked "every .emit() literal is in a schema list" test on both sides.
  5. Retire "single-operator tool" for "no unreviewed-third-party-code execution surface today," flagged for re-examination if kb ever ships install-from-URL plugins.
  6. Drop "features.ts betrayal" as supporting evidence entirely — checked against the repo, it's minimal and disciplined.
  7. Caveat co-change numbers as a young sample — kb-code is ~29 days old vs. the repo's ~97, and it produced the 13.5h outage within ~4 weeks; re-measure at 6–12 months.
