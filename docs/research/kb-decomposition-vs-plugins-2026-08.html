Should kb decompose into separately compiled plugins? (2026-08)

No — not as runtime plugins, and not by decomposing what already exists. The four needs hiding inside the word “plugins” are each already served by a proven seam; two of those seams deserve formal hardening now, and the refusals get explicit revisit triggers.

2026-08-16 status:applied project:kb 8 research agents measured builds

The question, and why it is four questions

The operator asked: does it make sense to think about plugins instead of this monolithic project — plugins that can be installed and compiled separately? kb today is one Cargo workspace (6 crates, two React SPAs), one ~128 MB daemon binary, ~98k LOC in kb-core alone, 35 architecture invariants at a hard cap.

This is not the first time the repo has faced the word “plugin”. The 2026-05-31 extensibility RFC and docs/extending.md already ruled on how outsiders extend kb: dylibs rejected, wasm deferred, subprocess IPC + event bus + declarative meta named as the extension story. But the operator’s question is different — it is about decomposing kb itself. And it decomposes into four distinct needs that the word “plugins” conflates:

NeedWhat would satisfy itWhere kb stands
Compile separately (build speed)Crate splits, CI isolationPartly shipped; measured below
Install separately (optionality)Separate binaries / daemonsShipped twice (kb-embedder, kb-code)
Extend without recompilingA plugin runtime or protocolAgent layer + sidecar protocol
Blast-radius legibilityCompiler-enforced boundariesThe genuinely open question

Each need gets a different answer. Treating them as one question — “plugins, yes or no” — is how projects end up building a plugin SDK nobody asked for while their actual pain (build time, drift, deploy risk) goes unaddressed. A fifth motivation — attracting external developers — arrived as an operator follow-up and gets its own staged answer in the addendum.

How this was researched

Two orchestrated workflows, eight worker agents (sonnet + grok lanes), 2026-08-16: an evidence sweep (kb-core coupling map, server/SPA seam inventory, build economics, external precedents, in-repo decision record + 400-commit co-change analysis) and a design round (a measured modular-monolith deep-dive with real timed builds, a sibling-daemon contract gap analysis against the live deploy scripts, and an adversarial red team attacking the draft thesis). The red team changed the thesis in three places — documented in the amended thesis. All raw tables, per-lane verification caveats, and source citations live in the companion appendix: kb decomposition research — evidence appendix.

What the monolith actually costs today

Measured on the development workstation (8 cores, warm cache, --profile fast):

ActionWall time
Touch kb-core/src/memory.rs (3,220 LOC) → rebuild kb-server19.7s
Touch kb-core/src/storage/mod.rs (11 lines) → rebuild kb-server16.6s
Touch a kb-server-only route file → rebuild9.7s (the floor)
Full warm rebuild of kb-core + kb-server2m22s

Two readings matter. First, the crate boundary, not the edit size, drives the cost: an 11-line re-export file costs ~7s of kb-core recompile; a 3,220-line feature file costs only ~3s more. Cargo’s recompile unit is the crate — which is exactly what a crate split would fix. Second, the inner loop is not actually broken: 10–20s per edit, with a ~9.7s floor (kb-server’s own recompile + linking a 133 MB binary) that no kb-core split can touch.

The heavier costs live elsewhere:

  • The lance tax is structural. lancedb/lance/arrow/datafusion (~104 crates) is a non-optional dependency of kb-core, so every binary that touches the index pays the whole graph — kb-code-server even declares its own second lancedb/arrow dependency set for its own dataset. Release binaries: kb 133 MB, kb-server 128 MB, kb-code-server 129 MB. The one thin binary, kb-code-cli at 9 MB, is thin precisely because it links neither.
  • CI cannot absorb more parallelism. The self-hosted runner is 2 slots at a 10 g cgroup each; cargo -j2 was capped this month (commit 10890afc) because higher parallelism OOM’d the sidecar. More crates compiled in parallel is plausibly a CI regression, not a win.
  • Drift, not compile time, is the visible monolith symptom. The sweep found the SSE type enum missing ~14 event kinds that production code actually emits, a stale hook list in kb-core’s own CLAUDE.md (6 documented, 7 live), and docs/extending.md undercounting the shipped plugins. But note: the SSE kind field is a plain String on both the Rust and TypeScript sides — crate boundaries would not have caught any of these. They are protocol-discipline failures, and kb’s own prior fix for the same class of drift was a generic frame decoder, not a stricter type.

Option A — modular monolith: real, modest, not now

The shape: split kb-core into a kernel crate (storage actor, indexer, search, events, config, ids, paths) plus per-feature engine crates (memory, sessions, atlas, comments, lists, notes/links, coderefs, share…), selected by cargo features on one binary — the Caddy/xcaddy/Vector compile-time composition model, which is also what every surveyed Rust tool that “has plugins” without a runtime actually does.

What the deep-dive established:

  • The registration machinery already exists. enrich.rs has a production trait EnrichmentHook + default_hooks() registry called from the indexer — the split would relocate the seven hook implementations into their owning feature crates and build the vec in a composition root. No new pattern needed there.
  • One genuine crate cycle blocks the split. The storage actor and its sqlite layer bake feature DTOs into their message enum — reading::{ReadingSectionRow, VisitRollup, ReadRollup}, lists::{ImportMode, NewListEntry, Patch, …}, sessions::ProjectFilter — while those same feature modules import StorageHandle back. That is a two-way dependency Cargo will refuse; breaking it means a DTO-only kernel crate carved out of the two largest, most invariant-dense files in the codebase (storage/actor.rs 6,295 LOC, storage/sqlite.rs 12,404 LOC).
  • The indexer needs a net-new extension point. Sessions’ body/excerpt/code fields are computed pre-upsert inside prepare_doc — the existing post-upsert hook registry cannot express it, so a split invents a FieldDerivationHook. About 150 further lines of never-hookified review-anchor logic sit beside the hook loop.
  • The lifecycle registries should NOT be feature-gated. CASCADE_STEPS/SWEEP_TABLES/relocate are pure data arrays; a DELETE against a disabled feature’s empty table is a harmless no-op. Compile the full lists always — feature-gating them would convert a no-op into a silent-strand hazard.
  • The SPA gains nothing. features.ts booleans are runtime property reads Rollup cannot tree-shake; the right SPA model stays one universal bundle probing daemon capabilities.

Verdict: not now. 8–13 person-days concentrated in the riskiest files, an ongoing per-route cfg tax across 178 route registrations, added load on an OOM-throttled CI — to save 6–10 seconds on a sub-20-second edit cycle. If the goal ever shifts from build speed to compiler-enforced blast radius, start with the atlas group (atlas.rs + atlas_field.rs + atlas_labels.rs + procrustes.rs, 4,756 LOC, 4.9% of kb-core, zero inbound references from any other feature, no indexer/enrich entanglement) as a cheap pilot that proves the pattern before touching the sessions/storage knot. Sessions is the largest feature (~13,600 LOC, 14% of kb-core) and the worst-coupled — it follows a successful pilot, never leads.

Option B — sibling daemons: the pattern that works, minus its fig leaves

kb already runs a federation of two: kb-code-server is a separate binary with its own store, own SPA, own CI recipes, path-filtered CI jobs, and a hard one-call-direction rule. The co-change evidence says the pattern genuinely decouples: kb-code co-changes with kb/* in only 6.2% of its commits (two episodes, not steady-state), web/ and web-code/ co-changed in 0 of 400 commits, and kb-embedder has been touched in 2 of 1,294 lifetime commits since isolation shipped.

The red team’s corrections keep this honest:

  • The boundary is partly compile-time, not protocol. kb-code links kb-server as a library for auth_bearer and the loopback predicates, and imports kb-core’s EventBus type. That is deliberate (never re-derive security logic) but it is recompile coupling wearing a daemon costume.
  • Federation tax is current and visible. Four of the five most recent commits on main are two-image plumbing (OOM tuning, shared build stage, image GC, cancel-in-progress blast radius). kb-code’s image only stopped paying for kb’s unused 1.34 GB embedder model tail on 2026-08-15 (c46fd184) — build independence was achieved, not free.
  • The 13.5h kbc outage was not cross-daemon skew. The draft thesis mis-cited it. Root cause: the deploy script’s naive 60s health check timed out mid-boot and auto-rolled-back the binary while its own volume had already forward-migrated — an intra-service binary/schema mismatch that a green liveness probe then masked. The already-shipped fixes (no auto-rollback on kbc, a migration-advance guard on kb, boot-backfill log waits) treat the real cause.

The missing piece: a kb-sibling/1 contract

What the outage and the precedents (nushell’s hard version Hello; rust-analyzer’s advisory-only handshake that let a v6 server talk past a v5 client for days in 2026) jointly demand is small and cheap:

  • Extend GET /api/identity with build_sha, sibling_protocol (exact-match string kb-sibling/1), sibling_major (must match), and schema_epoch (persisted on the volume after migration) vs the binary’s supported range — and refuse to boot, hard, when the volume’s epoch exceeds the binary’s. Advisory warnings are the documented failure mode.
  • A sibling client’s first call is GET /api/identity; protocol/major mismatch fails closed, distinct from degrade-to-unavailable (reserved for unreachable peers).
  • /healthz stays pure unauthenticated liveness — never a compat signal. Readiness is the boot-backfill log line, as the post-outage deploy scripts already do.
  • Give kb-code a schema.rs: its SSE kinds (annotation.changed, review.changed, …) are entirely undocumented today, in the exact drift class that has burned kb twice.

Extraction of existing features is not the move

All five plausible-sounding extractions were evaluated and fail, each on one dominating fact: atlas and memory are kb’s own embedding matrix and index (extracting them means re-fetching the corpus over HTTP to compute what the actor already holds); share is a pure library over the source tree already slated for a subprocess backend variant, not a daemon; resurface/timeline/daycard are stateless views that would fight the one-SSE-connection-per-browser invariant; sessions is the other half of the memory system — and kb-code already implements the correct sibling relationship to it from outside. Underneath all five: a sibling cannot open kb’s index.db or lance/ at all — the storage actor is single-writer per process with no file lock, so shared-state extraction is structurally forbidden, and API-mediated extraction reduces to “a client”, which is what the CLI already is.

Verdict: the sibling pattern is kb’s real “installable plugin” story — for genuinely new domains with their own data. Right shape when: own store, own read/write patterns, disjoint dependency families (kb-code brought tree-sitter + gix), a UI that is its own product, and a one-direction call graph. Wrong shape for anything that shares kb’s rows. Formalizing kb-sibling/1 is days of work and hardens both the existing pair and the next daemon.

Option C — the sidecar protocol: generalize on the second consumer

kb-embedder is already a textbook out-of-process plugin: separate binary, NDJSON over stdio (Embed/Rerank/Shutdown, a Ready handshake carrying model+dim), bounded startup timeout, 1 Hz liveness probe with in-place respawn, and zero ONNX linkage in the daemon. rust-analyzer’s proc-macro server — the industry’s closest analogue — validates the shape and supplies the warning: its separately-versioned protocol still skewed in 2026 because the version check was advisory. When a second sidecar appears (a different embedder family, an OCR/thumbnailer, a transcriber), lift the pattern into a declared [sidecar.*] config surface with a hard-fail version Hello. Until then, a generic protocol with one consumer is speculative generality — the same reasoning the repo already applied to MCP (“deferred-with-trigger”).

Option D — runtime plugins: dylib no, wasm still deferred, premise amended

Dylib: rejected, reaffirmed with new evidence. Rust has no stable ABI; the workspace’s exact arrow=57.3.1 pin means a plugin built against anything else is undefined behaviour rather than a load error; abi_stable has been unmaintained since 2023-10; and Helix’s plugin author reports trying a C ABI for Rust-to-Rust plugins “with little success” — Helix, nine years in, still ships no plugin system at all. The 2026 landscape did not soften this ruling; it hardened it.

wasm: still deferred, but the justification must change. The old rationale — “single-operator tool, no untrusted code” — is now literally false: kb is a public MIT repo with a DCO gate, a plugin marketplace, and adapters for four non-Claude harnesses. The red team is right that the framing was stale. The rationale that survives: PR review is a different threat model than runtime execution of untrusted code. Contributions arrive as reviewable diffs into a compile-time composition; nothing executes unreviewed. wasm becomes worth revisiting only if kb ever wants to run code it has not reviewed — see triggers.

Option E — the plugin system kb already has

The plugins/ marketplace ships five agent-layer plugins (kb-memory, kb-research, kb-comments, kb-reflect, kb-code): hooks + skills that drive the CLI, installed separately, versioned separately, zero daemon compile, zero SPA change. For a tool whose primary users are agents, this is the extension surface — behavior plugs in above the daemon, consistent with the no-in-daemon-LLM non-goal. The decision doc for “should kb have plugins?” must not overlook that it already does, and they are the cheapest kind.

The thin-CLI steelman worth keeping

The red team’s strongest constructive find: 50+ of kb-cli’s 61 command modules are already pure HTTP clients; only daemon.rs pulls in serve_loop (and with it the whole 133 MB link), and only 4 verbs touch lance directly for offline fallback. The cargo/git subcommand precedent (separate kb-* binaries on PATH, zero ABI) fits kb’s CLI shape naturally. What blocks it today: kb-core’s lance dep is non-optional, so any crate that links kb-core is a fat binary — a thin kb needs a kb-client crate (wire types + HTTP only, no kb-core). Not urgent — 133 MB on disk is cheap — but it is the honest answer to “compiled separately” for the CLI surface, and the 9 MB kb-code-cli proves it works.

The amended thesis

The adversarial round changed the draft in three places, kept it in the rest:

  • Corrected: the kbc outage as evidence for a cross-daemon handshake. It was intra-service; the schema-epoch boot-refuse is the fix the evidence demands, the Hello handshake is cheap insurance against the failure mode that has not happened yet.
  • Corrected: the single-operator premise for deferring wasm. The repo is public infrastructure now; the deferral survives on the review-vs-runtime threat-model distinction instead.
  • Adopted: the sibling pattern is not free (library-level auth coupling, federation plumbing tax, a young codebase whose 6.2% co-change is an early snapshot) — formalization, not celebration, is the right response.
  • Rejected attacks, for the record: “crate boundaries would have prevented the drift bugs” (the SSE kind is a String on both sides; discipline, not boundaries, was the fix that worked); “the monolith is quietly becoming configurable anyway” (2 of the 4 SPA feature flags are dead code; the 2 cargo features are build isolation, not composition); “vertical-slice commits would just become two PRs” (spot-checked commits are genuinely atomic single-intent changes — splitting them across repos manufactures coordination, it does not remove it).

Addendum — if external developers and outside ideas are the goal

Added 2026-08-16 on operator follow-up: “what if I want external developers and ideas on it?” The verdict does not flip — it re-orders. External contribution arrives in three tiers of trust, and kb already has the right seam for the first two. Only the third would ever justify a plugin runtime, and it gets a demand trigger, not a milestone.

Tier 1 — contributions you review (PRs into the repo)

The monolith is not the obstacle; it is arguably the right shape for reviewed contribution — Vector and Caddy accept third-party components exactly this way, as diffs into a compile-time composition. What actually blocks an external developer is legibility: ~98k LOC in kb-core, 35 invariants written for context-loaded agents, and docs that currently lie in places (the hook list, the plugin count). If external devs are wanted, the do-now list gets promoted from hygiene to onboarding surface, plus a human-facing CONTRIBUTING document. And the atlas crate pilot re-scores: its value was never build speed — it is letting a stranger touch one feature behind a compiler-enforced interface without first understanding the storage actor.

Tier 2 — built against kb, zero runtime trust

This is where outside ideas flow cheapest, because their code never runs in kb’s process:

  • Agent-layer plugins — the plugins/ marketplace accepts this today; anyone can ship skills/hooks that drive the CLI.
  • Sidecars — an outside developer could ship an alternate embedder, OCR, or reranker as a subprocess in any language; this is precisely the “second consumer” that triggers formalizing the sidecar protocol with its hard-fail Hello.
  • Sibling daemons — kb-code proves an entire product surface can be built against kb’s HTTP API by someone who never touches kb’s code. For outsiders this requires exactly what kb-sibling/1 prescribes, plus the SSE schema repair and the HTTP API documented as a stable contract. This tier is also where the recorded no-MCP ruling gets re-tested: external agent developers are the demand its trigger conditions anticipate.

Tier 3 — running code you have not reviewed, inside the daemon

The Obsidian/VS Code model: users install third-party plugins that execute in the host. Only this tier justifies a wasm runtime (the Zed/extism wasip2 stack), and it carries the real costs the precedents documented: designing a WIT capability API, a distribution story (Zed’s own maintainer expects their git-registry model “will likely have to go”), and a sandbox boundary kb has never needed. Ecosystems follow adoption — Zed and Obsidian grew plugin systems after users demanded them. Building this ahead of demand is the same speculative generality the repo already declined with MCP.

The staged path: publish the contract before the runtime. (1) Drift fixes + contributor docs — days. (2) kb-sibling/1 + the HTTP API and marketplace documented as “how you extend kb” — opens tiers 1 and 2 to outsiders entirely. (3) wasm only when tier-3 demand is demonstrated by real people asking to run unreviewed code. Stages 1–2 are cheap and are themselves the instrument that measures whether stage 3 is ever real.

Provenance and confidence

Orchestrated 2026-08-16 as two background workflows over eight worker agents (five evidence lanes, three design/adversarial lanes; sonnet + grok workers, ~763k worker tokens, 293 tool calls), with synthesis and the final positions written by the orchestrating model. Build timings were measured live on the development workstation, warm cache, fast profile. Known confidence limits: the two grok evidence lanes completed without their formal self-verification pass (one hit its turn cap mid-verify, one lacked the verify flag), and the two lanes that counted the SSE type enum disagree 57 vs 59 — exact counts in this document should be read as ±2.
