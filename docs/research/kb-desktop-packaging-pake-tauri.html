Packaging kb for the desktop: can Pake / Tauri deploy and distribute it?

A multi-agent, adversarially-verified evaluation of Pake and the desktop-wrapper option against kb's real distribution alternatives — for kb, a Rust daemon + React SPA + ONNX-embedder sidecar that already serves itself as a local web app.

kb · docs/research 2026-06-21 11-agent workflow · 5 adversarial verifiers verdict: tiered — not a desktop app first

Bottom line

Yes, something Pake-like can ship kb — but Pake the CLI itself cannot, and a desktop wrapper is the wrong first move for kb's current audience. Pake wraps a single URL in a webview with no backend or sidecar surface, so "use Pake" really means "fork down to raw Tauri v2 with externalBin sidecars." That path is feasible and Rust-native — but the recurring sign + notarize + auto-update + native-Windows cost is high and partly speculative, while two genuinely cheap channels already cover kb's developer / Claude-Code users.

Recommendation Adopt cargo-dist (curl|sh + Homebrew + npm) as the primary distribution and ship an installable PWA over the loopback SPA — both now, both cheap. Keep the Docker image as-is. Treat a thin Tauri tray-supervisor as a later, conditional audience-expansion bet — only if non-technical and/or native-Windows users are actually targeted, and only after closing two verified blockers.

The three tiers at a glance:

Now Tier 1 — cargo-dist + PWA + Docker

One-line install (brew / curl|sh / npm), an installable PWA for a windowed dock-icon feel, and the existing container. Low effort, low maintenance, matches the proven shape for this category (Meilisearch, Syncthing, code-server, Ollama all ship binary + brew + docker + browser-UI as the baseline).

Later, conditional Tier 2 — thin Tauri tray-supervisor (kb-tray)

A small Rust shell that sidecar-spawns the existing kb daemon on a loopback port, supervises its lifecycle, shows fleet status in a tray, and opens the UI. Justified only to reach non-technical or native-Windows users. Gated on the WebKit subdomain fix + non-unix supervision fix.

Rejected Pake CLI as-is, and a consumer WebView monolith

Pake can't bundle the daemon; a heavyweight all-in-one desktop app duplicates the CLI's bring-up and carries the most signing/maintenance surface for the least incremental value.

What "use Pake" actually means

Pake (tw93, GPL-3.0) is a command-line tool that turns one webpage into a lightweight Tauri-based desktop app, with JS/CSS injection and a system tray. That is the whole surface. Its CLI flag list contains no daemon, sidecar, or external-binary option; its only local-content flag, --use-local-file, recursively copies a static HTML/CSS/JS folder into the bundle. It cannot run kb's axum daemon, which is a live HTTP server that serves the React/Vite SPA via ServeDir, exposes a REST + SSE API, and serves artifacts on *.artifacts.<suffix> subdomains.

The reframe kb is not "a webpage to wrap." It is a server + sidecar (the kb daemon plus the kb-embedder ONNX process it spawns) that already renders a complete local web app. So the desktop question is not "can Pake wrap our page" but "is it worth bundling a Rust daemon into a desktop shell" — and Pake's own foundation, Tauri, is where you end up the moment you need a bundled backend.

Pake is built on Tauri, and Tauri fully supports bundling external binaries as sidecars. So the capability exists — but only once you fork Pake and drop into its src-tauri/ project, at which point you are doing raw Tauri development. (Adjacent webview toolkits — Neutralino extensions, Wails, or a bare OS webview pointed at localhost — could host the same "bundled daemon + webview" shape, but Tauri v2 is the strongest single choice for a Rust project: externalBin maps cleanly onto kb's two-binary rule, and the shell stays Rust.)

Whose problem are we solving?

kb's README frames it for developers and Claude-Code users who already have brew, cargo, docker, and a terminal, and who run many self-hosted corpora/daemons. For them the friction is not "I can't install a GUI app" — it is a one-line install and keeping daemons up. A signed desktop installer removes a barrier this audience does not have.

A signed / notarized / auto-updating desktop shell serves a different audience: non-technical "Obsidian-refugee" users who want click-an-icon → daemon-comes-up → tray shows fleet status, plus native-Windows users (kb is WSL2-only today). The repository's own Part IV deep-dive (docs/research/obsidian-competitive/kb-desktop-onboarding.html) independently reached the same conclusion: a thin tray supervisor + first-run wizard earns its keep for onboarding; a consumer WebView monolith does not.

The actual decision A desktop shell is an audience-expansion decision (do we want non-technical and/or native-Windows users?), not a "better distribution for current users" decision. Without that expansion goal, cargo-dist + PWA dominate on cost/benefit.

The real desktop path: Tauri + sidecars

If a shell is built, the verified-correct architecture is a thin supervisor that sidecar-spawns kb's existing daemon — not an in-process re-implementation, and not a port-less Tauri↔axum bridge (that would break the artifact-subdomain origin model). The shell:

  1. bundles kb + kb-embedder as externalBin (target-triple-suffixed, built in separate cargo invocations — architecture invariant #26, or ONNX links into kb too);
  2. picks a free loopback TCP port, writes a kb.toml with [server] addr = "127.0.0.1:<port>" (the kb daemon verb takes no port flag — the address comes only from config), and spawns kb daemon via the shell plugin;
  3. points the OS WebView at http://127.0.0.1:<port>/ — loopback, so kb's fail-closed no-token guard is satisfied with zero auth setup (invariant #4), and the daemon's [::1] companion bind (invariant #21) makes localhost resolve either family;
  4. sets KB_HOME (or the three KB_*_DIR vars) to Tauri's app_data_dir() so state/config/cache live in an app-owned dir — off-Linux this is the only redirect knob, since directories::ProjectDirs ignores XDG_* on macOS/Windows.

kb already does almost all the work: the daemon serves the SPA + API + artifacts from one loopback origin (which the SPA's same-origin SSE model requires — invariants #23/#24); the embedder never panics the daemon — but a missing embedder binary fails daemon startup with a clear error (and hybrid/semantic requests 400 without one), so the shell must ship both binaries (it does, via externalBin) and surface embedder health. It also reuses $KB_EMBEDDER_BIN as a single spawn chokepoint covering embed, rerank, and kb model download. The shell is roughly a src-tauri Rust file plus ~200 lines of lifecycle glue (free-port, health-poll /healthz, tree-kill on exit).

Three verified blockers (and two myths the verify pass corrected)

Blocker 1 — *.artifacts.localhost does not resolve in WebKit holds

kb serves artifact content purely on the Host header: an artifact iframe's src is always <id>.artifacts.localhost:<port>, and the daemon dispatches on that subdomain — there is no path-based artifact route today. Chromium and Edge/WebView2 hardcode *.localhost → loopback (RFC 6761), so artifacts render on Windows. But WKWebView (macOS < 26) and WebKitGTK (without systemd-resolved / nss-myhostname) do not — they defer to the OS resolver, which a stock localhost entry doesn't cover. kb already documents the macOS dnsmasq requirement for browsers (self-host.md). Result: in a WebKit desktop shell the SPA chrome would render but every artifact — the core feature — would fail to load. (macOS 26 "Tahoe" reportedly changes *.localhost handling; this was not bench-tested here, so verify on the actual target macOS version before assuming the blocker's full breadth.)

Hard prerequisite for a WebKit-targeting shell Add a DNS-free artifact origin before any macOS/Linux desktop build. Preferred: serve artifacts from a second loopback port (cross-origin isolation by port, not DNS) so the full probe/runtime/scroll/annotator/back-button injection pipeline is reused; or a Tauri custom-protocol / WKURLSchemeHandler / WebKitGTK URI-scheme handler giving each artifact a distinct origin (re-validate the iframe-sandbox localStorage isolation under the scheme). Worst option: ship a dnsmasq/resolver setup in the installer (sudo, poor UX). Plumb the new suffix through parse/extract/index per invariant #7 — artifact_host_suffix is runtime config, never hardcoded — and the SPA follows automatically.

Blocker 2 — cargo-dist feature-unification: already solved by precise-builds = true low

This concerns the recommended path, not the Tauri one — and it is largely already solved. A naive single dist workspace build would pull the local-embedder feature into kb via Cargo feature unification (cargo-dist#1740), violating invariant #26 (which exists precisely so kb never links ONNX Runtime). But cargo-dist's precise-builds = true runs one cargo build -p <package> per package — exactly the per-binary invocation invariant #26 requires — and kb's own docs/packaging.md already templates it as the load-bearing mitigation. So the work is to adopt the templated config and verify the dist build honours it, not to invent custom machinery. Fallbacks if precise-builds ever proves insufficient: split kb-embedder into its own dist package (accept package-prefixed tags), or a bespoke GitHub Actions release running the Dockerfile's two-pass build shape. The genuine cargo-dist "decide before release" weight sits elsewhere — version scheme, tag format, the Homebrew tap, and the aarch64-linux ONNX cross-link (all flagged in docs/packaging.md).

Blocker 3 — non-unix daemon supervision is a stub medium

In daemon.rs, send_sigterm bails on non-unix and pid_is_alive returns false — so kb daemon stop and double-start protection don't work off-unix. Native Windows needs this closed, or the Tauri wrapper must own full process-group tree-kill itself.

Two myths the adversarial pass corrected

Myth 1 — "Windows ONNX is a hard gap" Overstated. kb's pinned ort 2.0.0-rc.12 lists x86_64-pc-windows-msvc as a green-tier platform whose download-binaries feature fetches a prebuilt static ONNX Runtime (no onnxruntime.dll; the dynamic-load path is banned by invariant #26). So the embedder plausibly compiles on Windows. It is a new, unvalidated matrix entry (zero CI, /MD CRT → VC++ redist, aarch64-windows needs a source build), not a capability gap. Validate the static link + dual-binary placement + lancedb build before committing.
Myth 2 — "the two-binary sidecar discovery breaks" Mostly wrong. Tauri strips the target-triple suffix at bundle time, so in production the bare kb-embedder sits beside the app exe in .app/Contents/MacOS (or the resource dir) and kb's current_exe().parent()/kb-embedder sibling discovery succeeds with no env var. The suffix is retained only in target/debug — set $KB_EMBEDDER_BIN there (belt-and-suspenders: set it unconditionally). The real wrinkle that does hold: on macOS each embedded sidecar must be individually hardened-runtime-signed or notarization fails (tauri#11992); kb-embedder's static ONNX may need allow-unsigned-executable-memory / disable-library-validation entitlements.

If a shell is built: the phased sketch

Thin kb-tray supervisor, as a separate crate; sidecar-spawn the existing daemon; open the real UI. Never an in-process re-implementation.

  1. Phase 0 — de-risk. Close the two blockers that don't depend on packaging at all: (a) a DNS-free artifact-serving mode for WebKit, (b) the non-unix supervision stub. Neither requires Tauri; both are independently useful (the artifact-origin change also helps the Safari browser path).
  2. Phase 1 — shell + sidecar wiring (macOS + Linux first). externalBin the two binaries (separate builds), free-port + write kb.toml + spawn kb daemon, set KB_HOME/KB_SPA_DIST, health-poll /healthz before showing the WebView, tree-kill on exit (verify whether kb daemon already reaps kb-embedder on SIGTERM; on macOS app_handle.exit(0) on window-close or the daemon survives headless).
  3. Phase 2 — signing + updater. macOS Developer ID + hardened runtime + per-sidecar entitlements; Linux AppImage/deb carrying libgomp1 (ONNX OpenMP) + libssl3, built on glibc ≥ 2.38 (Ubuntu 24.04 / trixie, not 22.04); Tauri updater via GitHub Releases + static latest.json, signing mandatory (TAURI_SIGNING_PRIVATE_KEY). Decide the tag-format/version-scheme once — the same decision unblocks cargo-dist.
  4. Phase 3 — native Windows (only if the audience justifies it). Validate the static ort link end-to-end, close the supervision stub, Azure Key Vault (OV) or EV signing, WebView2 offlineInstaller (+~127 MB) for a true-offline installer.
  5. Model delivery. Default to first-run fetch via kb model download behind a progress UI (installer ~10–40 MB); offer a bundled-model build only for a true-offline SKU (+~130 MB for bge-small). Surface embedder health so the silent keyword-only degradation is visible.

Risk register

Low — a naive cargo-dist workspace build could unify ONNX into kb (feature unification, #1740), violating invariant #26 — but precise-builds = true (already templated in docs/packaging.md) builds each package on its own cargo invocation and resolves it declaratively.
Mitigation: adopt the templated precise-builds config and verify the dist build honours it; fallbacks (split kb-embedder into its own package, or a bespoke Dockerfile two-pass Actions release) only if it proves insufficient.
High — *.artifacts.localhost iframes fail in WKWebView / WebKitGTK: the SPA renders but every artifact errors. Validated only in Chromium/WebView2.
Mitigation: add a DNS-free artifact origin (second loopback port or custom protocol) before any WebKit-targeting build; re-validate iframe sandbox isolation.
Medium — macOS notarization fails because embedded sidecars aren't individually hardened-runtime-signed (tauri#11992); static ONNX may need extra entitlements.
Mitigation: codesign each sidecar with Developer ID + per-binary entitlements; budget entitlement tuning for ONNX.
Medium — native Windows is unvalidated end-to-end; the non-unix supervision stub means stop/double-start don't work off-unix; /MD CRT → VC++ redist dependency.
Mitigation: treat Windows as a fresh CI target with its own spike; close the supervision stub or own tree-kill in the wrapper; keep the static link (no DLL).
Medium — Tauri child.kill() doesn't kill grandchildren: kb-embedder orphans and holds the loopback port → "address already in use" on relaunch; on macOS closing the window leaves the daemon headless.
Mitigation: tree-kill via process group; app_handle.exit(0) on window-close; first check whether kb daemon already cascades SIGTERM to the embedder.
Medium — recurring maintenance tail: Apple Developer (~$99/yr), Windows cert, notarization queues, per-release .sig, fatal-if-lost updater key, ~200 lines of supervisor code — for an audience that mostly doesn't need it.
Mitigation: don't build the heavy shell for the current audience; gate it on a concrete non-technical / native-Windows signal; keep it the thin tray-supervisor variant.
Low — bundling the ~130 MB bge model balloons the installer; first-run fetch needs network + a progress UX, and until the model is present hybrid/semantic search returns an error (the keyword path still works).
Mitigation: default to first-run fetch with a progress UI; surface embedder health/respawn count so the missing-model state is visible.

Recommendation & sequencing

Do not build a Tauri/Pake desktop shell as the deployment answer for kb's current audience. Sequence:

  1. Now — cargo-dist. Adopt curl|sh + Homebrew + npm as the primary distribution, resolving docs/packaging.md's blockers. The ONNX feature-unification concern is handled declaratively by precise-builds = true (already templated) — adopt it and verify the dist build honours it. The real "decide before release" weight is the version-scheme/tag-format (decide once — also unblocks a future updater), the Homebrew tap, and the aarch64-linux ONNX cross-link. Keep Docker as-is.
  2. Now (cheap) — installable PWA. Add a web manifest (+ optional service worker) to web/dist. Near-zero cost; gives the windowed/dock-icon feel for the in-front-of-screen use. Quick check that the SPA origin and *.artifacts.localhost subdomains don't fight over manifest/SW scope.
  3. Later, conditional — thin Tauri tray-supervisor. Only if a non-technical and/or native-Windows audience is actually targeted. Hard prerequisites: a DNS-free artifact mode and a closed non-unix supervision stub. Then accept the macOS sidecar-signing/notarization (and, if Windows is in scope, the new MSVC ort validation + signing).

Pake-the-CLI is out (no backend). Raw Tauri v2 is the right shell technology if a shell is built (Rust-native; externalBin maps to the two-binary rule), but it is an audience-expansion bet, not a better way to reach today's users.

Open operator decisions

  • Audience. Do we want to expand to non-technical and/or native-Windows users? This single decision determines whether a Tauri shell is worth building at all.
  • Tag-format / version-scheme. Cargo.toml is 0.0.0; the real version comes from git tags. "One shared workspace version, unprefixed v-tag per milestone" fits kb's cadence and unblocks both cargo-dist and a future updater — unless the kb-embedder-as-separate-package workaround forces package-prefixed tags.
  • cargo-dist ONNX feature-unification. Resolved in principle by precise-builds = true (templated in docs/packaging.md); the only open item is verifying the dist build honours it on the release runners — with split-package or a bespoke Dockerfile-Actions release as fallbacks.
  • DNS-free artifact mode (if a shell ships): second loopback port (simplest, reuses the full injection pipeline) vs a custom protocol / URI-scheme handler (distinct origin, must re-validate sandbox isolation) vs installer-shipped dnsmasq (poor UX).
  • Model delivery for a desktop/offline SKU: first-run fetch (small installer, needs network) vs bundle the bge model (large installer, true offline).
  • Fleet shape & ownership. Is the desktop value a single tray supervisor for all ~18 daemons (a GUI analog of the existing kb tui) or per-daemon windows — and who owns the recurring Apple/Windows/updater signing infrastructure if a shell ships?

Methodology & caveats

An 11-agent kb research workflow drove this. Five parallel gather arms collected evidence — three read the kb codebase (daemon launch + embedder sidecar; web-serving + artifact-subdomain surface; build/packaging), two ran web research (long-lived Rust server in Tauri v2; the non-Tauri alternatives). Five adversarial verify agents each tried to refute a load-bearing claim. A final synthesis produced the tiered recommendation. Current-state web facts (Pake CLI surface, Tauri v2 sidecar/updater/signing, ONNX cross-platform) were verified inline before the workflow, so the agents built on ground truth rather than memory.

Codebase claims carry file:line citations against the repository at the time of writing (kb v0.19, June 2026). The adversarial pass corrected two over-statements — Windows ONNX is plausible via ort's green-tier windows-msvc static binaries (a new, unvalidated matrix entry, not a hard gap), and Tauri strips the triple suffix in production so kb's sibling discovery of kb-embedder works with no env var. Caveats: the WebKit *.localhost behavior (and the macOS 26 "Tahoe" change) was not bench-tested in a real WKWebView here — it is inferred from WebKit bug reports and kb's own documented dnsmasq requirement; the native-Windows ONNX link, the cargo-dist two-pass build under feature unification, and the sidecar-notarization entitlements are all predicted-tractable but unproven and each needs a spike before commitment.
