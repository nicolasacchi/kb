kb: a complete guide to every feature and how it works

kb is a self-hosted Rust daemon that watches folders of LLM-generated HTML & Markdown, indexes them for hybrid keyword-plus-vector search, and serves them through a sandboxed web app, a terminal dashboard, and a CLI — with comments, an agent-memory store, a 2-D map, and fleet operation layered on top.

Superseded for day-to-day use. The current operator-facing guide is the standalone multi-page site under docs/guide/ (post-v0.24: TUI retired, sessions as episodic memory, reading lists, wikilinks). This page remains a frozen v0.16-era feature snapshot in research.

What kb is

If you generate a lot of standalone HTML documents with an LLM — research reports, design reviews, RFCs, deep dives — you end up with a pile of files that are individually good but collectively unsearchable. kb is the answer to "where did I put that, and can I find it by meaning, not just filename?" It is a long-running daemon that indexes, searches, and serves a personal collection of those artifacts.

The mental model is three nouns. A daemon is one running process; you can run many side-by-side. Each daemon serves one or more kbs — a kb is simply a folder of artifacts (a "corpus"), declared in ~/.config/kb/kb.toml. Each artifact is one self-contained HTML or Markdown file. The daemon watches the folders and keeps its index in step automatically.

One daemon, three ways to use it: the kb command-line tool, a five-tab terminal dashboard (kb tui), and a single-page web app served at /. By the numbers, kb is roughly 93000 lines of Rust across five crates (crates/kb-core, crates/kb-server, crates/kb-cli, crates/kb-tui, crates/kb-embedder) plus a ~27000-line React + TypeScript SPA under web/src. It has shipped in tight phased milestones: the first spikes (2026-05-11), v0.1–v0.7 in a two-week sprint (2026-05-12 to 2026-05-14), the embedding bake-off and TUI build-out (2026-05-19), the agent-memory and atlas milestones (2026-05-22 to 2026-05-25), and v0.14 (2026-06-01) — with v0.15–v0.16 work (created-time sort, the query DSL, a proactive embedder liveness probe) since landed on main. The author's live instance runs at kb.example.com.

Design stanceEverything is local-first and LLM-free at runtime. Search ranking, atlas layout, and memory recall are all deterministic algorithms — the only neural component is the embedding model, and it runs as a supervised out-of-process subprocess. kb never phones home.

How it works

The whole system is a pipeline from a file on disk to a row you can search. A source folder is watched; a changed file is parsed; the parsed document flows through a back-pressured channel into the indexer; the indexer writes to storage and asks the embedder for a vector. The server reads that storage to answer queries and to serve the artifact itself.

source folders
   │  (file watcher, ~400ms debounce)
   ▼
parser  ──►  title · headings · kb-tags · kb-category
            kb-prompt · cross-artifact link edges
   │  (per-kb, back-pressured mpsc ingest)
   ▼
indexer ──►  storage actor  ──►  lance (vectors)  +  sqlite (metadata)
   │                    ▲
   └──► embedder sidecar ┘  (bge-small, NDJSON over stdio)
                 │
   axum server ◄─┘  REST /api/*  ·  SSE /api/events  ·  SPA  ·  artifact subdomains

Storage is split by job. Vector embeddings and the BM25-searchable body live in a LanceDB dataset per kb (under <state>/<kb>/lance/); everything relational — history, errors, link edges, sessions, bookmarks, notes — lives in sqlite. All writes funnel through a single-writer storage actor so concurrent indexing and queries never race on the dataset. Because lance is built on Apache Arrow, lance and arrow are pinned to one exact version so their RecordBatch types unify.

The server is axum. It exposes a large REST surface under /api/*, a Server-Sent-Events firehose at /api/events (the authoritative event registry is served at /api/events.schema.json), the SPA shell, and the sandboxed per-artifact subdomains. Every live surface — the TUI, the SPA, the comment panels — stays current by subscribing to that one event bus rather than polling.

Indexing your corpus

You point a kb at a folder — either in kb.toml or with kb add /path/to/corpus --kb research. From then on the daemon owns keeping the index correct. A file watcher fires on changes, debounced (~400ms) so a burst of edits collapses into one pass.

The parser

Each HTML file is parsed for its real <title>, its heading hierarchy, its kb-tags and kb-category meta, the handoff text inside <template id="kb-prompt">, and any cross-artifact links (which become edges in the link graph). Markdown files are first-class too: a .md file with kb-category: note is treated as a note. The indexed body deliberately excludes text inside <script>, <style>, and <template> — those are data, not prose.

Dedup, quarantine, and re-indexing

Re-indexing is content-hash-gated: a file whose bytes are unchanged is not re-parsed or re-embedded, so a reindex over a large corpus is cheap. A file that cannot be parsed is quarantined (visible at /api/kb/{kb}/quarantine) rather than silently dropped. To force work, kb reindex re-walks and re-emits every file (bypassing the hash dedup); kb reset --kb NAME wipes a kb's index state (lance + sqlite) while keeping your .review/ comments unless you pass --all. Ingestion is a per-kb back-pressured channel, not the shared event bus, so a slow embedder throttles its own kb without stalling the daemon.

Search & embeddings

Search is the core verb. kb search "borrow checker" --kb canon or the search box in the web app both hit GET /api/search?q=…&mode=….

Three modes

There are three retrieval modes. keyword is pure BM25 lexical matching. semantic is pure vector similarity over the embeddings. hybrid (the default) fuses the two with Reciprocal Rank Fusion at k=60 — it takes the best of exact-term matching and meaning-based recall, and is what you almost always want. Both hybrid and semantic need an embedding model configured; without one the daemon returns a 400 problem+json. kb search --offline reads the lance dataset directly for a keyword-only answer with no daemon running.

The query DSL

Beyond a bare phrase, queries support a small DSL: OR fan-out to union several sub-queries, NOT to exclude terms, and field filters. This makes "everything about embeddings but not the bake-off" expressible in one line, across the gallery and the CLI alike.

Embeddings and the model sidecar

Embeddings come from an out-of-process embedder sidecar — the daemon spawns kb-embedder per model and talks NDJSON over stdio with a capability handshake. The default model is bge-small-en-v1.5 (384-dim, ~130MB, downloaded once to <XDG_CACHE_HOME>/kb/models/), running on ONNX Runtime. Three layers pick the model at startup — per-kb embedding_model, a daemon-wide [defaults], then the registry default. A v0.16 liveness probe try_waits each subprocess every second and respawns a dead one before the next query; if it can't, semantic search degrades to keyword-only and a "degraded" signal surfaces in the TUI and SPA.

Model swapsThe on-disk vector dimension is checked against the model at boot; a mismatch fails loudly rather than corrupting the dataset. A same-dim swap can use kb model set NAME --kb KB --in-place; a dim change means stop the daemon, rm -r <state>/<kb>/lance/, restart. A bake-off found bge-large lifts hybrid Recall@1 by +15.6 points over bge-small; bge-base is roughly a wash on technical English.

Measuring quality (kb bench)

kb bench {init,discover,run} turns search into something measurable: scaffold a queries.jsonl, auto-discover relevant ids, then compute Recall@k, MRR, and nDCG per (kb × mode) — and, as of the search-quality program, warm-cache p50/p95 latency alongside quality, so you can see both axes move when you change a model or chunking. kb synth generates a deterministic synthetic corpus (same seed → same bytes) for stress tests.

Serving & reading artifacts

kb does not just list your files — it renders them safely. Each artifact is served on its own subdomain, <id>.artifacts.<domain>, where the id is sha256(source-relative-path) truncated to 12 hex chars (deterministic, survives edits, changes on rename). Serving each artifact from a distinct origin is what makes it safe to embed arbitrary LLM-written HTML in an iframe: the artifact's scripts are walled off from the SPA and from every other artifact by the browser's same-origin policy.

Inside the SPA, the artifact loads in an iframe with a small injected runtime (/_kb/runtime.js) that captures and resumes scroll position, and — with ?cm=on — the comment annotator. Because the parent SPA is a different origin, artifacts must not reach for it: no <base href>, no target="_top", no window.parent.document (it throws a cross-origin SecurityError). The back button is handled with a single clean history entry per artifact.

Outbound scrubbing

For a kb you expose past a reverse proxy, an optional per-kb privacy layer strips the <template id="kb-prompt"> block and applies regex redactions — but only when the request looks non-loopback (its X-Forwarded-For resolves to a non-loopback IP). Local dev is untouched and pays zero overhead. Invalid regexes are logged and skipped rather than failing daemon boot.

The web app

The SPA (React 18 + React, built with Vite) is the primary reading surface. The daemon serves the built bundle from web/dist via ServeDir; permalinks live at /a/{kb}/{id}.

The gallery

The landing view is a faceted gallery backed by GET /api/kb/{kb}/docs. You can filter by tag, folder, capability, and recency (since=7d|30d|all); sort by recent, indexed, title, word count, or created time (the v0.15 sort key); and group by folder. Facet chips are driven by /api/kb/{kb}/tags and /api/kb/{kb}/folders rollups.

Detail view, versions & diff

Opening an artifact gives the iframe render plus a context bar (search-within, the annotate toggle, path pill, siblings). The same view exposes versions and diff: three sources sit behind one façade — git history (resolved relative to the git root), the index's own snapshots, and the live working tree — and auto picks the right one per file. GET /api/kb/{kb}/artifacts/{id}/diff returns rendered-prose or raw-byte hunks between any two version refs.

History & command palette

A history timeline (/api/kb/{kb}/history) records artifact opens with scroll position, searches (deduped within 5 seconds), and comments authored — newest first, enriched with titles. A cmdk-style command palette gives keyboard-first navigation with a recents list. The Settings page tunes theme, accent, and density, and manages the multi-daemon list (stored in localStorage["kb:daemons"]).

The 2-D atlas

The atlas (/?view=atlas) is a spatial map of a kb: every artifact placed as a point, colored by cluster, so related documents sit together and you can browse by neighbourhood instead of by list. It reads atlas_x / atlas_y / atlas_cluster off each artifact, populated by a recompute pass.

Layout is computed in kb_core::atlas: it tries a UMAP-style projection first (brute-force KNN k=15, random init, 200 SGD iterations of attractive/repulsive forces) and falls back to PCA (power iteration with Gram-Schmidt deflation) on degenerate output. Cluster labels come from k-means (Lloyd's, up to 12 clusters, empty clusters reseeded). The whole thing is deterministic — same inputs and seed produce bit-identical coordinates across machines. Artifacts older than the last recompute fall back to a hash placement, greyed at 45% opacity so the real cluster signal stays clear. Trigger with kb atlas recompute --kb NAME; the faster kb atlas recluster --k N re-runs only k-means to retune cluster count without paying the layout cost. Per-kb k and layout overrides live in kb.toml.

Comments & review

kb has a full review system so you (or Claude) can annotate an artifact in place. Each artifact's thread lives at <state>/<kb>/.review/<id>.json in the kb-comments/1 schema. The daemon owns that file exclusively — you never edit it by hand.

The annotator

Click the annotate button in the detail view and the iframe reloads with ?cm=on; the daemon injects window.__KB_COMMENTS and /_kb/annotate.js. Clicking a block picks an anchor scope by context: a text selection becomes a Selection anchor (CSS path + offset + 200-char snippet), a heading becomes a Chapter, an element with an id becomes a Section. Submitting postMessages the new comment to the parent SPA (origin-validated), which POSTs it to the daemon.

Anchors, staleness & reanchor

After every reindex the daemon re-resolves each open comment's anchor against the freshly-parsed HTML. If the target moved beyond tolerance (Section id missing, Chapter token Jaccard < 0.5, Selection Jaro-Winkler < 0.85) it emits comment.anchor_stale and the SPA paints a badge; when the inverse transition is detected it emits comment.anchor_resolved and clears it. Crucially this resolver is detection-only — it never rewrites the frozen original anchor, so it can't silently drift onto the wrong element. When an edit genuinely moves a target, kb comments reanchor re-points it with ground truth. Stale transitions persist to a .anchors-stale.json sidecar so the badge survives a daemon restart.

Concurrency & the Claude loop

The whole-document write was retired in favour of fine-grained mutation endpoints (add comment, resolve, reply, …); each runs load → mutate → save under a per-kb review_lock sharded by kb name, so targeted edits are atomic without the client juggling ETags. Comments and replies can carry file/image attachments (magic-byte sniffed, XSS-safe serve). The Claude round-trip is built in: kb comments export emits a Claude-prompt-formatted thread (server-rendered, streamed with a 32MB cap); Claude works through kb comments reply / resolve (never the file), which re-emit comments.updated so the SPA refreshes live; kb comments watch turns that into a realtime loop you can drive from a terminal.

Agent memory

kb doubles as Claude Code's persistent memory backend. Memories are written as ordinary artifacts (POST /api/kb/{kb}/artifacts, write-only — the watcher indexes each once) and recalled at GET /api/memory/recall?q=…, which fans out across corpora and ranks hits by a deterministic, LLM-free formula: rank-position × salience × decay. Supersede and forget are applied at recall time, so a corrected memory drops out of results without a destructive rewrite.

On top of the ranking sit operator controls: pin holds a memory above the decay floor, promote lifts a project memory to global scope, and a memory can be linked-visible into other kbs. A daemon-wide decay policy (strict / balanced / loose) tunes how fast unreferenced memories fade, with per-kb overrides in kb.toml. Because recall is just an HTTP GET with a deterministic ranker, it is fast and reproducible — the same query against the same store always returns the same order.

Sessions & reading progress

Sessions

kb can capture Claude Code transcripts as session artifacts and expose them cross-kb at /api/sessions (cursor-paginated, newest-first). For a given session you can pull the memories it produced, the artifacts its transcript referenced (/api/sessions/{id}/touches — exact 12-hex hits vs fuzzy path substrings), and the read-counterpart, what the human actually read in the SPA during the session window (/api/sessions/{id}/readings). kb sessions list and kb sessions show drive this from the CLI.

Reading progress

As you read in the SPA, a beacon reports per-section dwell time. The daemon merges it cumulatively (a max-merge, so re-reads only ever increase coverage) into a summary you can fetch at …/artifacts/{id}/reading or with kb reading <id>: how far the doc was read, which sections were read vs skimmed vs unseen, where the reader stopped, and which sections held attention. It follows the history lifecycle — seeded on open, idempotent, no SSE noise. The point is editorial: before revising a long doc, Claude can consult kb reading --json to see what actually got read.

Notes, bookmarks & anchors

Three lightweight layers sit on top of the corpus for personal organisation.

Notes & checklists

A note is not a new entity — it is a Markdown artifact with kb-category: note, so it is searchable and commentable like anything else, but excluded from the gallery grid and the atlas. kb notes new --folder D makes an ad-hoc note (or the scope's canonical _notepad.md); GFM checklist items toggle with kb notes check <note> --item N and grow with kb notes append. The full CRUD also lives under /api/kb/{kb}/notes.

Bookmarks, the anchor corkboard & saved queries

Bookmarks (v0.13) store per-kb reader state — a status, a note, and labels — per artifact, with a cross-kb fan-out at /api/bookmarks. The anchor corkboard (v0.10) pins specific anchors across kbs at /api/anchors for a cross-corpus "pinned spots" board. And a daemon-wide saved-queries store (/api/saved-queries) persists DSL queries you reuse.

The terminal dashboard

kb tui is a fleet-aware daemon monitor — a dark, k9s-style ratatui app built on ratatui that holds a persistent SSE connection to every daemon it knows about (from ~/.config/kb/daemons.toml). Its header aggregates the whole fleet (●N/M daemons · Σ N kbs · ⚡ N events · ◐ N indexing), and each daemon gets a deterministic positional color.

Sharing & publishing

Reading is local; sometimes you need to hand an artifact to someone else. kb share <target> publishes a source-relative file or folder to a static host: Cloudflare Pages behind Cloudflare Access (gated) by default, or GitHub Pages with --public. The --gate rule is repeatable (email:DOMAIN, an explicit allow-list, google, or github). kb share list and kb share revoke <name> manage what's live.

The publish engine runs daemon-side (the host API tokens come from the daemon's environment, never the CLI), and an export always strips the kb-prompt regardless of per-kb scrub settings — your private execution contract never leaves with the artifact. Separately, kb download streams a single artifact's raw source, or a folder / whole kb as a .zip, pipe-friendly for kb download --folder x | tar.

Fleet & self-hosting

Multi-daemon

kb is built to run as a fleet. The TUI reads ~/.config/kb/daemons.toml; the SPA keeps its list in localStorage. The status pill aggregates max severity, in-flight count, open errors, and open comments across every daemon, and each daemon's Last-Event-ID is persisted so reconnects resume cleanly. kb fleet replicate --kb NAME diffs artifact ids across daemons and can copy the missing-anywhere ones into a local dir.

Security & deployment

Bearer-token auth guards /api/* for non-loopback requests; loopback (127.0.0.1, ::1) bypasses entirely so the local CLI/TUI/SPA just work. The token lives at ~/.config/kb/token (mode 0600), generated with kb token generate. Security fails closed — a request whose client IP can't be established is rejected, not trusted — and the proxy chain is only walked when trusted_proxies is configured (empty by default). Four independent per-token rate-limit buckets (search, atlas_recompute, review_post, history_post) return 429 with Retry-After. A reverse proxy like Traefik terminates TLS for *.artifacts.<domain> with a wildcard cert and forwards X-Forwarded-For; optional mDNS advertises the daemon as _kb._tcp.local..

Operations

For day-to-day running: kb status / kb daemon doctor give a green/yellow/red health report, kb metrics prints request and pipeline timing tables, kb backup <kb> makes a consistent tar.gz (sqlite via VACUUM INTO + validated lance + .review), kb restore reverses it, and POST /api/kb/{kb}/compact forces a lance compaction. The daemon also runs periodic auto-compaction in its reconcile loop.

Authoring artifacts that index well

kb indexes what you feed it, so a few authoring rules make the difference between an artifact that's findable, commentable, and stable across regenerations and one that isn't. The full guide is docs/authoring-artifacts.md; the essentials:

  • A real, human-readable <title> matching the single <h1> — it is the primary BM25 field and the gallery card title.
  • A clean <h2>/<h3> hierarchy where every heading carries a stable kebab id derived from its text — comment anchors fuzz-match on these and die on uuids or timestamps.
  • The execution contract inside <template id="kb-prompt">, capped at 8KB — indexed locally, stripped on public serve.
  • <meta name="kb-tags"> and <meta name="kb-category"> for the facets.
  • Self-contained and sandbox-safe: inline CSS, no external fonts or scripts; and no <base href>, target="_top", or window.parent reach-arounds (the iframe parent is cross-origin).

An optional visual floor — an AA-contrast token preamble plus a working skip-link, :focus-visible ring, and prefers-reduced-motion — gives every artifact an accessible baseline without dictating layout. kb new --template … scaffolds one for you; this very document follows the contract.

Extending kb

kb has no generic plugin SDK on purpose, but it ships three real extension seams. Subprocess IPC is the template — the embedder is itself an out-of-process plugin (NDJSON, capability handshake, supervised), the pattern for any heavy or foreign-language extension. The event bus makes anything reading /api/events a plugin; for connectionless consumers a [webhooks] bridge POSTs selected event envelopes to a URL. And declarative <meta name="kb-*"> lets artifact authors extend indexing, recall, and memory behaviour with zero code.

What is deliberately not a seam: the single-writer storage actor, the fail-closed security middleware (so no plugin-contributed routes), and the deterministic atlas. On the Claude Code side, the repo is a plugin marketplace shipping kb-memory (agent-memory hooks), kb-research (the kb-artifact authoring skill), and kb-comments — all LLM-free, every hook driving the kb CLI.
