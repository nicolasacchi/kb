The Live Sessions Cockpit

Following every agent session live — in progress, waiting on you, finished — across Claude Code, Codex, Grok, Kimi and opencode, in the SPA, in the CLI, and in a feed an LLM or an ntfy bridge can act on.

Status: design ratified by evidence, not yet built · Prior art mined: an earlier internal cockpit prototype (retired), a retired helper tool · 7 worker probes + 1 working spike · No daemon code changed this round

Yes, it can be done — on all five harnesses, with real signals rather than guesses. Every harness writes an append-only per-session event file with explicit turn boundaries, and four of the five also offer a push hook. The hard part is not detection. It is that kb's existing live lane is structurally dead in the deployment the operator actually runs, and that the honest unit of state is not three buckets but two axes.

1. The verdict

The operator wants three lanes: in progress, waiting for my input, finished — ordered, live, visible from the SPA and the CLI, and machine-readable enough to point an LLM or a notifier at. Taking each part in turn:

Feasibility per harness. "Proven" means observed in a live experiment or in real on-disk artifacts on this box during this round.

The single most important finding is not on that table. It is this:

Load-bearing defect, found this round kb already ships a live-session lane — GET /api/sessions/presence, GET /api/sessions/{id}/live, kb sessions read --live. In the deployment the operator actually runs, all of it is unreachable. The daemon runs in Docker; requests from the host arrive from the bridge gateway, not loopback, so the hard loopback gate 403s the host's own CLI. And [sessions] live_transcripts_dir is not configured, and ~/.claude/projects is not among the container's bind-mounts — so even from inside, the answer would be {"enabled":false}. Verified live: curl with a valid bearer token returns "forbidden: the live-session lane (presence/live) is loopback-only in v1", and kb sessions read <my-own-live-session> --live returns "session not live (no resolvable live transcript)".

That is not an argument against the feature; it is the argument for its shape. A cockpit that polls the filesystem can only ever work for a bare-metal daemon co-located with the sessions. The operator's daemon is neither. Collection must therefore be push-first — the harness hooks, which run on the host and can reach the daemon over HTTP, are the only channel that survives containerisation, and the only one that would survive sessions running on a second machine.

Prior art, and what it cost

Two previous attempts are directly relevant, and both were mined in full this round.

An earlier internal cockpit prototype (Go, retired) was a read-only live cockpit for Claude Code sessions. Its retirement is recorded not in its own repo but in kb's kb-sessions-rethink-2026-07.html: "the project is dead, and kb builds this capability natively… its field notes are stolen with attribution." The field notes worth keeping: stat-only bounded discovery (a bounded 64 KiB head + 96 KiB tail window, never a full parse just to render a status row); byte-offset tailing with complete-line discipline and restart-on-truncation; lazy-open engines reaped when no subscriber is attached; polling deliberately chosen over inotify (no watch-limit exhaustion, no missed events on rotation); and arrival-sequence ordering rather than wall-clock, because real transcript timestamps collide at millisecond resolution.

The mistake not to repeat the prototype's entire state model was "has anything moved in the last 45–90 seconds", applied at three layers with three different windows, and one of them (one of its subsystems) was wired to a global launch flag rather than per-session activity — which made its "done" phase practically unreachable. Waiting-on-human and finished both collapsed into one idle bucket. Meanwhile it parsed Message.StopReason onto every turn and never read it again. The field that answers the operator's actual question was captured and discarded.

A retired helper tool spiked opencode 1.17.9 and a cross-harness codex worker. Its transferable findings: opencode's permission.asked → BLOCKED → permission.replied cycle is a genuine first-class "waiting on you" signal; codex in exec mode runs approval_policy=never and therefore has no blocked concept at all; and its own review found two high-severity state-machine bugs that a bucketer must design against — a late error event overwriting an already-correct terminal state, and a recoverable error hardcoded as fatal, freezing a session that was still alive.

3. The model: two axes, not three buckets

The naive design makes "in progress / waiting / finished" a single enum derived from file recency. That is exactly the trap the earlier prototype fell into, and the spike built for this round reproduced the failure before it was fixed: a session running a twenty-minute cargo build appends nothing to its transcript, so a recency rule calls it stalled, and a "waiting on you" lane fills with sessions that are working hard.

The correct decomposition is two independent axes:

AxisSourceValues
Who holds the ballTurn-boundary records in the harness's own event file, or the hook that firedagent · human · none (ended)
How long since it movedstat mtime, or the last beat's timestampseconds, plus a confidence label

The three lanes the operator asked for are a rendering of the first axis. The second axis never flips a lane — it only decorates, and escalates to an honest doubt marker:

In progress — the agent holds the turn
0skbSessions live tracking and orchestration stop_reason=tool_use
6mkbMemory sessions, code, and artifacts connections tail=tool_result
52mobsRebuilding the metrics pipeline stalled? silent >45m
Waiting on you — longest wait first
50mkbDaemon connection loss handling and KB link routing end_turn
17musageHistoric token usage metrics and caching end_turn
4mresearchMonitoring tools CLI integration blocked: permission
Finished · Cold
2hshelfFix empty book reader SessionEnd
2dkbResearch plugin architecture cold — waiting >8h

Four honest labels fall out of the two axes, and each is a statement kb can defend:

  • working — agent holds the ball, moved recently.
  • stalled? — agent holds the ball, silent past a threshold well above any plausible single tool call (45 minutes). Never reclassified as "waiting on you": the transcript says the agent has the turn, and silence is not evidence to the contrary.
  • waiting — human holds the ball, since a known instant.
  • cold — human has held the ball longer than a working day's patience (8h). Still resumable, sorted below, out of the notification path.

Plus two terminal cases: finished (an explicit end signal fired) and presumed ended (no end signal, but the lease expired and no capture landed) — which must be labelled differently, because one is a fact and the other is an inference.

4. Collection, harness by harness

Every harness turned out to have the same two-part shape: an append-only per-session event file with explicit turn boundaries, and a hook or plugin that can push. The adapter per harness is small; the model above is shared.

Claude Code — the dominant case

Scale first, because it decides priority: 55 main session transcripts (191 MB), 21 touched in the last 14 days, with 999 subagent and workflow transcripts nested beneath them. By comparison codex has 4 rollouts in the same window. Claude Code is not one of five equal harnesses; it is the feature.

Pull signal, verified first-hand: the last assistant record's message.stop_reason is the ball-holder oracle.

stop_reason = "tool_use"   → agent holds the turn (a tool call is outstanding)
stop_reason = "end_turn"   → agent handed control back → WAITING ON YOU
last record is a user text block   → the human just spoke → agent holds the turn
last record is a user tool_result  → mid-turn, agent holds the turn
Subtlety that costs correctness A tool_result and a human prompt are both type:"user" records. They mean opposite things for state. The discriminator is the content block type: tool_result is the agent feeding itself; a text block is the human speaking. The spike got this wrong on the first run and mislabelled an actively-working session.

Push signals, confirmed live by a worker running an instrumented claude -p with a throwaway --settings file:

SessionStart      {"source":"startup"}
UserPromptSubmit  {"prompt_id":…,"permission_mode":"default","prompt":"…"}
Stop              {"hook_event_name":"Stop","last_assistant_message":"ping",…}
SessionEnd        {"hook_event_name":"SessionEnd","reason":"other"}

Two of these matter enormously. Stop carries last_assistant_message inline — the cockpit gets its "what did it last say" line for free, with no transcript re-parse. And SessionEnd fires reliably, including on interactive Ctrl-D — it is the FINISHED transition, and it is not currently registered in kb's plugin.

Honest gap, and a real fact about this operator Notification (the permission-prompt / idle-prompt hook) is documented in the bundled Anthropic plugin-dev docs but could not be confirmed firing on this box after seven attempts — because the operator's own ~/.claude/settings.json sets permissions.defaultMode: "auto" and settings.local.json broadly pre-allows Bash. Permission prompts effectively never fire for this operator. The "blocked on permission" sub-state is therefore real but nearly moot here, and should ship as best-effort, never as a load-bearing signal. SessionEnd.reason was observed as the generic "other" for both a -p completion and a manual exit — treat it as low-information, not a classifier.

A further gotcha worth recording: a claude process spawned from inside another Claude Code session inherits CLAUDE_CODE_CHILD_SESSION and friends, which silently turns transcript saving off and forces auto-approve. Anyone testing this feature from inside Claude Code must scrub the environment first.

opencode — richest signals, hardest plumbing

opencode has the best vocabulary of any harness: an SSE stream at GET /event?directory=… carrying session.status{type:"busy"|"idle"}, permission.asked, permission.replied, session.error, and per-part streaming deltas. A pending permission is a first-class, observable "waiting on you".

But the state is memory-only inside an ephemeral, randomly-ported process. There is no always-on opencode serve on this box, and nothing durable in opencode.db records busy/idle. Polling is therefore not merely expensive — it is impossible, because there is no port to poll and no registry of ports.

The answer is already half-built: ~/.config/opencode/plugin/kb-memory.ts exists and already registers a generic event handler, today filtered to session.idle. Widening that filter to forward session.status, permission.asked and permission.replied as fire-and-forget POSTs is a few lines in a file kb already owns. Note the schema's snake_case-column / camelCase-JSON split: the SSE field is properties.sessionID.

Grok — a real event log, and a trap

Grok writes ~/.grok/sessions/<url-encoded-cwd>/<session_id>/events.jsonl with exactly the records this design wants: turn_started, turn_ended, phase_changed{"phase":"permission_prompt"}, permission_requested / permission_resolved, plus tool phases. Sub-state within "in progress" (waiting-for-model vs streaming vs tool-execution) is directly readable.

Do not build on active_sessions.json ~/.grok/active_sessions.json looks like a live registry and is the obvious first target. It is empty for the invocation shape this operator actually uses (headless -p via grokclaude) — it serves a leader/dashboard architecture that is unused here. Separately, the job tier .grokclaude/jobs/<ulid>/meta.json.status has a proven three-week-stale "running" bug, so a job claiming to run must be cross-checked against progress.jsonl mtime before being believed.

Codex — clean turns, ambiguous ending

Rollouts at ~/.codex/sessions/<y>/<m>/<d>/rollout-*.jsonl carry task_started, task_complete and turn_aborted event_msg records; the canonical id is session_meta.payload.id, which kb-capture-codex.sh already extracts. A last record of task_started with nothing after it means the agent holds the turn; task_complete means it handed back — but waiting vs finished is genuinely ambiguous from the file alone, because codex exits after an exec run and lingers in an interactive one. Disambiguation is process liveness on the same host, or an honest "presumed" label off-host. The experimental app-server exposes ThreadStatusChangedNotification with an activeFlags containing waitingOnUserInput; that is the precise signal, and it should stay out of v1 as an experimental dependency.

Kimi — hooks work, sandboxed workers do not

Kimi 0.37.2 lives at ~/.kimi-code/ (not ~/.kimi) and writes wire.jsonl with turn.prompt / turn.ended records. kb's hooks are already installed for direct kimi, and SessionEnd is authoritative for finished. The split that matters: kimiclaude worker jobs run kimi -p inside bubblewrap, where kb's hooks are not injected into the generated per-job config — so those are pull-only, via the per-job wire.jsonl tail or progress.jsonl mtime.

5. The wire contract

One canonical shape, kb-live/1. Adapters emit events; the daemon derives state. This split is the whole discipline: a hook is never allowed to assert "I am waiting", only "my turn ended at T". Everything the operator sees is computed, and can therefore be recomputed, explained, and corrected.

The beat (adapter → daemon)

POST /api/kb/{kb}/sessions/beat
{
  "v": 1,
  "session_id": "bf283e00-fa36-4a92-899a-980b2ea06d5c",
  "harness":    "claude",            // claude|codex|grok|kimi|opencode
  "event":      "turn_end",          // start|prompt|tool|turn_end|blocked|unblocked|end
  "at":         "2026-08-21T20:41:02Z",
  "host":       "workstation",
  "pid":        1820040,
  "cwd":        "~/project/kb",
  "model":      "claude-fable-5",
  "lease_secs": 900,
  "title":      "Sessions live tracking and orchestration",   // optional
  "last_line":  "…capped, scrubbed, opt-out-able…",           // optional
  "detail":     {"reason": "permission", "tool": "Bash"}      // optional
}

The derived state (daemon → everyone)

{
  "session_id": "bf283e00-…", "kb": "sessions", "harness": "claude",
  "holder":  "human",            // agent | human | none
  "state":   "waiting",          // working | stalled | waiting | cold | finished | presumed_ended
  "since":   "2026-08-21T20:41:02Z",
  "since_secs": 2947,
  "source":  "hook",             // hook | transcript | capture  — how we know
  "confidence": "observed",      // observed | inferred | presumed
  "project": "kb", "model": "claude-fable-5",
  "title":   "Sessions live tracking and orchestration",
  "resume":  "claude -r bf283e00-fa36-4a92-899a-980b2ea06d5c",
  "artifact_id": "9f8b7182d433"  // the landed capture, when one exists
}

source and confidence are not decoration. They are what lets the UI tell the truth about a session it learned about from a stale capture rather than a live hook, and they are the mechanism by which this feature avoids the earlier prototype's central failure.

6. Shaping the server

Storage: nothing

The live registry is an in-memory map in the daemon, TTL'd. Not a table. This is not minimalism for its own sake — it is the standing ruling. LF-7, recorded in the sessions-rethink design round, says of the live lane: "Everything the live lane shows is derived + ephemeral + never stored — no new tables, columns, lance writes, or review files." And invariant #11 already fixes the tie-break: if the live view and a landed capture ever disagree, the capture wins by definition.

The cost is that a daemon restart loses live state. The mitigation is that it degrades into something already true: on boot, the cockpit rebuilds a Tier-0 view from the durable capture rows (ended_at age per session, newest-capture-scoped), labels every row confidence: "presumed", and sharpens each one the moment its next beat arrives. A cold cockpit is honest rather than empty.

Two costs avoided No migration means no contention with the in-flight v0.38 milestone, which has already claimed V0038 for its Kb-Memory trailers, and no schema-epoch bump — which matters because refuse_if_volume_ahead hard-refuses boot when a volume's epoch exceeds the binary's, the exact mechanism behind the 13.5-hour kbc outage.

Routes

RoutePurposePosture
POST /api/kb/{kb}/sessions/beatAdapter push. Cheap, idempotent, never blocks the callerauth_bearer

The posture question deserves a direct answer, because it looks like a violation and is not. LF-5 made the live lane loopback-only because live transcripts are unscrubbed mid-flight content containing secrets the operator has not yet seen. That reasoning applies to transcript bytes. It does not apply to "session X, harness claude, project kb, human has held the ball for 49 minutes", which is metadata of exactly the kind kb already serves under auth_bearer behind Authelia. LF-5 itself wrote down the graduation: "if D-LF1 ever mounts live transcripts into prod, /live graduates to the export-route posture (token + forced scrub)." This design takes that documented path for the state lane only, and leaves the content lane exactly where it is. The optional last_line field is the one place content leaks in, so it is capped, scrubbed, and switchable off by config.

Events

One new SSE kind, session.state, emitted only on transition — never per heartbeat, or a busy fleet would flood every browser. Elapsed timers are a client concern; useNowTick already exists for exactly this. The kind must be registered in routes/schema.rs's type table in the same commit, because a drift test enforces it.

Liveness without a PID namespace

The daemon is containerised and cannot see host PIDs, so process-based liveness is unavailable to it. Liveness is therefore a lease: every beat carries lease_secs; an agent-held session whose lease expires becomes stalled?, and a session with no beat and no capture for a long window becomes presumed_ended. A host-side kb sessions reap (cron or systemd timer) can optionally harden this by checking /proc/<pid> for beats it originated and reporting confirmed deaths — an enhancement, never a dependency.

7. The human interface

Not a new dashboard. kb retired its TUI with a recorded refusal — "don't rebuild a terminal dashboard" — and the sessions-rethink round fenced off the earlier prototype's supervision half against a "recorded no-dashboard non-goal". A separate cockpit route would walk straight into both. The design instead puts the live state where sessions already are, and puts one number where the operator always is.

  1. A "Now" band at the top of /sessions — the three lanes above the existing day-buckets, collapsed to nothing when every lane is empty. The page already renders kb-ses__bucket groups and already threads a presenceSet into rows; this is a new group kind, not a new page.
  2. A TopBar chip: "2 waiting" — the global, always-visible signal, linking into the waiting lane. This is the piece that makes the feature worth building: the operator should not have to go look.
  3. Rows are actions, not readouts. Each row carries the harness glyph, the project, the elapsed timer, the last assistant line, and one primary action — copy the resume command. buildResume / ResumeCommand already exist in sessions.tsx.
  4. Ordering per lane: waiting sorts longest-wait-first (that is the "you are the bottleneck" signal); in-progress sorts most-recently-active first; finished sorts newest-first.

Reuse is mandated, not optional: sessionPresence.ts for the bucketing primitive, sessionChips.ts as the one chip vocabulary, useNowTick for timers. The refresh cadence becomes the fifth documented exception to invariant #23's staleTime: Infinity rule — and the precedent is exact, because sessions presence is already a named poll-based carve-out.

8. The CLI and the machine surface

The operator asked to see session state from the CLI and to be able to point an LLM or a notifier at it. Three verbs, one of which already exists.

# The snapshot — grouped, ordered, human-first
kb sessions status
kb sessions status --state waiting --project kb
kb sessions status --json          # the machine/LLM surface

# The stream — already exists, no new machinery
kb events --follow --types 'session.state' --json

# The offline path — direct-disk, zero daemon (matches `kb sessions read --live`)
kb sessions status --local

--local is not a fallback; it is the honest primitive. It reads the harness event files directly, exactly as the spike does, and works when the daemon is down, when the hooks are not wired, and on a laptop with no kb at all. It is also what makes the feature testable without touching the daemon.

For an LLM, --json is the contract; a small companion rendering (--brief) collapses the fleet to a few lines suitable for pasting into a prompt, so an agent can be asked "which of my sessions needs me, and why?" without being handed a wall of JSON.

9. Notification without new outbound code

The operator's box already runs the delivery infrastructure: an observability stack in ~/deploy/obs containing ntfy, ntfy-alertmanager, and an Alertmanager whose default route is a webhook to it. And kb already has a [webhooks] event bridge. So the answer is configuration, not code:

# Path A — kb's own bridge (in-daemon, already sanctioned)
[webhooks]  → subscribe to session.state → POST to ntfy

# Path B — the shell, zero config
kb events --follow --types session.state --json \
  | jq --unbuffered -r 'select(.payload.state=="waiting") | .payload.title' \
  | while read -r t; do curl -d "waiting: $t" https://ntfy…/kb-sessions; done

Both leave kb doing what kb does — making state observable — and leave delivery to the operator. That matters beyond elegance: kb has a repeated, recorded posture against push mechanics in its read surfaces ("no push, no streaks/goals/completion %, no badges"). Building an ntfy client into the daemon would invite that refusal. Exposing an event and letting the operator's existing alerting consume it does not.

Caveat to honour The [webhooks] bridge is documented as fire-and-forget and explicitly unsuitable for synchronous decisions. A notifier built on it must tolerate dropped and lagged events. For "you have been blocking a session for 20 minutes", that is fine. For anything that must not be missed, poll --json on a timer instead.

10. What this refuses to do

Recorded now, so the next round does not have to re-litigate them.

  • No control. The cockpit never answers a prompt, approves a permission, kills, or resumes a session. It shows state and hands you a command to run yourself. The earlier prototype built steering and then hard-refused the fleet-commanding half of it with a 501; kb should not start down that road at all. Read-only is the whole posture.
  • No persisted state. Honours LF-7. If durability later proves necessary, amend LF-7 deliberately with evidence — do not smuggle a table in.
  • No second transcript interpreter. Invariant #11's "one engine, three presenters" rule stands; the ball-holder derivation extends session-view/1's existing PendingCalls/unpaired tracking. A ruling landed today (2026-08-21) also forbids kb and kb-code sharing a cursor over the same JSONL files — the beat path must not become a second tailer.
  • No new invariant slot. The budget is capped at 35 and full. This is an amendment to #11, in the same way the W7 live-follow round was.
  • No per-user scoping. One trust tier: identity is attribution, not authorization. Every co-operator sees every session, by design.
  • No pretending at parity. Where a harness cannot distinguish waiting from finished, the UI says so rather than picking one.

Risks worth naming

  • Hook latency. Every beat sits in the operator's turn loop. Beats must be fire-and-forget with a hard sub-second timeout and an unconditional exit 0, matching the capture hooks' existing fail-open discipline. A cockpit that slows down typing is a net loss.
  • Beat volume. Per-tool beats would be hundreds per session. Beat on turn boundaries and lifecycle only, with a throttled mid-turn heartbeat reusing kb-capture-throttle.sh's pattern.
  • The hot repo. A concurrent milestone holds uncommitted WIP across routes/, web/src/lib/, README and CLAUDE.md. L1 touches none of it; everything later should land by explicit pathspec, never add -A.
  • Cold-cache scan cost. 0.098s warm for 55 transcripts, but 8.4s cold on this box's RAID5 spindles. Cache by (mtime, size) and keep the bounded-window discipline; never full-parse to render a row.

12. Evidence appendix

The spike

A working classifier was built and run against this box's real transcripts during this round. It walks ~/.claude/projects, reads at most a 256 KiB tail of each candidate, and buckets by the two-axis model. Live output, correctly separating three concurrently-working sessions from five waiting ones:

=== IN PROGRESS (agent holds the turn)
      6m  kb        Memory sessions, code, and artifacts connections   [stop_reason=tool_use, tail=tool_result]
      2m  kb        alex@prod-host cleanup and cache removal           [stop_reason=end_turn, tail=user_prompt]
      0s  kb        Sessions live tracking and orchestration           [stop_reason=tool_use, tail=assistant]

=== WAITING ON YOU
     50m  kb        Daemon connection loss handling and KB link routing [stop_reason=end_turn]
     49m  shelf     Fix empty book reader and improve UI with icons     [stop_reason=end_turn]
     17m  usage     Historic token usage metrics and caching strategies [stop_reason=end_turn]

=== COLD (waiting on you > 8h)
      5d  kb        kb-code-review-interface                           [stop_reason=end_turn]

It was sampled repeatedly over a minute and tracked the author's own session flipping between tail=assistant and tail=tool_result in real time.

Negative results — things that look like signals and are not

  • ~/.grok/active_sessions.json — empty for the invocation shape actually used.
  • permission-mode records in Claude Code transcripts — carry the mode (auto/default/plan), never a pending approval. There is no in-transcript record of "blocked awaiting approval"; only the Notification hook can tell you.
  • Process file descriptors — Claude Code appends and closes, so /proc/<pid>/fd does not map a process to its session. Nor does the environment: no session id is exported. The hook is the only reliable process↔session binding.
  • opencode's sqlite — 1100 sessions, but no durable busy/idle/permission state. The live truth is memory-only in an ephemeral process.
  • SessionEnd.reason — observed as "other" in every case tested.
