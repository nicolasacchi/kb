kb as memory for non-Claude harnesses — inventory, a codex capture adapter, and the MCP trigger ruling

The MCP deferral’s trigger — “a second agent harness enters real use here” — fired: codex has been in real use since June. But everything the second harness actually needed was buildable without MCP, and was built and verified this session. Recommendation: keep the deferral, replace the trigger with the three gaps only an MCP server closes.

2026-07-06· status:applied (README non-goals re-ruled 2026-07-10; codex integration live)· companion: cross-harness idea board

The question

The README non-goals ledger records, verbatim (README.md:981, ruled 2026-07-02):

The recorded ruling“No MCP server yet. Ruled 2026-07-02 as deferred-with-trigger: the CLI is the protocol — any shell-capable agent drives kb today — so kb mcp gets built when a second agent harness enters real use here, or credible inbound demand asks for it. A recorded ruling, not an oversight.”

Two questions follow, and this artifact answers both empirically rather than by taste:

  1. Can foreign harnesses actually use kb as memory today? Inventory what codex / opencode / gemini-cli emit (transcripts, session ids, hook points), test whether a capture adapter can satisfy kb’s capture-HTML contract, and prototype one for the most-used non-Claude harness.
  2. Has the deferral trigger fired — and was it the right trigger? Enumerate the verbs a foreign harness needs, audit whether the CLI-via-shell suffices per harness, and isolate what only an MCP server would unlock.

Method note: every claim tagged measured or verified below was executed on this machine on 2026-07-06 against codex-cli 0.139.0, opencode 1.17.9, and kb v0.20-50-g838eaa1e. Documentation claims are cited to official sources and were spot-verified against the local binaries where possible.

Codex is the second harness, and it is real use

Measured on this machine: 30 rollouts (2026-06-15 → 2026-06-22, two touched 2026-07-06), sessions on several other projects, research, and the kb repo itself; ~/.codex/config.toml pins model = "gpt-5.5" at model_reasoning_effort = "xhigh" with 21 trusted project dirs. For scale: Claude Code holds 3,895 transcripts since 2026-06-01 — codex is a distant second, but it is not a toy. Codex also ships adjacent state kb should know about: memories_1.sqlite (the experimental, default-off Memories feature — two-phase LLM distillation of rollouts; 0 rows here), goals_1.sqlite, and a Claude-Code-shaped hook system whose stdin/stdout JSON schemas match Claude’s down to field names (hook_event_name, transcript_path, additionalContext — extracted from the binary and confirmed against developers.openai.com/codex/hooks).

opencode and gemini-cli: capturable, not urgent

Measured: opencode’s 482 sessions decompose as 444 in 2026-03 (a bulk orchestration experiment — titles like “conductor”, sessions spawning codex workers), 18 in April, 20 in June; last use 2026-06-21. Its capture surface is the richest of the three — a global JS plugin gets session.status idle events plus a full SDK client to fetch every message/part, and opencode export <id> / direct sqlite reads work with zero plugin — but until opencode re-enters real use, an adapter is speculative. Gemini-cli is simply absent here; its documented surface (11 hook events, AfterAgent with transcript_path, 30-day transcript retention that an adapter must outrun) makes an adapter straightforward when it arrives. Adapter sketches for both live on the companion idea board (I7, I8).

Part 2 — kb’s side of the contract

kb’s episodic pipeline has a narrow waist, and knowing exactly where it sits is what makes foreign capture cheap (all cites verified in-source this session):

  • Detection is category-driven. One predicate — kb_category == "memory-session" — routes an artifact into session enrichment (indexer.rs:1146, enrich.rs:137, sessions.rs:32). Filename and kb-session meta matter only for identity.
  • The id ladder repairs itself. parse_session_html_full (sessions.rs:273-278): JSONL sessionId > <meta name="kb-session"> > filename regex > stem. An adapter that stamps all three is triply safe.
  • One parser feeds everything. parse_session_activity (sessions.rs:472-672) reads Claude-shaped lines — message.role, tool_use blocks (Bash commands for git commit/push/tag with SHA pairing, Write/Edit/Read for file touches, WebSearch/Task/Skill for research rows, AskUserQuestion answers for decisions), file-history-snapshot for the authoritative edited set, message.usage for tokens. Downstream — the R1 digest (sessions.rs:305-387), the five sqlite tables (enrich.rs:141-312), kb why, kb recollect, the SPA panels — reads derived rows, never raw JSONL.
  • Foreign shapes degrade gracefully, to uselessness. A verbatim-wrapped codex rollout indexes without error but yields an empty digest (guard at indexer.rs:1153), a bare sessions row, zero child rows — and the raw JSONL becomes the searchable body, exactly the retrieval-burying failure R1 exists to prevent. So a capture adapter must translate, not merely wrap.
  • Ingestion is watcher-only. No direct-index API: kb add registers folders, POST /artifacts is the memory-artifact renderer and still writes a file for the watcher. The adapter writes session-<ts>-<sid>.html into the sessions corpus dir via temp-file + atomic mv, mirroring wrap_envelope (import.rs:317-339).

The one measured friction: codex’s sandbox

Measured, using codex sandbox (no LLM in the loop): under the default policy, kb recall inside the sandbox fails (“daemon not reachable”; loopback curl returns 000) while the identical command outside answers 5 memories in 320 ms. With two config lines — sandbox_mode = "workspace-write" and [sandbox_workspace_write] network_access = true — loopback returns 200 and kb verbs work. Without config, each agent-initiated kb call becomes an out-of-sandbox approval escalation. So: real friction, config-sized fix, comparable in setup cost to registering an MCP server (also a config edit). Note the asymmetry that saves the memory story: hooks run in the harness process, outside the sandbox — recall injection and capture are untouched by this entirely; only the agent’s own kb invocations feel it. opencode and gemini-cli have permission prompts but no network-blocking sandbox around shell.

What only an MCP server would unlock

  1. No-shell surfaces. ChatGPT desktop, claude.ai remote connectors, IDE-embedded agents without a shell tool. None are in use against kb on this machine today — but this is the one structural gap the CLI can never cover.
  2. Typed, prompt-tax-free discovery. Tool schemas + descriptions delivered by protocol instead of a 28 KB manifest pasted into AGENTS.md (or a hand-trimmed 2 KB subset that drifts as verbs evolve).
  3. Codex’s privileged MCP channel. MCP servers configured in codex run outside the sandbox as a first-class capability — no network opt-in, no per-call approval, structured results. The config-lines fix above is equivalent-cost but grants the whole sandbox network access rather than just kb; an operator who tightens that back down would feel the difference.
  4. MCP resources/prompts primitives. Artifacts as subscribable resources, kb templates as prompts. Nice, speculative, zero demand recorded.

What MCP would not solve

  • Ambient recall and capture — the actual memory loop — remain per-harness hook work in every scenario. The two artifacts this session produced (adapter + idea board) are unaffected by any MCP decision.
  • The daemon still has to run, reachable, with the corpus mounts — MCP moves no operational burden.
  • Teaching the discipline (recall before re-deriving, remember after decisions) is prose in an instructions file either way; schemas don’t carry norms.
  • A second operator gains nothing: the one-daemon-one-operator ruling (2026-07-06) already routes them to kb share or their own daemon; an MCP endpoint must not become a side door.

Cost of building it anyway

A second protocol surface that must stay in lock-step with 44 CLI verbs (drift = the worst kind of doc rot: machine-readable and wrong); MCP spec churn (three revisions in 18 months, OAuth resource-server semantics still settling); auth plumbing decisions (stdio inherits the CLI’s token file; HTTP transport re-opens the bearer/proxy questions the security review just closed); test surface; and — the doctrinal cost — the first standing invitation for foreign writers into a store whose value is that every write is deliberate and attributed.

The ruling recommendation

Keep the deferral. Re-specify the trigger. The 2026-07-02 trigger (“a second agent harness enters real use here”) fired as written — codex qualifies — but this evaluation shows it was a proxy for needs that turned out to be hook- and shell-shaped, all satisfied without MCP. Proposed replacement ledger text:

“No MCP server yet. Re-ruled 2026-07-06 after the codex evaluation (docs/research/kb-memory-for-foreign-harnesses-2026-07.html): the CLI is the protocol — codex/opencode/gemini all drive kb via shell + instructions file, and ambient memory (recall injection, capture) is hook work MCP cannot carry. kb mcp serve gets built when one of: (1) a harness in real use here has no shell tool or no config escape from its sandbox (e.g. adopting ChatGPT desktop / claude.ai connectors as kb clients); (2) real dual-harness use shows recurring kb-call approval fatigue that config + AGENTS.md cannot fix; (3) a harness regression removes transcript_path/additionalContext hooks, leaving MCP as the only integration point. Inbound demand from a second operator is NOT a trigger (see one-daemon-one-operator). If triggered: read-only stdio facade in kb-cli (search, recall, why, recollect, get) over the existing HTTP API — extension lanes #1/#2, never in-daemon, writes stay CLI-only.”

Why read-only if ever built: the read verbs are idempotent, provenance-preserving, and match what a foreign reader needs; remember/forget over MCP would let any connected client mutate memory without the deliberateness the CLI enforces (a human or agent choosing to run a write verb, visible in the transcript, capturable by the very sessions machinery this artifact exercised). And why kb-cli, not kb-server: the daemon’s non-goals (no in-daemon LLM, fail-closed auth stack) stay untouched; a stdio sidecar reuses kb-cli’s existing HTTP client, token loading, and federation semantics — the same doctrine that keeps the embedder out-of-process (docs/extending.md, mechanism #1).

One follow-through this evaluation does recommend now, independent of MCP: register kb-capture-codex.sh as a codex Stop hook, add the trimmed memory-protocol block to AGENTS.md in shared projects, and set the two codex sandbox config lines — that is the entire integration, and it makes the dual-harness data that would justify (or permanently retire) trigger condition (2) accumulate by itself.

When to revisit

  • Any of the three re-specified trigger conditions occurring — especially adoption of a no-shell client surface against kb.
  • Codex Memories (experimental, off, empty here) shipping in a form worth bridging — the moment codex itself consumes memory over MCP, interop pressure changes shape (idea I6 on the companion board).
  • Six months of dual-harness capture data (post hook registration): if codex sessions accumulate and approval fatigue never materialises, consider hardening the deferral from “yet” to a plain non-goal.
