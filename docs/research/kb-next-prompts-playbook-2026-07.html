The next-prompt playbook — what to run on kb next, in order, and the research recipes to reuse anywhere (2026-07)

2026-07-06 · synthesized from the coverage-gap analysis (20 verified gaps), the session-memory deep review (36 defects, ranked portfolio), and the live working-tree state · companion: workflow-sessions design

Three standing rules before any prompt

  1. No new review sessions until R0 (triage) has run. Five July reviews already sit untriaged; review throughput is ~10:1 ahead of implementation. Every additional review before triage makes the pile-up worse — the coverage-gap analysis measured this loop happening.
  2. Every session ends in commits or recorded refusals. "Research-only" is a valid outcome only when the artifact itself IS the deliverable. A session that produces recommendations must either schedule them (plan file), implement a slice, or decline them with rationale in the artifact — otherwise it feeds the untriaged pile.
  3. One prompt, one session, its own acceptance test. Each queue entry below carries explicit acceptance criteria inside the prompt. If a session can't meet them, it should say so plainly rather than declaring victory — the deep review found several "shipped" features that no client ever rendered.

The queue — run these in order

Ordering logic: R0 converts stored review findings into decisions (unblocks everything, prevents re-derivation). R1 protects the working tree (uncommitted engine, highest data-risk). R3 protects the public bind (live exposure). R4 restores cadence. Then the two milestones. Each prompt is self-contained — paste it as the session opener.

Five research recipes that generalize — use on any project

These are the patterns that measurably worked in the July program (38 candidate defects → 36 confirmed by adversarial verification; 45 ideas → 5 convergent programs). Each is a parameterized prompt — replace the {PLACEHOLDERS} and paste. All assume the ultracode keyword when you want multi-agent scale.

T1Coverage-gap meta-review — "what have all my sessions never covered?"

When: a project has accumulated 20+ sessions and you suspect blind spots. Why it works: classifying sessions into covered-tags vs a repo-derived universe makes absence provable instead of vibes; requiring cited evidence-of-absence killed a third of candidate gaps here.

Template 
Map what all my past sessions on {PROJECT_PATH} covered, then find what is MISSING. ultracode it: (1) classify every captured session (kb sessions list --folder {PROJECT_PATH} --json; enrich big ones with kb sessions show) into covered-topic tags + outcome (shipped/research-only/ops/abandoned) + explicitly-unfinished items; (2) enumerate the reviewable universe from the repo itself (docs, crate/module layout, CI, quality dimensions any serious product needs: security, perf, a11y, durability drills, migrations, licenses, onboarding, observability, scalability, chaos); (3) census existing research/review deliverables; (4) gap analysts across three frames — subsystem, quality-dimension, follow-through (started-but-never-finished) — every gap needs cited evidence of absence; (5) a critic dedupes, spot-checks against the repo, and ranks into run-this-month / before-{MILESTONE} / nice-to-have with a paste-ready session prompt per gap. Output one HTML research artifact in {RESEARCH_DIR}.

T2Fidelity harness — "does the record match reality?"

When: any system that summarizes/records something (logs, digests, dashboards, ETL, backups) whose consumers trust it blindly. Why it works: per-item ground-truth comparison with a numeric rubric turns "seems fine" into a 2.6/5 you can re-measure after fixes — it becomes the acceptance test.

Template 
Evaluate how faithfully {RECORDING_SYSTEM} represents reality. ultracode: one reader agent per {ITEM} (take the {N} most recent): pull the stored record, then independently reconstruct ground truth from {RAW_SOURCE} (sample with jq/grep — never read multi-MB files whole) and {CORROBORATING_SOURCE} (e.g. git log for the same window). For each item: what the record captured, what it missed or fabricated (concrete, quantified — "records 12, reality 2,215"), and a 1–5 usefulness score: would a future consumer acting on this record alone avoid re-deriving the work? Then verify every claimed defect adversarially in the code (file:line or reproduction). Output: per-item fidelity table, defect census grouped by pipeline layer, and the harness itself written into the artifact's kb-prompt so it can be re-run as the acceptance test after fixes.

T3Multi-lens ideation + judge panel — "improve X without vanity features"

When: you want an improvement portfolio, not a wishlist. Why it works: lens diversity finds different idea classes (the retrieval and product lenses independently converged on the same two fixes here — convergence is signal); the feasibility judge inspecting the actual codebase catches understated effort; the strategy judge rewards deletions.

Template 
Generate and rank improvements for {SUBSYSTEM}. ultracode: 4–5 ideation lenses in parallel — {CONSUMER}-experience, data-quality/fidelity, {CORE_QUALITY e.g. retrieval/performance}, product-workflow, and first-principles (question the mechanism itself; argue for deletions where usage evidence is absent). Every idea must cite the evidence motivating it and state why it doesn't violate {CONSTRAINTS/NON-GOALS}. Feed all lenses the same evidence pack. Then a 3-judge panel scores each idea 0–10: value-to-{CONSUMER}, feasibility-in-THIS-codebase (judge may inspect the repo; penalize understated effort), strategic fit (reward leverage and deletions). Average scores, median tier (now/next/later/reject), cluster convergent ideas into programs. Output the ranked portfolio as an HTML artifact with per-program acceptance criteria.

T4Adversarial verification sweep — "which of these claims are real?"

When: any list of suspected defects/claims before acting on them. Why it works: instructing verifiers to REFUTE (not confirm) with file:line or live reproduction is what makes a 36/38 confirmation rate meaningful — and the 2 refutations prevented two wrong fixes. Always publish the refuted column; it's the credibility of the confirmed one.

Template 
Adversarially verify these {N} claims about {TARGET}: {CLAIM_LIST or artifact link}. One independent skeptic per claim, instructed: default to refuted; confirm only with a file:line mechanism or a reproduction you ran yourself; if the behavior is intended per {DESIGN_DOCS}, say so — "not-a-bug" with the design rationale is a valid verdict. Each verdict: confirmed/refuted, corrected one-sentence summary (claims are usually right in direction and wrong in detail), severity, minimal fix sketch. Output both columns — confirmed AND refuted/intended — grouped by {LAYER}.

T5The review→triage→land loop — the discipline that makes T1–T4 compound

When: always. Why: the coverage-gap analysis measured what happens without it — five reviews in four days, one slice landed, and the memory system re-deriving its own findings. The loop: (1) review produces an artifact with stable per-finding ids; (2) a triage session rules accept/defer/reject on every finding and updates the plan file; (3) implementation sessions reference ruling ids in commits; (4) re-run the review's own harness as the acceptance test. A finding without a ruling is debt; a ruling without a commit or a recorded refusal is theater.

F3 · capability exists, never composedTemporal knowledge — "what did this corpus know in June?"

State: the pieces all exist — versions/diff façade (invariant #14: git + index snapshots + working tree), append-only history (#8), session timestamps, memory supersede chains — but no query composes them. You cannot ask "show me this artifact as it stood before the July rewrite," "which memories were live when I made that decision," or "what changed in this kb between the two reviews." For a system whose thesis is remembering, time is oddly second-class.

Prompt 
Research a temporal query surface for kb, composing what already exists (versions façade #14, append-only history #8, memory supersede chains, session timestamps) — deterministic, no new storage if avoidable. Candidate queries to design against: kb cat <id> --as-of <date>; kb diff <id> --between <date> <date>; kb recall "<q>" --as-of <date> (which memories were live then, honoring supersedes); a "corpus changelog" view (what appeared/changed/died in a window — the week-in-review idea's deterministic core). Assess per query: which existing source answers it (git? snapshots? history table?), gaps, cost. Output a design artifact with a thin-slice recommendation — the ONE temporal verb with the best value/effort — and explicitly reject the rest with rationale so this doesn't become a time-travel epic.

F5 · never exploredAttention-based resurfacing — the read-it-again queue
