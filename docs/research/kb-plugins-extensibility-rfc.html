Design RFC · Extensibility

A plugin / extensibility architecture for the kb daemon

kb already runs three working plugin mechanisms — it just never named them. This RFC names the seams, recommends formalising the one in-process hook worth extracting, and weighs the Claude-Code surface honestly against kb's own prior design conclusion — rather than inventing a generic plugin framework the daemon's correctness invariants would reject.

Recommendation in one screen

Do not build a generic plugin framework. kb is a single-author / small-fleet daemon whose value rests on correctness invariants (single-writer storage, deterministic atlas, fail-closed security). A generic framework would fight all three. Instead:

  • Adopt Name the three mechanisms kb already runs — subprocess IPC (the embedder), event-bus subscribers (SSE), and declarative <meta>/config — as the plugin story.
  • Adopt Formalise the indexer's post-upsert enrichment into an in-process hook registry — the single highest-leverage refactor; it turns the most painful internal-feature path into an additive one. This is the architectural proof-of-concept.
  • Adopt An outbound event-webhook bridge — ~one subscribe task + a config block; near-zero risk; the smallest possible proof that the event bus is a plugin substrate.
  • Adopt A generic <meta name="kb-*"> registry — kills the most repeated friction (every new facet edits the parser today).
  • Defer WASM (no untrusted-code threat model yet) and Reject dynamic .so loading (no stable Rust ABI; the pinned arrow graph makes it unsound).
  • Adopt Package what already works as Claude-Code plugins (a kb-research and a kb-comments bundle from existing skills + commands). Treat a read-only exploration MCP server (search / related / open-comments) as an Optional ergonomic upgrade — kb's own research/memory/21 rejected MCP for memory; for exploration the token-cost trade is genuinely open. Recall stays a hook either way.

1Context & question

kb is a tightly-integrated Rust daemon: an indexer, a hybrid (BM25 + vector) search store, an axum HTTP server, a CLI, a TUI, and an SPA, all in one workspace. It is fast and coherent precisely because nothing is abstracted for its own sake. The cost shows up when a feature is added: each one is threaded by hand through the same long pipeline — parser → lance schema → migration → indexer → storage actor → routes → router → daemon state → CLI → SPA.

This RFC answers two operator questions:

  1. How and if kb should grow a plugin / extensibility architecture.
  2. What existing functionality can already be moved out as a plugin with low effort.

The friction is real and measurable. Three recent features, by surface area:

Cost of adding a feature today (measured across the workspace)

BookmarksOrthogonal sqlite table~7400–600migration + actor delegation + routes + CLI + SPA. The cheap baseline.
Sessionsparser + lance column + indexer hook~9–10500–800new <meta> in parser, additive lance column, post-upsert enrichment, enrichment sqlite table, daemon-wide cache.
Memory-linkstwo migrations + boot backfill + recall filter~10+~1200two migrations, a daemon-startup seeding hook, indexer seeding, and a change to recall ranking itself.

The thesis of this document: the answer is not "build a plugin SDK." It is "stop hand-threading the two or three seams that actually repeat, and recognise the seams kb has already built but never documented."

2How kb is extended today

kb extends itself with three idioms, none of which is a plugin system: closed enum dispatch, static const registries, and hardcoded route/CLI tables.

The grain: explicit dispatch over indirection

The clearest example is the share engine. ShareBackend is an enum, not a trait, and the module header records the reason verbatim:

"An enum (not a dyn trait): Rust async-fn-in-trait doesn't object-dispatch cleanly, and the two hosts sequence very differently (Cloudflare deploys and gates; GitHub only deploys)." crates/kb-core/src/share/host.rs:1–6

Note what this is and isn't. The comment justifies the enum on technical grounds — a language constraint (async fns don't object-dispatch without boxing) plus genuine behavioural divergence between hosts — not as a stated policy against plugins. But the consequence is the grain this RFC must respect: adding a host is a new variant plus a match arm, in one obvious place. An extensibility proposal that introduces a trait object "for symmetry" fights both the language and that grain. The bar for a real seam is therefore high: the same edit must repeat across many features, or the extension must genuinely belong out-of-process.

Closed enums & static registries

  • Embedding models — a static const array, SUPPORTED_MODELS (4 entries), looked up by name; the backend is a 2-variant enum EmbedderBackend::{Local, Ipc}. embed.rs:67–100, 139–142
  • Search modes — BM25 / vector / hybrid are StorageMsg variants dispatched by match, dim-locked to the kb's lance column.
  • Atlas layout — UMAP / PCA is a config enum.
  • Storage — a single-writer-per-kb actor; every mutation is a StorageMsg variant (storage/actor.rs:1, 24, 28). This is a correctness boundary, not a candidate seam (see §9).

Hardcoded tables

  • HTTP routes — assembled by hand in router.rs (.route() / .merge()) behind a fixed tower stack (count → auth → rate-limit).
  • CLI verbs — a flat clap Cmd enum plus one big match in kb-cli/src/main.rs.
  • Parser metadata — ten kb-* metas are each a field on a Fields struct plus a compiled CSS Selector on ParserSet: kb-category, kb-tags, kb-status, kb-severity, kb-salience, kb-decay, kb-supersedes, kb-session, kb-global, kb-linked-kbs. parser.rs:32 (Fields), 53–104 (the meta docs), 231–240 (selectors). Every new facet so far paid this tax.

3What "plugin" means for kb

Define a plugin narrowly, to match the codebase's temperament: added behaviour that does not require the N-file pipeline surgery of §1, and ideally no recompile of core. Under that definition there are six candidate seams — and three of them already exist as de-facto plugins that were simply never named:

#SeamStatus today
1Indexer post-upsert enrichment hookHardcoded; the cleanest in-process seam to formalise.
2EmbedderAlready a plugin — a subprocess over NDJSON IPC.
3Event subscriberAlready a plugin pattern — anything that reads /api/events.
4Declarative <meta> / configAlready userland — authors extend behaviour with zero code.
5Share hostEnum (technical reasons, §2); the codebase's reference example of explicit dispatch.
6Route contributionNo seam — and there shouldn't be one (security stack, §9).

So the work is mostly recognition, not invention. kb runs a subprocess plugin (the embedder), a publish/subscribe firehose (the event bus), and a no-code extension model (<meta>). The RFC's job is to (a) document those as the supported extension surface, (b) formalise the one in-process hook worth extracting, and (c) decline the seams that would break invariants.

In-process hook registry — adopt, but as kb already does dispatch

kb hit the async-fn-in-trait wall and documented it (host.rs:1–6). Don't fight it: a hook is either a closed enum, or a Vec<Box<dyn EnrichmentHook>> whose method is sync or returns an explicitly-boxed future. The natural site is the indexer's post-upsert phase: after upsert_doc lands, the indexer branches on is_memory_session / is_memory_artifact and runs best-effort enrichment in line — parse_session_html → sessions_upsert, the memory-link seed, then record_edges — each one logging and continuing on error (indexer.rs:828–954). Cost of a panic = the indexer task; mitigate by keeping hooks Result-returning and best-effort, which the current code already is.

Subprocess IPC — adopt; kb already ships the reference implementation

The embedder is an out-of-process plugin. Its protocol is small, tagged, correlated, and supervised:

// crates/kb-core/src/embed_ipc.rs:14–28  (NDJSON, one JSON value per line)
#[serde(tag = "kind", rename_all = "snake_case")]
enum Request  { Embed { req_id: u64, texts: Vec<String> }, Shutdown }
enum Response { Ready  { model: String, dim: u32 },            // handshake
                EmbedOk { req_id: u64, vectors: Vec<Vec<f32>> }, // correlated
                Error   { req_id: u64, msg: String } }

It declares capabilities in a Ready handshake, correlates by req_id, discovers its binary via $KB_EMBEDDER_BIN → sibling-of-exe → PATH, and kills the child on Drop. The documented rationale is isolation: the child runs ONNX at nice 20 so it can't starve the daemon's HTTP/SSE handlers, and a dead-flag + respawn contract means a crashed child can't take the daemon down (embed.rs:122–127; embed_ipc.rs:36, 112). That is the exact argument for any third-party plugin lane. Generalise this envelope and you have kb's out-of-tree plugin protocol for free.

Event-bus / webhook — adopt; cheapest, ships first

/api/events is already durable, resumable, filtered pub/sub: a 1024-entry replay ring, a 1024-deep broadcast channel, monotonic ids, and snapshot_since(last_id) + events_stream for resume-after-gap, with synthetic Lag/Gap frames (events.rs:27–28, 83–91, 139). Subscribers already include the TUI, SPA, kb push, and internal history rings. An external process reacting to the SSE stream is already a plugin. The only missing piece for consumers that can't hold a connection is a daemon-side webhook bridge — and the template already exists: the per-kb history-ring task (lib.rs:1058–1074) is exactly bus.subscribe() → filter by kb → act.

WASM — defer; .so — reject

WASM (wasmtime/extism) buys sandboxed third-party code without a separate process — but kb has no multi-tenant / untrusted-code threat model, and a WASM runtime is a heavy new dependency on top of an already-pinned, slow-to-link graph (arrow =57.3.1; cold links run 20+ minutes). Subprocess IPC gives ~90% of the isolation for ~5% of the complexity, and kb already runs it. Dynamic .so loading is unsound here: Rust has no stable ABI, and the exact arrow/lance pin means a plugin built against a different arrow is undefined behaviour, not a load error — while keeping the in-process crash blast radius. Reject it on both counts.

5Recommended architecture

A four-tier model, from no-code to out-of-process, each independently useful:

Tier 0 — declarative meta / config registry (no code)

Collect every unrecognised <meta name="kb-*"> into a BTreeMap<String,String> on Fields, persisted as one JSON lance column, exposed in search filters and event payloads. New meta-driven facets then land with zero parser/schema/migration churn. Typed promotion (its own column) stays the path for facets that need BM25 ranking. This is the closest thing to a true userland plugin — and it directly attacks the parser tax of §2 (ten hand-written selectors today).

Tier 1 — in-process enrichment hook registry (in-tree)

Extract a hook trait from the three enrichers the indexer already runs post-commit (session parse, memory-link seed, edge recording). Keep order, best-effort semantics, and emitted events byte-identical.

/// Runs after a Doc is committed to lance. Best-effort: an Err is logged
/// and skipped — it must never fail the index. Writes go through the
/// StorageHandle (never lance/sqlite directly) — see §9.
trait EnrichmentHook: Send + Sync {
    fn interested(&self, fields: &Fields) -> bool;          // cheap pre-filter
    fn enrich<'a>(&'a self, ctx: EnrichCtx<'a>)
        -> BoxFuture<'a, anyhow::Result<()>>;                // boxed: dodges RPITIT
}
// indexer holds: Vec<Box<dyn EnrichmentHook>>, run in registration order
// after upsert_doc — today's inline is_memory_session / memory-link / edge
// branches each become one impl. (crates/kb-core/src/indexer.rs:828–954)

This is the architectural unlock: the next sessions-shaped feature becomes one new impl instead of edits scattered across nine files. Share hosts stay an enum (the technical reason is in host.rs:1–6); if a third host is ever needed, add a single ShareBackend::Subprocess variant rather than a trait.

Tier 2 — out-of-tree subprocess plugin protocol

Lift the embed_ipc envelope into a reusable plugin_ipc module: a versioned, kind-tagged Request/Response, a handshake that declares the plugin's kind + capabilities, and the generalised locate_*_bin discovery. A plugin is then any executable speaking the protocol — alternate embedders (done), alternate extractors for new file types (PDF/notebook → Fields-shaped JSON), or a subprocess share host. Build this only when a concrete plugin demands it.

Tier 3 — reactive event-webhook bridge

A config section plus one bus.subscribe() task that POSTs selected envelopes to a URL — a direct clone of the history-ring task:

# kb.toml
[webhooks]
url   = "http://127.0.0.1:9000/kb-hook"
types = ["artifact.indexed", "comment.added", "session.captured"]
# daemon: one task in lib.rs, cloned from the lib.rs:1058–1074 history-ring task:
#   let mut rx = bus.subscribe();
#   while let Ok(env) = rx.recv().await { if matches(env, &types) { post(url, env) } }

Read-only and post-emit, so it respects every security invariant (§9). Eventually-consistent and fire-and-forget — never for a synchronous in-request decision.

7Claude-Code packaging

kb already ships as a Claude Code plugin: .claude-plugin/plugin.json declares kb-memory v0.9.0 — three LLM-free hooks (UserPromptSubmit → recall, SessionStart → wake, Stop → capture), each just running a kb verb. No skills, no commands, no MCP server today.

kb has already weighed an MCP server — and rejected it. But read the scope carefully: memory/21-memory-mcp-and-memory-tool.html ("Approach B — dedicated kb CLI verbs") rejects MCP as a memory front-end, i.e. as a way to expose recall / remember:

"MCP server (kb mcp): a stdio server advertising recall/remember as typed tools — tool definitions cost context every session; it's a second process to run and supervise. Its only real edge — auto-fire — is largely recovered by a CLAUDE.md line + a recall hook." research/memory/21 §02 — Alternatives, weighed; verdict: "No MCP server enters the picture at any rung."

Two halves of that argument cut differently for our question:

  • The cost objection generalises. Any MCP server's tool schemas sit in the context window every session, used or not (doc 21 cites ~2.5k tokens for Anthropic's memory tool). An exploration server pays that too.
  • The "auto-fire is recoverable" objection does not. It only holds because recall has an unconditional UserPromptSubmit hook that injects memories before the model answers — strictly better than a tool the model must elect to call. There is no equivalent hook for "search the corpus mid-task" or "what's related to this." For those exploration verbs, the model electing to call is the mechanism, not a weakness — and doc 21 never evaluated them.

(a) Bundle kb-research / kb-comments plugins — do this first

plugin.json already supports skills + commands + MCP servers; kb-memory just doesn't use them yet. Two bundles made entirely of pieces that already work: kb-research (the existing kb-artifact authoring skill + the kb tools manifest, so an agent authors and indexes in one flow) and kb-comments (the kb comments export | claude round-trip + the kb comments watch SSE loop). The CLI surface exists today: commands/tools.rs, push.rs, comments_watch.rs. This is packaging, not new daemon code — zero risk, immediate leverage.

(b) An exploration-only MCP server — optional, eyes open

Everything an agent needs to explore kb is already reachable today through the Bash tool + the kb CLI (kb find / search / related / comments) — which is precisely doc 21's principle: the daemon you already run, driven by the tool Claude already has, at zero persistent context cost. An MCP server exposing search / get_artifact / related / list_open_comments is therefore an ergonomic upgrade, not a necessity: it trades a per-session schema cost for more reliable, typed, model-elected discovery. Recommend it only if that trade is worth it to the operator. Two non-negotiables if built: keep recall/remember as hooks (doc 21's verdict stands), and make the server a read-only client-side shim over the existing HTTP API (kb-cli/src/http.rs) so the daemon stays LLM-free and prompt-free. A thin kb mcp subcommand (JSON-RPC over stdio) is the whole implementation.

Net: the safe, high-leverage Claude-Code move is (a) — package what already works. The MCP server (b) is a real option doc 21 didn't evaluate, but it is not the slam-dunk the daemon's own design history might suggest; present the token-cost trade honestly rather than overselling it.

9Risks & invariants any design must respect

These are load-bearing. Breaking one surfaces as a subtle runtime failure, not a compile error.

  • Single-writer-per-kb storage actor (storage/actor.rs:1, 24). No plugin gets a second writer. In-process hooks write through the StorageHandle; subprocess / webhook plugins are read-only or go through the HTTP API (which funnels to the actor). A plugin opening lance directly corrupts the guarantee.
  • Embedding-dim-per-kb lock. The vector column width is fixed at kb open. An embedder plugin MUST declare its dim in the Ready handshake (embed_ipc.rs:25) matching the kb's column; a wrong-width row returns Err, never a panic, so one bad plugin can't kill the actor.
  • Fail-closed security stack. Auth / rate-limit / origin / loopback bypass must never sit behind a plugin; a missing ConnectInfo fails closed. This is why route-contribution is not a seam — expose capability via MCP (read-only) or the event bus instead.
  • Outbound prompt scrub. Export-bound bytes are scrubbed before any share backend sees them, so a subprocess share host physically cannot leak the <template id="kb-prompt">. A Tier-0 meta registry MUST skip <template>/<script>/<style> regions — the parser already does.
  • Atlas determinism (atlas.rs:26–32) — bit-identical across libc, achieved with only IEEE-754 primitives. A pluggable layout engine would have to re-prove that; keep layout a config enum.
  • Bounded event bus (ring + channel = 1024). A slow subscriber gets lag/gap frames, not daemon backpressure — by design. Plugins must tolerate gaps and resume via Last-Event-ID; never assume exactly-once.
  • No hot-reload. Config and corpora are discovered at daemon (re)start. Plugins load at restart too — set that expectation; don't promise hot-add.
  • Arrow / lance exact pin (=57.3.1) — the second reason dynamic .so plugins are out.
