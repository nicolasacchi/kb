Does recall order matter? The MR2 order probe and its null result (September 2026)

kb's per-prompt hook injects five recalled memories into every turn. The slate design called their order the one free lever nobody had measured, and made measuring it the precondition for flipping the default. So it was measured: 540 model calls over 30 frozen recall packs, three layouts and two models. The lever did not move — and the more useful finding is why the instrument could not have detected it if it had.

1. The question, and the rule that binds it

Every turn in every Claude, codex, Kimi and omp session on this box begins with a block that plugins/kb-memory/hooks/kb-recall.sh injects: five memories, ranked, each a title and (sometimes) a summary. It has looked essentially the same since v0.9. The kb slate design of record asked what that block spends its characters on, and made an uncomfortable observation: of every device available for making one of those five hits land harder — bigger text, grouping, emphasis, a superseded ghost line — exactly one costs nothing and had never been tested. Order.

So the design refused the other devices on the evidence and put order behind a measurement, with the rule stated in advance so it could not be negotiated afterwards:

The flip rule (design §11, binding)

KB_RECALL_LAYOUT's default flips from v2 to v2-last — the same block with the pack printed in reverse, so the top hit reads last — only on a ≥ 5-point win on every model that ran. Otherwise v2 stays.

Two things about that rule are worth naming. It is a pre-registration: the threshold, the direction and the models were fixed before a single call was made, so a 2-point wobble could not be talked into a decision. And it is asymmetric on purpose — the default does not move without evidence, because moving it costs a re-verified byte shape, a hook release and every downstream capture, while leaving it costs nothing.

The design was equally explicit about what the instrument is not: kb bench measures Recall@k, MRR and nDCG over artifact ids and cannot see model behaviour at all. It was not extended for this. A new harness was needed, and building it honestly turned out to be most of the work. The distinction is the same one the temporal-query design drew when it rejected recall --as-of: an instrument that cannot see the thing being claimed is not a weak instrument, it is the wrong one.

2. The instrument

plugins/kb-memory/bench/recall-order-probe.sh. The full design is in that directory's README.md; the load-bearing choices are these. It is a sibling of the corpus's other measured-rather-than-argued pieces — the search-quality bake-off and the memory-instrument bench — and follows the same rule: the threshold is written down before the numbers are.

The renderer is the hook itself

The probe does not re-implement the three layouts. It runs kb-recall.sh with a fake kb on PATH that serves a frozen pack, under each value of KB_RECALL_LAYOUT in turn. A probe with its own renderer measures its own renderer; this one measures the bytes that ship.

The packs are frozen

Thirty queries, each with the five hits kb recall --limit 5 --json returned for it on 2026-09-05, snapshotted into probe-queries.jsonl. Pulling live per run would have been closer to the design's sketch and would have made the whole experiment irreproducible: the questions are keyed to specific memories at specific ranks, and one kb remember anywhere on the box silently invalidates them.

The block sits where an injection sits

80,000 characters — roughly 20K tokens — of one captured session transcript's first <pre>, unedited, precede the block; the question follows it. That is the geometry of a real UserPromptSubmit injection: buried context, then the block, then the user's turn. Characters, not tokens, are the unit given here, for the same reason the slate refuses token-denominated budgets — the daemon links no tokenizer and Claude's is proprietary.

Hermeticity, which nearly went wrong

The confound that would have invalidated everything

This repo's own kb hooks fire on claude -p and codex exec. Left alone, every probe call would have had a real recall block injected into it by the very hook under test, on top of the synthetic one — five extra memories, chosen for the probe's own prompt text, in an order the probe did not control. The probe's model calls therefore run with KB_DAEMON_URL pointed at a dead port, KB_SESSIONS_DIR cleared and KB_BEAT=0, so every kb hook fails silently. This was verified by asking a model, under those settings, whether its context contained the string Relevant memories from kb. It answered NO.

The same settings keep the probe's 540 turns out of the sessions corpus and out of the live-session registry, which matters for a different reason: a probe that pollutes the corpus it samples from cannot be re-run.

Scoring, and what counts as a failure

Normalized exact match: case-folded, punctuation-stripped, whitespace-collapsed. A model that answers RATIFIED. is right; one that answers the word is ratified is wrong, and the prompt says so in as many words.

An empty answer is not a miss. The first full run turned up a codex call that returned nothing at all — a transport failure, not a wrong answer — and scoring it as a miss would have quietly penalised whichever model happened to be flakier that hour. That is precisely the confound this probe exists to avoid, so the harness now retries once and then records error: true; accuracy is computed over scored calls and the error count is reported beside it.

3. Two departures from the sketch, and why

The design sketched a question "answerable only from hit k's summary". Building it exposed two facts about the wire that made that shape impossible to execute honestly. Both departures are recorded here rather than in a footnote, because each one changes what the numbers mean.

The answer comes from the title, not the summary

A recall hit's summary is the artifact's <meta name="kb-summary">, passed through the wire verbatim. Two things follow. Most live memories have none — sampling this corpus, whole five-hit packs came back with zero summaries between them, so a summary-sourced question set would have had nothing to ask about for most queries. And more decisively: layout v2 renders no summary at all at ranks 4 and 5. That is the depth-by-rank cut, and it is the point of v2. A summary-sourced k=5 question would therefore have been unanswerable under two of the three layouts, and the resulting v1 "win" would have measured the cut, not the order.

A title is rendered byte-identically at every rank in all three layouts. Sourcing the answer there makes position the only variable — which is the one thing the probe exists to isolate.

A cloze, not a use-the-fact task

Each question shows hit k's title with one word blanked and asks for that word. This is the standard needle-in-a-haystack instrument, and it answers "does a line at position k get attended to". It does not answer "would the model act on that memory". Read the numbers as attention, not utility.

Two guards make the cloze mean something. The blanked word must occur exactly once across the whole pack — otherwise a model could answer from a different hit — and it must occur nowhere in the 20K-token filler, or it could be answered without reading the block at all. Both are re-checked on every run (--verify runs them alone), and answers were preferentially drawn from tokens carrying a digit or an internal capital — a commit sha, a version, a shouted RATIFIED — because those cannot be completed from world knowledge. 58 of the 90 answers are of that kind; the other 32 are ordinary words, and they set a guessing floor that applies equally to all three layouts.

4. Results

540 calls, 30 packs, three layouts, three target ranks, two lanes. Zero transport errors. The committed evidence is plugins/kb-memory/bench/run/results.jsonl (one line per call, with the model's raw normalized reply) and run/report.md; the 45-call proving run is in run-reduced/.

The second model is a second tier, not a second tokenizer

The design asked for two models "for a second tokenizer and model", and the harness was built for codex exec. On the day of the run codex answered every call with an empty string: "You've hit your usage limit for GPT-5.3-Codex-Spark… try again at Sep 9th", and no alternative model was available on a ChatGPT account. The second lane is therefore claude -p --model sonnet beside haiku — a genuinely different model with different capability, but the same family and tokenizer. The count of 540 is met; the tokenizer-diversity intent is not, and no conclusion here should be read as tokenizer-independent. The harness now probes each lane with a live call before running, so "installed, on PATH and out of quota" can never again masquerade as available.

On haiku the three layouts are indistinguishable and at the top of the scale — one miss in 270. On sonnet they are not, and v2-last is the worst of the three. Reading that as "reversing the order hurts retrieval" would be wrong, and the reason is the most interesting thing this run found.

Sonnet reads the injected block as a prompt injection

Of sonnet's 52 non-matching replies, 49 are not wrong answers at all. They are refusals — long, careful paragraphs that flag the prompt's own shape:

this message is structured oddly and i want to flag it before doing anything
else … at the very end — after all that transcript data styled to look like
its part of the kb recall system output — theres a plain-text instruction
asking me to fill in a blank … thats a classic prompt-injection pattern …
the memory index entry in question reads kb memory-instrument shipped +
tagged v035 on adf79c98 — so the blank would be adf79c98 but im not going to
treat a fill-in-the-blank extraction request that arrived this way as a
legitimate task

The model found the answer and declined to give it in the requested form. Scoring that as a positional miss would be nonsense. Only three of sonnet's 270 calls are genuine one-word misses; haiku has exactly one in 270, and the whole run recorded zero transport errors. Classifying purely by length — the prompt asks for one word, so a reply over five words did not comply — separates the two failures, and the classification is blind to layout by construction:

5. Verdict

Decision

KB_RECALL_LAYOUT stays v2. v2-last is not adopted. The pre-registered rule required a ≥ 5-point win over v2 on every model that ran. Measured deltas: haiku 0.0 points (100% vs 100%), sonnet −4.4 points (80.0% vs 75.6% on exact match), and with refusals separated out both lanes are flat. Neither model met the bar; one moved in the wrong direction. v2-last remains in the codebase as the harness's third arm and nothing else.

The claim this licenses is narrow and worth stating in the form it will be quoted in: at a 20K-token context with a five-hit block, on two Claude tiers, the rank at which a memory sits does not measurably change whether the model can read it back. Not "order never matters". Not "position is irrelevant to LLMs". The instrument saturated, and §7 says what that costs.

The finding nobody was looking for

Sonnet's refusal rate rises monotonically across the three layouts: 11 of 90 on v1, 16 on v2, 22 on v2-last (12.2% → 17.8% → 24.4%). Between the extremes that is a two-proportion z ≈ 2.1, p ≈ 0.03 — marginal, unpre-registered, one model, and exactly the kind of result that should be recorded and then left alone until someone tests it on purpose. Haiku refused zero times in 270.

The plausible reading, and it is a reading not a result: the terser the block, the more it looks like machine-generated context carrying an instruction rather than something a human typed — and v2-last is the most suspicious of all, because its reading order visibly contradicts the pos= numbers in its own markers. A model asking "why is the thing labelled pos=1 printed last?" is not being paranoid.

Why this probably overstates the production risk — and where it might not

The probe delivers the block as raw prompt text. In a real Claude or codex session it arrives as hookSpecificOutput.additionalContext, which the harness frames as system-supplied context, not as something the user pasted. Most of this refusal rate is likely an artifact of the probe's delivery channel. But not all of it: KB_HOOK_FMT=kimi prints the block bare on stdout, which is precisely the channel measured here. If a Kimi session ever refuses a turn while quoting its own recall block back, this table is where that behaviour was first seen, and v1 is the layout it happened least under.

No action is taken on it. It is one model, one channel, a marginal p, and the mitigation would be a wording change to a block whose bytes were just re-verified — precisely the sort of unmeasured tinkering the design's §11 refusals exist to prevent. It is recorded here so the next person to see it recognises it.

6. What shipped anyway (MR1)

The verdict above concerns order only. The rest of the recall-line track (MR1) never depended on the probe, and it landed in the same commit. Those are byte and schema facts, and they are tested rather than argued.

Layout v2 is the default

Relevant memories from kb (recall — these persist across sessions):
- demo-repo build cache setup  [kb]
    ↳ installed 2026-08-01; measured a modest speedup of roughly 15% (not the hoped-for 60%) …
<!--kb-recall/1 kb=kb id=a1b2c3d4e5f6 pos=1-->
- ⚠ disputed: Wrong port for the staging service  [main] [⚠ 1 drift-flagged citation(s)]
    ↳ the staging service binds 127.0.0.1:9000 in the demo env and a spare port everywhere else …
<!--kb-recall/1 kb=main id=0f0f0f0f0f0f pos=2-->

The (id …, read 42% — stopped at §3) parenthetical is gone: the id appeared twice and now has one home, the marker; the reading percentage was noise on a one-liner and remains available through kb memory expand. Depth is by rank — ranks 1–2 keep up to 320 summary characters, rank 3 up to 200, ranks 4–5 the title alone. On the shared five-hit fixture the block is 1,349 bytes against v1's 1,772, a 24% cut, while rank 1's summary is rendered past the 220 characters v1 truncated it at. test-recall-layout.sh asserts v2 ≤ v1 on that fixture, and layout v1 is diffed byte-for-byte against a baseline captured from the unmodified hook before any of this was written.

The budget claim, stated honestly

v2 ≤ v1 is a property of that fixture, not a universal bound. A pack whose top two hits carry 320-character summaries while ranks 4–5 carry none has nothing left to cut in exchange, and v2 would be the larger of the two. The test asserts the property on a realistic pack rather than claiming a bound the layout cannot have.

The marker grammar widened, and that was not cosmetic

parse_recall_marker split the marker body once on " id=". That grammar would have rejected layout v2's own pos= marker outright — every hit falling through to the free-text fallback, which v2 also breaks by deleting the (id …) anchor it keys on, and the memory_recalls ledger silently going to zero the day v2 shipped, with only DerivedRecalls.failed as the tripwire. The body is now an unordered whitespace-separated bag of key=value pairs: kb and a 12-hex id required, pos optional in 1..=99, and unknown pairs ignored so a future hook can add one without a kb-core release landing first. A malformed id is the single fatal defect — it is the row's identity. A malformed pos degrades to "rank unknown" and never costs the row.

The pos column, and why it can never be scored

memory_recalls gains a nullable pos INTEGER (V0040, ALTER-only), written from the marker's pos= pair and from nothing else, surfaced on GET …/recalled-by and GET /api/sessions/{sid}/recalls and printed by kb memory recalled-by as a [#N] marker. It joins invariant #10's surfaced-never-scored lane for a sharper reason than its neighbours: a ledger column recording where the ranker put a memory, if any scoring path could read it, would close a loop in which today's ranking is evidence for tomorrow's.

NULL is a first-class value. A pre-MR1 capture, a fallback-only parse and an out-of-range pos all read as "rank unknown", and nothing infers a rank from the hit's position in the transcript — under v2-last those two disagree by construction, and no capture records which layout produced it. The [#N] marker is omitted rather than printed as [#?]: to a reader, an unknown rank and a rank of nothing look the same, and the honest rendering is silence.

7. The ceiling: what this does not license

A null result from a saturated instrument is worth exactly one sentence of generalisation, and it is not "order does not matter". It is: at this difficulty, order does not matter. Everything else the reader might want to conclude is unlicensed, and the reason is worth being precise about.

A cloze over a distinctive token, in a 20K-token context, with the target block sitting immediately before the question, is an easy task for a 2026 frontier model — easy enough that both models solved essentially all of it regardless of where in the block the target sat. When two conditions both score at the top of the scale, the difference between them is unmeasurable by construction; no amount of additional n at the same difficulty changes that. Running the 540 calls was still worth doing, for two reasons: it converts "we assume order does not matter" into "we measured it and it did not, at n=540", and it proves the harness end to end, which is the reusable asset.

What a future run must change

Re-running this probe unchanged will reproduce the ceiling and measure nothing. To have resolving power it must move the task off the top of the scale — a longer filler (100K+ tokens, where positional effects are documented to appear), more hits per pack than five, a smaller/cheaper model tier, a question requiring two hits to be combined, or an adversarial pack in which a plausible wrong answer sits at a different rank. Any of those is a new instrument and needs its own pre-registered threshold; none of them is a reason to re-open the flip rule on the old evidence.

There is a second, quieter limit. The probe measures attention — whether a line at rank k can be read back — and not utility, whether the model would have used that memory to do something differently. Utility is what the design actually cares about, and nothing here measures it. That gap is not fixable by tuning this harness; it needs a different experiment, and kb's no-in-daemon-LLM boundary means any judge for it lives in the agent layer.

8. Reusing the harness

The harness outlives its verdict. It is resumable by construction — one results.jsonl line per call, keyed <query_id>|<layout>|<k>|<model>, and a key already present is skipped — so a killed run resumes where it stopped, and a second model can be added to a completed run without re-paying for the first.

./recall-order-probe.sh --verify        # input invariants only, no model calls
./recall-order-probe.sh --reduced       # 5 packs × 3 layouts × 3 k × 1 model = 45
./recall-order-probe.sh                 # 30 × 3 × 3 × 2 = 540
./recall-order-probe.sh --report-only   # rebuild report.md from results.jsonl

It waits when /proc/pressure/io's full avg10 is at or above PROBE_IO_CEILING (default 40), because this box is IO-bound on spinning RAID5 and other sessions build on it. The runs reported here were taken with that ceiling raised to 85, and the reason is recorded rather than hidden: the probe issues HTTP calls and appends one JSONL line per result, so its own disk footprint is negligible, and the default ceiling exists to keep the harness from piling onto a build. With self-hosted CI runners holding the box at full avg10 ≈ 40 for hours, the default would have converted a courtesy into an indefinite stall without reducing contention at all.

The design names one further use: pointed at a slate digest fixture, this same harness is the gate for any change to the slate's section order or its echo line (decision D24). Whoever takes that on should read §7 first. The needle-in-a-haystack literature this borrows its shape from is summarised at LLMTest_NeedleInAHaystack; the ceiling described in §7 is the same one that work reports for short contexts.
