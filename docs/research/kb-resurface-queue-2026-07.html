A resurfacing queue for kb — pull-only, explainable, and it forgets

kb's library is write-only after first read. This designs the fix — a deterministic kb resurface ranked by open comments, unfinished reads, and (later) importance — plus the anti-feature analysis of why resurfacing queues are universally annoying and how this one structurally can't be. The thin slice is implemented.

2026-07-06 · status:open · project:kb · resurface

The brief, and what's already ruled

This answers recipe F5 from the next-prompts playbook. The idea has prior standing: the architecture review (private) formally ruled resurfacing accept-in-principle — "the frontier is synthesis and resurfacing on rails already laid" — proposing importance × attention-staleness over edges + history + reading, with the recorded risk: "Could nag — cap to top-2, dismissible, opt-in per kb." The improvement portfolio roadmapped it at effort M. Nothing was ever built (grep: no resurface/spaced/today surface in code).

One correction to the brief itself: it asks for "--explain like recollect's" — but kb recollect has no --explain flag (clap definition at crates/kb-cli/src/main.rs:180-203). What recollect actually established is better: a house style where every hit always carries its signals inline (score, age_days, stale, error_count — surfaced, never silently filtered), scoring constants are named and doc-commented (RECOLLECT_RANK_K = 60, 365-day recency half-life, 180-day stale threshold), and behavior is golden-tested ("recency is gentle, not dominant" pins a 1-year-old hit to ~half weight). kb resurface follows that style: reasons are always printed; --explain additionally prints the per-term arithmetic.

Anti-feature analysis — why resurfacing queues are annoying

Every mainstream resurfacing system (inbox-zero apps, spaced-repetition decks, "your daily review" features) converges on the same pathologies, because they optimize for engagement rather than the reader:

PathologyMechanism of harmThis design's structural counter
Streak mechanicsManufactured obligation: the tool invents a daily debt, then punishes lapses. The queue becomes about the streak, not the content.No time-boxed anything. The queue has no concept of "today", no history of whether you looked at it, no reward for looking.
Guilt accumulationUnbounded counters that only grow ("247 unread"). Abandonment becomes visible debt; the rational response is to stop opening the app.The queue forgets. Unfinished reads decay with a 45-day half-life and fall off entirely below a score floor (~90 idle days for a half-read artifact). Only explicit, resolvable debt (open comments) persists — and that set is bounded and closable.
Push interruptionNotifications convert a library into a demand stream.Pull-only, like everything in kb. The queue exists only where you already chose to look: the gallery you opened, the CLI verb you ran. Zero push paths exist to misuse.
Chrome badgesA persistent red dot is a notification you can't dismiss — ambient guilt on every glance.No count anywhere in persistent chrome, ever. The strip renders inline in the gallery body, shows at most 2 items, and renders nothing when empty — no "all caught up!" celebration either (gamified emptiness is the same mechanic inverted).
Algorithmic opacity"For you" ranking you can't interrogate breeds distrust; you can't tell signal from manipulation.Deterministic arithmetic on two named constants, reasons on every item, --explain prints the exact formula. Same inputs + same clock → same queue, reproducible in a test.
Queue-tending as a chore"Mark done / snooze / archive" adds a second inbox to manage — state about state.Stateless. There are no queue rows. Acting on the underlying object clears the item naturally: resolve the comment, finish (or let time fade) the read. The only dismiss is a per-tab sessionStorage hide of the strip — no server ever knows.
The invariant behind all sixThe queue is a view over existing state, never state of its own. That single property makes streaks, badges, accumulation, and queue-tending impossible to add without first violating the design — which is exactly the kind of structural refusal kb's non-goals list exists for.

The full score design — five signal families

The general shape: score(artifact) = Σ wi · termi, every term in [0,1], every term computed from stored rows plus an injected now_unix (the recollect/rerank pattern — one clock parameter, pure function behind it). Per family, the source, the gap, and the verdict:

Open comments thin slice

Source: the kb-comments/1 review store. Enumeration exists: the fleet inbox (GET /api/inbox) already walks .review/ dirs keeping status == open (crates/kb-server/src/routes/inbox.rs:136-213); comments carry created_at and deliberately no resolved_at (resolve is a status flip, review.rs:719-724). Term: min(open_count, 4)/4 — piecewise-linear, saturating, trivially explainable. No decay: an unresolved comment is explicit, human-created, resolvable debt; letting it fade would silently drop a promise. The oldest-open age appears in the reason string but not the score (surfaced, not scored — the recollect precedent). Cost: one dir walk per request (the known-blocking, N+1 walk on main; the resurface route bounds the per-doc lookups to the truncated result, and the perf-sweep branch's memoized walk supersedes this wholesale when it merges).

Unfinished reads thin slice

Source: reading_rollup (crates/kb-core/src/storage/sqlite.rs:812-901) — one indexed window-function pass over history yielding every artifact's newest open visit + completion_pct + derived state; InProgress (opened, <95% complete, no override) is exactly the unfinished set. The search route already exposes this as a facet (read=in_progress&sort=progress), so resurfacing adds scoring and composition, not capability. Term: (completion_pct/100) · 0.5^(idle_days/45) — progress-weighted (endowed effort: the 70%-read design doc you were interrupted in outranks the 10% skim you abandoned on purpose) times a 45-day half-life on idleness. The decay is the anti-guilt mechanism, not an accident. Bonus reason string: "~N min left" = word_count · (1 − completion/100) / 220wpm — progress-aware remaining time is new (lists' remaining_minutes counts each unfinished entry's full estimate; EST_WORDS_PER_MINUTE = 220, lists.rs:41-51).

List membership phase 2

An artifact sitting unread in a reading list is a deliberate queue signal (someone put it there). But lists already own a continuation surface — continueTarget / the QueueBar / "Continue reading" on ListCard — and the resurface queue must not duplicate a working affordance. Phase 2, if wanted: a small additive term for "in a list, state Unread/InProgress", sourced from list_entries + the same derived read state, with the list name in the reason string. Deferred until the thin slice proves retention.

Importance (backlinks) phase 2

The architecture review's proposed axis: inbound edges (backlinks_of, invariant #29) as an importance multiplier, so a hub document with five backlinks outranks a leaf note at equal attention-debt. Cheap (edges table), deterministic, explainable ("5 backlinks"). Deferred only for thinness: multipliers interact with weights, and tuning two constants on real use beats tuning four on guesses.

Memory salience + decay not this queue

Memories already have a deterministic attention economy: recall's rel × salience × exp(−k·age) with supersede/forget drops (invariant #10). Re-ranking them here would create a second, disagreeing authority over the same rows. The right surface for "memories needing attention" is the roadmap's memory hygiene view (tombstoned / superseded / near-floor listing) — a triage view, not a reading queue. Resurface excludes memory-* categories outright (they're also excluded from snapshots and default search for the same reason: different lifecycle).

Artifact age vs subject's git activity reject

The idea: a design doc whose subject files kept changing after it was written is stale and worth re-reading. Three defeaters, in code: (1) prod has no git — the container ships without .git, so the versions façade falls back to snapshots there; a headline signal that silently vanishes in the primary deployment is a trap. (2) Artifact→subject mapping is guesswork — session_files from the producing session, or paths mentioned in the body, are heuristics; a scoring term whose input is a guess breaks the explainability contract even when the arithmetic is exact ("your doc is stale because we think it's about indexer.rs" is not an explanation, it's an assertion). (3) Cost: git is shelled per-request with no server-side cache. The honest version of this need is the temporal surface's kb diff --between (already designed) — pull the diff when you suspect staleness, not a scored guess pushed at you.

The thin slice, specified and implemented

Per the brief — and the field data agrees — "commented but never resolved + unfinished reads" is the value core: both are things you did (wrote a comment, started reading) that point back at a specific artifact with a specific next action. Implemented on branch feat/resurface-thin-slice (worktree, isolated from the in-flight v0.24 tree).

Score

score = 0.6 · min(open_comments, 4)/4
      + 0.4 · (completion_pct/100) · 0.5^(idle_days/45)

idle_days = (now_unix − last_opened_unix)/86400
floor: items with score < 0.05 are dropped (the queue forgets)
order: score desc, then artifact_id asc (total, deterministic)

Constants are named and doc-commented in kb_core::resurface (COMMENT_WEIGHT, READ_WEIGHT, COMMENT_SATURATION, READ_HALFLIFE_DAYS, SCORE_FLOOR) — the recollect pattern. Golden tests pin: determinism, the 45-day half-life ratio, comment saturation at 4, the floor fade-out horizon, comment-debt-beats-decayed-read ordering, and the id tie-break.

Surfaces

  • HTTP: GET /api/kb/{kb}/resurface?limit= (default 8, clamp 1–50; per-kb only — fleet scope deferred; when wanted it must ride buffered_join per invariant #28). Response: { items, now_unix }; each item carries id, title, source_rel, score, both terms, the raw signals (open_comments, oldest_open_unix, completion_pct, last_opened_unix, est_min_left), and server-built reason strings — one wire truth for CLI and SPA. ts-rs types regenerated (just types), route table regenerated (just api-docs) — both are CI drift-guards.
  • CLI: kb resurface [--kb] [--limit] [--explain] [--json]. Reasons always print (house style); --explain adds the arithmetic line per item, e.g. score = 0.6·2/4 + 0.4·(0.62·0.5^(5/45)) = 0.300 + 0.229 = 0.529.
  • SPA: a gallery strip (template: the sessions strip, .gallery-sessions-strip in chrome.css:1247) showing the top 2 items with their first reason, linking into the reader. Gated like the sessions strip (only on the unfiltered gallery), renders nothing when empty, per-tab dismissible (sessionStorage only). Not reader chrome — invariant #30 untouched. Hook useResurface is a bare TanStack query (staleTime: Infinity, zero fetch plumbing); the SSE bridge maps comments.updated and history.recorded → invalidate ["resurface"] (invariant #23; reading-progress beacons have no SSE by design — #19 — so the read term refreshes on the next natural invalidation, which is correct for a calm surface).

Verification

  • Golden tests on the pure scoring module (six behaviors above).
  • Route test: seeded history + review file → expected order, floor, and reason strings.
  • cargo fmt + workspace clippy (excl. kb-embedder) + kb-core/kb-server/kb-cli test suites + just types-check + just api-docs-check + SPA typecheck + vite build.
  • Deterministic by construction: the route computes now_unix once and threads it; tests pass a fixed clock.

Standing rejections (the never-list)

  • Streaks, daily goals, review targets — never. They invert the tool's loyalty.
  • Unread/queue counts in persistent chrome (header, favicon, tab title) — never. The existing header inbox pill is an inbox (explicit debt you created); resurface adds no second badge.
  • Push/notifications/scheduled digests — never in-daemon. If the operator ever wants a weekly nudge, that's the agent layer's job (a cron running kb resurface --json), outside kb — same boundary as the no-in-daemon-LLM non-goal.
  • Server-side dismiss/snooze state — rejected; it's the second-inbox trap. The strip's sessionStorage hide is deliberately ephemeral.
  • Git-activity staleness term — rejected above; the pull-shaped answer is kb diff --between.
  • Memory re-ranking in this queue — rejected above; belongs to the memory hygiene view.

Open questions

  • The weights (0.6/0.4) and half-life (45d) are reasoned guesses; a month of real use should tune them. They're single named constants — retuning is a one-line diff plus a golden-test update.
  • Arch review suggested "opt-in per kb". The strip self-gates on having items and the verb is pull-only — is a config knob solving a problem anyone has? Leaning no until asked.
  • Phase 2 ordering: importance multiplier (backlinks) vs list-membership term — importance first, it's cheaper and benefits every item.
