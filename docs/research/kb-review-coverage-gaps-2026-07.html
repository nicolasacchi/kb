What kb's 50 review sessions never covered — coverage-gap analysis (2026-07)

2026-07-06 · ultracode workflow wf_003e4eef (11 agents: 7 sonnet mappers, 3 opus gap analysts, 1 opus critic; 670k subagent tokens, 169 tool calls) · companion to the session-memory deep review

Verdict

kb has been reviewed a lot — but along a narrow set of axes. Since 2026-06-05 there have been dedicated security, architecture, performance, agent-experience, code-craft, and web-UI reviews. What the history shows instead is two systemic failure modes and a set of never-touched surfaces:

  • A research-to-implementation gap. 8 of the 50 sessions are research-only, and they cluster in the last four days: five July reviews produced 10+ verified-findings documents, of which only one slice (the v0.24 plan's first two commits) has landed. The July 2026 security review explicitly says remediation was deferred — and no fix commits followed while kb.example.com is publicly bound.
  • Follow-through debt. 24 explicitly-deferred or left-broken items across the 50 sessions, including a 5-commit perf branch (perf/sweep-2026-07) stranded off main in violation of the repo's own no-long-lived-branch cadence, and a ~900-line uncommitted delete-cascade engine sitting in the working tree right now.
  • Whole quality dimensions never run. No accessibility audit, no backup/restore drill, no schema-migration story, no PII audit of what session capture indexes, no release rehearsal, no scalability ceiling, no chaos testing. These are exactly the dimensions that would embarrass an open-source launch — and Release Zero is the stated next act.

Method and limits

Seven sonnet agents classified the 50 most recent kb-folder sessions (titles, first prompts, and kb sessions show enrichment) into covered-topic tags, an outcome, and explicitly-unfinished items; one enumerated the reviewable universe (69 areas from CLAUDE.md, the crate layout, docs/, justfile, workflows); one censused all 111 existing deliverables in docs/research/ and ~/project/research. Three opus analysts then hunted gaps through three frames — subsystem, quality-dimension, follow-through — each gap requiring cited evidence of absence (30 candidates). An opus critic spot-checked candidates against the repo (git log, branch lists, workflow files), killed duplicates and false gaps, and ranked the 20 survivors.

Known blind spot The sessions list API silently caps at 50 rows with no pagination (80 sessions exist for this folder — itself finding B15 of the companion review). The oldest ~30 sessions, pre-2026-06-05, are the foundational build era; gaps were only claimed where the repo itself (docs, git history, branch list) corroborated absence, not just the truncated session list.

Reading the pattern

Three structural observations sit above any single gap:

  • Reviews are cheap now; rulings are the bottleneck. Ultracode made producing a 50 KB verified review a two-hour affair, so five accumulated in four days. The scarce resource is the accept/defer/reject decision that converts findings into either commits or recorded refusals. A standing rule — no new review session while an untriaged review exists — would have prevented most of the current pile-up.
  • The repo's own memory system under-records exactly these sessions. The five July review sessions are the ones with digest blind spots (multi-agent work invisible — see the companion deep review), which is why this gap analysis needed raw-transcript archaeology rather than kb recollect.
  • Everything in the "pre-OSS" tier shares one property: it is work whose absence is invisible to the sole author-operator but immediately visible to a stranger — restore drills, migrations, a11y, first-run, SECURITY.md. That tier is effectively the definition of "productization" left after Release Zero's packaging work.
