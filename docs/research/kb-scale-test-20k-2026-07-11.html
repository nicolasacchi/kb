20k-doc full-stack scale test: what actually breaks

The only scale benchmark kb had before this was atlas UMAP/k-means at ≤5,000 synthetic artifacts. Gallery/facets scans, sqlite side-stores, backup, and index/reconcile had never been measured at scale, and a separate piece of storage-consolidation research asserts a ~50k-doc migration trigger with no measurement behind it. This report measures the daemon against a real 20,000-doc synthetic corpus, on real (shared, noisy) hardware, and reports exactly what held up and what didn't — including several findings that surprised us.

kb 0.22-68-ga8dd891f waves/gap-closure-2026-07 BM25-only 8-core / 62GiB host
Headline A cold bulk index of a large pre-existing corpus is the real cliff, not the read path. Ingest throughput fell from 1.73 docs/s to 0.36 docs/s within the first ~1,500 docs of one continuous run, and a restart mid-backlog fell further to ~0.05 docs/s — roughly 30× slower than the fresh start. We could not complete a full 20k cold index inside this test's time budget. Root cause: one Lance fragment + manifest commit per document upsert, with no batching across the ingest queue, even under a multi-thousand-document backlog.

fixed 2026-07-12 Both halves of this headline are now resolved on HEAD: the per-doc-commit cold-index cliff by drain-batched upserts (GC-B7, 2026-07-11) and the restart-with-backlog stall by the dedup-heal fix (SC1, 2026-07-12) — a full 20,000-doc restart drain now completes in 269.1s (~68 docs/s). See Restart & reconcile.

Method

Binary: the shared --profile fast build at ~/project/kb/target/fast/kb (target dir is symlinked into the kb-waves worktree), rebuilt fresh and confirmed at kb 0.22-68-ga8dd891f, exactly matching the worktree's HEAD commit a8dd891f at test time (binary mtime after the commit timestamp).

Lab at /tmp/kb-scale-lab, scratch KB_HOME, one [kb.scale] corpus. The generator (kb synth exists in-tree for this exact purpose, but its output lacks kb-category, <h2> sections, and cross-references, so we wrote a small deterministic Python generator instead — seed 20260711, reproducible byte-for-byte):

  • 20,000 single-file HTML artifacts across an 18-folder, 2-level hierarchy (changelog/2025, changelog/2026, ideas, incidents/{active,resolved}, pm/{initiatives,retros}, guides/{setup,advanced}, docs/{api,ops}, features, runbooks, decisions, research/{spikes,landscape}, postmortems, design-reviews), weighted realistically.
  • Real <title>/<h1>/<h2 id="sec-…"> structure (2-27 sections per doc), kb-tags drawn from a 40-term zipfian pool (rank-1 tag ~40× more likely than rank-40), kb-category from a 13-value vocabulary.
  • ~10% of docs (1,962 measured) carry one relative <a href> cross-reference to another generated doc, to exercise the edge-record hook / backlink graph the same way real internal links do.
  • mtimes spread over ~450 days back from generation time, for facet from/to testing.
  • Size distribution (n=20,000): min 2,052B · p50 4,795B · p90 18,289B · p95 28,099B · p99 55,226B · max 68,838B · mean 8,127B. Total corpus: 193MB on disk. Generation took 2.6s.

Embeddings were deliberately out of scope per the task brief. [defaults] disable_embedder_fallback = true with no embedding_model anywhere in kb.toml resolves every kb to None (kb_core::config::KbConfig::resolved_embedding_model), and the daemon log confirms it: kb opened: no embedding model configured (semantic/hybrid disabled). Every number below is BM25-only; hybrid/semantic search and atlas layout quality are untested here by design.

Host caveat — read every number with this in mind This is a shared dev box, not an isolated bench rig: a 4-core desktop-class box with 64 GiB RAM, 31GiB swap already ~30GiB in use before this test started from unrelated processes (Docker, netdata, several other Claude Code sessions, a VPN container), with unrelated background load. uptime load-average samples taken through the run: 5.43 → 16.87 → 24.83 → 17.32 → 6.22 → 10.96 — a 4-core box repeatedly running well above its core count. Every timing below is noisy as a result. Where it matters, we ran the same measurement 3 times and report the spread, and where a finding could plausibly be host noise instead of a real architectural effect, we say so explicitly and note what evidence rules it out (see Restart / reconcile).

Cold index: throughput decelerates, hard

The main attempt pointed the daemon at all 20,000 files and let it cold-index continuously. It reached 1,619 docs in 1,222s (20.4 minutes) before we stopped it — not because we ran out of patience arbitrarily, but because the rate had already collapsed to the point where finishing was no longer a same-session proposition. Windowed throughput (10-sample rolling windows over the run's own progress log):

1,291 → 1,462209.0s0.82
1,462 → 1,541219.0s0.36

A naive linear extrapolation from the best observed rate (1.73 docs/s) puts a full 20k index at ~3.2 hours. Given the visible deceleration, that number is an underestimate, not an estimate — we report the trend rather than inventing a false point figure. RSS grew alongside it, from a ~140MB idle baseline to a peak 1.48GB (VmHWM 1,482,604KB) at 1,619 docs — call it roughly 800KB-1MB per doc in the observed window, though growth itself slowed as the rate slowed.

To separate "the whole host is just busy" from "the kb corpus is the problem," we ran 3 clean, isolated cold-index reps of a 500-doc subset of the same corpus, each against a freshly emptied state directory (no backlog, no prior fragmentation):

Mean 81.9s, spread 76.3-88.2s (~15% of the mean) — that's the host-noise band. But the mean rate, ~6.1 docs/s, is 3-17× faster than the main run's rate at similar-or-lower doc counts, measured in overlapping wall-clock windows on the same contended host. Host noise alone does not explain a persistent multi-fold gap between "500 docs in one shot" and "the same corpus past ~1,000 docs in a continuous run." The corpus's own growth is doing this.

Root cause, read from source: the ingest consumer calls the storage layer's singular upsert one document at a time —

// crates/kb-core/src/indexer.rs:1441
if let Err(e) = storage.upsert_doc(doc).await {

— with no batching across the mpsc queue, even when thousands of items are already pending. A batched API already exists one layer down and is unused by this path:

// crates/kb-core/src/storage/lance.rs:588
pub async fn upsert_docs(&self, docs: &[Doc]) -> Result<()> {

Each singular upsert commits its own Lance fragment and manifest version. kb's own compact command help text already names this exact mechanism: "each upsert commits a fragment + manifest, so thousands of small writes shred the dataset." That line was written before this test; this test is the first measurement of how much it costs at five figures of documents.

fixed 6c9baa38 2026-07-11 (GC-B7) The batching fix landed the same day this report was filed: the ingest loop now drains up to 32 pending same-kind items (8MB byte budget) from the mpsc into one storage.upsert_docs merge-insert commit (indexer.rs). The commit's own scratch before/after benchmark (git-stashed old code vs new, 500 synthetic docs, no embedder — isolating pure commit overhead) measured 145.1s → 0.53s per 500 docs (3.45 → 943.6 docs/s). The deceleration curve above is the historical pre-fix record; Recommendation #6 — re-running this harness to completion at 20k/50k — is the live follow-up.

Restart & reconcile: fast when idle, a real stall with a backlog

Two very different restart stories, both measured directly:

Good news — idle restart is flat Killing and restarting the daemon against an already-fully-indexed 500-doc corpus (no backlog) served doc_count=500 via /api/stats in 0.74s — the daemon just reopens the existing Lance/sqlite state, it doesn't re-walk or re-embed anything. Restarting the larger, partially-indexed corpus (1,621 of 20,000 docs already indexed) reported stats in 3.06s. Restart cost for an idle or fully-caught-up kb does not scale with total corpus size in any way that matters.
Bad news — restart with a large backlog can stall for minutes The SAME restart, with ~18,379 not-yet-discovered files still sitting in the source directory, made zero visible ingestion progress for over 7.5 minutes (the scheduled reconciliation pass never logged "complete" once in that window), then advanced by only 24 docs (1,621 → 1,645) by the time we stopped watching — an effective ~0.053 docs/s, about 30× slower than the fresh cold-index rate. The process was not hung: it held ~100-157% CPU throughout and RSS grew (882MB → 912MB over 15s), so it was doing real work, just not work that resulted in queryable docs. Critically, this happened while the host's own load average was falling (from ~17-25 down to 6-11) — ruling out "the host got busier" as the explanation. We did not isolate the exact root cause inside this session's budget (candidates: an unindexed O(n²) new-vs-known diff, unbounded candidate-list construction for the corpus's cross-reference resolution across the whole undiffed backlog, or a full-table scan per candidate) — see Recommendations.
Resolved 2026-07-12 (SC1) — root-caused and fixed

fixed 87dcb0d5 2026-07-12 (SC1) A dedicated follow-up (Recommendation #2, re-run in /var/tmp/kb-scale-lab) root-caused this to a single line, and it was none of the O(n²) candidates guessed above. The indexer's dedup pre-gate (process_ingest_batch, crates/kb-core/src/indexer.rs) called storage.touch_mtime unconditionally on every dedup-skip — never comparing the on-disk mtime against the stored one. LanceStore::touch_mtime is a table.update().only_if(id=X): a full artifacts-table scan (every fragment, all columns including body/html/raw) that rewrites one row into a fresh one-row fragment + one manifest commit, serialized on the single-writer storage actor ahead of the real UpsertDocs batches. Every duplicate emission of an already-indexed unchanged file fired one, and three feeders emit duplicates in bulk: the watcher's initial_walk re-emits the WHOLE corpus on every restart (no mtime map); the periodic reconcile re-emits every not-yet-indexed file, so any backlog outliving one reconcile_secs interval storms mid-drain; and the inotify-overflow rescan walks with no mtime map ("the content-hash pre-gate keeps it cheap" — that comment was the bug). Touch cost grows with fragment count, which the touches themselves inflate → O(N·(F₀+N)) quadratic. A scratch build with the heal removed drained the same 18,379-doc backlog in ~646s — causal proof it was the stall.

The fix makes the heal conditional: the dedup cache now carries the stored mtime beside the content hash (the list_content_hashes projection was extended), and the heal fires only when disk ≠ stored — so duplicate emissions (equal mtime) are write-free, while a genuine git checkout-style touch still heals exactly once and teaches the cache the new value. Secondary: initial_walk now takes a known-mtimes map (the reconcile G5 projection, fetched once in bring_up_kb), so a restart emits only new/changed files instead of re-hashing the whole corpus. A third bug surfaced alongside (lab flag a): periodic auto-compact rode the reconcile loop as a tail call, so reconcile_secs=0 silently disabled it AND a bulk drain blocked the reconcile emission for the entire backlog — zero compaction passes across a 20k drain, 625+ fragments at completion. It now runs on its own always-on ticker.

Re-measured 2026-07-12 (same 20,000-doc corpus, BM25-only, same shared host): the identical restart-with-18,379-doc-backlog scenario now drains to 20,000 docs in 269.1s (~68 docs/s) — against 10,725/20,000 still crawling at ~1 doc/s when the pre-fix run was killed at t=854s. Manifest versions now grow ~linearly with the batch-commit cadence (56 → 900, not the pre-fix 269 → 1,994 per-touch storm); five sub-second periodic auto-compact passes fire during the drain (fragments held ≤~217, collapsed to 1 each pass, old_versions_removed finally non-zero); and post-drain reconcile passes settle at ~250ms. An idle restart of the fully-indexed 20k corpus is likewise flat: manifest count pinned, CPU bleeding from process-startup ~42% down to ~3% over 240s with zero UPDATE commits — the pre-fix ~240% CPU / +543-manifests-in-150s idle storm is gone. Regression tests (restart_reemission_of_unchanged_corpus_adds_zero_lance_commits, touched_but_unchanged_file_heals_mtime_exactly_once) pin both halves in kb-core.

Separately, at small scale (500 docs), reconcile itself is exactly as advertised most of the time: three consecutive periodic passes logged elapsed_ms of 44, 4, and 3 — "near-free" as the docs promise. But we also caught one pass, sandwiched between two restarts, that silently re-touched all 500 rows (see next section) despite logging deletes=0 — worth flagging even though it didn't recur in the passes we watched afterward.

Storage: fragmentation, disk blowup, and compaction's blind spot

The main run's state directory was 319MB for 1,619 docs, against ~15.6MB of raw source HTML for that same subset (1,619/20,000 × 193MB) — a ~20× blowup, directly attributable to the one-fragment-per-doc-commit mechanism above.

We caught the fragment/version churn directly in the daemon's own auto-compact diagnostics. On the 500-doc corpus, a reconcile pass logged files=500 deletes=0 (i.e. "nothing changed"), and was immediately followed by:

auto-compact: dataset fragmented, optimizing kb=scale500 trigger="periodic" rows=500 fragments=500 small_fragments=500 versions=1823
auto-compact: done kb=scale500 trigger="periodic" ms=1665 fragments_removed=500 fragments_added=2 old_versions_removed=0

Versions had been at 1,320 barely a minute earlier (right after the prior startup compact) — so roughly 500 new manifest versions, one per existing doc, were committed during a reconcile pass that reported zero real content changes. We watched three subsequent periodic passes and none repeated this (each logged 3-4ms, no auto-compact fired) — so this looks like a one-time event tied to the two rapid, interrupted restarts that preceded it, not a permanent per-cycle tax, but it demonstrates the mechanism is real and reachable.

Auto-compact itself is a genuine bright spot: fast and effective at the logical level every time we saw it fire —

triggerbefore → after (fragments)time
startup (500-doc corpus)141 → 2793ms
periodic (500-doc corpus)500 → 21,665ms
manual kb compact (main, 1,621 docs)235 → 23,702ms

But it has a blind spot: every single compaction we observed reported old_versions_removed=0 (0 bytes freed), and a raw filesystem count of data/*.lance fragment files stayed far above the logical fragment count after compaction (1,808 physical files on disk vs. ~2 logical fragments for the 500-doc corpus at one point). Old fragment and manifest-version files are retained on disk even after compaction merges them away logically — physical disk usage for a heavily-reindexed kb can keep growing under routine operation even with compaction running on schedule, unless a longer-horizon vacuum/prune is also exercised (we did not find one fire in this test).

Read endpoints: mostly flat, one real cliff

All figures are p50/p95 over 20 samples via timed curl loops (hyperfine wasn't installed on this host; a controlled bash loop was the fallback). Two very different regimes: idle (the fully-indexed, auto-compacted 500-doc corpus, nothing else running) and under load (the main 1,621-doc corpus, mid-way through its own backlog, actively contending for the same storage actor).

Good news — pagination has no offset cliff Deep-page latency (offset=475 of 500, or offset=1,590 of 1,621) is statistically indistinguishable from page-1 latency at every scale tested. Reading crates/kb-core/src/docs_query.rs confirms why: paginate() slices an in-memory Vec that the route already built from a per-(kb, index-generation) memoized full scan (invariant #15) — the expensive part (scan + filter + sort) happens once per index generation and is shared across every page and every concurrent requester, so "page 200" costs exactly what "page 1" costs. No classic OFFSET-scan antipattern here.
Watch this — facets has no such memo /facets scales roughly with doc count: 17.8ms idle at 500 docs vs. 67-83ms at 1,621 docs under load — a bigger jump than the ~3.2× doc-count growth alone would predict, but the scan-every-time design (no memoization comparable to the docs route) means it will keep climbing as the corpus grows. Projected (not measured) at 20k under similar conditions: high hundreds of ms to low seconds — worth fixing before it's user-visible.

The multi-second max spikes under load (1.7-3.6s, on every endpoint we tested, including the flat ones) are the more interesting cliff: kb's storage actor is a single-consumer per-kb design (invariant #15/#28), and a foreground read has to wait in the same queue as thousands of pending ingest upserts. Running a manual kb compact mid-test dropped search p50 by only ~28% (39.7ms → 28.6ms) — a modest fragmentation effect — while the tail spikes barely moved (3,308ms → 2,824ms max), pointing at actor-queue contention with the concurrent ingest backlog as the dominant tail-latency cause, not fragmentation.

Backup and SSE

kb backup on the idle 500-doc corpus (state dir 50MB at the time): 1.05s wall time, tarball 3,098,114 bytes (3.0MB) — roughly 16:1 compression. That ratio is almost certainly an artifact of this synthetic corpus's repetitive lorem-ipsum sentence bank; real prose would compress less well, so treat the ratio, not the number, as the caveat-worthy part — the 1.05s wall time for a 50MB state dir is the more portable data point.

SSE: connects and starts delivering (including its Last-Event-ID replay ring, invariant #24) in well under 50ms. A scripted mutation roundtrip — POST /api/kb/scale500/history/open (66ms, 200 OK) — produced the matching history.recorded event on the same live SSE stream within the same second. No cliff found here at this scale; both the read (event delivery) and write (mutation-to-event) sides held up cleanly.

Atlas: queued behind the backlog, and out of scope anyway

POST /api/kb/scale/atlas/recompute returned 202 (queued: run id + /api/events filter) in 143ms, but never emitted atlas.recompute.complete within a 30s wait while the daemon had an active ingest backlog — consistent with the same single-consumer storage-actor queueing described above: the recompute's own storage reads have to wait behind thousands of pending ingest upserts.

Separately, and by design: this test ran BM25-only (no embedder), and crates/kb-core/src/atlas.rs has a test literally named recompute_for_kb_skips_docs_without_embeddings — every doc in this corpus lacks an embedding vector, so a real atlas layout at 20k was never going to happen here regardless of queue contention. The task brief called embeddings out of scope for this run, and this confirms exactly why: atlas at 20k needs its own follow-up test, with an embedder configured, budgeted separately (embedding 20k docs was explicitly out of scope for this session).

What stays flat (the good news, collected)

  • Warm restart of an idle, fully-indexed kb: sub-1s to ~3s, independent of doc count tested.
  • Docs-page pagination: offset has no measurable effect on latency at any scale tested.
  • SSE connect + mutation roundtrip: fast and correct throughout.
  • Auto-compact (the logical-fragment fix, not the disk-space fix): consistently sub-2s even when collapsing hundreds of fragments.
  • Zero open indexing errors at any point (GET /api/kb/scale/errors returned [] throughout, including during the slowest windows).

Does the ~50k trigger hold up?

Not as stated. The evidence here points to the ingest path degrading well before 50k — the deceleration (1.73 → 0.36 docs/s) was already underway by ~1,500 docs into one continuous run, and a restart mid-backlog was another ~30× slower still. If "50k" means "a single bulk cold-import of 50,000 new documents," this test suggests that scenario would be in serious trouble well before it gets there — plausibly even at 5,000-10,000 docs in one shot, based on the trend, though we did not measure that range directly and say so plainly.

But that framing matters: this is specifically a bulk/cold-import failure mode, not organic growth. A kb that gains a handful of files a day via the live watcher pays ~180-200ms per new file (measured from individual index.file SSE events during the clean 500-doc runs) — utterly negligible at any realistic daily rate. The realistic trigger for this cliff is "I just pointed kb at a large pre-existing archive for the first time" or "I restarted the daemon before that first migration finished" — not "a single daemon slowly accumulated 50,000 docs over years of normal use." The storage-consolidation research's 50k figure may be a reasonable estimate for the latter scenario and a serious overestimate for the former; this report can't fully resolve which one the original research meant, only that it was asserted without either being measured.

We also could not reach 20k — let alone 50k — to directly measure steady-state (fully-indexed, at-rest) read-path behavior at that scale. The 500→1,621-doc trend (facets 17.8ms→67-83ms p50, search 0.6ms→28-40ms p50) is suggestive but confounded by "idle" vs. "still actively indexing," so a clean 20k-at-rest number remains a real gap — see below.

Recommendations

  1. Batch the ingest consumer. fixed 6c9baa38 2026-07-11 (GC-B7 — drain-batched upsert_docs, 145.1s → 0.53s per 500 docs) Accumulate N pending WatchWork items (e.g. 50-200, or a time-boxed drain of the mpsc) into one storage.upsert_docs() call instead of one upsert_doc() per event. The batched API already exists (lance.rs:588) and is unused by the indexer's consumer loop (indexer.rs:1441) — this directly targets the one-fragment-per-doc mechanism behind every ingest-side finding in this report.
  2. Investigate the restart-with-backlog stall specifically. fixed 87dcb0d5 2026-07-12 (SC1 — unconditional dedup-skip touch_mtime heal, O(N·fragments) quadratic; 18,379-doc restart backlog now drains in 269.1s / ~68 docs/s) 7.5+ minutes with zero visible progress, under active CPU/RSS growth, is a distinct finding from ordinary deceleration and deserves its own root-cause session — candidates worth ruling out first: an unindexed new-vs-known diff, unbounded candidate-list construction for cross-reference resolution across the whole undiffed backlog, or a full-table scan per candidate file.
  3. Memoize /facets the same way /docs already is (the existing per-index-generation row-set memo, invariant #15) — it is the one read endpoint here without that protection.
  4. Give foreground reads a way to not queue behind a large ingest backlog on the same storage actor — even a coarse priority lane would keep search/facets/atlas responsive during a large import, which is exactly when an operator is most likely to be checking on progress.
  5. Add a vacuum/prune pass fixed 6c9baa38 2026-07-11 (GC-B7 — explicit Compact + Prune, 5-minute retention, delete_unverified: true) (or lower the retention window) so old_versions_removed isn't perpetually 0 in normal operation — otherwise physical disk usage for a heavily-reindexed kb keeps growing even with compaction running on schedule.
  6. Re-run this harness to completion once (1) lands, ideally on quieter hardware or with hyperfine installed, to get a clean 20k (and eventually 50k) number for both the ingest and at-rest read paths. This report is a first empirical pass, not the final word — see the architecture review (private) and the graph-at-scale findings for related, previously-measured surfaces.
