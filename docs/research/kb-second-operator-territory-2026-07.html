kb’s second-operator territory — three scenarios, mapped to rulings (2026-07)

kb is single-operator per daemon by construction; this map turns that accident of the auth code into two recorded non-goals — the second human gets a share or their own daemon, never a seat inside yours.

2026-07-06· status:applied· project:kb· non-goals

The verdict, in one table

Three ways a second human meets kb, each with a different answer. Only one of them is new ruling territory in the code sense — but two of them were accidental boundaries until today, enforced by nothing more than a doc comment and the shape of an enum.

Method and evidence

Five read-only survey passes over the codebase and the production deployment, run 2026-07-06: (1) the auth and capability surface of kb-server; (2) the kb-comments/1 data model under two authors; (3) operator-private SPA/API surfaces and shared read-state tables; (4) the share/export engine versus live serving; (5) the prior-art trail for the onboarding gap. Every load-bearing claim below carries a file:line reference into the repo at commit 9279de1c, the production reverse-proxy compose + kb.toml, or a named section of an existing research artifact. The threat-model framing follows a July 2026 security review (private): loopback is the assumed-trusted posture, and the interesting question is what a holder of the single valid token can do.

Scenario A — the stranger operator (reference, don’t redo)

A stranger self-hosting kb for themselves is not second-operator territory at all — they become a first operator of their own daemon, which is exactly the supported shape. Every gap on their path is already named, with owners and prompts, in four artifacts. This section exists only to pin the citations:

  • The first-run gap — kb-review-coverage-gaps-2026-07.html#gap-onboarding: quickstart, packaging docs, install.sh and /kb-setup all exist but were “authored by the person who cannot experience first-run friction”; no session has ever walked the happy path on a clean VM. Carries a paste-ready clean-VM dry-run prompt.
  • The distribution gap — installing-kb-everywhere-2026-07-06.html#what-ships-today: no v* tag has ever fired release.yml end-to-end; the tarball ships no SPA; no self-update mechanism; integrity is checksum-only (and install.sh passes when the sha tool is missing); single-arch image. #the-two-floors adds the silent excluders: glibc ≥ 2.39 and an x86-64-v3 CPU floor (pre-Haswell machines SIGILL at first inference, undocumented).
  • Build feasibility — cross-compiling-ci-zigbuild-spike-2026-07-06.html#recommended-ci-design: kb can go static-musl (one upstream lance AVX-512 defect away); kb-embedder can never be zig-linked (C++ ABI wall) — so the native-runner matrix stays trunk.
  • Secure-by-default at the flip — kb-improvement-portfolio-2026-07.html#the-public-flip-changes-the-math and #p07-private-serve: with [outbound] unset (the default — KbSection.outbound is Option, default None, config.rs:429-435), served artifact bytes get zero scrub; “self-hosters without an edge gate inherit that silently.”

The authority to cite rather than redo is itself recorded: kb-next-prompts-playbook-2026-07.html#f6-stranger scopes the second-operator question into exactly these three scenarios and delegates (a) to the onboarding gap. What already exists and works: docs/self-host.md is a real production guide (systemd hardening, Docker, backup/restore, token auth, hardening checklist) — with one known staleness, the ORT_STRATEGY/ORT_LIB_LOCATION guidance (ort 2.x uses ORT_LIB_PATH).

Ruling-vs-feature call: feature. Nothing here needs a refusal; it needs the already-queued onboarding work. No ledger entry.

Scenario B — a second human inside the operator’s daemon

The concrete picture: a partner or colleague gets the SPA URL and either the shared bearer token or a seat on the same machine (loopback). The daemon cannot tell them apart from the operator — not as a bug, but as the entire shape of the system.

The trust model is binary, and the deferral that would have changed it never landed

There is exactly one bearer token per daemon, loaded from <config>/kb/<daemon>/token (paths.rs:181) into an AuthConfig that holds only the token and the trusted-proxy list (state.rs:643-651) — no scopes, roles, expiry, or read-only tier. auth_bearer (middleware.rs:193-233) gates the whole /api/* tree with two outcomes: loopback bypasses unconditionally (:216-218), everyone else either presents the token or gets 401. A grep for read_only|visibility|acl|role|viewer across config and server finds nothing inbound-auth-related.

The accidental boundaryThe doc comment at paths.rs:178-180 reads: “Single shared token in v0.4; per-kb ACLs + multi-token defer to v0.5+.” That deferral was never revisited and never recorded as a decision — it is the exact species of boundary this artifact exists to convert into a ruling. docs/self-host.md’s only “multi-user” section (“Multi-user comment isolation”, self-host.md:779) turns out to be proxy cache-header hygiene (Cache-Control: private, no-store + Vary) — the docs’ sole mention of a second user is a caching footnote.

Comments survive; identities merge

The comment data model is mechanically safe under two authors and semantically incapable of representing them:

  • Author is a role, not an identity. enum Author { You, Claude } (review.rs:114-120) — a closed two-variant, client-supplied label reused identically in replies, attachments, the manifest, the HTTP bodies, the ?author= filter, and the SPA’s TS union. The SPA hardcodes you (useReview.ts:201); kb comments reply hardcodes claude (commands/comments.rs:1026). Nothing derives it from the caller. Two humans collapse into one you.
  • Cross-human permission leaks by construction. The SPA’s “own comments” edit gate is comment.author === "you" (CommentModal.tsx:47) — with two humans, either edits (and detaches attachments from) the other’s comments; delete is ungated for everyone.
  • Concurrency is safe, conflicts are silent. Every mutation serializes under the per-kb review_lock (invariant #6), so nothing corrupts and appends never lose. But no write path passes an If-Match — every save is save_atomic(&path, &file, None) (comments.rs:240 et al.), so a same-comment body edit race is last-write-wins with no 412. Tolerable for one human + one agent; wrong for two humans.
  • The agent loop assumes exactly one you. kb comments watch’s echo-safety surfaces only you-authored items and skips claude (docs/comment-workflow.md:204-208) — a second human’s comments enter the operator’s triage loop indistinguishably, as if the single reviewer wrote them.

So: do comments survive two authors? The files survive; the authorship doesn’t. The limiting factor is the data model (the enum), not the UX — the panels already render comment.author verbatim and would happily display richer identity the schema cannot hold.

The privacy leak is total: memory, sessions, and the live firehose

Every operator-private surface sits inside the same one-gate /api tree. A second human with SPA access sees, with no additional gate anywhere:

Shared read-state: the second reader silently corrupts the first

All “what have I read” state is per-daemon, keyed on nothing resembling a user. The reader route fires POST history/open on open (detail.tsx:410 → INSERT INTO history, sqlite.rs:467), scroll and section-dwell beacons upsert with max() into the same rows (sqlite.rs:495,627), and reading-list read-state is derived from those shared tables per response (derive_read_state, lists.rs:354; ≥95% scroll = read, reading.rs:38). The schemas confirm it: history (V0003) has no user/client/owner column — its header comment says “per-user activity log,” but the user is the daemon; reading_sections (V0014) keys on (visit_id, section_id); lists (V0015) likewise. A partner who reads three artifacts pollutes the operator’s recents, flips list entries to Read, clears unread badges, and inflates section heatmaps — irreversibly (the history table is append-only by invariant #8, and history/purge wipes it for everyone).

And the blast radius is everything

“Read-only human” is not a configuration that exists. The same credential that lets them read lets them: rewrite tags into source files (PATCH .../meta), delete artifacts, DELETE /api/kb/{kb} (wipe the index — drop.rs:28), POST /api/shutdown, and PUT /api/config — which persists a new kb.toml and trips an in-process restart (config.rs:245-251), i.e. full daemon takeover. The type-the-name confirmations on the Admin tab are client-side only (Admin.tsx:158-203); the routes accept no confirm token. The security review’s threat model already prices this in: past the token there is no inner boundary.

Ruling-vs-feature call: ruling

Making a second human safe inside one daemon would require: a real identity source, multi-token auth, per-user read-state columns across four table families, a widened Author type threaded through three creation paths and the TS client, per-surface visibility gates on memory/sessions/SSE/config, and server-side authorization tiers — a materially different product (the one the no-CRDT/multiplayer refusal already declined, arriving through the back door). The honest recording is a refusal: one daemon, one operator. The second human’s supported paths are a static share or a daemon of their own (scenario C’s machinery, pointed inward).

Scenario C — a public read-only mirror of selected kbs

The static story is complete

The share engine (invariant #9, crates/kb-core/src/share/) already answers “publish a subset” end to end: target a file, a folder, or the whole kb ({kb_name}-all.zip, routes/share.rs:273-277); walk the filesystem (mod.rs:285); always strip kb-prompt regardless of per-kb [outbound] config (scrub_export, scrub.rs:118-124, pinned by test :207-215; --no-scrub is a loud opt-out); relativize in-share cross-artifact links into a self-contained bundle (mod.rs:1195-1235) with out-of-share danglers surfaced (or rewritten to live_origin with --links absolute). Three delivery shapes: Cloudflare Pages behind CF Access (--gate email:…|google|github, validated mod.rs:789-821), GitHub Pages (public-only), or a local zip via --local/POST /share/export (256 MB / 10k-file caps, share.rs:31-32). Note the “share tokens” in the daemon env are host API credentials (KB_CF_API_TOKEN/KB_GH_TOKEN, config.rs:577-612) — gating of a published share is Cloudflare Access’s job, not a kb primitive.

Live primitives exist — but only below the API line

Three pieces of the daemon are already built for strangers’ eyeballs: the auth-free artifact subdomains (<id>.artifacts.<suffix> served via the top-level fallback, deliberately outside the /api auth nest — router.rs:571-586, self-host.md:116-120); the permalink shells with server-spliced OpenGraph meta for unfurlers (spa.rs:77-130, invariant #34); and the outbound scrub that strips kb-prompt + redactions for non-loopback requests (artifact.rs:622-642). Two catches: the scrub is a per-kb opt-in ([outbound] default None — portfolio P07’s exact complaint), and everything above the artifact-bytes line — search, gallery data, lists, notes — lives in /api where auth is all-or-nothing.

What a shared daemon cannot do

Inside one daemon there is no notion of a public subset. KbSection (config.rs:393-489) has no public/visibility/allowlist field. And it wouldn’t compose if it did: every federated read — scope=all search (search.rs:1021), ~40 sessions endpoints, memory recall, notes, lists, anchors, stats, the cross-kb id resolver — fans out over state.kbs unconditionally (invariant #28 hardens the concurrency of that fan-out, not its scope). A public visitor’s search on the operator’s daemon would hit the private corpora, full stop. The production instance makes the stakes concrete: one daemon, ≈26 corpora in a single process — showcase artifacts beside an audit corpus, incident runbooks, agent memory, and captured sessions — published only to 127.0.0.1:4000, with Authelia on both routers and a bearer-injecting middleware. There is currently no unauthenticated path to anything, which is correct and fragile: one Traefik router misconfiguration away from scenario B.

The live mirror that works today: daemon-per-audience

The isolation mechanism already exists and is load-bearing: a daemon serves exactly the corpora its own kb.toml mounts (state.kbs is built solely from config.kb — lib.rs:302,1045). The unconditional fan-out becomes safe when the corpus set is the public set. A live public mirror is therefore a deployment recipe, not a code change:

  1. A second kb-public service with its own kb.toml: own [daemon] name, own port, mounting only the public corpora (read-only bind-mounts if comments should be off).
  2. Every mounted corpus carries [outbound] strip_kb_prompt = true — mandatory, since the scrub is per-kb opt-in.
  3. Token-less behind the proxy via KB_ALLOW_NO_AUTH=1 (middleware.rs:242-244 — the documented “proxy is the gate” posture), on a Traefik router without Authelia.
  4. The edge allowlists the read surface. Method-blocking (drop non-GET) kills every mutation — but is not sufficient: GET /api/config leaks the full config and GET /api/events streams the index firehose. Allowlist artifact subdomains, /a/… permalinks, the SPA shell, and the handful of read APIs the mirror should answer (search, docs, facets); default-deny the rest.
Residual sharp edges the recipe must ownEmpty-but-present surfaces (sessions/memory endpoints return empty sets when no such corpora are mounted — harmless but probe-able); history pollution from public readers (their opens write into the mirror daemon’s own history — contained, but it makes the mirror’s “recent” meaningless); and comments — a writable .review on a public daemon is an open guestbook, so mount read-only or block the routes.

Ruling-vs-feature call: ruling, plus one docs feature

The refusal: no per-kb visibility flags, no server-side read-only mode, no in-daemon “public” tier. Each would introduce a second trust level inside a process whose every subsystem — fan-out, SSE, read-state, config — assumes the operator is the only tenant; the audit surface of that assumption is the whole codebase. The accepted answer is composition: the corpus mount is the ACL, the daemon process is the isolation boundary, the edge is the gate — the same posture the fleet design (many daemons side-by-side) was already built on. The one genuine feature this leaves behind is documentation: a “public mirror” recipe section in docs/self-host.md encoding steps 1–4 and the sharp-edges list above.

The rulings (as added to the ledger)

Added verbatim to README.md → Non-goals on 2026-07-06, alongside the existing seven entries:

One daemon, one operator — no second identity

The daemon has exactly one bearer token and no user concept; author: you|claude on comments is the human↔agent role split, never an identity. Roles, read-only tokens, viewer accounts, and per-user read-state are refused — a second human inside your daemon is a guest wielding your full authority, seeing your memory and sessions and polluting your read-state. The supported answers: hand them a static share (kb share), or give them a daemon of their own.

No in-daemon visibility, ACLs, or public mode — the corpus mount is the ACL

Every federated read fans out over every mounted corpus by design; a daemon serves exactly what its kb.toml mounts. A live public mirror is a dedicated daemon mounting only public corpora behind an edge that allowlists the read surface — a deployment recipe, not a daemon feature. Per-kb public flags and a server-side read-only mode would smuggle a second trust tier into a process built on the operator-is-the-only-tenant assumption; kb share stays the blessed way to move content across a trust boundary.

Scenario (a) deliberately gets no entry: a stranger operating their own daemon is the supported shape, and its gaps are queued feature work, not refusals.

What the rulings do not refuse

Single-operator hardening is compatible with both rulings and this survey surfaced four cheap pieces of it — defense-in-depth for the one-operator model, not multiplayer by stealth:

  • Server-side admin confirmation. DELETE /api/kb, history/purge, and /api/shutdown accept no confirm token; the type-the-name modals are client-side only (Admin.tsx:158-203). Mirror the token server-side.
  • Gate GET /api/config. It returns the full live kb.toml (config.rs:34-44); it belongs in the same privileged bucket as PUT.
  • If-Match on comment writes. The 412 machinery exists and is dead (save_atomic(…, None) everywhere) — wiring it in protects even a solo operator with two browser tabs.
  • Scrub-by-default at the public flip — already adopted as portfolio P07; this survey independently re-derived its necessity (per-kb [outbound] opt-in is the one step of the mirror recipe humans will forget).

Also explicitly untouched: richer display of the existing two-value author (pure UI), and the deferred-with-trigger MCP ruling (a second agent is not a second operator — agents ride the operator’s credential by design).

Open questions

  • Should the public-mirror recipe ship in docs/self-host.md before or after the first external request for it? (It is pure docs; the trigger could simply be “someone asks.”)
  • Read-only bind-mounts on a mirror daemon: the indexer tolerates them for serving, but the recipe should verify watcher/index behavior on a truly read-only corpus before it’s written down.
  • Does the fleet’s loopback-CORS multi-daemon story (one SPA reading several local daemons) need a matching note in the ledger, or is it already covered by “the daemon process is the isolation boundary”?
