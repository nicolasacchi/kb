kb sessions rethink: from event log to worklog

The ratified program for the sessions milestone — what is true today (with evidence), what ships (seven tracks, W0–W6), what stays open (six operator decisions), and what it costs.

2026-07-28 status: proposed repo main @ b44043c spec of record: synthesis memo (binding) evidence: 5 designs · 2 verify · 6 maps

Executive summary

Thesis. kb's session capture is excellent and its session reading is a faithful event log — which is the problem. Capture writes a byte-identical transcript at every Stop (537 captures on disk); the renderer then emits one card per JSONL event with no join layer, no interpretation of protocol-shaped text, and no destination. The corpus is head-biased at every layer: the first prompt is parsed, digested, and displayed everywhere, while no last-message/outcome field exists at parse, capture, digest, wire, or CLI-render time (verified field-by-field: crates/kb-core/src/sessions.rs:42-197, crates/kb-server/src/routes/sessions.rs:75-120; the cli map calls it "a structural gap, not a rendering oversight"). This milestone converts the sessions surface from an archive of things that started into a worklog of things that ended some way — joined, interpreted, project-scoped, closable from a phone, readable from a terminal, and extended to a fourth harness.

What ships. ONE deterministic interpretation engine (session-view/1, crates/kb-core/src/sessions/view.rs) with three presenters — the HTML renderer migrates onto it this milestone, a real terminal reader kb sessions read, and a /view + /raw wire (T1). A closure quintuple — one extraction function, column last_assistant_text, wire outcome, a recomposed digest, anchor #ses-outcome — gated by a week-1 validation run over all 537 captures (T2). Projects become first-class: a derived key + read-time registry, project= on every sessions read, two-lane search, a projects home (T3). The surfaces catch up: outcome-first list rows, a real mobile bottom sheet, a session-adaptive inspector rail, ?turn= deep links, replay tail windowing (T4). The CLI reaches full parity with genuinely redesigned outputs (T5). Capture expands: Grok Build transcripts + report lane + backfill, workflow journals and task outputs, a LIVE lane with staleness badges and presence (T6). Moonshot finishers: turn-anchored comments, find-in-transcript, the project ledger with an agent-layer /kb-weekly (T7). And — added mid-design by the operator (A12, ratified as R15) — kb learns to really follow the ongoing session: two honest liveness tiers, a follow mode with an interpreted live tail panel and a seamless live→captured handoff, and kb sessions read --live --follow (T8).

Shape. A W0 foundation wave (no schema; the bug fix, the extraction gate, the constants, the fixtures) plus seven feature waves W1–W7 (phasing). Two files are contended across waves — crates/kb-core/src/session_render.rs and web/src/routes/sessions.tsx — and each is rewritten by one hand in one wave. Seven decisions stay with the operator (D1–D6 + D-LF1), each presented with the memo's recommendation. Everything in the daemon is deterministic and golden-testable; the only LLM steps in the program are agent-layer skills, clearly marked.

T1The engine — session-view/1, one interpretation, three presenters

The ratification (R1). Both the reader and CLI designs independently specced "the one engine" as different artifacts (session-ir/1 in session_render/ir.rs vs session-view/1 in sessions/view.rs) — the program's central collision (adversary C1). Ratified: one module, crates/kb-core/src/sessions/view.rs (sibling of replay.rs, mirroring the proven replay_timeline pattern: pure kb-core fn, versioned grammar, cached route, CLI renderer), grammar session-view/1, absorbing the reader design's richer semantics. The engine is pure and deterministic — no clocks, no randomness, transcript order preserved, BTreeMap only.

The four joins (fixing P4/P7/P9/P1 structurally, once):

  1. requestId merge — consecutive main-thread assistant events sharing a requestId merge into ONE turn (collapses the observed 6-card shatter; 1,047 requests → honest exchange counts).
  2. tool_use ↔ tool_result pairing — results fold into the call's card by tool_use_id (precedent: parse_session_activity's pending_git map, sessions.rs:516); a user event carrying only results emits no user turn — "user" is reserved for humans; a mixed event splits; unpaired results render standalone (tolerance floor).
  3. Task threading — a TaskRegistry built from TaskCreate/TaskUpdate/TaskOutput/Workflow launches and parsed task-notifications; every task-touching node carries a task_ref; TaskList calls render reconstructed board snapshots (completed struck, ◐ in-progress, ○ pending); the FINAL board renders in the outcome footer.
  4. Sidechain grouping — consecutive isSidechain turns group into a collapsible SideLane ("↳ sidechain — N turns · M tool calls") instead of interleaving flat.

Three presenters, one tree: (a) the HTML renderer — session_render.rs migrates onto the view IR this milestone (cli-grok D3-A ratified; one designer's hand, W1); (b) kb sessions read (verb name ratified; kb cat keeps byte-truth envelope semantics); (c) GET /api/sessions/{sid}/view with a load-bearing fields= projection (fields=header,outcome gives list/rail surfaces a KB-sized outcome fetch), LRU-cached with scrub posture in the key exactly like replay, scrub-first-then-interpret (routes/sessions.rs:3629 ordering), newest-capture-scoped via find_session (#11) — plus GET /api/sessions/{sid}/raw → text/plain decoded JSONL, with non-loopback forcing the secrets scrub floor (the export-route precedent, :3124-27, #4).

Turn identity (R2, settles adversary C5/critic C-3). Stable uuid-primary ids t-<uuid12> (first 12 hex of the first merged event's uuid; the reader design's u-<uuid8> variant is retired), with the ordinal kept as data-turn + visible label. Outline rows carry BOTH n and id; ?turn= accepts N (resolved via the outline) and end. This lands WITH the join pass — because joining/ghost-elimination renumbers ordinals, ordinal-only links are renderer-version-scoped, and this doc says so plainly: uuid ids are the durable grammar; numbers are labels. R2 is also load-bearing for the live-follow handoff (T8): t-<uuid12> derives from the JSONL record uuid, so the id is IDENTICAL in a live tail delta and the later captured render — the live→captured reload lands exactly where the reader was, no jump.

T3Projects & search — derived key, registry, one scoping param, two lanes
