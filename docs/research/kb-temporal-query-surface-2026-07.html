A temporal query surface for kb — one verb, not a time-travel epic

Four candidate temporal queries assessed against what kb already stores. One survives on value/effort: kb diff --between <date> <date> — a pure date→ref resolver over the existing versions façade, zero server changes, zero new storage. The rest are rejected here, with reasons, so they stay rejected.

2026-07-06 · status:open · project:kb · temporal

The brief

This answers the F3 recipe from the next-prompts playbook: kb's pieces all record time — the versions façade (invariant #14), the append-only history table (#8), memory supersede chains (#10), session timestamps (#11) — but no query composes them. Candidates to design against: kb cat --as-of, kb diff --between, kb recall --as-of, and a corpus changelog (the week-in-review idea's deterministic core). Constraints: deterministic (no in-daemon LLM — a recorded non-goal), no new storage if avoidable, and a thin-slice verdict rather than an epic.

Four candidates, assessed

kb diff <id> --between <date> <date> ship

Source that answers it: the versions façade, fully. kb diff --from/--to already exists, ref-addressed (git sha | index:<id> | WORKING), with server-side similar-crate hunks and a prose-vs-raw mode. The only missing piece is date→ref resolution — and every timeline entry already carries ts_unix.

Gap: one pure function. The diff route's current from default resolves by position in the newest-first list (default_from, crates/kb-server/src/routes/versions.rs:203-208), never by timestamp; nothing anywhere resolves a date (a repo grep for as-of/nearest-before finds nothing).

Cost: smallest possible. The CLI already fetches GET /versions as JSON; resolve each date client-side with a resolver that lives in kb-core (so a future server route reuses it), then call the existing GET /diff?from=&to=. Zero server changes, zero new storage, zero schema. Roughly: ~15-line resolver + golden tests in kb_core::versions, ~80 lines of CLI flag + date parsing + output annotation.

Value: answers the natural agent and operator question — "what changed in this doc between June 1 and July 1?" — for any artifact with git history (full depth locally) or snapshots (25 revisions of depth everywhere, including prod). Deterministic: same timeline JSON → same refs.

kb cat <id> --as-of <date> second slice

Source: same façade; raw_at(ref) already returns any version's bytes in kb-core.

Gap: two, and one is structural. First, the same date→ref resolver as above (shared). Second, no HTTP route exposes single-version content — the façade serves a list and a diff, never bytes-at-ref. And kb cat today bypasses the façade entirely: it opens lance directly and dumps the current on-disk file (crates/kb-cli/src/commands/cat.rs:38-45), no daemon involved.

Cost: the resolver (shared with --between) plus one new endpoint (GET .../artifacts/{id}/at?ts= running resolve + raw_at), a wire type, and a daemon-backed mode for cat. Modest — but strictly more than --between, entirely because of the missing content-by-ref route.

Verdict: not rejected — sequenced. It is the natural second slice: by then the resolver exists, is golden-tested, and has proven its edge semantics in the field. Shipping it first would mean paying the new-route cost before knowing whether anyone asks temporal questions at all.

kb recall "<q>" --as-of <date> reject

Source: partially the memory rows. The good news is real: superseded memories are soft-kept with timestamps intact; the moment B stopped being live equals its superseder's created_unix; and the recall pipeline's decay clock is a single injected now_unix into a pure rerank (crates/kb-server/src/routes/memory.rs:398 → crates/kb-core/src/memory.rs:147-218) — an as-of instant would drop in with no math change.

Why rejected anyway — three reasons, one fatal:

  • Fatal: forgotten memories are unrecoverable. kb forget removes the file and the lance row with no tombstone and no timestamp. A memory that was live on date D and later forgotten simply cannot appear in an as-of-D recall — and nothing can even warn that the answer is incomplete. A temporal query that silently lies about the past is worse than no temporal query.
  • Chimera ranking. Pins, salience edits, and the recall policy are current-state only. An "as-of June 1" recall would honor supersedes as of June 1 but rank with today's salience and today's pins — a state that never existed at any point in time.
  • This ground is already ruled on. The memory-system evolution review rejected the bitemporal entity-graph (D3), and the endorsed salvage was kb memory log <id> — walk one supersede chain with timestamps, no ledger, no as-of. That remains the right memory-side temporal verb if one is ever wanted; recall --as-of would re-litigate a settled rejection at higher cost.

Cost if built anyway: moderate — list_supersede_targets flattens supersede edges to an untimed id set, so timing them means threading each superseder's created_unix through lance, the reranker, the route, and the CLI, plus widening the per-corpus over-fetch (as-of filtering drops recent rows and under-fills the current limit×4 fetch). All of it in service of an answer with a hole in it.

Corpus changelog — "what appeared, changed, died this week" reject for now

Sources, per column:

  • Changed — well covered today. indexed_at_unix advances only on real content change, snapshots timestamp each revision, and the gallery already answers "changed in window" via the ?from&to mtime filter (invariant #35). No build needed for a listing; only presentation is missing.
  • Appeared — approximate at best. There is no first-seen column; indexed_at_unix is overwritten on every reindex; created_unix is nullable filesystem btime tracking the file, not the index; the earliest surviving snapshot is floor-bounded at 25 revisions.
  • Died — unanswerable. Deletion is a hard cascade that persists nothing, index_runs carries no artifact ids, and the event ring is volatile. Only git can answer, and prod has no .git.

Why rejected now: the honest version requires exactly what the brief avoids — new storage (a deletions journal) — plus inputs the deep review has already flagged: week-in-review was explicitly deferred there ("real ideas, wrong quarter") pending the session-data repair programs, and the funnel/rollup aggregates it would sit beside were recommended for deletion. Building a summary view over known-untruthful inputs launders them.

Defer-with-trigger, not never: revisit when (a) the session-data repairs land and verify on real data, and (b) — optionally, cheaply — a deletions journal rides cascade::delete_artifact, which v0.24 R2 just made the single choke point every removal flows through. One small append-only table (artifact_id, path, deleted_at) written at that choke point would make "died" answerable forward from the day it ships. Worth considering while cascade.rs is fresh, even with the consumer deferred.

The thin slice: kb diff --between, specified

Resolver semantics

resolve_as_of(versions, at_unix) in kb_core::versions: over the façade's newest-first, stably-sorted timeline, return the first entry with ts_unix ≤ at_unix. Pure, golden-tested. The four edge cases the tests pin:

  • Ties — equal ts_unix resolves by the façade's existing stable order (working → git → snapshots); documented, not accidental.
  • Below the floor — a date older than the oldest known version is a hard error naming that oldest version's date. Never a silent empty result.
  • Above the ceiling — a date at or after the working tree's mtime resolves to WORKING.
  • Non-monotonic git author dates — rebases can reorder author dates; the resolver operates on the ts-sorted list the façade already produces, so it stays well-defined.

CLI shape

kb diff <target> --between 2026-06-01 2026-07-01 [--raw --kb --json --daemon]

resolved --between:
  2026-06-01 → 3f2a9c1 "docs: v0.23 reader chrome" (git, 2026-05-29 18:04)
  2026-07-01 → index:#812 (snapshot, 2026-06-30 22:11)
  • --between takes two dates and conflicts_with --from/--to (clap-enforced).
  • Date grammar: YYYY-MM-DD means end-of-day 23:59:59 UTC — "as of June 5" includes June 5's changes; full RFC 3339 for exact instants. Always UTC: local-midnight parsing would make the same command resolve differently per machine, breaking determinism.
  • The resolution is always echoed (as above): each date prints the ref it resolved to, that ref's real timestamp, and its source. The approximation stays visible instead of pretending dates are exact.
  • Both dates resolving to the same ref → empty diff, exit 0, "no recorded change between d1 and d2".
  • Implementation is pure composition: GET /versions → resolve twice → GET /diff?from=&to=. No server delta; the existing text/raw diff modes come along for free.

Verification

  • Golden tests on resolve_as_of in kb-core (the four edges above).
  • CLI integration: a repo-tracked artifact diffed --between two dates straddling a known commit reproduces the same hunks as the equivalent --from <sha> --to WORKING.
  • Snapshot-only path: an untracked corpus file edited twice, diffed between pre/post dates, shows the edit — proving the prod (no-.git) path.
  • One green-CI commit; invariant #14's entry gains the resolver sentence (no new invariant — the 35 cap stands).
Why this one winsThe other three candidates each require something that doesn't exist — a content-by-ref route (cat --as-of), timed tombstones plus unforgettable forgets (recall --as-of), a deletions journal plus truthful session data (changelog). --between requires only a 15-line pure function over data every corpus already has. If temporal queries turn out to earn their keep, the resolver is the foundation the second slice reuses; if not, kb carries ~100 lines, not an epic.

Open questions

  • One-date convenience: should --between <d1> (single value) default the second date to now? Leaning yes, but it can wait for field use.
  • Is 25 snapshots of depth enough in prod, where auto rides snapshots only? A per-kb snapshot_keep override is cheap if real use hits the floor.
  • Should the deletions journal ship opportunistically now, while cascade.rs is fresh, even though its changelog consumer is deferred? It only helps forward from the day it exists.
