kb-users/1 — identity is attribution, not authorization (v0.34 frozen design, 2026-08)

kb gains N named users — per-user read-state, per-user comment authorship, per-user API/CLI attribution — without gaining a single line of authentication: Authelia stays the identity authority, the daemon only resolves who an already-admitted request is, and every identity keeps the operator’s full authority.

Provenance — directive, evidence trail, panel

Operator directive, 2026-08-01, verbatim: “I want multiple users that track reading/comments/everything separately, visible to each other (a team), and API/CLI usage attributed to a user. Decide Authelia vs something different.” Multi-user attribution; team visibility; API/CLI per-user.

The scope reversal, stated honestly

This milestone reverses half of the recorded non-goal “One daemon, one operator — no second identity”, ruled 2026-07-06 in kb’s second-operator territory map. That ruling refused a second human inside the operator’s daemon for two families of reasons: identity merge (one you, polluted read-state, unattributed API use) and privacy plus authority (memory/sessions leak, total admin blast radius). kb-users/1 repairs the first family and deliberately re-affirms the second.

What it reverses: identities now exist — N named users, per-user read-state, per-user comment authorship, per-user API/CLI attribution. What it keeps, and re-records:

  • One trust tier. Every identity wields the operator’s full authority (admin, delete, config). No roles, no read-only tokens, no ACLs, no visibility tiers. A team member is a co-operator, not a guest.
  • No in-daemon authentication. kb never stores or checks a password and never manages a login session. Authentication stays at the edge (Authelia) or in possession of a bearer token. kb resolves who an already-authorized request is, never whether it may enter.
  • Everything visible to everyone. All users see all users’ activity — that is the point (team awareness), and it is what keeps this out of ACL territory.
Identity is attribution, not authorization.

Bookkeeping: the README/CLAUDE.md non-goal narrows from “one daemon, one operator” to “one trust tier — identities are attribution, not authorization”, records the 2026-08-01 directive, and keeps the refused list (passwords, ACLs, roles, per-user visibility). Invariant slot #2 — open since the kb-tui retirement in v0.24 — is filled with the identity ladder + attribution-not-authorization invariant.

The decision — stay with Authelia; kb gains an attribution layer only

Three candidate architectures were considered:

  • (A) In-daemon users (passwords/sessions in kb): rejected. Massively expands daemon scope, contradicts the deterministic/lean daemon ethos, duplicates what Authelia already does well, and turns kb into a security product. Nothing in the ask requires it.
  • (B) OIDC in the daemon (kb as an OIDC RP validating Authelia JWTs): rejected for v1. Adds a crypto/JWKS dependency and a config surface for a problem the edge already solves; forward-auth headers deliver the same claim set over a hop we already trust for XFF. Revisit only if kb ever needs to run without a header-trusting proxy AND without tokens.
  • (C) Edge-auth + trusted identity header + per-user tokens: chosen. Zero new authentication surface; reuses the existing trusted-hop machinery (invariant #4) verbatim; matches the auth-proxy pattern of Grafana (auth.proxy), Miniflux (AUTH_PROXY_HEADER), FreshRSS, and Gitea/Forgejo.
The plumbing already exists (verified 2026-08-01)Authelia’s forwardauth middleware already sets authResponseHeaders=Remote-User,Remote-Groups,Remote-Name,Remote-Email (the reverse-proxy compose file), and users already exist in Authelia’s file DB (alex/admins, kb-bot, testbot-e2e). The kb router chain is authelia@docker → kb-inject-bearer (same compose file) → daemon — so every edge request already arrives carrying both transport auth (the shared bearer) and identity (Remote-User); today the daemon reads the former and drops the latter. grep Remote-User crates/ = zero hits before this milestone.

The identity resolution ladder

Identity is resolved once per request inside the existing auth_bearer middleware (middleware.rs:193-233 — it already owns both the trusted-hop verdict and the token match), inserted as a request extension Identity { user, source }. Handlers take Extension<Identity>. The order:

  1. Per-user token (explicit beats ambient). If a registry token matched — presented as the Authorization bearer (direct/host lane) OR as X-Kb-Token (edge lane, where kb-inject-bearer overwrites Authorization with the shared daemon token) — identity = that user, source = token. An agent or script with its own token running behind a proxy session must attribute as itself, and Authelia client_credentials machine clients arrive with no Remote-User (verified: Authelia only sets Remote-* when introspection yields a username, handler_authz_authn.go) — so tokens are the only machine attribution lane. X-Kb-Token is attribution-plus-auth on the direct lane and attribution-only behind the edge; it is honored regardless of peer (possession of a valid token IS the credential).
  2. Trusted identity header. If the immediate peer passes the existing trusted-hop gate (peer.is_loopback() || trusted_proxies.contains(peer) — the same rule that gates XFF, middleware.rs:328-331) and Remote-User is present and valid (^[A-Za-z0-9._@-]{1,64}$), identity = that value, source = header. A non-trusted peer’s Remote-User is never read (fail-closed, the same posture as XFF). Loopback peers may set it too — deliberate: loopback already holds full authority; this is how agents, tests, and e2e attribute themselves. Belt-and-braces at the edge is verified: traefik’s forwardAuth deletes the client-supplied value of every authResponseHeaders-listed header before copying Authelia’s (forward.go: req.Header.Del then copy — docs + source confirmed).
  3. Legacy shared token (<config>/token, unchanged) → identity = the configured operator, source = legacy.
  4. Loopback, no credentials → operator, source = loopback.

Ladder notes (all ratified)

  • The header name is configurable ([identity] header = "Remote-User") for authentik/oauth2-proxy users; default Remote-User.
  • An invalid header value logs once and falls through the ladder — never a 500.
  • 401 semantics are unchanged for Authorization. An X-Kb-Token that matches the registry also satisfies transport auth on the direct lane (it is a bearer credential by another name); an invalid X-Kb-Token is simply ignored — the request still needs normal admission.
  • Rate-limit buckets key on the resolved user in v1 (panel point 7: under kb-inject-bearer every edge user shares one token-hash bucket today — multi-user makes that a real regression, not a follow-up). Fallback to the token-hash key when identity is operator-by-default.
  • Machine clients through the edge (kb-bot): give them a registry token + X-Kb-Token; without one they attribute as operator via legacy — documented, never “invented” (the client_credentials lane sets no Remote-User by design).
  • Username normalization (panel point 8): lowercase-fold at resolve time, header and token-registry users alike; config operator/users[].name are required lowercase (hard config issue otherwise). History is append-only — case forks would be permanent ledger splits.
Implementation trap (panel point 4)Today auth_bearer returns early on loopback before reading Authorization (middleware.rs:216-217). The ladder must always inspect X-Kb-Token/Authorization/the identity header for attribution even when admission is already decided by loopback — otherwise a loopback agent with its own token silently attributes as operator. Admission logic stays byte-identical; only identity resolution reads credentials on all paths.

Tokens (secrets never live in kb.toml):

  • <config>/token — the unchanged single shared token → operator (back-compat).
  • <config>/tokens — a new optional registry, one entry per line: <user>:sha256:<hex> (preferred — hash at rest, the Gitea lesson) or <user>:<plaintext> (accepted), # comments, mode 0600, loaded at startup beside AuthConfig. Both files may coexist. kb token issue <user> generates 32 random bytes, appends the hashed form, prints the plaintext once. kb token revoke <user> removes the line. Restart to load (same as the existing token file).

No users table in sqlite. Usernames are plain strings; the config users list is display sugar. /api/users = configured ∪ observed (distinct users in history/comments), so an unconfigured teammate still shows up.

Data model — per-kb sqlite, migration V0034

Keying rule: every per-user row stores the resolved username string. No FK, no users table. Usernames come from Authelia (already the identity authority); kb is an attribution ledger, not an identity provider; strings survive config reloads and cross-kb federation trivially (see the recorded tradeoff).

history: one column, three keying fixes

ALTER TABLE history ADD COLUMN user TEXT NOT NULL DEFAULT '' ('' = pre-migration, mapped to operator by the startup backfill). The append-only invariant #8 is unchanged. user is stamped on all three kinds (open, search, comment) — panel point 1 caught that this is three keying fixes, not one:

  • (a) the 30-min visit-gap re-open dedup (history_record_open, sqlite.rs:788-829) matches the latest open row per (artifact_id, user) — today two teammates within 30 minutes share one row and overwrite each other’s scroll;
  • (b) the 5-second search dedup (history_record_search, sqlite.rs:866-868) keys per (query, user);
  • (c) idx_history_artifact_open gains user.

The scroll/reading upserts are already visit-id-addressed, so they become per-user for free. source ('web'|'cli') stays — it is the channel, orthogonal to user. reading_sections (V0014) needs no schema change: it keys on visit_id, which becomes per-user once history visits are; the cumulative-idempotent max() upsert (invariant #19) is untouched.

Reading rollup and ?read=

reading_rollup_inner (sqlite.rs:1339-1440) gains a user filter (WHERE user=? before the ROW_NUMBER partition — a narrowing, not a multiplication). ?read= on /docs AND /search (the grammar is lock-step, invariant #35) now means “read state for the requesting user”. Rollup consumers — resurface, daycard, graph — pass the requester too.

Load-bearing (panel point 2)The rollup’s override overlay at sqlite.rs:1411-1414 still reads the frozen list_entries.read_override column — it must switch to list_entry_user_state for the requesting user in the same change, or ?read= silently stays operator-global.

Reading lists: shared objects, per-user state

Lists + entries + anchors stay shared team objects (the global-unique title index stays). Per-user state moves to a new table list_entry_user_state(entry_id REFERENCES list_entries ON DELETE CASCADE, user TEXT, read_override TEXT, updated_at, PRIMARY KEY(entry_id, user)). The legacy list_entries.read_override column is frozen — backfilled into the new table for the operator, never written again (refinery files are append-only; columns are not dropped). derive_read_state takes the requester; dwell/scroll signals already flow per-user via visits. Panel point 9: the wire stays requester-only in v1; the “read by N” per-user map is deferred (an additive wire path exists), and the team-awareness claim is correspondingly narrowed to history + comment attribution.

Comments (kb-comments/1, invariant #6)

An additive optional user field on Comment / Reply / Attachment / Verdict — the uniform wire name is user everywhere (panel point 11: no by_user wobble; the verdict’s hardcoded by: Author::You at review.rs:836 gains user too). It is server-stamped from resolved identity on every create/reply/attach/verdict — never client-supplied — unlike author, which stays the client-sent you|claude role: a “claude” comment records which user’s agent wrote it — the token owner (panel point 10). Absent user (old files) = operator at render time. The schema string stays kb-comments/1 — additive optional field, old files parse byte-identically, reanchor untouched, and the whole-file review_lock already serializes concurrent authors.

Server mutation policy (panel point 3 — decided)Comment/reply body edit and delete are owner-only, enforced server-side (403 problem+json when identity.user != row user; legacy rows with no user belong to the operator). Resolve / reply / attach / reanchor stay open to every user — they are the collaboration surface (the agent triage loop resolves the human’s comments by design). This is attribution hygiene within one trust tier, not an ACL: any user retains full daemon authority elsewhere. The SPA edit-gate mirrors it (user==me, operator fallback for legacy rows).

Backfill

One idempotent post-migrate startup pass (config in hand): UPDATE history SET user=:op WHERE user='' plus the read_override copy. Runs on every boot, matches zero rows after the first. Known limitation, recorded: all pre-migration rows attribute to the operator — if informal sharing already happened (someone else read artifacts over the operator’s shoulder or session), that history is unrecoverably blended. Accepted: day one of identities is the migration moment.

What deliberately stays global/shared in v1

Stated in full because the 2026-07-06 ruling’s original why was the privacy leak, not just read-state pollution (panel point 6). Adding a teammate means accepting all of this; the deploy doc says so in exactly these words:

  • Agent memory (the kb remember/recall corpus) — every user reads and writes the one shared memory; a teammate sees your memories by design.
  • Corkboard anchors, pinned_memories, saved queries, memory decay policy.
  • Sessions tables + transcripts — captured per-machine by each member’s own hooks (a later wave); a teammate can read captured transcripts on this daemon.
  • Server-side theme/accent/density (already per-browser localStorage in practice).
  • History purge / DELETE /api/kb / config writes / shutdown — whole-daemon verbs: one trust tier, every user is a co-operator wielding full authority.

kb-code-server (kbc.example.com) is out of scope for kb-users/1 (panel point 12). It reuses auth_bearer, so the ladder arrives there mechanically when its crate recompiles against the shared middleware — but no kbc route consumes identity in v1, and its annotations/review surfaces stay single-operator. Recorded so nobody assumes otherwise.

API surface

  • GET /api/identity gains user + identity_source (already the CLI’s probe).
  • GET /api/users — configured ∪ observed users, with display names.
  • ?user= filter on the history + comments list routes (analogous to ?author=).
  • Comments POST bodies: author unchanged; any client-sent user is ignored (the server stamps; additive fields must not 400 old clients).
  • SSE: additive user on the per-action payloads (history.recorded, comment-carrying events, list entry events). The envelope (types.rs:57-83) is untouched — payload-level and additive, so the SharedWorker/cursor machinery (invariant #24) and old clients are unaffected.
  • Everything else unchanged; scope=all federation untouched (user strings are corpus-independent).

CLI

  • kb whoami — resolved identity + source (hits /api/identity).
  • kb users — list /api/users.
  • kb token issue <user> / kb token revoke <user> — manage the registry file (daemon-side file on the same host; restart to load, same as today).
  • Existing verbs unchanged — identity is server-derived from the token, so kb comments add --author claude now lands as (author=claude, user=<token owner>).

SPA

  • Current-user chip (from /api/identity) in the top bar; users in Settings.
  • Comments render user beside the role badge; the edit gate is user==me.
  • Read-state UI stays “yours”; history/recents can show teammates’ chips (team awareness) — v1 keeps gallery badges per-requester and adds user chips on the artifact History panel only. Deliberately small: the SPA can grow a “team activity” surface later without wire changes.

Deployment (kb.example.com) — nothing mandatory changes

Authelia already stamps the headers; traefik already forwards them. Adding a teammate = add them to Authelia’s users_database.yml (+ optionally [[identity.users]] for a display name + a token via kb token issue). The kb-inject-bearer middleware stays exactly as is.

Security posture (invariant #4 extension): Remote-User is honored only from trusted hops — the same trusted_proxies list, exact-match, empty by default. A direct LAN request to 127.0.0.1:4000 (docker bridge gateway peer ≠ traefik IP) that forges Remote-User is ignored and falls to the token ladder.

Header-strip verified; ship gate (panel point 5)Traefik’s forwardAuth overwrites every authResponseHeaders-listed header on the forwarded request — delete-then-replace, confirmed from both the traefik forwardAuth docs and forward.go source (research job 01KYZFWX1YR448EAP69RRPGBS7; the pattern is Authelia’s documented trusted-header SSO integration). The ship gate: self-host.md requires the configured identity header to be listed in authResponseHeaders, plus negative tests. Token ops (panel point 14): distribute the plaintext once, out-of-band; rotation = revoke + issue + restart — documented in self-host.md in phase D.

Recorded tradeoff — username strings, not numeric user ids

Prior art (Miniflux, Gitea, and the research job’s recommendation) prefers a users table + numeric user_id FK, because usernames rename. kb deliberately keys by the resolved username string anyway:

  • kb runs ~20 per-kb sqlite DBs plus cross-kb federation — a numeric id would need a global identity store kb refuses to own (Authelia is the identity store);
  • kb’s rows already key on string ids everywhere (artifact_id);
  • a rename is an operator event with an operator remedy — a future kb users rename <old> <new> backfill (UPDATE across the per-user tables + review files) is cheap, mechanical, and recorded here as the accepted mitigation.

Renames are rare on a personal-team Authelia; FK-less attribution degrades to “old rows show the old name”, never to data loss.
