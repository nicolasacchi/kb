Two answers to the same question: reviewing agent-written HTML

A fit-for-purpose comparison of redline — a single-file human↔AI review tool — and kb-comments, the review subsystem of the kb knowledge-base platform this document ships in.

kb · docs/research 2026-06-17 multi-agent fact-checked verdict: depends — not winner-takes-all

Summary

In the same weeks of mid-2026, two projects independently built an answer to the same emerging problem: agents now author plans, specs, and reports as rendered HTML, and the natural place to review them is the page itself — with margin comments the agent reads back as structured feedback and acts on. Both reject the copy-paste shuffle between a browser and a chat window.

redline

github.com/umangjaipuria/redline · MIT (LICENSE) · v0.1.0

A young, single-purpose tool: point it at one HTML file, comment on it like a Google Doc, and your agent revises it in place. Comments live inside the file; zero infrastructure; agent-agnostic.

TypeScript ~92%PreactBun ≥1.3single file

kb-comments

this repository · kb-comments/1 · ~v0.18+

One feature of a long-running Rust knowledge-base daemon that indexes, searches, and serves a whole corpus. Comments live out-of-band in a daemon-owned sidecar and compose with search, atlas, sessions, and sharing.

Rust · axumlancedb + sqliteReact SPASSE live loop

They are not really competitors — they are two points on one curve. redline optimizes the document: one portable, self-contained file is the whole review world. kb optimizes the corpus: review is a slice of a multi-artifact, always-on platform. The striking signal is how much they converged on the hard parts, which validates that the problem — and the rough shape of a good solution — is real. The divergences are deliberate scope tradeoffs, not quality gaps.

Where they independently agreed
  • The rendered page is the review surface; margin comments are the agent's structured feedback channel.
  • The agent is a first-class commenter — explicit author identity, threaded replies, resolve, a dedicated re-anchor verb.
  • Anchoring against a mutating document is THE core problem, solved with fuzzy text resolution against current text plus an audit trail — never brittle inline markup spliced into the body.
  • Keep the original/frozen quote after a re-resolve (redline's originalQuote; kb's frozen anchor) so an anchor's provenance is never silently lost.
  • Ship an agent skill that encodes the same loop: read anchors before editing, edit, then re-check and re-anchor the stragglers.
  • The same human-in-the-loop triage: resolve a clear fix hands-off; for anything ambiguous or large, reply with a question and leave the thread open.
  • Lean on stable authored element ids as the most durable anchoring foundation (redline as a bias; kb as an exact-id identity check).

1 · Problem framing & positioning

The convergence is the headline: two codebases, built independently, landed on the same core insight and even the same sub-mechanisms (agent author identity, threaded replies, an explicit re-anchor verb, a skill that scripts an edit-then-reanchor loop). What differs is the unit of optimization, and it is a scope choice, not a quality gap.

redline optimizes the document. The file is self-contained and portable: the comment state rides in the <head>, identity is the file path, and you can mail the HTML — comments included — with no infrastructure. kb optimizes the corpus. The daemon owns review state in a locked sidecar so comments survive any regeneration of the source, many readers can subscribe live over SSE, and comments compose with search, sessions, lists, and sharing — at the price of a running daemon, a hosted SPA, and an authoring contract. One is a pocket-knife you carry to any HTML file; the other is a workshop the file must come into.

Verdict — this dimension Depends, and both are fit-for-purpose. redline wins when you want a review loop on an arbitrary HTML file with zero infrastructure and agent-agnostic tooling; its single-file design is exactly right for that, not "lesser" for being small. kb wins when the document is one of many in a long-lived, hosted corpus and review must be durable, live for many readers, and composable with the rest of the platform.

2 · Where comment state lives — the sharpest fork

This single decision propagates into everything else. The fork is about who owns the file and what "durable identity" means.

redline — in the document

One inert JSON block in the <head>: <script type="application/json" id="redline-state">{schemaVersion, updatedAt, threads[]}</script>. No database, no sidecar. A <meta name="redline-agent-guide"> tag advertises the block to agents. No anchor markup is written into the body — highlights are drawn in the browser at view time. The file path is identity; derived docIds must not be cached.

kb — beside the artifact

A daemon-owned sidecar at <state>/<kb>/.review/<artifact_id>.json (kb-comments/1). The source HTML is never touched (invariant #6). The id is path-derived. Every mutation runs load → mutate → atomic-save under a per-kb review_lock; GET returns an ETag; SPA panels live-update over SSE.

Each side's strength is the other's structural cost, and both costs are real. redline's exposure is the rewrite-clobber: the skill itself warns that if an agent regenerates the whole file it must hand-carry the #redline-state block, or the threads vanish — an in-band design cannot, on its own, defend its state against a tool that rewrites the container. (It mitigates this two ways: the skill's discipline that the agent owns the content while redline owns only the state block, plus a self-healing resolver that re-anchors surviving threads silently.) kb's symmetric cost is the opposite dependency: the sidecar is inert without the daemon (the CLI never reads .review/ from disk — every verb goes over HTTP), it is keyed on a stable path, so moving or renaming the source out-of-band orphans the comments, and the artifact carries none of its review state when shared as a standalone file.

3 · Anchor model & reconciliation

Both resolve text anchors fuzzily against the current text rather than trusting stored offsets, and both keep the original quote for auditability. The deepest split is what happens after a successful re-resolve.

redline — self-healing text-quote anchor

One anchor per thread: a normalized quote, sliced prefix/suffix context, and posStart/posEnd position hints (they bias the search, never persisted as ground truth). Resolution is a cascade: an exact quote match wins at confidence 1.0 (duplicate quotes disambiguated by a context-overlap score plus a bounded position-affinity bonus, 0.25·exp(−distance/500), capped at 0.25); on a miss it falls to a Levenshtein-derived fuzzy ratio near the hint, scored confidence = 0.6·fuzzy + 0.4·context and bucketed ANCHORED ≥ 0.9 / NEEDS-REVIEW ≥ 0.6 / ORPHANED < 0.6. On a high-confidence re-resolve it lazily rewrites the stored selectors to the edited text while keeping originalQuote for audit. The auto-heal is bounded by real guards: reconciliation is idempotent when text is unchanged, and a rule forbids a later duplicate phrase from stealing an existing anchor.

kb — id-first ladder, detection-only

Four scopes ranked by regeneration-stability: file (never stale) › chapter (heading-leaf token-set Jaccard ≥ 0.5) › section (exact match on an element id / data-kb-id) › selection (CSS path + ~200-char snippet, Jaro-Winkler ≥ 0.85; thresholds env-tunable). When the artifact carries stable authored ids — which kb's authoring contract mandates — a Section anchor re-resolves by an exact identity check, immune to surrounding-prose churn as long as the id survives. Crucially the resolver is detection-only: it keeps the frozen original, re-evaluates it every reindex, and emits comment.anchor_stale / comment.anchor_resolved over SSE; the only rewrite is an explicit ground-truth kb comments reanchor (the only-anchor-rewrite rule, invariant #6).

Neither is strictly better — they are correct answers to different problems, and the discriminator is document ownership. redline reviews documents it does not own and cannot constrain, so the quote is the anchor and self-healing is how a comment survives an edit; its guards (idempotence, the anti-theft rule, the retained originalQuote) are first-class engineering, not damage control. kb dictates its corpus's authoring, so it can lean on exact ids and refuse to ever drift silently.

Honest caveat

Neither anchoring engine is benchmarked here against real edit/regeneration traces — these are architectural arguments, not measured win-rates. Any text-quote resolver, redline's included, can still mis-heal in the genuinely ambiguous case (two near-identical passages, both edited); the anti-theft rule bounds that risk, it does not eliminate it.

Verdict — this dimension For arbitrary agent-written HTML you do not control, redline's structure-free self-healing anchor is the better fit. For a corpus whose authoring you dictate, kb's id-first ladder with detection-only reconciliation wins on auditability. The choice is whether you can impose an authoring contract or must work on documents as found.

4 · Agent integration & the review loop

Both expose an agent CLI and a skill, and both independently encode the same triage discipline. The defining axes are pull-batch vs SSE-push and agent-agnostic vs Claude-Code-leaning.

redline's contract is a stateless request/response cadence the agent runs on its own schedule: anchors before, edit the document it owns, anchors after, apply to commit a batch atomically. There is no event stream and no notion of waiting on a human in real time — an excellent fit for an agent revising a document it owns while redline merely annotates. The skill ships in-repo for Claude Code (.claude/skills/redline-review/), mirrored for Codex (.agents/skills/redline-review/) with an AGENTS.md, so any skill-capable agent can drive the plain CLI.

kb makes the loop event-driven and bidirectional. Because comments live in a daemon-owned sidecar and the daemon already runs an SSE bus, a human comment in the SPA can wake a long-lived kb comments watch inside a Claude /loop, and the reply round-trips back to the same open tab with no refresh. That live human-to-agent back-and-forth is something redline's stateless architecture does not attempt — bought with a persistent daemon, an SSE transport, and a tighter coupling to Claude Code (the watch drives a loop; the plugin ships slash commands; export emits a Claude prompt).

Verdict — this dimension For portable, dependency-light review where the agent owns a single file and works on its own schedule, redline's pull-batch model and agent-agnostic skill are the better fit (its atomic apply is a clean write primitive). For a real-time human-to-agent conversation across many artifacts inside a running platform, kb's sidecar + SSE watch + /loop does what redline's stateless design does not attempt. Both converged on the same triage rules — the strongest signal each solved the real problem.

5 · Tech stack & architecture

The two designs sit at opposite ends of a complexity-vs-capability axis, and the footprint asymmetry is large but largely a function of scope, not bloat.

redline — one language, one process

~92% TypeScript (the rest CSS; effectively no hand-written JS) on the Bun runtime (engines.bun >=1.3), Preact for the UI, ESM throughout, Playwright tests. A few thousand readable LOC at v0.1.0, MIT per the repo LICENSE. Bun doubles as the bundler; no database, no framework beyond what Bun ships. The whole persistence layer is the #redline-state block.

kb — a Rust platform

A 5-crate workspace (~101k Rust LOC) plus a ~32k-LOC React 18 + Vite + TypeScript SPA; ~790 crates in the lockfile. The axum daemon fronts lancedb (vectors) + sqlite, drives a bge ONNX/fastembed embedder as a sidecar subprocess over IPC, and pushes SSE to the SPA. ONNX Runtime is deliberately isolated to one crate and kept out of the default build.

Comparing the two only on the comment feature flatters redline — it does that job in a fraction of the code. Comparing them as platforms is a category error: most of kb's mass pays for hybrid search, an atlas, agent-memory, sessions, lists, share, versions/diff, a TUI fleet monitor, and self-hosting — things redline never attempts. The honest framing is that redline is small because its problem is small, and that smallness is a feature: you can read the whole thing in an afternoon, and an agent of any flavor can drive it.

Verdict — this dimension As a fit-for-purpose comment tool, redline pays a far smaller complexity and operational tax for the same core job. As a platform, kb wins on capability by construction. Each pays a real cost: redline accepts a single-writer model and a whole-file-rewrite clobber risk for its simplicity; kb accepts ~790 lockfile crates, a sidecar embedder, and a mandatory daemon for its reach.

6 · A focused tool vs a knowledge-base platform

The honest framing: redline and kb answer different questions. redline asks "how do a human and an agent collaborate on this one document?" and answers with the smallest thing that works. Nothing in it indexes, ranks, or remembers across files — and for a single plan you are actively iterating on, a corpus index and an embedder are pure overhead.

kb asks "how do I live with hundreds of agent docs over time?" The things it adds are all corpus-scale: search across every artifact, a 2D atlas, agent-memory, captured Claude sessions, reading lists, notes, reading-progress, saved queries, and gated publishing with the model prompt scrubbed out. Its watch loop is folder-scoped, not file-scoped, so one Claude /loop can service review across a whole directory. None of that is reachable from a tool whose unit of work is one open file — and none of it matters until finding and remembering documents becomes the actual problem.

Verdict — this dimension Depends entirely on how many documents you have and how long they live. For a single agent-authored spec you are editing today, redline is the better-fit tool — kb's daemon and index would be pure overhead. The moment "which doc was that?" and "have I read this?" become real questions, the calculus flips. Smaller is not lesser here; it is the right answer to a narrower, equally real problem.

7 · Collaboration, real-time & self-host

The decisive split is the trust model — and both projects are genuinely local-first. Neither phones home; neither requires a cloud account. They draw the security perimeter in different places and pay different costs for it.

redline's perimeter is the loopback socket (127.0.0.1:7331) plus a single file on disk. It has no auth, proxy, or scrub code because it structurally cannot be reached from off-box — and that absence is a real privacy property, not a missing feature: there is no token to leak, no X-Forwarded-For chain to misconfigure, no subdomain isolation to get wrong, and the entire review state travels with the document as one portable, inspectable file. Its minimalism is itself part of its security argument. (Worth noting: redline is minimal in transport, not in anchoring — it still re-resolves every anchor fresh, scores it, and self-heals carefully; the simplicity is in how it ships state, not how carefully it tracks it.)

kb makes the opposite bet. Because it is a persistent daemon that serves many artifacts — and is explicitly built to be reverse-proxied onto a domain behind an external auth layer — it ships a full hardening stack: bearer auth on all of /api/* (loopback-bypassed), per-route rate-limit buckets, outbound prompt-scrubbing gated on a fail-closed looks_non_loopback check that walks X-Forwarded-For right-to-left over trusted proxies, *.artifacts.<host> origin isolation, and opt-in mDNS. The flip side is more attack surface and more configuration that can be set wrong — which is exactly why the codebase encodes those rules as load-bearing invariants. kb's SSE bus also buys the real-time round-trip redline does not attempt.

Verdict — this dimension A "different goals" axis. For a persistent, multi-artifact setup that may become a shared, internet-reachable service, kb ships the real-time round-trip and the full self-host stack redline deliberately omits. Both are honestly local-first; they diverge only on whether the design ever intends to leave the laptop.

8 · Maturity & when to choose which

The two sit at different points on one curve, and the cleanest way to see it is the storage decision, which propagates into everything else. Neither is more correct — they answer different questions.

Choose redline if…

…you're a solo dev who wants to red-pen one agent-written spec or plan today. You want it portable (comments travel inside the HTML), zero-setup (bun run), agent-agnostic (Claude Code, Codex, or anything skill-capable), and easy to read and hack. Its in-file storage and lazy self-healing anchors are exactly right for a fast, single-document edit loop. Being young and small is a feature here, not a deficiency.

Choose kb-comments if…

…you're building a searchable, long-lived corpus of agent artifacts where review is one workflow among many. You get out-of-band storage that keeps sources pristine and regenerable, detection-only anchoring with a fleet-wide stale dashboard, a live SSE round-trip, threaded replies, quick-reply choices, attachments, and an in-iframe annotator — at the cost of running a Rust daemon + embedder and committing to a Claude-Code-centric integration.

Overall verdict Depends — and that is the honest answer. They serve different points on the same curve, so neither wins outright. If comment review is the whole job, redline is the better fit-for-purpose. If it's a feature of a larger knowledge platform you already want, kb's review is richer and comes essentially for free. The convergence validates the problem; the divergence is a deliberate scope tradeoff.

Convergence & divergence

The clearest way to hold both projects in mind: where they independently agreed (a strong signal the problem is real) and where they deliberately parted.

The sharpest divergences

  • Unit of optimization — redline optimizes the document (one portable file is the whole world); kb optimizes the corpus (review is one feature of an indexed, always-on platform).
  • Where state lives — in-file <script id="redline-state"> block vs out-of-band daemon-owned .review/<id>.json sidecar.
  • Anchor-rewrite philosophy (the deepest) — redline lazily self-heals toward the edited text on a high-confidence match (guarded by idempotence, the anti-theft rule, and originalQuote); kb is strictly detection-only and rewrites only on an explicit reanchor.
  • Anchor shape — a single structure-free text-quote (works on any HTML) vs a 4-scope stability ladder that exploits an authoring contract kb can enforce.
  • Survival of full-file regeneration — kb survives in place; redline accepts a clobber risk if the state block isn't carried over.
  • Delivery — single-doc, re-render-on-file-change, no event bus vs serialized multi-author writes and a true SSE round-trip.
  • Agent portability vs platform integration — genuinely agent-agnostic vs a Claude-Code-shaped layer over an agent-neutral CLI.
  • Operational footprint — a few-thousand-LOC Bun app vs a ~101k-LOC Rust platform with an embedder sidecar.

What each could borrow from the other

redline could take from kb

An opt-in strict mode: surface stale/needs-review prominently and offer a "never auto-rewrite" toggle for high-stakes docs — keep the default self-heal, add an audit-first path.

Id-first as a preferred rung: when the HTML happens to carry stable element ids, resolve by exact id first (an identity check immune to prose churn), falling back to the text-quote cascade — kb's precision for free on structured docs, without losing work-on-anything resilience.

Clobber-resilience: a content-hash or pre-rewrite snapshot of the state block so a full-file regeneration that drops it can recover the threads.

kb could take from redline

A portability export: bake the .review state into a self-contained copy of the HTML (a redline-style inert <head> block) so an artifact can be shared with its comments intact — closing the "not portable as a standalone file" gap.

Agent-agnosticism above the CLI: since the kb CLI is already agent-neutral, ship Codex/Cursor skill mirrors and an AGENTS.md alongside the Claude Code plugin.

An atomic apply batch: a single transactional payload that lands many comment/reply/edit/reanchor ops at once, reducing round-trips versus fine-grained per-endpoint deltas.

And both could borrow each other's clarity about scope-as-design: redline's docs make "we own only the state block, the agent owns the content" an explicit contract; kb's invariants make "detection-only — the resolver never drifts" load-bearing. Each project's discipline is a documentation pattern the other could mirror to keep future contributors from eroding the core choice.

Methodology & caveats

redline's facts were gathered from its README, the redline-review SKILL.md, docs/comment-behavior.md, src/core/anchor.ts, package.json, and the GitHub API, then audited by a dedicated agent that re-fetched the sources and corrected the draft. Eight comparison dimensions were each analyzed and then adversarially verified for factual accuracy and fairness to the smaller project before synthesis. kb's facts come from this repository's docs/comment-workflow.md, docs/authoring-artifacts.md, README, and CLAUDE.md, cross-checked against the source (review.rs, indexer.rs, scrub.rs, the router).

Explicitly unverified
  • redline's prefix/suffix context-window size — the constant is imported into anchor.ts but defined elsewhere; the often-quoted "~32 chars" could not be confirmed, so no figure is asserted here.
  • redline's total commit count — not cheaply exposed by the API; only the active window (created 2026-06-02, last pushed 2026-06-11), 9 stars, and v0.1.0 are stated.
  • redline is MIT via the repo LICENSE file; package.json carries no license field, so the LICENSE is the cited source.
  • kb's Section-scope synthetic-id fallback (<slug>-<tag>-<nth>) is documented but deferred — Section currently resolves by exact id/data-kb-id or reports stale.
  • The anchoring comparison is architectural, not benchmarked — no measured win-rate on real edit/regeneration traces backs the self-heal-vs-detection-only argument.

Both projects are evolving; figures and mechanisms reflect the state observed on 2026-06-17.
