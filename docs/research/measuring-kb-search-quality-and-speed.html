Measuring kb search: a quality-and-speed tester, and what it found across technical and non-technical corpora

kb’s search is now measured on two axes at once. kb bench run reports relevance and latency per (corpus × mode), with a signed delta against a saved baseline — so every future change has to answer “did it move quality, or speed?” out loud. Run against a technical-English corpus and a non-technical Italian one, it says: hybrid is the safe default everywhere, semantic-only is risky on non-English prose, and — once a corpus is compacted — search is uniformly fast (~9 ms), so the best model is simply the most accurate one (bge-large). It also caught a real fragmentation regression hiding behind fine relevance.

2026-06-06 · status:shipped · project:kb · bench

The question this answers

The earlier write-up — Stepping up kb search & recall — laid out a measure-first, bench-gated program (SQ1–SQ5) and shipped it. But two gaps remained in how we judged the work:

  • Speed was invisible. The bench harness scored relevance (Recall@k / MRR / nDCG) but never timed anything. So “did this change cost latency?” was answered by feel, not by a number.
  • Only technical English was tested. Every gold-set query was about lance, the storage actor, RRF fusion. Nothing said whether the gains held for ordinary prose — or for another language.

This artifact closes both. It introduces the quality-and-speed tester baked into kb bench, and reports what it found when pointed at two very different corpora: kb-docs (the technical design docs you are reading inside) and corpus-b (a newly-added, non-technical Italian-language book-synthesis corpus).

The tester: both axes, one run

The change is small and surgical: kb bench run still computes the same relevance metrics, but every query is now timed, and the markdown/JSON report grows a Speed table beside each Quality table — per corpus, per mode.

AxisWhat it reportsRead it as
QualityRecall@1/5/10, MRR, nDCG@10higher = better
Speedwall-time p50 / p95 / mean, plus the daemon’s own srv p50lower (ms) = faster

Three decisions make the speed number trustworthy:

  • Warm-cache, by design. Before timing, the harness fires the whole query set once, untimed. That warms kb’s persistent query-embed cache and loads the lance indexes, so the timed pass measures the search pipeline (fusion, title-boost, the BM25/vector arms, any reranking) rather than the one-time embed. The embed is a fixed model cost — about 90 ms for bge-large on this CPU — that the cache pays once and then reuses; it is real, but it is not what a pipeline change moves.
  • Modes stay comparable. Without the full warm-up, whichever mode ran first ate the cold embed and the rest looked artificially fast off its warmed cache. (The first draft of this tester showed exactly that: hybrid 98 ms, semantic 7 ms — an artifact of run order, not a real gap. Warming the whole set per cell fixed it.)
  • Signed delta on both axes. Pass --baseline old.json and every cell gains its movement vs. the saved run: 0.812 (+0.031) for quality, 108.0 (-12.0) for speed. For latency a negative delta is the win. Old baseline files (pre-speed) still load — the latency fields default in, and their speed delta is simply omitted.
Why fold it into bench, not build a new toolSpeed lives in the same harness that already owns the gold sets, the daemon driver, and the report writer. One run now answers both questions for any retrieval change — and there is exactly one workflow to remember.

The headline: quality climbs monotonically with model size (R@1 0.650 → 0.750 → 0.800), which is why the prod default is bge-large — and once the corpus is compacted, that quality costs essentially nothing. All three models land at ~9ms hybrid p50 (9.8/9.0/8.8ms for small/base/large) and ~4–5ms semantic; the spread between models is now ~1 ms, i.e. noise. So the choice is simply “pick the most accurate model” — large.

What the tester caught — and the fixA first run showed small/base hybrid at 33ms–45ms, ~4× slower than large’s 8ms — the opposite of what vector dimensionality predicts, and reproducible across run orders. The cause was lance fragment/version accumulation: the bench data dir had been reused across dozens of runs, so each kb carried ~150 data fragments and 200–500 stale index versions that every query re-read (exactly the degradation compact_all exists to prevent). The per-kb spread merely tracked which kbs had crossed the >200-version startup auto-compact threshold. Running kb compact on all three (small alone shed 58 fragments → 1) collapsed it: hybrid is now 8.8–9.8ms across all models, monotonic in dim as a brute-force scan over 91 rows should be. Not an index bug — an ops one, and the tester surfaced it.

Results: non-technical Italian (corpus-b)

The corpus-b corpus is the user’s newly-added, non-technical kb: 10 chapter syntheses plus a concept-map index of a non-technical self-help book, in Italian. 24 natural-language queries (“cos’è la crescita silenziosa”, “attraversare la stagione delle radici e del silenzio”, “il raccolto è uno specchio”…), each labelled to the chapter whose concept it owns, covering all 11 documents. bge-large, warm-cache.

Two things jump out, and they are the inverse of the usual technical-corpus intuition:

  • Semantic-only lags badly (R@1 0.583). bge is an English-centric embedder; on Italian prose the vector arm loses signal, so pure semantic search misses the right chapter at rank 1 over 40% of the time.
  • Keyword matches hybrid on Recall@1 (both 0.792). With the embedding weakened, the lexical (BM25) arm carries recall — exact Italian terms (“silenzio”, “crescita silenziosa”, “raccolto”) are unambiguous and land the chapter; the vector arm adds little to finding it here.
Hybrid is the safety netHybrid ties keyword on Recall@1 (0.792) but edges it on ranking quality (MRR 0.883 vs 0.871, nDCG 0.913 vs 0.903): RRF fusion lets the strong lexical arm carry recall while the weak vector arm still refines the order — without the operator having to know, per language, which arm to trust. This is the SQ2 fusion + title-boost work paying off on exactly the kind of corpus it was never tuned for. The non-tech corpus didn’t need special handling; it needed hybrid.

The arms swap importance between the two corpora — lexical matters more on non-English, semantic matters more on technical English — but hybrid is the right default in both cases, and the fusion absorbs the difference. The practical rules:

  • Default to hybrid. It is the only mode that never finishes worse than the alternatives, on either corpus.
  • Be wary of semantic-only on non-English content. If a corpus is not English, the lexical arm is doing more work than the relevance score alone reveals — do not drop it.
  • Speed is not the constraint — but keep the corpus compacted. Warm-cache p50 runs 5.3ms–10.1ms on corpus-b and 4.1ms–9.8ms on kb-docs once compacted; the one cost to keep in mind is the one-time ~90ms embed on a novel query (the persistent cache amortises it). Left un-compacted, fragment accumulation can inflate hybrid latency several-fold — run kb compact after heavy re-indexing.
  • SQ4 reranker and SQ5 chunking stay opt-in / OFF. Neither helps short documents (the reranker scores too thin an excerpt; chunking fixes a 512-token truncation that short docs rarely hit). They are levers for noisier candidate sets and genuinely long documents — enable per corpus and bench that corpus.

Using the tester on the next change

The whole point is repeatability. To judge any future retrieval change:

# 1. bench daemon, no auth, both corpora (kb-docs-{small,base,large} + corpus-b)
./target/fast/kb daemon --config bench/kb.local.toml      # loopback :4100

# 2. baseline BEFORE the change
kb bench run --queries bench/queries/corpus-b.jsonl --kbs corpus-b \
  --modes hybrid,semantic,keyword --k 1 --k 5 --k 10 \
  --daemon http://127.0.0.1:4100 \
  --json docs/bench/corpus-b-base.json --output docs/bench/corpus-b-base.md

# 3. make the change, rebuild, then re-run with --baseline
kb bench run --queries bench/queries/corpus-b.jsonl --kbs corpus-b \
  --modes hybrid,semantic,keyword --k 1 --k 5 --k 10 \
  --daemon http://127.0.0.1:4100 --baseline docs/bench/corpus-b-base.json

Read the deltas: quality up is a win; speed down (ms) is a win. Ship only when relevance is at least flat and the latency cost is justified for that corpus. The saved reports for this run live at docs/bench/kb-docs-2026-06-06-qs.{md,json} and docs/bench/corpus-b-2026-06-06.{md,json}.

Open threads

  • Compaction is part of measuring (resolved). The one “anomaly” this run produced (small/base hybrid 33–46 ms) was traced and fixed: stale lance fragments/versions in a reused bench dir, cleared by kb compact — latency collapsed to ~9 ms across all models, monotonic in dim. Lesson folded back in: compact the bench corpora before trusting absolute latency, and read a sudden latency climb as a fragmentation signal, not a code regression.
  • Chunking on a long-doc corpus. SQ5 is shipped and OFF. The bench bears out that short docs don’t benefit; the unmeasured case is a genuinely long-doc corpus (research / platform). Enable chunked_embeddings per kb, reindex, and bench that corpus before trusting it.
  • Reranker with real passage text. Re-bench SQ4 once it scores chunk text rather than the thin body excerpt — that is the combination the plan always intended.
  • More non-tech gold sets. One non-English corpus is a strong signal, not proof. A second (different language or domain) would harden the “don’t drop the lexical arm” rule.
