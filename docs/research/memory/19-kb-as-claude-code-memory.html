Topic 19 · Hub · kb as Claude Code memory · Research · 2026-05-22

kb is already most of a memory
for Claude Code.

Claude Code forgets everything between sessions. The usual fixes — CLAUDE.md rules and the file-based auto-memory — hold static facts and compressed summaries, but lose the reasoning: what you tried, why it failed, the conditions that made one approach work. A wave of tools (memplace.app/MemPalace, Mem0, claude-mem) fills that gap with a vector store behind an MCP server. Here's the thing: kb is that, and more — hybrid search over a watched corpus, plus a UI, a comment system, and a 2-D atlas. This series asks how to turn kb into Claude Code's memory, across three approaches, and argues kb's real edge isn't storage — it's being the only memory you can see and correct.

The thesis, and the recommendation

Thesis: storage and retrieval are solved problems; kb already does them well. The differentiated value is a memory cockpit — browse it in the SPA, map it in the atlas, and correct it by comment through the loop kb already ships. No off-the-shelf memory tool has a UI. Recommendation: start with Approach A (a [kb.memory] corpus + a CLAUDE.md protocol — an afternoon, no code); add dedicated kb CLI verbs when the shell-call friction bites; build C only if agent memory becomes a direction kb means to own.

01 — The problem

What CLAUDE.md and auto-memory can't hold

Two memory mechanisms ship with Claude Code today. Both are real; both have a shape-shaped hole.

  • CLAUDE.md — hand-curated rules, always in context. Perfect for "always use the fast profile". But it's static, you maintain it by hand, and it's not searchable beyond being a file the model reads top-to-bottom.
  • File-based auto-memory (~/.claude/projects/<slug>/memory/) — a MEMORY.md index plus typed markdown notes (user / feedback / project / reference). A real step up: the agent writes and reads these across sessions. But the index is loaded wholesale into context and grepped, not semantically searched, and entries trend toward compressed summaries.
The gap everyone names. CLAUDE.md stores rules; auto-memory stores summaries; neither preserves the diagnostic path — the approaches you tried, why some failed, the exact conditions that made one work. That nuance is precisely what you want back three weeks later, and precisely what a summary throws away. Filling it needs (a) a richer store than a one-line note, and (b) semantic recall so you find the memory without remembering its words.

Two recurring lessons from the field. One: the tools won't fire without a CLAUDE.md telling the agent to save and recall — MemPalace solves it with a "Memory Protocol" injected by its status tool. Two: the interesting design choices are about capture (lifecycle hooks vs. manual), recall ergonomics (CLI verbs vs. an MCP server), and curation/trust — not about which vector DB. Everyone ships ChromaDB/Qdrant/SQLite; nobody ships a way for the human to look at and fix the memory.

The cockpit thesis

The missing 20% is behaviour (a protocol so the agent uses it), ergonomics (MCP / faster ingest), and framing. The framing is the real insight: every competitor is a black-box store you query and trust. kb is the one memory that's a browsable, mappable, comment-curated, self-hosted cockpit — the only place a human can see what the agent remembers, search it, annotate it, and converse to correct it. That's not a vector-DB feature; it's the thing kb already is. Reframe the question from "is kb a good memory store?" to "kb is the missing UI and curation layer for agent memory."

04 — Three approaches

From an afternoon to a product

Each gets its own deep-dive; each is judged on usefulness for Claude-the-agent and for the end user.

A · Corpus + protocol (zero-build)

A [kb.memory] corpus of HTML memories; a CLAUDE.md recall/remember protocol; tiny recall/remember skills; an optional episodic [kb.sessions] corpus fed by a SessionEnd hook. No kb code. Highest leverage-per-effort — the place to start.

B · dedicated kb CLI verbs (integrate)

Promote A's skills to dedicated kb verbs — kb recall / kb remember — invoked through the Bash tool Claude already has: no MCP server, no extra process, zero context-token tax. (An MCP server, Anthropic's memory tool, and buying Mem0/MemPalace are weighed and rejected for Claude Code.) Small kb-cli code.

C · Native subsystem (full build)

Memory as a first-class kb feature: salience/decay ranking, a real ingest endpoint, lifecycle-hooks plugin, comment-driven invalidation, an SPA Memory view with the atlas as a mind-map. Most powerful, most expensive — defer unless memory becomes a pillar.

The data underneath every approach is the same kb HTML artifacts, so moving up the ladder never migrates memories — only the front door and the polish change. That makes the phasing below low-risk: each step is additive.

06 — Recommendation

A phased path

  1. Now — Approach A. Add [kb.memory], drop the memory protocol into CLAUDE.md, add the recall/remember skills. Live with it. This alone is a real semantic memory with a UI.
  2. When the shell-call friction annoys you — Approach B. Promote the skills to dedicated kb recall/remember verbs and add the UserPromptSubmit recall hook — no MCP, nothing extra to run.
  3. Only if agent memory becomes a kb pillar — C. Pull the native pieces in cheapest-first: a kb remember/recall verb pair → the UserPromptSubmit proactive-recall hook → the Memory view → decay/consolidation.
  4. Sanity check. If a need is purely "remember ambient facts", a throwaway off-the-shelf tool is fine — but spend kb's effort on the long-form, curated material no off-the-shelf tool provides.
Dogfooding note. This report is itself a kb artifact in the kb-docs corpus — so the natural way to react to it is to open it in kb and drop comments on the bits you disagree with. That comment loop is exactly the curation mechanism Approach A proposes for memory. The medium is the message.
