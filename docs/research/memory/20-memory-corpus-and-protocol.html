Topic 20 · Approach A · Corpus + protocol · Research · 2026-05-22

Give Claude a memory it can search —
without writing a line of kb code.

kb is already a hybrid-search engine over a watched folder, with a comment-driven review UI and a 2-D map of everything in it. So the cheapest useful memory for Claude Code is convention, not code: point a [kb.memory] corpus at a directory, write each memory as a small HTML artifact, and teach Claude — in CLAUDE.md — to recall before it answers and remember after it learns. The whole build is a config block, a protocol, and two tiny skills. The honest costs: memories must be HTML (kb won't index .md), and a freshly-written memory is searchable after a ~400 ms watcher debounce.

The whole approach in five lines

Store: a [kb.memory] corpus (an HTML artifact per memory). Write: Claude drops a file with the Write tool → the watcher indexes it. Recall: kb search "<topic>" --kb memory --mode hybrid --json. Curate: the human browses the SPA / atlas and steers via kb comments + kb comments watch. Behave: a CLAUDE.md "memory protocol" makes the loop actually fire — the single lesson every memory tool learns the hard way.

01 — How it works

A watched corpus is already a memory store

Writing a memory is writing a file; recalling one is a search. Everything else kb already does.

The write path

A memory is a single-file HTML artifact dropped into the corpus directory. kb's watcher (crates/kb-core/src/watcher.rs) emits a synthetic watch.create, the indexer parses it (title, kb-tags, kb-category, headings, body), computes a path-based id (ArtifactId::from_path — so editing a memory keeps its id; only renaming changes it), embeds the <body> text, and writes the row. Claude already writes files — so "remember this" is just a Write with the right <meta> tags.

Two facts that shape this approach (verified in the code): kb indexes .html/.htm only (watcher.rs:184 is_html; non_html_files_are_ignored covers the rest), so memories are HTML — the existing ~/.claude/.../memory/*.md store can't be pointed at kb unchanged. And there is no "POST a doc body" ingest endpoint — the path is write-file → watcher (~400 ms debounce, config.rs DEFAULT_DEBOUNCE_MS). POST /api/kb/{kb}/reindex forces a rescan but takes no body. For human-paced memory this latency is invisible; for tight write-then-immediately-recall loops it's worth knowing.

The recall path

kb search "user's deploy preferences" --kb memory --mode hybrid --json --limit 5
kb get <id> --kb memory --format html    # read a hit's full HTML (body included)

Hybrid mode fuses BM25 over title/body/headings with bge-small vector similarity via reciprocal-rank fusion (storage/lance.rs, RRF k=60). That is exactly the retrieval a memory layer needs — keyword precision and semantic recall — and kb has shipped it since v0.1. --json gives Claude a clean envelope ({hits:[{id,title,path,kb_category,…}], ms}) to reason over.

Where it lives

Memory is personal and local, so the natural shape is a local kb daemon on 127.0.0.1:4000 with a [kb.memory] corpus pointing at a host directory; the kb CLI talks to it with no extra flags. The already-running dockerised instance at kb.example.com can host it too — just bind-mount the directory to /srv/memory (it serves corpora from /srv/<name>) — but for an agent reading/writing on the same box, local-first is simplest and lowest-latency.

Hybrid recall needs the daemon running. kb search --mode hybrid runs the embedder inside the daemon; with no daemon reachable the CLI silently falls back to keyword-only (BM25), losing the semantic half — and errors outright if the corpus was never indexed. Keep the local daemon up, or pass --daemon http://127.0.0.1:4000 to force HTTP and get a hard error instead of a quiet downgrade. On the dockerised kb.example.com instance the host CLI also needs its bearer token, and the artifact host suffix is deployment-specific (.artifacts.kb.example.com).
02 — Useful for Claude?

Storage was never the problem — behaviour is

kb gives Claude excellent recall. Whether Claude uses it is a prompt-engineering problem, not a storage one.

Recall quality: high. Hybrid search over embedded prose beats the status quo handily. Today's file-based auto-memory is a hand-maintained MEMORY.md index that is loaded wholesale into context and grepped — there is no semantic search. Swapping that for kb search means Claude can ask "what did we decide about rate-limiting?" and get the right memory even if the file never used the word "rate-limiting".

The catch — and it's the whole game — is the protocol. Every memory system in the wild (MemPalace, Mem0, claude-mem) reports the same lesson: the tools won't fire on their own. Without an instruction telling Claude to search-before-answering and to persist what it learns, memories are written rarely and read never. MemPalace bakes a "Memory Protocol" into its status tool; here the equivalent lives in CLAUDE.md (recipe §05). This is the single highest-leverage artifact in the whole approach.

Token budget & transparency. Recall is just-in-time: Claude pays tokens only for the hits it pulls, not for a wholesale memory dump — the right shape for long sessions. And because recall is an ordinary kb search shell call, every read/write is a visible tool call in the transcript: auditable, debuggable, no hidden retrieval.

What Claude gains vs. CLAUDE.md + auto-memory today
  • Semantic recall instead of grep over an index file.
  • Scale — hundreds/thousands of memories without bloating the always-loaded context (only MEMORY.md-style indices grow with the store; kb keeps the index on disk).
  • The diagnostic path survives — a memory artifact can hold the full "what I tried, why it failed, what worked", not just a one-line summary. That nuance is exactly what CLAUDE.md and compressed auto-memory throw away.
03 — Useful for the user?

You can finally see what the agent remembers

This is kb's un-copied edge. No other memory tool gives the human a browsable, correctable view of the agent's mind.

Mem0, MemPalace, claude-mem all store memory in a database you never look at. kb's memory is a corpus you can open in a browser: the SPA gallery lists every memory; full-text + semantic search works from the UI; the UMAP atlas draws a 2-D map of clusters — literally a picture of what Claude knows about you and your projects. For an end user, that turns "trust the black box" into "read and edit the notebook".

Memories stay split from your other artifacts. Point a dedicated [kb.memory] corpus at its own directory and it becomes its own gallery in the SPA — chosen from the kb dropdown, never merged into kb-docs / research / the rest (the gallery scopes to one active kb at a time). So the split the design wants is the corpus boundary itself, for free. What zero-build does not give you: an in-gallery facet to split memories by category inside one corpus, or a single bespoke "memory platform" surface — a dedicated Memory view (timeline + atlas + inline curate in one place) is the Approach C upgrade.
The curation loop (already built)

Open a memory, disagree with it, and drop a kb comment — "this is stale, we moved to Postgres". kb comments watch --path <memory> --json surfaces it to a Claude loop; Claude edits the memory artifact, kb comments reply + resolve, and your SPA tab updates live over SSE. Human-in-the-loop memory curation, by conversation — the comment system kb shipped for reviewing artifacts is exactly a memory-correction protocol. Quick-response --choice-json buttons even let you approve/forget a proposed memory with one tap.

Continuity: this doesn't replace the auto-memory taxonomy you already use — it upgrades it. Keep the four types from the auto-memory taxonomy as kb-category values — memory-user / memory-feedback / memory-project / memory-reference (the memory- prefix facets them apart from other artifacts and matches the recipes below); the difference is they're now embedded, searchable, visualised, and commentable. Self-host: it's your daemon on your box — nothing leaves the machine (the same property MemPalace markets, but you already run the daemon).

04 — A second corpus

Episodic memory: store the sessions verbatim

Curated memory is the summary. A parallel [kb.sessions] corpus is the unabridged transcript — searchable forever.

MemPalace's strongest idea is the split between closets (compressed summaries) and drawers (verbatim originals, never deleted) — keep everything, make it findable, don't let an extraction step discard the reasoning. kb makes this a one-line addition: a second corpus, [kb.sessions], into which a SessionEnd hook drops each finished conversation as an HTML artifact. Recall then spans both: curated facts from memory, and "what exactly did we say three weeks ago" from sessions.

  • memory — small, hand/agent-curated, typed, the hot path for "what do I know about X".
  • sessions — large, append-only, verbatim; the cold archive for "find the conversation where we worked out Y". bge-small embeddings make even a big transcript pile semantically searchable.

Because kb ids are path-based and the store is just files, the sessions corpus is also trivially prunable, greppable, and backup-friendly. The capture hook is in the recipes (§05).

05 — Recipes

Copy-paste: stand it up today

A config block, a protocol, two skills, one hook. Nothing here touches kb's source.

a · kb.toml — the corpora

# local `kb daemon` config (127.0.0.1:4000)

# GLOBAL / user-wide memory — facts true across every project
[kb.memory]
path = "~/.claude/kb-memory"          # Claude writes HTML memories here
embedding_model = "bge-small-en-v1.5"         # 384-dim → hybrid + semantic recall
[kb.memory.outbound]
strip_kb_prompt = true                        # belt-and-braces if ever served non-loopback

# PROJECT-LOCAL memory — one corpus per project (the analogue of a project CLAUDE.md)
[kb.memory-kb]
path = "~/project/kb/.kb-memory"      # lives alongside the project it's about
embedding_model = "bge-small-en-v1.5"
[kb.memory-kb.outbound]
strip_kb_prompt = true

# EPISODIC — verbatim transcripts (recipe e)
[kb.sessions]
path = "~/.claude/kb-sessions"
embedding_model = "bge-small-en-v1.5"

# On the dockerised kb.example.com: bind-mount each dir to /srv/<name> in
# ~/deploy/docker-compose.yml, then set path = "/srv/memory" etc.
Memory scopes — local + global. kb has no single "search everything" query (recall hits one corpus at a time; folder filters scope the gallery, not search), so model levels as separate corpora: a global [kb.memory] for user-wide facts and a project-local [kb.memory-<project>] per repo — mirroring global ~/.claude/CLAUDE.md vs a project CLAUDE.md. The protocol picks the scope on write (user preference → global; a project decision → that project's corpus); recall searches both and merges (recipe c). A single native cross-scope memory search — one query spanning local + global, or folder-scoped recall within one corpus — is an Approach C enhancement; zero-build, it's two searches and a merge.

b · CLAUDE.md — the memory protocol (the part that makes it work)

## Memory (kb-backed)

You have a persistent, searchable memory: the `memory` kb corpus. Treat it as
long-term memory that survives across sessions.

RECALL — before you act. At the start of a task, and before you answer anything
about the user, this project, past decisions, or prior work, search first:
  kb search "<topic>" --kb memory-<project> --mode hybrid --json --limit 5   # project-local
  kb search "<topic>" --kb memory --mode hybrid --json --limit 5            # then global
Read promising hits with `kb get <id> --kb <the hit's kb> --format html`. Don't guess
when memory might know — search both scopes, then answer. (Also search `--kb sessions`
for "what did we say about X" recall.)

REMEMBER — after you learn. When you learn something durable — a user preference,
a project decision, a corrected mistake, a useful external reference — write a
memory — a project-specific fact in the project-local corpus dir, a user-wide one in
the global ~/.claude/kb-memory/ — as a small HTML file <kebab-slug>.html with a
real <title>, one <h1>, <meta name="kb-category" content="memory-{user|feedback|
project|reference}">, <meta name="kb-tags" content="...">, and the content as
<body> prose (only <body> is embedded). One memory per file.

DON'T. Don't store secrets, ephemeral task state, or anything already in CLAUDE.md
or the code. Search before writing — edit the existing memory instead of adding a
near-duplicate (editing keeps its id; renaming changes it).

c · the recall skill (.claude/skills/recall/SKILL.md)

---
name: recall
description: Search kb memory for relevant past context before answering or acting
---
Search project-local memory, then global, and merge the hits (kb has no single
cross-corpus query, so search each scope):
  kb search "$ARGUMENTS" --kb memory-<project> --mode hybrid --json --limit 5
  kb search "$ARGUMENTS" --kb memory --mode hybrid --json --limit 5
For promising hits, read the body: kb get <id> --kb <that hit's kb> --format html
Report only what's relevant to the current task; cite the memory titles.

d · the remember skill (.claude/skills/remember/SKILL.md)

---
name: remember
description: Persist a durable learning as a searchable HTML memory artifact
---
First `kb search` to avoid duplicates. Then write ONE HTML file to
~/.claude/kb-memory/<kebab-slug>.html:
  - <title> = one-line summary (BM25 primary field)
  - <meta name="kb-category" content="memory-{user|feedback|project|reference}">
  - <meta name="kb-tags" content="comma, separated, retrieval, keys">
  - <h1> matching the title; the memory as <body> prose (only <body> is embedded)
If a near-duplicate exists, EDIT it instead (keeps the artifact id). The watcher
indexes the file within ~400 ms.

e · episodic capture (settings.json + a hook script)

// .claude/settings.json
{ "hooks": { "SessionEnd": [ { "hooks": [
  { "type": "command", "command": "~/.claude/hooks/kb-capture.sh" } ] } ] } }
#!/usr/bin/env bash
# ~/.claude/hooks/kb-capture.sh  — wrap the finished transcript as an HTML memory
set -euo pipefail
DIR=~/.claude/kb-sessions; mkdir -p "$DIR"
payload=$(cat)                                   # hook JSON arrives on stdin
tp=$(jq -r '.transcript_path // empty' <<<"$payload"); [ -z "$tp" ] && exit 0
sid=$(jq -r '.session_id // "session"' <<<"$payload"); ts=$(date +%Y-%m-%dT%H-%M-%S)
text=$(jq -rs '[.[].message.content?] | flatten | map(strings) | join("\n\n")' "$tp" 2>/dev/null | head -c 200000)
{ printf '<!doctype html><html lang="en"><head><meta charset="utf-8">'
  printf '<title>Session %s</title>' "$ts"
  printf '<meta name="kb-category" content="memory-session">'
  printf '<meta name="kb-tags" content="session, transcript, episodic">'
  printf '</head><body><h1>Session %s</h1><pre>' "$ts"
  printf '%s' "$text" | python3 -c 'import html,sys; sys.stdout.write(html.escape(sys.stdin.read()))'
  printf '</pre></body></html>'; } > "$DIR/$ts-$sid.html"
Sketch, adapt to taste. The transcript is JSONL; the jq filter above is a pragmatic flatten — tune it to keep only user+assistant turns, or to summarise instead of storing verbatim. The SessionEnd hook payload carries transcript_path and session_id on stdin.

Recommendation
