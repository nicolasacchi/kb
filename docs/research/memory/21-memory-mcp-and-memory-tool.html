Topic 21 · Approach B · Dedicated kb CLI verbs · Research · 2026-05-22

The integration is a CLI verb,
not an MCP server.

The right question turned out to be: why add an MCP server when a CLI tool does this better? Approach B is exactly that — give Claude Code memory through two purpose-built verbs, kb remember and kb recall, invoked through the Bash tool it already has. No extra process, no tool-schema tax on every session's context — just the daemon you already run. This file sketches the verbs, makes the token + simplicity case, and weighs the alternatives it replaces (an MCP server, Anthropic's memory tool, and off-the-shelf Mem0/MemPalace) so the rejection is honest, not hand-waved.

Why CLI verbs win

An MCP server advertises typed tools the model auto-calls — but its definitions sit in the context window every session, used or not (Anthropic's own memory tool injects ~2.5k tokens of schema). Dedicated kb verbs ride the Bash tool that's already there, so they add zero persistent overhead — you pay only for the calls you make, plus a few CLAUDE.md lines. MCP's genuine edge is narrow (auto-fire reliability + cross-client reuse), and a tight protocol plus a recall hook closes most of it. So Approach B is two small verbs — the rung between A's skills (no code) and C's native subsystem (lots).

01 — The verbs

Two commands carry the whole approach

Purpose-built kb subcommands — more robust than composing kb search + a write in a skill, testable, and usable outside Claude too.

Proposed memory verbs (net-new kb-cli subcommands)
VerbWhat it doesExample
kb recallhybrid-search the memory corpora and merge; the read pathkb recall "deploy prefs" --scope all --json
kb rememberwrite a memory artifact into the chosen scope; the watcher indexes itkb remember "prefers Postgres" --scope global --category memory-user
kb forgetdelete (or soft-flag) a memory by idkb forget 7f3a… --kb memory

Scope is the one real subtlety. kb search runs against one corpus at a time, so "local + global" is two corpora — a project-local [kb.memory-<project>] and a user-wide [kb.memory] (the split Approach A sets up). kb recall --scope all queries both and merges by score; --scope project / global narrow it. kb remember writes to the scope you name (a user preference → global; a project decision → project). The verbs are a thin, robust layer over kb internals that already exist — kb remember writes the right HTML into the right corpus dir (watcher indexes within ~400 ms), kb recall wraps the hybrid search and stitches the per-scope result lists.

What's new vs. Approach A. A delivers the same operations as skills — prompt files that tell Claude to compose kb search and a Write. B promotes them to real kb subcommands: deterministic, unit-testable, scriptable, and not dependent on the model assembling the right invocation each time. Small kb-cli code, no daemon change required — the synchronous-ingest and ranking work is Approach C.

02 — Alternatives, weighed

Why not an MCP server, the memory tool, or Mem0

All three were the original draft of this approach. Here's why a CLI verb beats each — for Claude Code specifically.

Rejected for Claude Code (kept here as honest context)
OptionWhat it isWhy CLI verbs win instead
MCP server (kb mcp)a stdio server advertising recall/remember as typed toolstool definitions cost context every session; it's a second process to run and supervise. Its only real edge — auto-fire — is largely recovered by a CLAUDE.md line + a recall hook (§04).
Anthropic memory toolclient-side /memories CRUD via the API SDK (BetaAbstractMemoryTool)it's an API / Agent-SDK feature for agents you build — not a backend the Claude Code CLI exposes. Relevant only if you write your own agent; then kb can back it, but that's outside this CLI.
Buy (Mem0 / MemPalace)off-the-shelf memory layers, themselves MCP serversmore moving parts (a server, sometimes cloud); they don't give you a browsable, comment-curated store. Use one for throwaway ambient facts if you must — and keep kb for the long-form, curated memory it's uniquely good at.
The principle

The only process that should run is the kb daemon — it already serves the artifacts and holds the memory; recall and capture are just verbs that talk to it over the CLI Claude already uses. Every alternative above adds a second moving piece to buy back convenience the daemon + a verb already provide.

03 — The two lenses

Useful for Claude? Useful for the user?

For Claude-the-agent

Reliable recall without the token tax. A registered MCP tool fires a little more readily than "remember to run a command" — but a CLAUDE.md protocol ("recall before you answer") plus the UserPromptSubmit recall hook in §04 makes recall happen before the model even responds, which is stronger than auto-fire and costs nothing until invoked. Every read/write stays a visible Bash tool-call: auditable, debuggable, no hidden retrieval, no schema sitting in context.

For the end user

Nothing new to run. No MCP server to configure, supervise, or reason about — the daemon you already have answers kb recall and absorbs kb remember. You keep the whole kb cockpit (browse, atlas, comment-curation), it stays fully self-hosted, and the memory is just files you can read and edit. The cost is honest: the verbs are net-new code (a small kb-cli addition), so B isn't quite as zero-effort as A's skills — but it's far less than C.

Lock-in is nil. The store underneath is plain kb HTML artifacts. Start with A's skills, promote to these verbs, later pull in C's subsystem — the memories never migrate; only the front door changes.
04 — Recipes

The verb sketch, the protocol, the recall hook

A thin clap surface over existing kb internals, plus the two lines that make the agent use it.

a · the verbs (kb-cli — illustrative clap surface)

// crates/kb-cli/src/main.rs — new subcommands
enum MemoryCmd {
    /// Search memory (project + global) and merge by score.
    Recall { query: String, #[arg(long, default_value="all")] scope: Scope,
             #[arg(long, default_value_t=5)] limit: u32, #[arg(long)] json: bool },
    /// Write a memory artifact into the chosen scope.
    Remember { text: String, #[arg(long, default_value="project")] scope: Scope,
               #[arg(long)] category: Option<String>, #[arg(long)] tags: Vec<String> },
    /// Delete (or soft-flag) a memory by id.
    Forget { id: String },
}
// recall  → for each in-scope kb: GET /api/search?q=&kb=… (hybrid); merge + truncate.
// remember→ render memory HTML, write into the scope's corpus dir; watcher indexes (~400ms).
// forget  → remove the file (or set kb-status="forgotten").

b · CLAUDE.md — the protocol (unchanged from A, minus the skill)

## Memory (kb-backed)
RECALL before you act: `kb recall "<topic>" --scope all --json` — read the top hits,
don't guess when memory might know. REMEMBER durable learnings:
`kb remember "<fact>" --scope project|global --category memory-{user|feedback|project|reference}`.
Don't store secrets or ephemeral state; search before writing to avoid duplicates.

c · optional — proactive recall on every prompt (.claude/settings.json)

{ "hooks": { "UserPromptSubmit": [ { "hooks": [
  { "type": "command",
    "command": "kb recall \"$CLAUDE_USER_PROMPT\" --scope all --limit 5 --json" } ] } ] } }

This injects the top memories before the model answers — true RAG, no tool call, no MCP. It's the single highest-value automation and the natural bridge to Approach C, which makes the hook + ranking first-class.

Recommendation

This is the integrate step after A. Live on A's skills first; when the prompt-composition gets fiddly, promote them to kb recall/kb remember verbs (this file) and add the UserPromptSubmit recall hook. Reach for the full native subsystem — synchronous ingest, salience/decay ranking, the Memory view — only when these verbs hit their limits: that's Approach C. No MCP server enters the picture at any rung.
