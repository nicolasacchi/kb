Topic 22 · Approach C · Native subsystem · Research · 2026-05-22

If memory becomes a pillar,
build it into kb.

Approaches A and B sit on top of what kb already is. Approach C turns memory into a first-class kb feature: a memory-aware artifact schema with salience and decay, a synchronous ingest behind a kb remember verb that kills the file-drop latency, a Claude Code lifecycle-hooks plugin that captures and recalls automatically, comment-driven invalidation built on machinery kb already has, and an SPA Memory view that renders the atlas as a mind-map of everything the agent knows. It is the most powerful option and the most expensive — so the verdict, up front, is conditional.

Read this before you fall in love with it

Everything below is a proposal, not a current kb feature. It is genuinely good — recency/decay ranking, synchronous ingest, auto-capture hooks, a forgetting mechanism, a mind-map UI — and it would make kb a real, differentiated agent-memory product. But it is a multi-crate build with ongoing maintenance, and Approach A already delivers ~80% of the user-visible value for an afternoon's work. Build C only if "agent memory" becomes a direction you want kb to own — not to scratch the first itch.

01 — Schema & ranking

Memories aren't documents — they age, repeat, and contradict

A memory subsystem needs three things plain artifacts don't: salience, decay, and supersession.

Keep the four types from today's auto-memory as kb-category values (memory-user, memory-feedback, memory-project, memory-reference) and add three memory-specific metas the parser would learn to read:

<meta name="kb-salience"   content="0.8">          <!-- 0..1 importance; boosts ranking -->
<meta name="kb-decay"      content="slow|fast">    <!-- how fast recency weight fades -->
<meta name="kb-supersedes" content="<old-id>">     <!-- this memory replaces that one -->

Ranking = hybrid × salience × recency. kb's hybrid BM25+vector score answers "is this relevant?"; a memory layer also needs "is this still important and current?". A post-fusion re-rank multiplies the RRF score by a salience weight and a recency-decay factor (a project note about a sprint decays fast; a user preference decays slowly). The re-rank itself is just re-sorting the rows lance already returns — it doesn't touch the index; the only index-side work is surfacing kb-salience/kb-decay onto the result rows (a parser + schema add, since today's DocSummary carries neither).

Consolidation ("closets"). Borrow MemPalace's compression idea: a periodic job clusters memories (kb's atlas already runs k-means over the embeddings) and proposes a single summary memory per cluster — the "closet" — linking the originals as kb-supersedes sources. The summary becomes the hot recall target; the originals stay as the verbatim record. The agent proposes the closet; the human approves it (§04).
02 — Close the ingest gap

Write a memory and recall it in the same breath

The one architectural limitation A and B work around: there's no way to add a doc except by writing a file and waiting for the watcher.

Today the only ingest path is file-drop → watcher (~400 ms debounce); there is no body-POST endpoint (verified — the closest is POST /api/kb/{kb}/reindex, which takes no body). For human-paced memory that's invisible, but for an agent that writes a memory mid-task and wants to recall it moments later, the round-trip matters. Yes — make it a kb command (the natural answer to "can this be a CLI verb?"): kb remember writes the artifact and asks the daemon to index it now. Nothing new runs — just the daemon you already have:

# the interface: a CLI verb — no MCP, no extra process
kb remember "user prefers Postgres for new services" \
    --kb memory --scope global --category memory-user \
    --tags db,prefs --salience 0.8 [--supersedes <id>]
→ remembered 7f3a… · indexed · searchable now

# daemon-side it writes the HTML artifact + indexes it synchronously;
# the same op can also back an optional POST /api/kb/{kb}/artifacts for the SPA.

Mechanically, kb remember writes the HTML artifact into the corpus dir (so it stays a plain file the watcher and reconciler still own) and tells the daemon to index it synchronously, returning once it's searchable. One interaction to design around: the corpus dir is under the live watcher, which fires a watch.create ~400 ms later — and Created events bypass the indexer's content-hash dedup gate (only Modified is gated), so a naïve version would embed the file twice (embedding is the ~170 ms-per-doc slow path). The verb (or the daemon op it calls) must pre-seed the content-hash cache, or suppress the watcher's next event for that path, so the follow-up is a no-op. The point of the comment that prompted this: no MCP and no second process — the daemon that already serves the artifacts does the indexing; kb remember is just its front door.

Invariant to respect: the storage actor is single-writer-per-kb by design (storage/actor.rs, CHANNEL_CAPACITY = 1024). The ingest (driven by kb remember, or the SPA) enqueues through the same actor — no parallel writer — so this stays consistent with kb's concurrency model.
03 — Capture

A lifecycle-hooks plugin so memory is automatic

The agent shouldn't have to remember to remember. Claude Code's hooks make capture and recall ambient.

Ship a kb plugin of Claude Code lifecycle hooks — the same pattern Mem0 and claude-mem use — so the loop runs without the model deciding to. Every hook is just a shell command that calls a kb CLI verb against the daemon; nothing new runs (no MCP, no sidecar) — the daemon that serves the artifacts also holds and answers the memory. What's actually needed is a small set, and only one of them is load-bearing:

What's really needed — the minimal hook set
HookNeedWhat it does (a kb verb)
UserPromptSubmitkeystoneproactive recall — run kb recall "<prompt>" and inject the top 3–5 re-ranked hits as context before the model answers. This is what makes recall reliable without MCP auto-fire: true RAG, no tool call needed. If you build one hook, build this.
SessionStartusefulwake-up: inject the memory protocol + a compact index (a couple of cheap kb reads) so the model knows the store exists and how to use it.
SessionEndusefulpersist what was staged this session with kb remember, run optional consolidation/dedup, and drop the transcript into the episodic corpus.
PostToolUse / Stopoptionalper-turn candidate capture — noisy and easy to overdo; skip it until SessionEnd capture proves insufficient.

The UserPromptSubmit proactive-recall step is the biggest behavioural upgrade over A/B: instead of hoping the agent calls recall, the relevant memories are already in context before it answers. It's also where token discipline matters most — inject the top 3–5 re-ranked hits, not the corpus.

The keystone hook, concretely

Claude Code runs a UserPromptSubmit hook command before the model sees the turn; the hook receives the turn's JSON on stdin (including the prompt), and whatever it writes to stdout is injected as additional context. So the whole proactive-recall loop is one small script — no MCP, no daemon change:

// .claude/settings.json
{ "hooks": { "UserPromptSubmit": [ { "hooks": [
  { "type": "command", "command": "~/.claude/hooks/kb-recall.sh" } ] } ] } }
#!/usr/bin/env bash
# ~/.claude/hooks/kb-recall.sh — inject relevant memories before Claude answers
set -euo pipefail
prompt=$(jq -r '.prompt // empty')                    # the turn text, from stdin
[ -z "$prompt" ] && exit 0
hits=$(kb recall "$prompt" --scope all --limit 5 --json 2>/dev/null) || exit 0
[ "$(jq 'length' <<<"$hits")" -eq 0 ] && exit 0      # no hits → stay silent, spend nothing
{ echo "Relevant memories (auto-recalled — pull a full body with kb get if useful):"
  jq -r '.[] | "- [\(.kb)] \(.title) (id \(.id))"' <<<"$hits"; }   # stdout → injected context

For UserPromptSubmit, the hook's stdout is prepended to the turn's context (equivalently, emit {"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":"…"}} as JSON). Token discipline lives here: inject only titles + ids for the top 3–5 and let the model fetch a full body with kb get only when it needs one; stay silent when recall is empty so quiet turns cost nothing. The exact stdin field and the stdout-injection contract are Claude Code hook behaviour — worth a last check against the current hook docs before shipping. This is the one piece to build first; everything else in §03 is gravy.

04 — Trust & forgetting

Invalidation, reusing machinery kb already has

A memory you can't correct or expire becomes a liability. kb's comment system is already a correction protocol.

The hardest part of any memory system is un-remembering — stale facts that quietly mislead. Two mechanisms, both leaning on what kb has:

  • Staleness, reusing the anchor lifecycle's plumbing. kb's indexer already detects when a comment's anchor no longer resolves and emits comment.anchor_stale / anchor_resolved, with the SSE event, a SPA badge, and a sidecar behind it. Memory reuses that plumbing (the event, the badge, the down-rank-pending-review behaviour) — but the trigger is net-new: the anchor resolver only re-checks against the artifact's own re-parsed DOM, whereas "this memory-project note's referenced file/decision changed" is an external signal you'd detect yourself. Detection-only, never silently rewriting the memory (mirroring the resolver's "keep the original, flag it" rule).
  • Correction by conversation. The comment loop is the consolidation/forgetting UI: comment "superseded — we moved to Postgres" on a memory; kb comments watch surfaces it; the agent writes the replacement with kb-supersedes pointing at the old one and resolves the thread. Forget = delete the file (or a soft kb-status="forgotten" that the re-ranker zeroes out). Quick-response --choice-json buttons make "keep / merge / forget" one tap.
Why this is kb's natural advantage

Every other memory tool has to invent a curation UI from scratch. kb's review subsystem — anchors, replies, resolve, the two-way watch loop, the SPA panels — was built for exactly "a human correcting a document a model produced". Memory correction is the same problem with the same solution.

05 — The Memory view

The atlas becomes a mind-map of the agent's knowledge

kb already draws a 2-D map of a corpus. Pointed at memory, that map is a picture of what the agent knows about you.

A dedicated SPA route (/memory) reusing components kb already ships:

  • Timeline — memories by authorship recency via the gallery's existing ?sort=recent over mtime_unix/indexed_at_unix, weighted by kb-decay. (Note: kb's history table is a per-kb activity log — opens/searches/comments in the SPA — not an authorship record, so it tracks when you read a memory; for an agent-written corpus that signal is sparse and is the wrong basis for freshness.)
  • Mind-map — the UMAP/k-means atlas (AtlasView.tsx, deterministic layout) over the memory corpus: clusters are topics, distance is relatedness. Click a cluster to see (and consolidate) its memories.
  • Curate inline — edit, merge (apply supersedes), or forget a memory; stale badges from §04; the comment panel for the correction loop.

This is the payoff of the whole series' thesis: memory you can see and shape, not a database you query blind. None of the off-the-shelf tools have it because none of them started as a visual artifact browser.

06 — The two lenses

Useful for Claude? Useful for the user?

For Claude-the-agent

The best possible version. Proactive recall means relevant memory is in context unprompted; synchronous ingest means write-then-recall is instant; decay + consolidation keep recall sharp as the store grows; supersession stops stale facts misleading it. This is what a memory system is supposed to feel like.

For the end user

The richest cockpit — at a real cost. The Memory view, mind-map, and inline curation are a genuinely new capability no competitor offers. But the user now owns a subsystem: schema migrations, a re-ranker to tune, hooks to maintain, a consolidation job that can mis-merge. That's fine if memory is something kb means to be; it's overhead if memory is a side feature.

Open questions before committing to C
  • Does proactive recall on every prompt cost more tokens than it saves? (Tune injection count; measure.)
  • Who owns consolidation correctness — can a bad auto-merge lose a memory? (Human-approve closets; keep verbatim originals.)
  • Is the salience/decay re-ranker worth the tuning burden vs. plain hybrid? (Start without it; add only if recall degrades at scale.)

Recommendation

Defer — but keep the design. Don't build C to get memory; build A now (and B1 if the friction warrants). Build C only after living with A/B has proven that (a) you want kb to be an agent-memory product, and (b) you've hit A/B's specific limits — write latency, missed recall, stale facts, no UI to manage it. Then pull these pieces in one at a time, cheapest-first: a kb remember/recall verb pair → the UserPromptSubmit proactive-recall hook → the Memory view → decay/consolidation. Each is independently useful; none requires the whole thing.
