omp × kb deep integration — the territory, three verified defects, and a tiered idea portfolio

The existing omp integration uses 6 of 45 extension events and none of the tool/command registries; two silent defects mean omp never reaches the live cockpit and headless fleet jobs leave zero episodic trace. The best next moves are all extension-side, not upstream patches.

2026-08-28 · status:applied · project:kb · project:oh-my-pi
Applied 2026-08-29The program shipped the day after this landscape: D1+1c (kb c4e7a687), D2 (grokclaude 510f79e), Tier 1 (kb 92a092b4 extension v2, fd2b03f9 kb-code adapter), Tier 2 (kb fe5165f7), and Tier 3a as an upstream-ready oh-my-pi branch feat/register-memory-backend plus a feature-detected kb backend (5bcd53c4). Confirmed while executing: no omp session-id env var exists (trailer arm skipped — marker fallback stands), and @oh-my-pi/collab-web is not npm-published (3c parked as predicted). Commit hashes are pre-rebase for the plugins commits; resolve via git log --grep='(OK'.

The question

omp's (Oh My Pi's multi-provider coding agent, github.com/can1357/oh-my-pi, checked out at ~/project/oh-my-pi, installed v18.0.8) workflow model is the one this design adopts, and it is open source. What deep integrations between omp and kb/kb-code are worth building — beyond the memory loop that already ships in plugins/kb-memory/hooks/kb-omp.ts?

Method: a 6-agent exploration workflow (two Opus deep-reads over omp's extension API and memory/session internals; four Sonnet surveys over omp's auxiliary packages, kb's agent-facing surface, kb-code's agent-facing surface, and the capture pipeline), followed by a 3-agent adversarial verification pass with live probes. Every load-bearing claim below carries a file citation; the three headline claims were re-verified in refute mode, including live --dry-run reproduction on real job directories.

What exists today

The current integration is real but narrow. kb-omp.ts (243 lines, symlinked into ~/.omp/agent/extensions/kb-memory.ts) subscribes to six lifecycle events — session_start, before_agent_start, tool_call, session_stop, session.compacting, session_shutdown — and shells out to the same harness-agnostic scripts every other harness uses: wake (memory protocol + recent-memories index + distill-pending relay, once per session), recall (every prompt, injected as a hidden custom_message), transcript capture (a dedicated leaf-chain translator for omp's append-only session tree, not a naive reuse of Claude's flat shape), a distill nudge via ctx.ui.notify, and live-cockpit beats.

What it does not use is most of omp's extensibility surface. The canonical contract (packages/coding-agent/src/extensibility/extensions/types.ts, 1,769 lines) exposes 45 subscribable events plus registerTool (first-class model-callable tools), registerCommand (slash commands with argument completion), registerFlag, message/thinking renderers, composer widgets and status chips, dialog primitives, appendEntry (durable custom entries in the session tree), sendMessage with steer/followUp delivery, and session-control from command context (newSession, branch, navigateTree). kb-omp.ts calls none of the registries — every kb verb an omp model invokes today rides the generic bash tool on the model's own initiative.

The asymmetryToday kb can only push text at omp (a hidden context blob at prompt time). omp cannot ask kb anything mid-turn except by guessing shell commands. Closing that asymmetry is the single highest-leverage theme in this portfolio.

Broken today — two verified defects

Both were found by three exploration agents independently, then confirmed in refute-mode with live probes. They are prerequisites: several portfolio ideas silently build on surfaces these defects disable.

D1 — "omp" is not in kb's closed harness set

crates/kb-core/src/sessions/constants.rs:29 pins HARNESSES to exactly ["claude","codex","opencode","grok","kimi"]. Capture-side the harness ladder (enrich.rs:267-271) stores any string unvalidated, so 26 omp sessions already sit in the corpus with harness="omp" — but every read-side surface that validates against the closed set misbehaves:

  • Every live-cockpit beat fails. (Cockpit design: kb live-sessions cockpit, 2026-08.) POST /api/sessions/beat 400s on unknown harness (routes/sessions.rs:6144; live probe returned unknown beat harness "omp"). kb-beat.sh posts via detached fire-and-forget curl with nulled stdio, so the failure has been invisible since the integration shipped. omp sessions can never appear in the live-sessions cockpit.
  • The harness filter silently lies. GET /api/sessions?harness=omp returns unfiltered rows (live probe returned claude+grok): routes/sessions.rs:304 drops unknown csv values and an empty set means "no filter". The SPA even offers "omp" in its dropdown (built dynamically from harness_mix) — selecting it no-ops.
  • kb sessions status --harness omp hard-bails; the SPA harness glyph and resume_hint() fall back to generic placeholders.

Fix (small): add "omp" to the array + the pinned golden test, an omp arm in resume_hint() (session_bundle.rs) and HARNESS_GLYPH (web/src/lib/hints.ts); separately harden parse_harness_csv to 400 on unknown values rather than degrading a filtered query to unfiltered. This is a data change inside invariant #11, not a new invariant slot. An optional follow-on: a live_adapters/omp.rs Tier-0 rebuild arm mirroring opencode.rs.

D2 — headless fleet jobs leave zero episodic trace

grokclaude's shared engine fires a post-job capture hook for all four backends (grokclaude/codexclaude/kimiclaude/ompclaude) — but src/engine.rs:280-283 hardcodes the script to kb-capture-grok.sh, which resolves transcripts only under ~/.grok/sessions/ and only speaks grok's chat_history.jsonl directory schema. An omp job's real transcript is a single file at <job>/omp-home/sessions/<ts>_<sid>.jsonl; kimi's lives under kimi-home/. The verifier reproduced the skip (reason=session-dir-not-found) on four real omp/kimi job dirs, confirmed grok jobs capture fine as the control, and ran a corpus census: of 695 captured sessions, zero came from a headless non-grok job. The verifier also sharpened the claim three ways:

  • The adapter is grok-schema-only, not just grok-labelled: even handed the right path, its translate stage reads chat_history.jsonl + events.jsonl and would fail on omp's format.
  • The join key guarantees the miss: meta.json.grok_session_id is a legacy alias holding whatever backend's handle, which the script then looks up in the grok store.
  • Bonus gap: capture only fires in finish_ok_job (engine.rs:237, sole call site) — failed jobs never capture on any backend, grok included.

Fix (medium, mostly grokclaude-side): make trigger_kb_capture dispatch on meta.backend to the sibling adapters that already exist and work — kb-capture-omp.sh has a CLI mode that accepts a session-file path directly; kimi/codex have their own siblings. Add per-backend env overrides beside KB_GROK_CAPTURE_HOOK, and decide deliberately whether failed jobs should capture too (they are often the most valuable episodic evidence).

Tier 1 — upgrade kb-omp.ts in place (no upstream patch, no rebase tax)

Everything in this tier lives in a file kb already owns, carries zero fork burden, and preserves the hooks-never-block discipline.

1a. kb and kb-code as first-class omp tools

The headline move. pi.registerTool gives the model schema-typed, discoverable tools instead of guessed bash invocations: kb_context (the budgeted pack — substance, pulled by the model, which preserves the pull-only ruling), kb_recollect, kb_why, kb_remember, plus kb-code's four strongest verbs — kbcode_search (the unified 6-lane box), kbcode_usages (exact/likely/candidate trust classes, strictly better-labelled than grep), kbcode_why (pre-edit provenance), kbcode_pack (token-budgeted context assembly). All ride kb-code's ordinary auth_bearer router — no loopback constraint.

The one trap (verified, test-pinned upstream)A tool registered without loadMode: "essential" defaults to "discoverable", and because tools.xdev defaults to true it is removed from the top-level schema and mounted behind xd:// — the force-include of extension tools does not exempt it (essential-tools.ts:45, xdev.ts:83-86, sdk.ts:3199-3213). This is exactly how a kb tool integration would silently "work" while the model never calls it.

1b. Use the lifecycle return values kb currently no-ops

kb-omp.ts already subscribes to session_stop and session.compacting but returns nothing from either. Verified consumption paths:

  • Headless-visible distill gate. session_stop may return {continue: true, additionalContext} — a model-visible (user-hidden, display:false) continuation turn, capped at exactly 8, never fired for subagents (agent-session.ts:3535-3611). Today's distill nudge rides ctx.ui.notify, which is literally a no-op in -p mode (print mode installs no UI context, so hasUI is false). Returning the nudge as continuation context makes the agent itself write the memory before the turn settles — and works headless.
  • kb-informed compaction. session.compacting may return {context: string[], prompt, preserveData}: context lines are spliced into the summarization prompt as <additional-context> (compaction.ts:955), so compaction stops forgetting what kb knows matters; preserveData persists on the compaction entry — a durable kb provenance stamp across the boundary. Nuances: mutually exclusive with a session_before_compact full-replacement, and inert when the snapcompact method is selected.

1c. Cockpit completeness and visible recall

  • blocked/unblocked beats. omp's tool_approval_requested/tool_approval_resolved events are the direct equivalent of Claude's Notification hook; wiring them to the existing beat() helper lights up the cockpit's blocked/detail_reason sub-label (display-only; Working/Stalled classification is unaffected). A few lines — after D1 lands.
  • Rendered recall instead of an invisible blob. registerMessageRenderer("kb-memory-context", …) makes injected recall visible and collapsible in the TUI (the --explain decomposition inline); ctx.ui.setStatus("kb", "3 recalled") and a setWidget composer strip give kb a persistent presence — a natural home for the desk-v2 changed-since-last-read banner.

1d. A structural recall ledger via appendEntry

kb's recall ledger currently rides a text marker (<!--kb-recall/1 …-->) smuggled inside injected prose and re-parsed at capture time. On omp, pi.appendEntry("kb.recall", {kb, ids, query}) writes a first-class namespaced custom entry into the session tree — no text grammar, no parse-gap census, replayable via getBranch() on resume/branch. The free-text marker stays as the cross-harness fallback; the capture adapter learns to read the namespaced entry as a third, highest-confidence source. This also un-breaks memory_recalls for omp, which is structurally empty today because the capture rightly drops all custom_message content (kb's own injections must not echo back).

1e. kb-code provenance inside omp's loop

  • An omp arm for the why-hook. kb-code-why.sh has exactly two bindings today (Claude native, Codex via a translation shim). The same pattern — extract file paths from omp's tool_call event for edit-shaped tools, re-dispatch through the unmodified delegate — is proven twice in-repo.
  • tool_result enrichment. omp's tool_result middleware sees every tool's output; appending a one-line blame/why footer to read results (plus memories citing the path via DCB hints) gives provenance without the model spending a tool call. Needs a hard latency budget and memoization.
  • Commit trailer coverage. omp commits currently get Kb-Session: trailers only through the 40-minute marker-file fallback (written by kb-recall.sh, which kb-omp.ts already triggers per prompt). Verify whether omp exports a session-id env var into bash children; if so, add a direct arm to trailer-logic.sh beside CLAUDE_CODE_SESSION_ID/GROK_SESSION_ID.

1f. Commands, flags, task agents, packaging

  • registerCommand: /kb-context, /kb-distill, /kb-desk with argument completion — command context even offers branch/newSession, so /kb-distill can branch, distill, and return.
  • registerFlag("kb-off"): a real CLI kill-switch for the whole kb lane, which has none today.
  • Fix the dead plugin roots. omp reads Claude's installed_plugins.json and trusts installPath literally — kb-memory and kb-code point at cache dirs that do not exist, so /kb-distill, /kb-verify, /kb-weekly and kb-code's commands never reach omp. Better than repairing paths: give plugins/kb-memory/ a proper omp package manifest (omp.extensions) so omp's own provider picks up the extension, commands, skills and a shipped kb-librarian task agent (frontmatter granting only the kb tools) from one root.
  • kb daycard --since in the shared wake path — the ready-made "what happened while I was away" digest no harness calls today.

Tier 2 — capture fidelity: omp's transcript is richer than what kb keeps

2a. The omp subagent iceberg

Every omp task subagent writes a complete session JSONL at <sessions>/<parent-stem>/<AgentName>.jsonl (verified live: CliSurface.jsonl, ServerInternals.jsonl… beside per-agent .md reports; ~9 MB of subagent transcript in one session dir). kb captures none of it, and the failure is doubly structural: the adapter hands the engine a mktemp transcript, so the derived sidecar dir is /tmp/<sid>/subagents/ (never exists), and even the real layout matches neither the subagents/ level nor the agent-*.jsonl prefix filter (sessions_capture.rs:298-300). Fix entirely inside the adapter: stage <tmpdir>/<sid>/subagents/agent-<Name>.jsonl, translating each child with the same jq program — the existing W0.5 digest block and W0.6 sidecar-text evidence lane then light up for free, caps and scrubbing already enforced engine-side. This is the same subagent-iceberg defect kb already fought and fixed on the Claude side.

2b. Entry types the translator drops — including per-tool intent

The translator emits only type=="message" entries. Verified live against real session files, what falls on the floor:

  • tool_execution_start.intent — a natural-language statement of why the agent ran that tool, one per call (1,342 on this box, 100% discarded). Joined onto tool calls by toolCallId, this feeds kb why and kb-code's story lane with rationale no other harness provides.
  • compaction — summary, shortSummary, tokensBefore, details.readFiles/modifiedFiles: the agent's own distillation of discarded history — exactly the material /kb-distill wants, free. (Schema-verified upstream; no local session has compacted yet.)
  • session_exit — kind: normal|signal|fatal|process_exit + pendingToolCalls: an honest closure signal for kb's substance triage.
  • session_init (subagent contract: task, tools, system prompt) and branch_summary (agent-written summaries of abandoned branches — "roads not taken" evidence; 12 exist locally).

Emission should follow the capture envelope's precedent: additive post-<pre> tail blocks, never touching the byte-identical transcript contract. One correction from verification: kb's decisions extractor is not wholly Claude-shaped — plan-approval decisions and error counts already work for omp captures; only AskUserQuestion-kind decisions are unreachable (they need the toolUseResult shape omp never emits).

2c. Small honest wins

~/.omp/agent/history.db (FTS5) carries a session_titles table — a free backfill for the 26 captured omp sessions that landed with null titles, and a per-project prompt corpus kb has no equivalent of. If omp's local memory backend is ever enabled, its outputs are plain Markdown files kb indexes natively.

Tier 3 — big bets (upstream or architectural)

3a. kb as omp's memory backend — via an upstream pluggability PR

omp's memory backend id is a closed 4-value enum (off|local|hindsight|mnemopi) repeated across ~8 sites, and the memory tools bypass the MemoryBackend interface through hardcoded string gates — so "add kb as a fifth backend" is a multi-file patch to a vendored upstream with permanent rebase cost. mnemopi itself is not a seam: its storage is concretely bun:sqlite and its plugin system is an observer bus. But the hindsight backend proves a remote-HTTP backend works end-to-end, and there is no registerMemoryBackend on the extension API — an obvious upstream gap. The Fable-grade move is to upstream the registration API, not the kb backend: a PR adding registerMemoryBackend (and routing the memory tools through the interface's search?/save?) benefits every oh-my-pi user, and kb then ships its backend as a pure extension with zero fork burden. Until then, Tier-1a's tools deliver most of the value at none of the cost. Note: memory.backend is off on this machine — mnemopi competes with kb only architecturally, not operationally.

3b. RPC host mode for the ompclaude driver

Extensions cannot register internal URL schemes (the router isn't exported, and the installed omp is a bundle), but an RPC host can: omp --mode rpc lets the driver own set_host_tools and set_host_uri_schemes, so a kb-aware driver could expose kb://<id> and kbcode://<path>:<line> reads with no extension at all. Worth it only where kb already supervises omp processes — i.e. as a grokclaude/ompclaude evolution, after D2.

3c. omp's tool-render library inside kb's session views

collab-web ships a host-agnostic React renderer per omp built-in tool plus an <omp-tool-view> custom element taking plain JSON — the same bundle omp reuses for its standalone HTML session export. kb's session detail could embed omp's own maintained tool cards instead of reimplementing them. Blocker to verify first: the packages use workspace-catalog version refs and may not be npm-published.

3d. Parked, with reasons

  • kb MCP server — the recorded trigger (README Non-goals, re-ruled 2026-07-10 after the foreign-harness evaluation) is not fired: omp has a shell tool, config escapes, and an extension API that is strictly better than MCP for this integration. omp is even MCP-client-only (no server mode to point at kb). Stays parked.
  • omp stats/OTEL → kb SLO — omp's telemetry is real (GenAI-semconv spans, per-run cost/latency summaries) but kb has no ingestion route, and building one crosses kb's surfaced-not-scored posture for someone else's metrics. Its stats package is a separate local dashboard; leave it be.
  • kb-embedder as mnemopi's embedding provider — both projects independently confine ONNX Runtime to an IPC subprocess (kb invariant #26; omp's __omp_worker_mnemopi_embed), so sharing one instance via a /v1/embeddings route is elegant — but nothing duplicates today (memory.backend: off) and the default dims differ (384 vs 768). Defensive only.
  • Per-provider-call recall refresh via the context event — powerful (replace exactly what is sent, per call) but fires on every LLM request; without strict memoization it is a latency tax on the hottest path. Revisit only with a measured budget.
  • wire-package drift audit — packages/wire is the versioned TS truth for omp's entry shapes; add "diff kb's translator against wire on omp version bumps" to the kb-audit cadence rather than building anything.

Recommended sequence

  1. D1 + 1c — one kb-side commit: harness set, filter hardening, blocked/unblocked beats. Smallest change, ends two silent lies.
  2. D2 — grokclaude backend dispatch. The headless fleet starts leaving episodic memory; decide the failed-jobs question while in there.
  3. 1a + 1f — the tools + packaging wave: native kb/kb-code tools, commands, the kill-switch flag, the omp package manifest with a kb-librarian agent.
  4. 1b + 1d — lifecycle returns and the structural recall ledger (the capture-side reader for namespaced custom entries lands with 2b's parser work).
  5. 2a + 2b — capture fidelity: sidecars first (pure adapter), then the dropped-entry tail blocks.
  6. Then reassess Tier 3 — with 1a in daily use, real evidence decides whether an upstream memory-backend PR or the RPC driver is worth it.

Constraints that bind every idea

  • Hooks never block. Extensions are unsandboxed and in-process: a raw timer or detached promise that throws tears down the whole omp session. Only ctx.setInterval/setTimeout; every handler fail-silent.
  • Pull-only stands (invariant #11 R0/R3, from sessions as episodic memory): the context pack's substance is never auto-injected. A model-invoked tool preserves the posture; automatic injection would need a re-ruling, not an implementation.
  • custom_message stays dropped in capture — kb's own injected context must never echo back into the sessions corpus. The recall ledger goes through namespaced custom entries instead.
  • Namespace everything: customTypes share a global namespace with core-reserved values; commands must avoid built-in collisions and reserved shortcuts.
  • No new invariant slots needed: everything here is data/adapter/extension work inside invariants #11 and the plugin layer; the 35-slot budget is untouched.

When to revisit

  • omp ships registerMemoryBackend (or accepts the PR) → promote 3a immediately; the Tier-1 shim becomes the fallback.
  • omp changes its session-entry shapes → the wire-package diff (parked 3d) becomes an active task; the translator and tail-block parsers are the exposure.
  • The MCP trigger conditions actually fire (a harness in real use with no shell/config escape) → the read-only stdio facade ruling activates; omp is not that harness.
  • memory.backend gets turned on locally → the embeddings-sharing and local-artifact-ingest ideas stop being defensive.

Evidence and method

Exploration: 6 workflow agents (1.18 M tokens, 377 tool calls) over ~/project/oh-my-pi, ~/project/kb, ~/project/grokclaude, and live state (~/.omp, the kb daemon on 127.0.0.1:4000, KB_SESSIONS_DIR). Verification: 3 refute-mode agents (374 K tokens) with live probes — the beat 400 and filter degradation reproduced against the running daemon; the headless-capture no-op reproduced with --dry-run on four real job dirs plus a 695-file corpus census; the xdev demotion, session_stop continuation cap, compacting splice, and sidecar path derivation all traced to consumption sites (several pinned by upstream's own tests).
