from markdown to htmlFive prompts, ranked.
One baseline. Pick & paste.

Five Claude Code prompts that nudge it toward emitting self-contained HTML artifacts instead of markdown — ordered best to worst by my honest read of quality × adoption cost. All five are kb-aware: they reference the kb-* meta tag convention (topic 07), the <template id="kb-prompt"> embedding, and the data-kb-id section slug for comment-anchor stability (topic 09). A sixth general-purpose baseline drops all kb dependencies and keeps just the dogum/html-artifacts-style discipline — portable into any project.

TL;DR

Start with #1 (skill-based) if dogum/html-artifacts is installable in your Claude Code environment. Otherwise start with #2 (inline canonical recipe — ~60 lines added to CLAUDE.md). #3 (trigger-conditional) is the right fallback if #2 is too invasive — it preserves markdown for short conversational replies and only switches to HTML when trigger words fire. #4 and #5 are documented for completeness but produce more variance; not recommended for the kb workflow. The baseline (§F) is for non-kb projects that just want "HTML over markdown" without metadata.

#1 Skill · HIGH quality · LOW cost #2 Inline · HIGH quality · MED cost #3 Triggered · MED quality · LOW cost
A. Prompt #1 — Skill-based (RECOMMENDED)

Invoke dogum/html-artifacts + add kb metadata on top

What it is: a short CLAUDE.md instruction that delegates HTML-generation discipline to the dogum/html-artifacts skill (or a kb-fork of it) and adds the kb-specific metadata layer on top. The skill already ships the load-bearing rules — anti-patterns, category-specific guidance, system-font discipline, no-externals constraint, file-size target. kb just adds the meta-tag layer.

When to use: the dogum skill is reachable in your Claude Code config (or you've forked it into a kb-namespaced skill). This is the default first choice — highest quality, lowest authoring cost.

Tradeoffs: depends on skill availability; if the skill ever drifts from kb's expectations, the prompt may need an inline override. Mitigate by pinning a known-good version (or forking into your own org).

You have access to a kb-html-artifacts skill (forked from dogum/html-artifacts,
with kb-specific metadata conventions). For any response that would be a
long-form artifact — explainer, write-up, plan, design review, comparison,
report, slide deck, custom editor — invoke the skill and emit a self-contained
.html file rather than markdown.

The skill enforces:
- Real <title> + matching <h1> + first-paragraph TL;DR (dogum convention)
- System-font stack only; CSS custom properties at :root with dark-mode variants
- No external scripts, fonts, or stylesheets
- 10–30 KB target file size
- No "default AI aesthetic" — no gradient cards, no glass-morphism, no
  emoji-decorated headings, no four-shades-of-indigo palette

On top of the skill, kb requires:
- <meta name="kb-id"          content="$(generate ULID)">
- <meta name="kb-model"       content="$your-model-id">
- <meta name="kb-model-version" content="$model-date-stamp">
- <meta name="kb-created"     content="$ISO_8601_UTC_now">
- <meta name="kb-category"    content="$one of: exploration | code-review |
                                              design | prototyping | decks |
                                              diagrams | reports | research |
                                              custom-editor">
- <meta name="kb-tags"        content="comma,separated,tags">
- <template id="kb-prompt"> containing the user's verbatim prompt after a
  scrub pass: strip system prompt; redact AWS keys (AKIA[0-9A-Z]{16}),
  GitHub PATs (ghp_[A-Za-z0-9]{36}), Anthropic sk-ant-*, JWT-like strings,
  generic 32+ char high-entropy tokens; normalise /Users/<name>/ → ~/ and
  /home/<name>/ → ~/.
- data-kb-id="stable-slug" on each top-level <section> — kb's comment-
  anchor feature uses these to survive regenerations (see kb-research
  topic 09 §B).

Use markdown (not HTML) when:
- Response is conversational and under ~3 paragraphs
- Code-only answer (no narrative around it)
- Three-bullet summary
- Terminal-style: commands, exit codes, paths

~25 lines added to CLAUDE.md + skill install. Quality: HIGH. Preserves markdown for short replies: yes. kb-aware: yes.

B. Prompt #2 — Inline canonical recipe

Same discipline, no skill dependency, ~60 lines in CLAUDE.md

What it is: the dogum/html-artifacts discipline inlined into CLAUDE.md, plus the kb metadata layer. Same output quality as #1, just self-contained — no external skill required.

When to use: the dogum skill isn't installable, or you want explicit control over every rule rather than trusting an upstream skill's version drift. Higher authoring cost (longer CLAUDE.md), same quality ceiling.

Tradeoffs: ~60-line CLAUDE.md addition. You own the rule list — if dogum updates its anti-pattern catalogue (e.g. adds a new "AI aesthetic" to ban), you have to merge it manually.

When the user requests a long-form artifact — explainer, write-up, plan,
design review, comparison, report, slide deck, custom editor, "interactive
something" — emit a self-contained .html file rather than markdown.

Required structure:
- Real <title> matching the topic
- <h1> that matches or refines <title>
- First-paragraph TL;DR or framing sentence immediately under the <h1>
- <meta name="description"> with a one-sentence summary
- <meta charset="UTF-8">, <meta name="viewport">

kb provenance metadata (required):
- <meta name="kb-id"            content="$(ULID)">
- <meta name="kb-model"         content="$your-model-id">
- <meta name="kb-model-version" content="$model-date-stamp">
- <meta name="kb-created"       content="$ISO_8601_UTC">
- <meta name="kb-category"      content="$one of nine categories">
- <meta name="kb-tags"          content="comma,separated,tags">
- <template id="kb-prompt">
    [verbatim user prompt, after scrubbing system prompt and known secret
     patterns (AWS keys, GH PATs, sk-ant-*, JWT-like, 32+ char high-entropy
     tokens), and after normalising /Users/<name>/ → ~/ paths]
  </template>
- data-kb-id="stable-slug" on each top-level <section>

CSS conventions:
- System font stack only:
    font-family: system-ui, -apple-system, "Segoe UI", Roboto,
                 "Helvetica Neue", Arial, sans-serif;
    (monospace stack: ui-monospace, "SF Mono", Menlo, Consolas, monospace;
     serif stack: "Iowan Old Style", "Charter", Georgia, ui-serif, serif;)
- CSS custom properties at :root, with prefers-color-scheme: dark variants
- Restrained palette — pick 2–3 accent colours from a real design language,
  not "four shades of indigo"
- No gradient cards. No glass-morphism. No emoji-decorated headings.

Hard constraints:
- ZERO external dependencies: no <script src> to CDNs, no Google Fonts,
  no external stylesheets. Inline <style> and <script> only.
- Avoid frameworks (no React, no Vue, no Tailwind via CDN). Use platform
  primitives: <details>/<summary>, inline SVG, native HTML5 drag,
  CSS animations, native form controls, <canvas> when truly needed.
- File size target: 10–30 KB raw HTML.

Use markdown (not HTML) when:
- Conversational reply under ~3 paragraphs
- Code-only answer
- Three-bullet summary
- Terminal-style answers (commands, exit codes, paths)

~60 lines in CLAUDE.md, no skill needed. Quality: HIGH. Preserves markdown for short replies: yes. kb-aware: yes.

C. Prompt #3 — Trigger-conditional

HTML only when trigger words fire; markdown otherwise

What it is: a CLAUDE.md addition that enumerates trigger words and switches to HTML output only when one of them appears in the user's request. Everything else stays markdown — including ambiguous-length responses.

When to use: you want a clean markdown default for casual chat (the operator types "what's the difference between A and B?" → markdown reply), and HTML only when the request is explicit about artifact intent. Less invasive than #1/#2. Slightly more variance because the trigger list is finite.

Tradeoffs: some long-form requests don't match any trigger word and stay markdown when they probably should have been HTML. Iterate the trigger list as you spot misses.

When the user's request contains any of these trigger words, emit a
self-contained .html file rather than markdown:

  artifact  ·  explainer  ·  interactive  ·  diagram  ·  dashboard  ·
  page      ·  write-up   ·  review       ·  deck     ·  report     ·
  plan      ·  comparison ·  flowchart    ·  visualis(z)ation         ·
  side-by-side             ·  prototype

For ALL OTHER requests (including ambiguous-length responses), default to
markdown.

When emitting HTML, follow this discipline:
[insert the full structure + CSS + constraints + anti-patterns block from
 prompt #2, verbatim — or, if the dogum skill is available, invoke it and
 add only the kb metadata layer per prompt #1]

The default behaviour outside trigger words stays markdown; do not switch
based on response length or topic alone.

~15 lines + the inlined block from #2 or the skill ref from #1. Quality: MED-HIGH (depends on triggers covering the operator's actual phrasings). Preserves markdown for short replies: yes (and for unmatched long replies too). kb-aware: yes.

D. Prompt #4 — Output-format hint

Lightest CLAUDE.md addition (~10 lines), looser output

What it is: a short note telling Claude that HTML is available as an output format, with brief structural guidance. No enforcement, no mandatory metadata.

When to use: you don't want a long CLAUDE.md addition, and you accept that the output won't always match the kb conventions strictly. Useful for exploratory projects where kb ingestion isn't critical yet.

Tradeoffs: lower quality. Output may be missing kb-* metadata, may use external CDNs, may not match the file-size target. The operator may need to post-process before ingest.

You can output HTML files when the response would be a long-form artifact —
an explainer, a comparison, a design review, a plan, an interactive
illustration. HTML lets you use inline SVG diagrams, <details>/<summary>
for collapsible sections, native form controls, and CSS for side-by-side
layout — things markdown can't do.

Default to markdown for short responses. Use HTML when the layout would
genuinely help the reader.

If you emit HTML, make it self-contained (no external CDN scripts or fonts)
and aim for 10–30 KB.

For kb integration, include:
- <meta name="kb-id">       with a ULID
- <meta name="kb-model">    with your model id
- <meta name="kb-created">  with ISO 8601 UTC
- <template id="kb-prompt"> with the user's prompt (after a quick
  scrub for obvious secrets and pathnames)

~10 lines in CLAUDE.md. Quality: MED. Preserves markdown for short replies: yes. kb-aware: partial (suggested, not enforced).

E. Prompt #5 — Per-request opt-in

No CLAUDE.md change. Operator triggers HTML per message.

What it is: no project configuration. The operator types a phrase per message when they want HTML output. Default behaviour stays exactly as it was — markdown for everything Claude does normally.

When to use: one-off experiments. Trying out a few HTML artifacts to see if the kb workflow fits your project before committing to a CLAUDE.md addition. Or projects where most output should stay markdown and HTML is the exception.

Tradeoffs: highest friction per artifact (you have to remember to ask). No consistency guarantee — Claude's interpretation of "HTML artifact with kb conventions" may drift between sessions or model upgrades.

Per-message phrasings the operator can use (no CLAUDE.md change required):

  Full convention reference:
    "Generate this as an HTML artifact with kb conventions: kb-id ULID,
     kb-model and kb-created meta, kb-prompt template, system fonts only,
     no external assets, 10–30 KB target, data-kb-id on top-level
     sections."

  Once you've internalised the conventions (shorter):
    "Output as a kb-artifact HTML file."

  When kb conventions aren't needed (non-kb projects):
    "Reply with a self-contained HTML file (no external assets, 10–30 KB,
     system fonts, no AI-aesthetic gradients)."

  Quick-and-dirty (lowest quality, lowest friction):
    "Make this an HTML page instead of markdown."

Zero CLAUDE.md changes. Quality: variable. Preserves markdown for short replies: yes (default behaviour unchanged). kb-aware: operator-driven.

F. Baseline — general-purpose (no kb dependencies)

HTML-over-markdown discipline, portable into any project

What it is: the dogum-style HTML discipline (system fonts, no externals, 10–30 KB, anti-patterns called out), without the kb-* metadata layer, the kb-prompt template, or the data-kb-id section slugs. Just "Claude Code outputs good HTML instead of markdown for long-form responses."

When to use: a project that isn't kb-aware. The output won't ingest into kb without post-processing (no kb-id, no provenance metadata), but you get the editorial discipline of the kb-aware prompts. Useful for sharing the recipe with people who don't run kb.

Tradeoffs: portable; doesn't carry kb knowledge.

For long-form responses — explainers, write-ups, plans, design reviews,
comparisons, slide decks — emit a self-contained .html file rather than
markdown.

Required structure:
- Real <title> matching the topic
- <h1> matching or refining <title>
- First-paragraph TL;DR / framing sentence immediately under the <h1>
- <meta name="description"> with a one-sentence summary
- <meta charset="UTF-8">, <meta name="viewport">

CSS conventions:
- System font stack only (sans / mono / serif as needed)
- CSS custom properties at :root with prefers-color-scheme: dark variants
- Restrained palette — 2–3 accent colours, drawn from a real design
  language, not "four shades of indigo"
- No gradient cards. No glass-morphism. No emoji-decorated headings.

Hard constraints:
- Zero external dependencies (no CDN scripts, no Google Fonts, no
  external stylesheets). Inline <style> and <script> only.
- Avoid frameworks. Use platform primitives: <details>/<summary>,
  inline SVG, native HTML5 drag, CSS animations, native form controls.
- File size target: 10–30 KB raw.

Use markdown when:
- Conversational reply under ~3 paragraphs
- Code-only answer (no narrative around it)
- Three-bullet summary
- Terminal-style answers (commands, exit codes, paths)

~30 lines in CLAUDE.md. Quality: HIGH. Preserves markdown for short replies: yes. kb-aware: no (drop-in for non-kb projects).

Start with #1 (skill-based) if dogum/html-artifacts is reachable in your Claude Code environment. The skill is the most carefully-tuned authority on "good HTML artifacts" today (per topic 07); kb's contribution is the meta-tag layer on top.

If the skill is unreachable or you want explicit per-rule control, fall back to #2 (inline canonical recipe). Same quality ceiling, ~35 more lines of CLAUDE.md.

#3 (trigger-conditional) is the right fallback if #2's ~60-line CLAUDE.md addition is too invasive for your project, or if you have a lot of short-form interactions that should stay markdown and only a few long-form requests that benefit from HTML.

#4 and #5 are documented for completeness but not recommended for sustained kb use — output variance hurts ingestion. Use them only for exploration before committing to one of #1–#3.

The baseline (§F) is the right answer if you want the HTML-over-markdown discipline without kb-specific metadata — e.g. for a project that won't use kb, or for sharing the recipe with people who aren't running kb.

Open questions
  • Skill version drift. If you adopt #1, pin a known-good version of dogum/html-artifacts in your project config — or fork it into a kb-owned namespace. Upstream changes to the anti-pattern catalogue or category list could silently change your output.
  • Model upgrades. Reissue the prompt set when you move to a new Claude generation. The current text is calibrated for the model you tested with; a new model may interpret "no AI aesthetic" differently. Add a smoke test: generate one artifact per category after each model bump and eyeball the output.
  • Fork-and-pin the skill. Whether to maintain kb-html-artifacts as an actual fork (separate repo, independent versioning) or as a thin overlay on dogum (lookups at install time). Defer until #1 is in production; the answer depends on how often you need to diverge from upstream.
  • Category taxonomy. kb-category enumerates 9 values from dogum's classification. Are there kb-specific categories worth adding (e.g. commentary for operator-authored artifacts, regen for revisited ones)? Defer to first production use.
  • Multi-language artifacts. All conventions here assume English. Translated artifacts may want a <meta name="kb-lang"> tag and language-aware system-font stacks. Out of scope for v1.
  • The "Markdown still correct" list. Each prompt cites four cases (under-3-paragraphs / code-only / three-bullet / terminal-style). Are there others? Quick visual mocks vs full artifacts is a contested case — at what point does the operator want a real artifact vs a few CSS-in-markdown lines?
