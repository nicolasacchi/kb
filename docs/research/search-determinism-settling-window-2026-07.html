Deterministic scores, unpinned order

a determinism audit of kb search · Fable frontier run #5 · 2026-07-07 13:52–15:20 CEST · isolated daemon, 14-doc corpus, zero writes to any real corpus · mechanism refuted + corrected under adversarial review · status: finding, no code changed

Verdict. kb's claim of deterministic, reproducible ranking mostly holds — with one real seam. Vector search and the graph are bit-stable through everything. Keyword and hybrid rankings are unstable in the window right after indexing: scores nudge and stale postings transiently over-count as the FTS index settles, then converge to a state that was bit-identical across two independent from-scratch rebuilds. The mechanism I started with — "BM25 scores differ per lance fragment" — was refuted by the lance source: its corpus statistics are global. The real, code-pinned gap is smaller and sharper: bm25_query and list_embeddings return lance's top-k in physical scan order with no ORDER BY id tie-break, so any tied-score ordering rides the physical index layout, which moves as fragments merge. A one-line secondary sort closes it. (Atlas layout: untested — its endpoint is SPA-only; see bounds.)

1 · The hypothesis the code refuted

Refuted. I hypothesised that BM25 scores depend on lance fragment structure — that the same 14 docs stored as 14 one-doc fragments (fresh index) score differently than as 1 merged fragment (post-compaction), because IDF/avgdl are computed per physical fragment. A verifier read the pinned lance-index 4.0.0 source: IndexBM25Scorer aggregates num_docs, total_tokens → avgdl, and per-token document frequency globally across all inverted-index partitions (scorer.rs:70–131), and the emitted top-k scores are recomputed with that single global scorer (index.rs:461,521,543). Inverted-index "partitions" are size-driven (2048 MiB, builder.rs:56), not data fragments — a 14-doc corpus is one partition either way. Same documents → same IDF/avgdl → same score, fragment count notwithstanding. My mechanism was wrong.

Foregrounding this is the point, not an aside. Across this frontier program the adversarial pass keeps catching the author: run #4 corrected an inflated invocation count, and here run #5 corrected a wrong mechanism. What survives that is worth more than what's asserted without it.

The settling instability is real and query-visible. For "memory ranking", keyword top-doc 47320bbc ("Evolving the kb Memory System") across four captures of the same corpus:

fresh capture A (stale postings):   10 hits   top score 3.2050
fresh capture B (~1 min later):      8 hits   top score 2.9767   ← same daemon, changed
after compact + convergence:         8 hits   top score 3.0253
independent rebuild, converged:      8 hits   top score 3.0253   ← identical to above

Two effects compose here. (a) Over-counting: the 10-hit capture admits two extra low-scoring docs — stale postings from re-index churn not yet garbage-collected (it over-counts; it is not a partial/incomplete index — the doc table read 14 in every capture). (b) A score nudge: once membership settles at 8, seven of the eight scores are already bit-identical; only the highest-term-frequency doc keeps moving (2.9767 → 3.0253) until the version chain settles, because a small shift in the global length statistics moves the top-TF doc most. Then it stabilises — and a second, independent from-scratch rebuild produced the identical settled numbers.

3 · The real seam, code-pinned

Distinct from the transient settling above, there is a latent determinism gap in kb's own code that would bite cross-machine even after everything settles: no stable tie-break on the ranked read paths.

  • bm25_query (lance.rs:636–653) issues full_text_search(…).limit(limit) and returns lance's score-ordered top-k as-is — no secondary ORDER BY id.
  • batches_to_summaries (lance.rs:1608) folds record batches in physical scan order with no final sort — unlike the list/gallery decoders, which do sort (lance.rs:1033, 1256).
  • list_embeddings (lance.rs:1392) — the atlas input — is select(["id","embedding"]) with no ORDER BY, pure scan order.

Consequence: for documents whose BM25 scores are exactly (or floating-point) equal — common on short keyword queries over a similar corpus — which rows survive the limit and their rank order are decided by lance's heap plus physical row/fragment layout. Compaction reorders physical rows, so tied docs can swap ranks or swap in/out of the top-k. Scores are reproducible; order on ties is not pinned. The fix is one line each: a .then(a.id.cmp(&b.id)) secondary sort (kb already does exactly this in the recall reranker and the list decoders — it's simply absent from the search/embedding paths).

4 · Why this matters (beyond a tidy invariant)

  1. Reproducible evaluation. Anything that snapshots keyword/hybrid results — kb bench, a before/after A/B on a change that triggers reindex — can attribute a settling-window shift or a tie reshuffle to the change under test. My own earlier frontier runs captured search during unknown index states; the honest control is to compact and let the index settle before measuring.
  2. The "verified outcomes" ethos. The whole corpus is built on deterministic, reproducible artifacts; a user who queries right after adding docs sees a different keyword ranking than a minute later, for the same corpus. That is worth documenting even though it self-heals.
  3. The tie-break is a genuine latent bug for cross-machine reproducibility (invariant #10 / the atlas-determinism invariant aspire to bit-identical across machines) — and it's a cheap, safe fix that makes the aspiration true for the ranked paths.

5 · Honest bounds (what I did NOT establish)

  • Rebuild reproducibility is observed, not proven. Two independent rebuilds gave bit-identical settled output (atlas run-ids differed, ruling out an accidental copy). But determinism is asymmetric — two matches don't prove it; a rarer float-reduction or hash-order race could still settle identically most of the time. Read it as "bit-identical across 2 trials."
  • Atlas layout is untested. Its coordinate endpoint is SPA-only; I captured only the recompute run-id (a fresh random token per POST, which says nothing about layout). The "list_embeddings unsorted ⇒ atlas may be non-reproducible" point is a static-code hypothesis with zero empirical test here. It should be tested with a coords capture next.
  • Auto-compaction confounds the causal story. The daemon periodically auto-compacts on a timer (observed trigger="periodic" in the log), so "manual compact is what stabilised it" is not cleanly isolated — the daemon partly stabilises itself. The endpoint (settled + reproducible) stands; the attribution to the manual step does not.
  • Small scale, one machine. 14 docs, ~5 usable keyword queries (one was a stopword returning nothing), 2 rebuilds, single host. A case study that locates a seam, not a population measurement of its frequency.
  • Digest not tested. An earlier draft called the digest fragment-invariant; it was never captured in this rig — dropped.
