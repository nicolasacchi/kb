Stepping up kb search & recall: findings, options, and a bench-gated plan

kb search is already strong and now fast; the biggest untapped lever is that long artifacts are silently truncated to ~400 words in the vector arm — so here is what the code actually does today, the de-risking facts I verified, and a measure-first phased plan to lift relevance.

2026-06-05 · status:open · project:kb · design

Verdict

The 2026-05-19 embedding bake-off measured kb's default stack — bge-large-en-v1.5 in hybrid mode — at Recall@1 0.81, MRR 0.87, nDCG@10 0.87 over the 49-file docs/research/ corpus (32 hand-labelled queries). The last four commits (158f252, 550120e, 0987779, e80e40b) cut latency to roughly 5 ms keyword / 120 ms hybrid. Search works well. But every recent change was latency; relevance has not been touched, and a code-level audit found real headroom.

The one-line answer Search is good — don't rewrite it. Improve it surgically and provably: build a measurement spine first, then land low-risk fusion wins, then fix the long-document truncation that is the single biggest semantic-recall gap. Gate every change on the kb bench harness that already exists.

Who this is for

A future kb maintainer (human or Claude) deciding what to build next for search, and wanting the evidence in one place rather than re-deriving it from the codebase. The execution contract is in this artifact's kb-prompt template; the full phasing lives in the plan file ~/.claude/plans/i-want-to-step-curried-cerf.md.

What I found

I traced a query end-to-end through crates/kb-server/src/routes/search.rs → crates/kb-core/src/storage/lance.rs, read the embedder, indexer, query DSL, and the bench harness, and validated the hard parts against the pinned lancedb 0.27.2 / fastembed 5.13.4 sources. The picture:

The current pipeline

A search is: embed the query (for hybrid/semantic) → call one of bm25_query / vector_query / hybrid_query at limit=20 → return. The hybrid path (storage/lance.rs:713) chains lance's .full_text_search().nearest_to() and lets lance do the Reciprocal Rank Fusion internally (k=60). Lexical search is SQLite FTS5 (via lance) over five columns — title, body, headings, code, prompt (lance.rs:31); vector search is lance IVF-PQ, cosine, over a single per-doc embedding.

The truncation gap (the headline finding)

The indexer embeds each document's entire body as one vector — let embed_body = fields.body.clone(); at crates/kb-core/src/indexer.rs:1082, with no chunking. Every supported model is a BGE/Jina encoder that caps at 512 tokens (SUPPORTED_MODELS, embed.rs:67), and fastembed truncates to that limit. So for a long-form research artifact, the vector arm only encodes roughly the first ~400 words; everything after is invisible to semantic search.

Why hybrid still scores 0.81 The BM25/FTS arm indexes the full body (FTS is not truncated), so lexical recall covers the whole document and props up the hybrid number. Pure mode=semantic is where the truncation bites hardest — and where the most recall is left on the table for long artifacts.

A real eval harness already exists

This is the most important enabler: kb bench init|discover|run (crates/kb-cli/src/commands/bench.rs) computes Recall@k, MRR, and nDCG@k against hand-labelled query sets in bench/queries/*.jsonl, with reports in docs/bench/. It produced the bge-small vs. base vs. large bake-off (docs/research/foundation/14-embedding-bakeoff-2026-05-19.html). It means every change below can be measured, not guessed — but it was last run on 2026-05-19 against one corpus.

Load-bearing findings (what de-risks the work)

Six facts, verified against the pinned dependency sources, that make the plan cheaper and safer than it first looks:

  1. lance already exposes per-row scores — on the individual arms. _score (BM25, higher = better) and _distance (cosine, lower = closer) are auto-projected even with an explicit column select (the opt-out defaults off and kb never sets it). Reading them into the score-less DocSummary is net-new plumbing — kb deliberately ranks on position today (invariant #10) — but needs no query change. The combined hybrid call instead surfaces only a fused _relevance_score, which is exactly why Phase 2 runs the two arms separately and fuses in Rust.
  2. lance's hybrid RRF formula is identical to kb's own (k=60, 0-based, 1/(k+rank) — lance internally and kb_core::memory::rerank, memory.rs:18-20,174), so moving fusion into Rust reproduces the 0.81 baseline. One subtlety the review caught: the tie-break differs (lance dedups vector-arm-first then stable-sorts; memory::rerank breaks ties by id), so the port must replicate lance's tie-break rather than reuse memory::rerank verbatim — pinned by a parity test.
  3. Per-field FTS boost is supported in-version (MatchQuery::with_column + with_boost, composed via MultiMatchQuery) — with a no-API fallback (title/headings as a third RRF arm) if the live wiring disappoints.
  4. fastembed 5.13.4 ships a full reranker API (TextRerank, RerankerModel::BGERerankerBase and friends), gated on the hf-hub feature that is already enabled transitively — so no new crate. It does add operational weight: a ~280 MB reranker model download and a new kb-embedder run-mode (the sidecar loads one model eagerly today), so the prod cache volume must be provisioned before enabling it.
  5. Chunking must be a sidecar lance table. Putting multiple chunks as rows in artifacts would break the id-is-unique assumption — the review enumerated 10 sqlite tables + the lance merge key + 11 projections that key on a unique id (atlas, get_by_id, history, sessions, bookmarks, edges, …); a multi-vector column has no ANN path in lance. A sibling artifact_chunks table touches nothing else, and the doc-level embedding stays for atlas (list_embeddings → compute_layout).
  6. Federation is mostly built. routes/memory.rs::recall already fans out across corpora with correct embed-once-per-model keying and a keyword fallback. The reusable part is the inner per-corpus loop, not recall's memory-scope filter — search must fan out over all kbs — and the merge is that machinery minus salience/decay, by rank-position RRF.

The options

Five levers, scored on impact (relevance gain) and effort, with the dominant risk. "Impact" is judged against the long-form HTML research corpora kb actually serves.

Rust fusion: over-fetch + field weighting + filtered searchhighMlowno
Long-doc recall: passage / chunk embeddingshighestLhighyes + long reindex

Cross-encoder rerankerhigh (precision)Mmedno (model dl)

Measurement spine

Re-baseline kb bench on current code; expand golden sets beyond kb-docs to the research and platform corpora; implement the documented-but-missing --baseline delta column (bench.rs:13-17); expose a score (and an optional per-arm explain) on each hit. Cheap, zero relevance risk, and it makes every subsequent change auditable.

Rust fusion + quick wins

Run both arms at a ~150 candidate pool and fuse in Rust (rank-based RRF, parity-pinned to lance), then cut to limit. That one refactor unlocks: field weighting (title/headings outrank body), filtered ranked search by reusing the existing docs_query::matches() so tag:/category:/since: finally work with search, and optional recency/category boosts. Highest impact-per-unit-effort.

Long-doc recall (chunking)

The fix for the truncation gap: chunk the body into ~280-word passages with ~60-word overlap (safe under the 512-token cap), embed each into the artifact_chunks sidecar table, vector-search over chunks, and max-pool the best chunk per document. Biggest semantic-recall win for long artifacts — and the heaviest change, because it multiplies embedding work and needs a reindex. Opt-in per kb.

Federated cross-corpus search

Add scope=all to /api/search, fan out to every corpus on the daemon (reusing the recall machinery), and merge by cross-kb rank-RRF (scores are not comparable across corpora). One query over everything — high utility given 14 corpora, and the lowest-risk big feature (no schema, no model).

Cross-encoder reranker

Rerank the fused top-50 with a bge-reranker cross-encoder running in the kb-embedder sidecar, opt-in per kb. Cross-encoders move MRR/nDCG most (they fix ordering within an already-good candidate set). The cost is latency, so it stays opt-in and degrades to the pre-rerank order if the sidecar is unavailable.

Recommended order

Measure first so nothing ships on vibes; then the low-risk no-schema wins; then the reranker (which depends on the fusion refactor); then the heavy chunking lever last — and finally re-bench the reranker with chunk texts, because chunks give the cross-encoder the right passage to score.

Open questions

  • Passage prefix. BGE models expect a query: / passage: prefix asymmetry. Adopting it changes the doc-level vector too — bench both with and without before committing.
  • Recency boost default. A recency multiplier helps fast-moving corpora but hurts reference corpora; ship it config-gated and decide the default per corpus from the bench.
  • Which corpora to label. The expanded bench needs hand-labelled query sets; research and platform are proposed — confirm the set and budget the labelling.
  • Native FTS boost vs. rank-arm. Use lance's per-field boost if a smoke test plus a bench win confirm it; otherwise the title/headings rank-arm fallback.

Verification

Every phase runs the workspace gate — cargo test --workspace --no-fail-fast, cargo clippy --workspace --all-targets -- -D warnings, cargo fmt --all (the project's just ci) — plus the relevance gate:

kb bench run --kbs <a,b,...> --modes hybrid,semantic,keyword \
  --k 1 --k 5 --k 10 --baseline <saved>

No Recall@1 / nDCG@10 regression versus the committed Phase-1 baseline, and improvement on the lever's targeted query set. For chunking specifically, the gate is built from a long-document query set whose relevant answers live past the first ~400 words — the exact case truncation breaks today.

Independent verification

Before committing, I ran /deep-review — three parallel Opus agents, each verifying one claim-cluster against the actual code and the pinned dependency sources. All three returned GO WITH FIXES with no critical blockers; the load-bearing claims held:

  • Confirmed: lance auto-projects _score/_distance on the arms (lance-core scanner.rs, defaults on); the RRF formula matches memory::rerank exactly; the 512-token truncation is real (right-side, silent, ~384 words); the id-uniqueness blast radius is 10 sqlite tables + the lance merge key + 11 projections; fastembed 5.13.4's reranker API is present and hf-hub is transitively enabled.
  • Folded-in fixes: keep the existing hybrid_query intact for memory recall and add a separate pooled path for search (don't perturb invariants #10/#11); replicate lance's RRF tie-break rather than reuse memory::rerank; widen the slim search projection before post-filtering (it lacks the cap/tag/time columns docs_query::matches reads); Key::Category is ~6 edit sites, not one; chunking needs an explicit kb reindex backfill (the content-hash gate skips unchanged files), its own dirty flag, and must not bump_generation (invariant #15); federation lifts only recall's inner loop; the reranker needs a new sidecar run-mode + model provisioning.

These refinements are recorded in the plan file; none changes the recommended order.
