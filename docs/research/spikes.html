do not extend a spikeSix small experiments
in spikes/<name>/.

Each spike is a throwaway crate. Goal: learn something concrete about a hot-spot before committing real code. Each entry below states goal · what to test · expected finding · success criteria · effort. Findings get written into a spike-findings.md document; the architecture is updated based on what was learned.

Why spikes — and why throw them away

Spikes exist because architectural assumptions in a doc are cheap; assumptions in code are expensive. Each spike tests one assumption. None should grow into the real implementation. The pattern is: write 50–150 lines, measure or observe, update the architecture doc, delete the crate. The hardest discipline is not extending a working spike.

  1. spike-walker · ~50 LOC · 1 hour

    Baseline understanding of the HTML parser

    Goal: walk a directory of HTML files, parse each with scraper, print title + tag list. No db, no async. Builds intuition for what the indexer's pipeline costs and what gotchas the real artifacts contain.

    What to test

    • Parse 100 of Thariq's reference artifacts (or a similar synthetic corpus).
    • Extract document.title, first <h1>, first <p>, count of <svg>, presence of <details>, presence of <script>.
    • Time per file (mean, p95).
    • What HTML edge cases break scraper? Self-closing tags, malformed nesting, embedded CDATA, comments?

    Expected finding (from research)

    Topic 07's grep run shows: 20/20 artifacts have descriptive titles, 11/20 have inline SVG, 6/20 have <details>, 14/20 have <script>. scraper (built on html5ever) handles real-world HTML reliably; expect < 5 ms per file. Success means: the field-extraction list in topic 07's section D matches what spike-walker actually returns.

    Success criteria

    • Parses 100 files without panic.
    • Extracts the 6 fields above for every file.
    • Total runtime < 1 s.
    • Findings document updates topic 07 with corrected counts if the synthetic-vs-Thariq corpus diverges.
  2. spike-lance · ~100 LOC · 4 hours

    API feel for lancedb's hybrid search

    Goal: create a lancedb table with a few rows including a FixedSizeList<Float32, 384> column. Run keyword search (BM25), vector search (IVF-PQ), hybrid search (RRF). Confirm the API is ergonomic from Rust.

    What to test

    • Schema definition: FixedSizeList + String + scalar columns side-by-side.
    • Insert 10 rows manually with toy embeddings.
    • FTS index creation: Index::FTS(FtsIndexBuilder { with_position: true, ... }).
    • Vector index creation: implicit IVF-PQ on the FixedSizeList column.
    • Run three queries: BM25 only, vector only (cosine), hybrid (RRF reranker).
    • Cold-open latency: kill process, reopen, time first query.
    • On-disk layout: tree the dataset directory; identify _versions/, _indices/, _transactions/ + fragments.
    • Schema evolution attempt: add_columns, alter_columns, then a row insert. Does it hit bug #3136?

    Expected finding (from research)

    Topic 01 says lance's Rust crate exposes everything cleanly. Hybrid via query_type="hybrid" + RRF reranker is built-in. Cold-open is "tens of ms" for 10 rows. Bug #3136 may bite if schema-evolves past an embedding column. Success means: the recipe in topic 01 is achievable; you have working snippets for the real implementation.

    Success criteria

    • Hybrid search returns ranked results with both BM25 and vector contributing.
    • Cold-open < 100 ms.
    • Schema-evolution test produces a clear "yes works" or "yes hits #3136" answer.
    • Findings document quotes the actual sizes of _versions/, _indices/ directories.
  3. spike-sse · minimal axum · 2 hours

    Confirm the broadcast + ring + Last-Event-ID pattern works

    Goal: minimal axum server with one /events endpoint that broadcasts a counter every second. Test reconnection from curl -N and from a Node EventSource client. Confirm Last-Event-ID replay works.

    What to test

    • broadcast::channel(256) + per-connection BroadcastStream.
    • VecDeque ring buffer, capacity 1024, monotonic u64 id.
    • Handler reads Last-Event-ID header, drains ring, chains live stream.
    • KeepAlive::new().interval(Duration::from_secs(15)).
    • curl -N http://localhost:7000/events → see : heartbeats every 15 s.
    • curl -N -H "Last-Event-ID: 5" ... → only id>5 replays.
    • Subscribe-then-snapshot vs snapshot-then-subscribe order: which avoids duplicates?
    • Slow client: simulate with nc localhost 7000 + sleep; confirm BroadcastStreamRecvError::Lagged surfaces as a synthetic event: lag.

    Expected finding (from research)

    Topic 04's recipe should work as-is. The duplicate-on-reconnect concern is real — subscribe before snapshot and filter live items by id. Success means: the pattern is copy-pasteable into the real kb-server.

    Success criteria

    • Reconnect with Last-Event-ID replays exactly the missed events, no duplicates, no skips.
    • Heartbeats arrive every 15 s; never within 1 s of a real event.
    • Lag handling: client sees event: lag when broadcast slot full.
    • Findings document confirms (or refutes) the subscribe-first ordering.
  4. spike-ratatui · ~150 LOC · 4 hours

    Confirm thin-client pattern: SSE → ratatui

    Goal: minimal ratatui app that subscribes to spike-sse's counter via reqwest-eventsource, renders it. Confirms the thin-client pattern works end-to-end.

    What to test

    • 3-task pattern: input task (crossterm EventStream), SSE task (reqwest-eventsource), tick task (250 ms interval) — all feeding one mpsc::UnboundedSender<AppEvent>.
    • Render loop: tokio::select! with render_interval at 30 Hz, dirty-gated.
    • Header gauge showing the counter; footer connection dot via throbber-widgets-tui.
    • Component pattern: separate Header, Body, Footer components implementing a small Component trait.
    • Reconnect UX: kill spike-sse, watch the dot turn yellow → spinner → red. Restart spike-sse, confirm seamless reconnect with Last-Event-ID replay.
    • q to quit, terminal restored cleanly via Drop.

    Expected finding (from research)

    Topic 05 says no public end-to-end ratatui+SSE example exists; the plumbing is straightforward but you'll need to write it. Success means: kb-tui's file layout (topic 05 section "Concrete recommendation") is validated, and the dirty-gated render loop measurably saves CPU at idle.

    Success criteria

    • Counter updates appear in the gauge within ~33 ms of the SSE event.
    • At idle (counter steady), CPU usage < 1%.
    • Reconnect-with-replay works; no missed counter values after reconnect.
    • Component pattern feels right at 3 components — would scale to 6.
  5. spike-iframe · minimal axum + HTML · 3 hours

    Validate the sandbox + subdomain + postMessage recipe

    Goal: minimal axum server hosting (a) a parent page on http://localhost:7000 and (b) several HTML artifacts on http://<id>.artifacts.localhost:7000. Wildcard via /etc/hosts + a few static aliases. iframe-embed them with the recommended sandbox flags. Test postMessage parent↔iframe.

    What to test

    • Sandbox: allow-scripts allow-popups allow-popups-to-escape-sandbox allow-forms allow-modals allow-downloads. No allow-same-origin.
    • Subdomain serving: confirm localStorage.setItem works inside the iframe (different origin from parent → real persistent storage).
    • postMessage RPC: parent sends {type:'kb.init', prompt}; iframe replies {type:'kb.fetch', url}; parent fetches with session cookie and posts back.
    • Inter-artifact links: artifact does e.preventDefault(); parent.postMessage({type:'kb.nav', id}); parent SPA navigates.
    • External resources: artifact loads a font from fonts.gstatic.com + a script from cdn.jsdelivr.net. Both succeed.
    • fetch back to kb's API directly (without postMessage): confirm CORS rejects (Origin: null doesn't match).
    • Sandbox-removal attack: artifact tries parent.document.querySelector('iframe').removeAttribute('sandbox'). Confirm subdomain ≠ parent → CORS denied access to parent.document.
    • iframe-recreate-per-render: navigate between two artifacts; confirm the first artifact's globals are gone in the second.

    Expected finding (from research)

    Topic 06 recipe should work as-is. Success means: kb's sandbox model is provably safe (no cross-artifact contamination, no parent escalation) and ergonomic (storage + external assets work).

    Success criteria

    • localStorage persists across iframe reloads on the same artifact.
    • Cross-artifact storage isolation confirmed.
    • External font + CDN script loads succeed.
    • Direct fetch to kb API blocked; postMessage RPC works.
    • Sandbox-removal attempt fails with a console SecurityError.
  6. spike-fastembed · ~50 LOC · 1 hour

    Measure embedding latency, memory, model size on this machine

    Goal: ~50 lines that takes 100 plain-text strings, embeds them with fastembed + bge-small-en-v1.5, runs a knn query (toy: in-memory cosine). Measures latency, memory, model download size.

    What to test

    • Cold start: time the first TextEmbedding::try_new call (model download + load).
    • Warm embed: time a single embedding for a 100-token, 500-token, 2000-token input.
    • Batched throughput: time embed(&[strings; 32]).
    • Model file size on disk after download (~/.cache/kb/models/).
    • onnxruntime shared library size (after switching to load-dynamic).
    • RSS memory during inference.
    • Try BGESmallENV15Q (quantised) variant: same measurements, compare quality on a tiny relevance set (10 query/doc pairs from topic 07's artifacts).

    Expected finding (from research)

    Topic 02 says: ~5–15 ms/embed on M-series, 15–40 ms on x86; 300–800 embeddings/sec batched. Model is ~130 MB fp32, ~33 MB int8. Success means: the project-local benchmark numbers fall within these bounds; if not, the embedding decision (or model choice) needs revisiting.

    Success criteria

    • p50 single embed < 50 ms on this machine for 500-token input.
    • Batched p50 > 200 embeddings/sec.
    • Cold start < 5 s after model already cached; first-run with download < 60 s.
    • Quantised variant within 2% MTEB on the toy set.
Order & total effort
  1. spike-walker · 1 h — fastest; builds parser intuition before anything else.
  2. spike-fastembed · 1 h — measures the slowest hot-spot (embedding); informs whether bge-small is right.
  3. spike-sse · 2 h — validates the daemon's streaming primitive.
  4. spike-iframe · 3 h — validates the SPA's rendering primitive.
  5. spike-ratatui · 4 h — validates the thin-client pattern.
  6. spike-lance · 4 h — biggest commitment; do after spike-walker so you have a real corpus to load.

Total: ~15 hours of focused work. Run sequentially, write findings as you go. spike-findings.md at the end captures: what worked, what surprised, what the architecture should change. Then delete the spike crates.

If a spike fails
  • spike-fastembed latency > 100 ms p50 → revisit model choice (consider quantised default, or switching to Candle, or the matryoshka path from topic 02).
  • spike-lance hits bug #3136 → add a test case to the kb regression suite, pin patch version, file upstream issue.
  • spike-iframe wildcard subdomain too painful for local dev → fall back to topic 06's "single host + postMessage RPC for storage" plan; lose persistent localStorage from artifacts.
  • spike-sse Last-Event-ID replay produces duplicates → the snapshot/subscribe ordering needs revision; update topic 04 with the correction.
  • spike-ratatui dirty-gated render still burns CPU at idle → the architecture needs a different trigger (event-driven render only, no tick interval).
