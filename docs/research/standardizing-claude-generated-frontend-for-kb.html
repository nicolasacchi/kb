Standardize or stay free? A constrained-primitives, free-composition house style for kb's HTML artifacts

kb imposes a purely structural authoring contract and zero visual standardization, so Claude styles every artifact free-form. Should we standardize frontend patterns so Claude reuses known-good ones — or keep it free? The honest answer is a third option both sides converge on: standardize the accessibility/consistency floor, leave the aesthetic ceiling free.

2026-06-06 ·status:applied ·project:kb ·design · 42 research agents · 25/28 sources verified

Summary & recommendation

Recommended (you decide) Adopt a thin, inlinable accessibility + design-token FLOOR carried by the kb-artifact skill — an AA-contrast-locked :root token block (light + dark), a handful of native-primitive snippets, and a11y defaults (reduced-motion, :focus-visible, skip-link, ≥16 px) — and leave the CEILING free: layout, accent hue, density, illustration, per-artifact voice. This captures the two wins the evidence supports with high confidence (consistency and accessibility, which live in exactly the layer kb leaves open) at near-zero maintenance. It deliberately does not buy “better-looking” artifacts — that axis is where your “let Claude be free” gut is genuinely well-founded, and the floor leaves it untouched.
Ruling — 2026-07-03 (applied) Adopted, then evolved after a month in production. The paste-a-block floor shipped in June worked as an a11y floor but its “free accent override” went unused: 13 artifacts in this corpus shipped --accent:#3a5a9f verbatim, and 101 validator score rows showed structural compliance essentially solved (87× structural=100) with the weak dimensions being content (outlinks 54×, specificity 46×) — never the visual layer. The floor is now “verified outcomes, free values”: the standard token role names (--bg --surface --fg --muted --rule --accent --accent-fg [+ status trio]) remain the interface, every value is a free per-artifact design choice, and the kb-artifact skill’s contrast-check.py (hex/rgb/hsl/oklch) verifies every known role pair ≥4.5:1 in both themes — report-only. The old token block is demoted to a worked example; shipping its palette verbatim is flagged. Canonical text: docs/authoring-artifacts.md → “Visual floor (verified outcomes, free values)”.

This is the decision write-up. Its companion, “Why the frontend-design skill opposes standardization” (frontend-design-skill-anti-standardization-rationale.html, same corpus), explains why the loudest anti-standardization voice says what it says — and why that stance was never aimed at kb's document corpus.

The question, the current state, the two-skills tension

kb's authoring contract is deliberately structural: a real <title>, a heading hierarchy with stable kebab section ids, a <template id="kb-prompt">, kb-tags/kb-category meta, substance in <body>, and iframe-safety rules. Search, indexing, and embeddings key off structure — never off a button class or an accent hue. Styling is left entirely free-form. The question: should kb standardize the visual/component layer so Claude reuses known-good patterns, or keep generating freely?

Two installed skills already pull in opposite directions

Every kb artifact generation sits between two Claude Code skills that contradict each other:

  • The frontend-design skill (Anthropic official): commit to a bold per-context aesthetic, “No design should be the same,” “NEVER converge on common choices across generations,” reject reused patterns and system fonts.
  • The kb-artifact skill: a ~42-line reference CSS with system fonts, one callout component, “no gradients / no purple-pink oversaturation,” prefers-color-scheme dark, platform-primitives-only, single-file inline CSS, <25 KB.

One optimises distinctiveness; the other restraint and reuse. The tension dissolves once you split the floor from the ceiling: standardize the boring, accessibility-sensitive primitives (where reuse demonstrably wins and reinvention only adds risk); leave the expressive surface free (where distinctiveness adds value). A decisive practical point also defangs the “never converge” mandate: each Claude session is memoryless, so it cannot deliberately diverge from prior artifacts it cannot see. The only thing that reliably travels between isolated sessions is what the author carries in — a token block, an exemplar, a skill rule — which is the floor.

kb's own natural experiment

The repo already ran the experiment, and the result is verifiable in-tree:

  • The 4 free-form single-file canon artifacts (corpus/canon/*.html) each invent their own accent (oklch hues ≈ 30 red, 145 green, 22 red-orange, 290 purple), mix 3 light + 1 dark backgrounds (two of the light files even share one palette), and each invent their own button (add-btn vs copy-btn vs pager links) — and all four ship zero prefers-reduced-motion, zero skip-link, zero focus-visible.
  • The 43 docs/research + docs/review pages that link a shared stylesheet (33 → assets/style.css, 10 → docs/review's _assets/review.css) converge ~85% and inherit the accessibility primitives the free-form artifacts lack.
The decisive nuance Shared CSS ⇒ convergence + free accessibility; free-form ⇒ divergence + unmanaged accessibility. But the convergence mechanism was a linked stylesheet — which kb's single-file / sandboxed-subdomain constraint forbids for portable standalone artifacts. So the proven recipe has to be re-cast as an inlinable token + snippet block carried by the skill, not copied as a linked asset. That re-casting is the whole proposal.

Five steelmanned perspectives

1 · FOR a thin inlinable house standard

kb should standardize — but only as a thin inlinable layer (a token preamble + a few exemplars + the skill guidance kb already ships), not a heavyweight system. Free-form LLM output is inaccessible exactly in the visual/keyboard layer kb leaves free; “free” buys the slop mean because each generation is an isolated memoryless draw; and kb's own repo already proved shared CSS ⇒ ~85% convergence + free a11y.

Strongest counter: premature/wrong-abstraction lands hardest at solo scale — a thin standard is the easiest to ignore (so enforcement is uncertain) while tokens-alone demonstrably drift, so it may underdeliver while still trading Claude's slop for the operator's own monoculture.

2 · FOR keeping Claude FREE per-artifact

kb's value rests on a structural contract; divergence costs the product nothing functional. Per-artifact freedom is the documented antidote to AI slop, and imposing one house style re-converges every artifact onto a single look — manufacturing the very sameness the field warns against. Design-system ROI scales with contributors/reuse/longevity; a solo author of one-off artifacts is below every breakeven, and 4 artifacts haven't “screamed for abstraction” (the Rule of Three).

Strongest counter: the a11y case is not weak — free-form is the empirically worst mode, defects cluster in the free layer, prompts can't guarantee a contrast floor (non-deterministic even at temp 0), and “never converge” is unenforceable across memoryless sessions. A few inlinable tokens + a native-element rule add a real floor at near-zero cost, so “do nothing” is the weaker position on accessibility specifically.

3 · Accessibility & reading-UX lens

Free-form is a net negative for a11y precisely in kb's no-standard mode, and the defects cluster in Perceivable/Operable — the layer kb leaves free. kb's own canon proves it: zero reduced-motion/skip-link/ focus-visible, and their muted text computes at 4.33:1 and 3.73:1 — both below the AA 4.5:1 floor: same author, same model, both failing by luck rather than design. The highest-leverage wins are native-HTML defaults that constrain nothing visual. Design it as a floor (vetted AA tokens + a contrast/native-element check), not a ceiling.

Strongest counter: for a solo sole-reader there's no external/legal driver; “accessibility” collapses into ordinary readability the user can judge per-artifact, and a single defective shared primitive breaks every artifact at once. So the defensible slice is the narrowest non-visual defaults (native elements, reduced-motion, base font-size, contrast self-check), not a primitives library.

4 · LLM-behaviour / evidence lens

Graded by evidence strength: consistency across a collection is strongly supported (incl. kb's repo); less-broken / accessible is strongly supported for the structural layer; but “better” aesthetically is not supported — that is exactly where “let Claude be free” is genuinely strong. Reuse reduces output variance (few-shot gains plateau after ~2–5 exemplars); grounding is nuanced not a blank cheque — argue for a thin, selective standard on high-value/low-creativity axes.

Strongest counter: a reused token preamble risks the very slop median it's meant to avoid — if it encodes the safe restrained look, every artifact inherits a tasteful-but-generic baseline, an arguable downgrade on “better” even as it's an upgrade on “consistent.”

5 · kb-practical / implementability lens

Under kb's real constraints the debate collapses into build/maintenance cost: the enforcement-tier mechanisms that guarantee consistency in production tools (runtime import, scan-on-generation, linked stylesheets) are not buildable on kb's watch-a-folder / single-file / frame-ancestors-only path, and a full system never breaks even at solo scale. The viable, cheap move is an inlinable token+snippet preamble carried by the skill + de-conflicting the two skills, with kb-native exemplar retrieval (kb is itself a search engine) as a deferred second step.

Strongest counter: “guidance + inlinable tokens” is exactly the mechanism class practitioners most often report as insufficient (tokens drift, prompts are non-deterministic, production tools moved to hard enforcement) — so the cheap option may not produce the convergence it promises, and the only mechanism that reliably reproduces the shared-CSS result is a build-then-inline pipeline kb deliberately lacks.

Recommendation & rationale

Adopt Option 2 (thin inlinable token + accessibility floor via the kb-artifact skill), with Option 3's lightweight contrast/native-element self-check as a fast follow, and treat Option 4 (exemplar retrieval) as a deferred experiment. Standardize the floor; leave the ceiling — layout, accent hue, density, illustration, voice — free. Resolve the two-skill tension by scope, not by picking a winner: kb-artifact is authoritative for reading documents (research / RFC / review); reserve frontend-design's per-artifact-novelty mandate for genuine interactive / playground artifacts.

Why this, and not a rubber-stamp of either pole:

  1. The two wins the evidence supports with high confidence — accessibility-by-default and cross-artifact consistency — live in exactly the layer kb leaves free, and the floor fixes them once for all future artifacts at near-zero maintenance.
  2. The win your gut cares about — “better-looking,” distinctive artifacts — is the axis where reuse evidence is thin-to-absent and homogenization risk is real, so the recommendation deliberately leaves accent/layout/voice free. That is why it isn't a rubber-stamp of either side.
  3. kb's natural experiment is decisive on mechanism: shared CSS converged and shipped free a11y; free-form diverged and shipped none — and the proven mechanism re-casts cleanly into the only form the constraint permits (inlinable tokens + snippets + skill guidance), buildable today with a handful of doc/skill edits and no daemon/CI change.
  4. Solo-scale economics rule out a heavyweight system but favour the cheapest reversible unit; the floor is exactly that, and the wrong-abstraction risk is contained because it constrains only proven-recurring, low-creativity axes.
  5. Enforceability honesty: prose alone can't guarantee a contrast floor and “never converge” is structurally unenforceable, so a positive, reusable token block plus a soft contrast check is what actually makes the floor hold — without pretending any thin standard guarantees an aesthetic outcome.
The honest framing Standardize the parts that are correctness (accessibility) and cheap consistency; free the parts that are taste. Your “let Claude be free” instinct is right about taste and is preserved intact; it is only wrong about accessibility, which is the one place a floor pays for itself.

Appendix: the concrete proposal to adopt

Model: “constrained primitives, free composition.” Standardize a thin, inlinable, accessible floor carried by the kb-artifact skill and pasted into each single-file artifact; leave layout, accent hue, density, illustration, and voice free above it. This very document uses the floor below — its :root, skip-link, focus rings, and reduced-motion handling are the proposal, dogfooded.

1 · The inlinable token + a11y preamble

~30 lines of CSS custom properties (light + dark), AA-contrast-locked, with the a11y defaults. Paste into each artifact's <style>. --accent is an explicit per-artifact override — swap it freely; just keep it ≥4.5:1 against --bg where used for text.

:root{
  /* COLOR — AA-locked light defaults. --accent is a free per-artifact override. */
  --bg:#fbfbfa; --surface:#f3f3f1; --fg:#1b1b1a; --muted:#5f5f5c;   /* --muted on --bg = 5.6:1 */
  --rule:#d9d9d6; --accent:#3a5a9f; --accent-fg:#ffffff;            /* keep --accent >=4.5:1 for text */
  --warn:#8a5f00; --danger:#9a2f28; --ok:#256148;                  /* all >=4.5:1 on --bg/--surface */
  /* TYPE — >=16px reading floor */
  --fs-body:1.0625rem; --fs-small:.85rem; --lh:1.6; --maxw:46rem;
  --sans:system-ui,-apple-system,"Segoe UI",Roboto,sans-serif;
  --serif:ui-serif,Georgia,"Times New Roman",serif;
  --mono:ui-monospace,"SF Mono","Cascadia Code",Menlo,Consolas,monospace;
  --radius:6px; --focus:2px solid var(--accent);
}
@media (prefers-color-scheme:dark){
  :root{
    --bg:#16171a; --surface:#1f2126; --fg:#e6e6e3; --muted:#a3a39e; /* --muted on --bg = 6.9:1 */
    --rule:#2c2e33; --accent:#8fb0ee; --accent-fg:#11131a;
    --warn:#e0b24d; --danger:#f08079; --ok:#6fcaa0;                 /* lifted for dark-bg AA */
  }
}
@media (prefers-reduced-motion:reduce){
  html{scroll-behavior:auto}
  *,*::before,*::after{animation-duration:.001ms!important;transition-duration:.001ms!important}
}
body{margin:0;background:var(--bg);color:var(--fg);font-family:var(--sans);
  font-size:var(--fs-body);line-height:var(--lh)}
:focus-visible{outline:var(--focus);outline-offset:2px}
.skip-link{position:absolute;left:-9999px;top:0;background:var(--fg);color:var(--bg);
  padding:.5rem 1rem;z-index:100;font:600 var(--fs-small)/1 var(--mono);
  text-transform:uppercase;letter-spacing:.05em;text-decoration:none}
.skip-link:focus{left:.5rem;top:.5rem}

2 · Native-primitive snippets

The rule above them all: interactive elements are real <button> / <a>, never styled <div>s (the first rule of ARIA). One canonical button replaces the canon's divergent add-btn/copy-btn/pager.

/* BUTTON — native element; role/keyboard/focus/disabled for free */
.btn{font:600 var(--fs-small)/1 var(--mono);letter-spacing:.08em;text-transform:uppercase;
  display:inline-flex;align-items:center;gap:.4rem;padding:.5rem .8rem;
  border:1px solid var(--rule);border-radius:var(--radius);background:transparent;color:var(--fg);cursor:pointer}
.btn:hover{border-color:var(--accent);color:var(--accent)}
.btn:focus-visible{outline:var(--focus);outline-offset:2px}
.btn[disabled]{opacity:.5;cursor:not-allowed}
.btn--primary{background:var(--accent);color:var(--accent-fg);border-color:var(--accent)}
/* <button type="button" class="btn">Copy</button> */

/* CALLOUT — meaning carried by the text label, never by color alone (WCAG 1.4.1) */
.callout{font-family:var(--serif);border:1px solid var(--rule);border-left:4px solid var(--accent);
  border-radius:var(--radius);background:color-mix(in srgb,var(--accent) 7%,var(--bg));padding:.8em 1em;margin:1.2em 0}
.callout-label{font:650 .72rem/1 var(--sans);letter-spacing:.05em;text-transform:uppercase;
  color:var(--accent);display:block;margin-bottom:.3em}
.callout--warn{border-left-color:var(--warn);background:color-mix(in srgb,var(--warn) 9%,var(--bg))}
.callout--danger{border-left-color:var(--danger);background:color-mix(in srgb,var(--danger) 9%,var(--bg))}
.callout--ok{border-left-color:var(--ok);background:color-mix(in srgb,var(--ok) 9%,var(--bg))}
/* <aside class="callout callout--warn"><span class="callout-label">Caution</span>…</aside> */

/* CODE — outer <pre> drives the gallery glyph strip; inner <code> is BM25-indexed */
code{font-family:var(--mono);font-size:.88em;background:var(--surface);border-radius:4px;padding:.08em .35em}
pre{background:var(--surface);border:1px solid var(--rule);border-radius:8px;padding:1rem;overflow:auto;font-size:.85rem;line-height:1.5}
pre code{background:none;padding:0}

/* TABLE — real <thead>/<th scope> for screen-reader header association */
table{border-collapse:collapse;width:100%;font-family:var(--sans);font-size:.9rem;margin:1em 0}
th,td{border:1px solid var(--rule);padding:.5em .7em;text-align:left;vertical-align:top}
th{background:var(--surface);font-weight:600}

/* LINK — AA accent; visible focus ring; signal new-tab; never break out of the iframe */
a{color:var(--accent);text-underline-offset:2px}
a:focus-visible{outline:var(--focus);outline-offset:2px;border-radius:2px}
a[target="_blank"]::after{content:" \2197";font-size:.8em}

4 · How this reconciles the two skills

A clean altitude split, scoped by artifact type, rather than a winner. The floor (a11y defaults, a closed contrast-locked token set, native primitives) is standardized — the layer where kb-artifact's restraint+reuse posture is right and where reuse demonstrably wins, and which constrains nothing about hue, layout, or typeface. The ceiling (layout, the --accent override, density, illustration, voice) is left free — the layer frontend-design is genuinely good at. This dissolves the contradiction three ways: (1) system fonts vs not — the floor uses system fonts for the reading body (a deliberate, accessible, zero-weight choice); a showpiece may layer a display face above; (2) never-converge vs reuse — convergence is mandated only on the boring, accessibility-sensitive primitives, never on the expressive surface; (3) restraint vs distinctiveness — the floor makes restraint the free baseline while the per-artifact accent keeps each artifact recognizably its own (Dan Mall's 80/20: distinctiveness on the 20% that carries identity, coherence on the 80% that doesn't).

Open questions

  • Do you actually want cross-artifact recognition (favouring even a thin floor), or do you read each artifact as a standalone object where per-artifact distinctiveness is a feature? Your “free” gut suggests the latter for the ceiling — but the floor (a11y) is orthogonal to that preference.
  • Is the contrast self-check (Option 3) worth the added skill-engineering, or is a soft prose rule enough given you can eyeball-fix any contrast that bothers you in your own private corpus?
  • Should the standard touch already-served immutable artifacts at all? Propagation can't reach them, so the floor only helps future artifacts — is retroactive re-generation of the 4 canon files in scope, or explicitly out?
  • How aggressively should --accent be bounded? Free hue preserves distinctiveness but reintroduces per-artifact contrast risk — should the floor ship a small contrast-verified accent ramp (pick from N) rather than a fully free hue?
  • The strongest skeptical read: guidance + inlinable tokens is the mechanism class repeatedly reported as insufficient, and the only reliably-converging mechanism (build-then-inline) isn't worth building at solo scale — so is accepting some divergence (closer to Option 0/1) the more honest endpoint, with the floor scoped strictly to the non-negotiable a11y minimum?
