Topic 06 · Iframe vs Shadow DOM · Confidence MEDIUM → HIGH (refines the proposal)

verdictSubdomain per artifact.
Sandbox + same-origin, served from a different origin.

The proposed sandbox="allow-scripts allow-popups" is right in spirit but mis-located in practice. Without allow-same-origin, the iframe is an opaque origin — localStorage, IndexedDB, cookies all throw SecurityError. The fix is the CodePen / Observable / Claude pattern: keep allow-same-origin, but serve each artifact from a different origin (subdomain). That gives the iframe a real, isolated origin with working storage and denies it the parent's DOM.

Integration note · 2026-05-11 (amended post deep-review)

The Web Gallery design handoff was almost right. Its prototype used sandbox="allow-scripts allow-popups allow-forms allow-same-origin" — the right flag set, but served the iframe from the parent's origin (localhost:4000), which is the actual storage-broken footgun §A flags. Reconciliation: keep the flag set, change the serving origin. Per-artifact subdomain (<id>.artifacts.localhost:4000) gives the iframe its own real origin; the sandbox stays intact, storage works, and the parent's DOM is cross-origin (safe). The annotator bridge (topic 10 §I) works directly because allow-same-origin is in — but still uses serve-time injection (topic 10 §M-10) for cache-control and per-artifact-script delivery.

TL;DR

Sandbox flag string: allow-scripts allow-same-origin allow-popups allow-popups-to-escape-sandbox allow-forms allow-modals allow-downloads. Serve each artifact from <id>.artifacts.localhost (wildcard DNS, Chrome since M67 / Firefox since 84 auto-resolve; Safari needs dnsmasq) — the artifact gets a real, persistent, isolated origin so localStorage/IndexedDB/cookies all work, and the sandbox-removal attack is neutered (different origin → can't reach parent.document). Bridge fetch through postMessage (parent SPA does the actual call). Keep allow-top-navigation* off. Use Shadow DOM only for the JS-free artifact subclass; everything else: iframe. Recreate the iframe per render (CodePen pattern) — kills runaway loops, frees memory.

A. Sandbox flag semantics (current spec)

Each token re-enables one capability

sandbox="" applies all restrictions. Each token re-enables one capability:

TokenWhat it re-enables
allow-scriptsJS execution (does not allow popups)
allow-same-originRemoves the opaque-origin treatment. Document keeps its real origin → cookies, storage, same-origin fetch all work
allow-formsForm submission
allow-popupswindow.open and target="_blank"
allow-popups-to-escape-sandboxPopups don't inherit the sandbox
allow-modalsalert/confirm/prompt, <dialog>, BeforeUnloadEvent
allow-pointer-lock / -orientation-lock / -presentationNiche APIs
allow-top-navigationThe parent SPA gets blown away
allow-top-navigation-by-user-activationSame, but only after a user gesture
allow-downloads<a download> and download responses
allow-storage-access-by-user-activationStorage Access API (unpartitioned cookies)
allow-same-site-none-cookiesNew in Chrome 135 (2025) — narrow cookie use case
The footgun: combining allow-scripts + allow-same-origin when the iframe is served from your own origin is equivalent to no sandbox at all — the embedded script can parent.document.querySelector('iframe').removeAttribute('sandbox') and reload itself. MDN, WHATWG, and the W3C HTML validator all warn. Only safe combo: those two together when the iframe is served from a different origin.
B. Storage isolation specifics

Without same-origin, storage throws SecurityError

Concrete behaviour for localStorage.setItem('foo','bar') inside the iframe:

  • No allow-same-origin (opaque origin): hard SecurityError: localStorage is not available for opaque origins. Doesn't silently fail, doesn't quietly persist — the API throws on access. Same for sessionStorage, document.cookie.
  • With allow-same-origin, iframe served from kb's origin: the artifact shares localStorage with the parent SPA. Two artifacts can read each other's keys; a malicious artifact can clobber kb's state.
  • With allow-same-origin, iframe served from a different origin (subdomain): each origin has its own isolated localStorage. This is the architecture every serious sandbox uses (CodePen ⇒ s.codepen.io; Observable ⇒ <user>.static.observableusercontent.com; Claude artifacts ⇒ claudeusercontent.com).

IndexedDB: same rules. indexedDB.open() throws without allow-same-origin.

BroadcastChannel: in Chromium constructible from an opaque origin, but messages only reach contexts with the same opaque origin — no way to construct that match externally. Practically isolated.

Cookies: blocked, unless you add allow-same-site-none-cookies (Chrome 135+, not yet Firefox/Safari).

C. fetch() and network behaviour

Origin: null breaks CORS. Bridge through postMessage.

  • fetch('/api/...') from a sandboxed iframe with no allow-same-origin: request goes out with Origin: null. If kb's API replies with the standard Access-Control-Allow-Origin: <kb-origin>, the response is rejected. Access-Control-Allow-Origin: null is widely considered a footgun.
  • <script src="https://cdn.jsdelivr.net/...">: sandbox does not block external script loads. Only CSP can. Use the csp attribute to lock down (e.g. script-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net).
  • @font-face with https://fonts.gstatic.com/...: works from a sandboxed iframe; fonts are CORS-checked, Google Fonts sends correct headers.
  • Inline <style>: always allowed, sandbox doesn't touch CSS. Inline <script> runs only with allow-scripts. CSP is orthogonal.
D. postMessage parent ↔ iframe

The designed escape hatch — works even with sandbox=""

postMessage works regardless of sandbox flags — even with sandbox="", the parent can still send messages and the child can still receive them, provided the child has allow-scripts (it needs a listener). No flag needs to be added.

// in parent SPA, on iframe load:
iframe.contentWindow.postMessage({ type: 'kb.init', artifactId, prompt }, '*');

// in iframe artifact:
window.addEventListener('message', (e) => {
  if (e.source !== window.parent) return;
  // handle e.data
});

// RPC pattern: child requests data, parent fulfils
parent.postMessage({ type: 'kb.fetch', id: 7, url: 'kb://docs/x' }, '*');
window.addEventListener('message', e => {
  if (e.data.type === 'kb.fetch.reply' && e.data.id === 7) /* ... */;
});

Tradeoffs

  • Async only. No synchronous "give me my prompt".
  • Ordering is FIFO per channel but races easy when many messages arrive during init.
  • targetOrigin should be the actual origin when sending into the parent (event.origin for replies). Using '*' going into an opaque iframe is fine; out to the parent is a leak vector if you transmit anything secret.
  • For heavier RPC, use MessageChannel with transfer — each conversation has its own port.
  • Receivers must validate event.origin, event.source, and the schema of event.data. Treat the iframe as hostile.
E. Shadow DOM as alternative

Not a sandbox. Useful for the JS-free artifact subclass.

Shadow DOM gives you scoped CSS and DOM encapsulation. It does not give you:

  • Script isolation. None. An inline <script> in a shadow root runs in the host page's realm with the host page's window, document, globals.
  • Global listener isolation. A handler on document/window from one artifact sees events from every other artifact.
  • Library isolation. Two artifacts that both load jQuery / leaflet / three.js / d3 — they collide on window.$, window.L, window.THREE. First-load wins or last-load wins.
  • Crash isolation. A while(true) in one artifact freezes the whole tab.
  • Storage isolation. localStorage is keyed by origin, not by shadow root.

Shadow DOM is not a sandbox; it's a styling/DOM-encapsulation primitive that happens to look sandbox-shaped from a distance.

When Shadow DOM IS the right call for kb

  • Static, JS-free artifacts: rendered Markdown, SVG diagrams, stylised prose, tables. Win: one DOM, one realm, instant rendering, no postMessage hop, no iframe layout reflow per artifact.
  • Trusted artifacts authored by kb itself (system templates, chrome).
  • Tiny pure-CSS interactive widgets (<details>, :has, :checked toggles): no JS to collide.

A practical hybrid: classify artifacts at ingest time (look for <script> and external src) and route the JS-free class through a Shadow DOM renderer for performance while sending JS-bearing artifacts through the iframe path.

F. Other alternatives, briefly

Mostly skip

  • <object> / <embed>: opaque-origin for cross-origin content, but ergonomics dated, sandbox attribute is iframe-only. Not worth it.
  • Web Worker / Worklet: doesn't render. OffscreenCanvas + manual paint not viable for arbitrary HTML.
  • Strip <script> at ingest: kills the whole point of html-as-medium. Don't.
  • Closed shadow + Trusted Types + ShadowRealm: ShadowRealm (TC39 stage-3) isolates JS realms but has no DOM. Useful for plugin VMs, not artifact rendering.
  • srcdoc: same security model as src. Convenient for inlining without a server route, but does not unlock any extra origin/storage trick.
  • Credentialless iframes (credentialless attribute, Chrome shipping, Firefox WIP): each load gets an ephemeral storage partition tied to the top-level document's lifetime. Useful for COEP, not a sandbox substitute.

Decisions · 2026-05-11 (cluster 1: iframe + wildcard DNS — amended 2026-05-11 post-review)

After the Web Gallery handoff (topic 10) was integrated, the open-points discussion landed the following resolutions. Amended post-review: the original "drop allow-same-origin" decision was reversed — it conflicted with §B's own storage analysis (opaque-origin iframes can't use localStorage regardless of where served). The CodePen / Observable / Claude-Artifacts pattern (which §G surveys) keeps allow-same-origin; what makes it safe is the iframe being served from a different origin than the parent. Subdomain serving is the load-bearing piece.

  • DNS strategy. Per-artifact subdomain via <id>.artifacts.localhost. *.localhost first — Chrome (since M67, Dec 2017) and Firefox (since 84, Dec 2020) auto-resolve all .localhost subdomains to 127.0.0.1 (RFC 6761 §6.3). Safari is the actual blocker — macOS Safari delegates to mDNSResponder, which does NOT implement the RFC 6761 auto-resolution. Spike Safari compatibility before v0.1 SPA ships; dnsmasq fallback (address=/.localhost/127.0.0.1 plus address=/.localhost/::1 for IPv6) is the documented Safari workaround. Per-port isolation rejected (breaks bookmarks, kills per-origin process budget); /etc/hosts rejected (no wildcard). Caddy + DNS-01 is the self-host path.
    Spike update · 2026-05-11 · spike-iframe confirmed in Chromium (via Playwright MCP, 16/16 probes pass on 4 canon artifacts) and on the host CLI: *.localhost resolves out of the box on Arch Linux with glibc 2.41+ and systemd-resolved — no dnsmasq needed. getent hosts s01.artifacts.localhost returns ::1 localhost and curl -v resolves cleanly. Production install guide should document the wildcard as working on modern Linux + Chrome + Firefox out of the box, and reserve the dnsmasq fallback (address=/.localhost/127.0.0.1) for Safari and older glibc only. Firefox parity verification is still pending operator review (Playwright defaulted to Chromium). Full context: docs/spike-findings.md.
  • Sandbox flags (amended). v0.1 baseline: sandbox="allow-scripts allow-same-origin allow-popups allow-popups-to-escape-sandbox allow-forms allow-modals allow-downloads". Keep allow-same-origin — combined with subdomain serving, the iframe gets a real, isolated origin (per-artifact localStorage / IndexedDB / cookies all work), and the sandbox-removal attack is neutered (the parent's DOM is cross-origin, unreachable from the iframe). Drop only allow-top-navigation* (artifact must not navigate the parent SPA away). This matches CodePen / Observable / Claude-Artifacts. Topic 07's stricter allow-scripts-only default is deferred — kitchen-sink uses <dialog>.showModal() (needs allow-modals) and future artifacts may use storage. The design prototype's mistake was not the flag set; it was serving the iframe from the parent's origin. Subdomain serving fixes both.
  • iframe-recreate. React key={artifactId + ':' + pageIdx} on the <iframe>. The Web Gallery prototype already does this; keep it.
  • postMessage (amended). Direction-aware targetOrigin:
    • parent → iframe: targetOrigin = "http://<id>.artifacts.localhost:4000".
    • iframe → parent: targetOrigin = "http://localhost:4000". The iframe cannot derive the parent's origin a priori, so it hard-codes it; on receipt, the parent must validate event.origin matches the expected artifact subdomain before acting.
    Never '*' from the parent. The iframe MAY use '*' only when bootstrapping a handshake to receive the parent's origin; production code hard-codes the parent origin instead. Three message types from cluster 1 (open-artifact, pm:page, cm:add) extended in v0.2 with annotator bridge messages (cm:flash, cm:refresh, cm:mode) — see topic 10 §O″.
  • Annotator bridge (resolves topic 10 §M-10). Replace the prototype's parent-to-contentDocument injection with serve-time injection. When the SPA toggles annotate mode, it requests the artifact with ?cm=on; the kb daemon rewrites the response to insert <script src="/_kb/annotate.js" defer></script> before </body> (fallback: append at EOF if </body> not found; use lol-html streaming rewriter to avoid matches inside <script> string literals). The injection also includes the artifact's existing comments as inline JSON (window.__KB_COMMENTS = […]) so left-rail marks paint on first frame. Cache key includes ?cm=on. The script runs in the artifact's own origin, has full DOM access (we keep allow-same-origin), and posts to the parent with explicit targetOrigin.
  • HTTPS. HTTP on localhost is fine for v0.1 — the canon uses no secure-context-only APIs. Defer mkcert / self-signed wildcard certs to self-host docs. IPv6: the daemon binds 127.0.0.1:4000 (IPv4-only); if Firefox prefers ::1, either bind both or document the resolution preference.
  • CSP attribute caveat. The Recipe block below shows csp="..." on the iframe. This attribute is Chromium-only (Firefox / Safari treat it as a no-op). Production CSP must come from the artifact server's HTTP response headers, not the attribute. Treat csp= as belt-and-suspenders for Chromium users.
  • Multi-user cache. The ?cm=on injected response embeds user-specific comment data. v0.1 is single-user (loopback-bound daemon), so in-process LRU cache is fine. Self-host (deferred) must either disable caching on ?cm=on responses or key the cache on per-user identity.
Recipe Confidence · HIGH

Sandbox attribute

<iframe
  sandbox="allow-scripts allow-same-origin allow-popups allow-popups-to-escape-sandbox allow-forms allow-modals allow-downloads"
  src="http://<artifact-id>.artifacts.localhost:4000/index.html"
  csp="default-src 'self' https: data: blob:; script-src 'self' 'unsafe-inline' 'unsafe-eval' https:; style-src 'self' 'unsafe-inline' https:;"
  referrerpolicy="no-referrer"
  loading="lazy"
  allow="">
</iframe>

Note on csp=: Chromium-only (Firefox / Safari no-op). The load-bearing CSP comes from the artifact server's response headers (below); the attribute is belt-and-suspenders for Chromium users.

Justifications

  • allow-scripts — artifacts run JS.
  • allow-same-origin — combined with serving from a different origin (subdomain), this gives the iframe its own real, isolated origin. localStorage / IndexedDB / cookies work; the parent SPA's DOM is cross-origin and unreachable. Only safe combo per §A's footgun warning: allow-scripts + allow-same-origin + different serving origin.
  • allow-popups — artifacts may legitimately link out.
  • allow-popups-to-escape-sandbox — clicked popup behaves as a normal page, not an inheriting sandbox. An escaped popup runs at the artifact's origin without sandbox; it can read that artifact's localStorage but the per-subdomain isolation contains it.
  • allow-forms — many artifacts will be small forms (calculators, configurators).
  • allow-modals — alert/confirm/prompt + <dialog>.showModal(). Required by the kitchen-sink canonical artifact.
  • allow-downloads — forward-compat for artifacts that generate CSV/image exports. No current canonical artifact uses it.
  • NOT allow-top-navigation* — an artifact must not be able to navigate the parent SPA away.

Storage strategy

Serve every artifact from <id>.artifacts.localhost. Wildcard DNS (RFC 6761 auto-resolution on Chrome+Firefox; dnsmasq fallback on Safari — see §decisions). Each artifact gets a unique, persistent, real origin → localStorage/sessionStorage/IndexedDB/cookies all work, full isolation, sandbox-removal attack neutered (the iframe can't reach the parent's DOM because they're cross-origin).

Fallback if subdomain serving is infeasible for a target host: serve all artifacts from artifacts.localhost (single shared origin) without allow-same-origin → opaque origin, no storage. kb provides storage via postMessage RPC (storage.get, storage.set, scoped to artifact id). v0.1 canon doesn't need storage so this fallback is acceptable for restricted environments.

Fetch / network strategy

Artifact fetching kb's data: bridge via postMessage. Artifact posts {type:'kb.fetch', url}; parent SPA does the actual fetch with the user's session cookie and posts the result back. Artifacts cannot exfiltrate the user's session even if they go rogue. External CDN/font/script loads work directly, optionally restricted via csp=.

Inter-artifact links

Recommended: postMessage-routed nav. Artifact does e.preventDefault(); parent.postMessage({type:'kb.nav', id}). Parent SPA owns routing entirely. Keeps sandbox tight, gives kb full control over animations, breadcrumbs, history. Matches Claude/ChatGPT artifact-frame patterns.

Iframe lifecycle

Recreate the iframe element on each artifact change (CodePen pattern). Memory cleanup, kills any infinite loops, resets all globals.

CSP on the artifact server

Content-Security-Policy: default-src 'self' https: data: blob:; script-src 'self' 'unsafe-inline' 'unsafe-eval' https:; frame-ancestors http://localhost:4000;
Referrer-Policy: no-referrer
Cross-Origin-Resource-Policy: cross-origin
Cross-Origin-Opener-Policy: same-origin

frame-ancestors ensures only kb embeds artifacts; an attacker can't iframe an artifact into their own page to steal its storage.

Open questions
  • Wildcard cert for the artifact subdomain on a personal server — Caddy auto-issuance via DNS-01 is the cleanest path. Document setup.
  • Safari `*.localhost` spike. macOS Safari delegates to mDNSResponder, which does NOT implement RFC 6761 auto-resolution. Outstanding before v0.1 SPA. If it fails, dnsmasq is the documented Safari fallback (address=/.localhost/127.0.0.1 + IPv6 line). Chrome (M67+, Dec 2017) and Firefox (84+, Dec 2020) already auto-resolve — no spike needed for them.
  • The classifier that routes JS-free artifacts to Shadow DOM — define the heuristic precisely (presence of any <script>? external <script src>? onclick/onload attributes?). v0.2 — every v0.1 artifact goes through the iframe path.
  • Whether to expose a per-artifact "loosen sandbox" flag (e.g. allow camera/mic) — declare in artifact's <meta name="kb-permissions">. v0.2+; topic 07's kb-sandbox pragma is the kindred convention but not yet ratified.
