Topic 07 · HTML-as-medium · Confidence HIGH

verdictThesis confirmed.
Permissive sandbox baseline, per topic 06.

Thariq's Unreasonable Effectiveness of HTML is the design thesis. We grepped all 20 reference artifacts: every one is 10–29 KB, zero external scripts, zero external fonts (post fix-pass; kb-research-extended canon also conforms), zero localStorage, zero fetch(). The "rich" capabilities are achieved entirely with platform primitives. The kb-research-extended canon (5 sample artifacts incl. kitchen-sink.html with <dialog>.showModal()) needs allow-modals — so v0.1 ships topic 06's permissive baseline (allow-scripts allow-same-origin allow-popups…allow-modals allow-downloads + subdomain serving). The strict allow-scripts-only minimum survives as a v0.2+ option behind <meta name="kb-sandbox"> opt-in.

Canon extended · Web Gallery handoff (2026-05-11)

The Web Gallery design handoff (topic 10) ships five additional reference artifacts. They live verbatim at kb-research/sample-artifacts/ and extend Thariq's 20 with three patterns the upstream didn't include:

  • Multi-file artifacts — pm/ (SEV-1 postmortem, 4 files + shared style.css). New dimension to the canon: a pages: [{label, src, file}] data shape + pm:page postMessage handshake. Reference for everything multi-file in topic 10 §F.
  • Full-screen interactive — fullscreen-viz.html. Drag-to-resolve borrow checker. Confirms the thesis at the high end — interactivity is load-bearing, not decorative.
  • Component-showcase stress test — kitchen-sink.html. Every HTML primitive in one page: <details>, <dialog>, native sliders, sortable tables, drag-to-reorder, image zoom, popovers, copy buttons. Use as the iframe sandbox v0.0.1 smoke test — if anything in here breaks, the sandbox is too tight.

The other two (multi-page.html, cost-of-abstraction.html) demonstrate single-file long-reads with internal navigation and a cross-artifact backlink — both within the existing canon's range.

A. The thesis

Markdown's default era is over

Thariq's argument: markdown became the default LLM output for an outdated reason — the GPT-4-era 8K-token context window punished HTML's tag overhead. With 200K–1M context windows, that constraint is gone; the question becomes which format conveys the content best, not which is cheapest. He argues HTML wins for any output longer than a few sentences because markdown can only describe linearly: it cannot lay out two options side-by-side, draw a real diagram, animate a transition, expose a parameter slider, or round-trip a structured edit back to text. HTML can.

The "unreasonable" wins fall into three buckets:

  1. Spatial content — diffs, call-graphs, flowcharts — where markdown flattens information that has positional meaning.
  2. Interactive content — animations, easing tuners, prompt editors — that "can't be described, only felt."
  3. Navigational content — tabbed code, collapsible sections, glossary-in-the-margin — where the same words read very differently when structured.

His one explicit caveat: markdown is still right for short conversational replies, code-only outputs, terminal-style answers, three-bullet summaries.

"Twenty self-contained .html files an agent produced instead of a wall of markdown. Each one trades a document you'd skim for one you'd actually read." — Thariq Shihipar, gallery intro
"Motion and interaction can't be described, only felt. A throwaway page with the real easing curve or the real click-through tells you in five seconds what a paragraph of prose never could." — Thariq Shihipar, gallery intro
"Asking Claude for an explanation in HTML means it can drop in SVG diagrams, interactive widgets, in-page navigation and all sorts of other neat ways of making the information more pleasant to navigate." — Simon Willison, 2026-05-08

Recommended kb default (post cluster-1 amendment): <iframe sandbox="allow-scripts allow-same-origin allow-popups allow-popups-to-escape-sandbox allow-forms allow-modals allow-downloads" src="http://<id>.artifacts.localhost:4000/..."> — topic 06's permissive baseline. The earlier sandbox="allow-scripts" srcdoc="" minimum still covers Thariq's 20 but breaks the kb-research-extended canon (kitchen-sink modal); deferred to v0.2+ as a per-artifact opt-in.

Specific examples that would break under that sandbox: zero from Thariq's set.

kb policy

  1. Default sandbox is allow-scripts only. Covers 100% of the canonical reference set.
  2. Proposed (not v0.1): per-artifact escape hatch via <meta name="kb-sandbox" content="allow-scripts allow-same-origin">. Topic 06 cluster-1 decision shipped a permissive baseline instead; the meta-pragma escape hatch is deferred until v0.2+ if per-artifact tightening becomes desirable.
  3. Do not default to allow-same-origin without subdomain isolation. The cluster-1 amendment keeps allow-same-origin paired with serving from a different origin (subdomain), so cross-artifact contamination is prevented by the origin boundary (each artifact gets its own subdomain origin), not by the sandbox flag. The dogum skill's universal-rules ban on localStorage still applies as authorial convention.
  4. CDN access: not required. If a future v0.2 wants it, use <meta name="kb-csp" content="connect-src https://cdn.jsdelivr.net"> translated to a CSP header.
  5. Fonts: kb does not need to allow Google Fonts. The system-font stack is a feature, not a deficit.
Reconciliation with topic 06 (cluster 1, amended post deep-review): v0.1 ships the permissive baseline from topic 06 Decisions — sandbox="allow-scripts allow-same-origin allow-popups allow-popups-to-escape-sandbox allow-forms allow-modals allow-downloads", served from <id>.artifacts.localhost:4000. The kitchen-sink artifact's <dialog>.showModal() needs allow-modals; future artifacts may use storage which needs allow-same-origin. The strict allow-scripts-only minimum survives as a v0.2+ option behind <meta name="kb-sandbox">, but is not the v0.1 default.
D. Indexing implications

What's reliably extractable

Reliable signals

  • Title. document.title is filled and descriptive in 20/20.
  • First <h1>. Present in 20/20, often duplicates <title> but sometimes more verbose. Use as fallback heading.
  • First paragraph. Most artifacts open with a TL;DR per the dogum skill mandate.
  • Body text. DOM-walk excluding <script>, <style>, <template>. Preserve <code>/<pre> but tag separately for code-search facet.
  • Code blocks. Index in a separate "code" field for prefix/regex search.
  • alt, aria-label, title=. SVG figures often label parts via aria-label.
  • <details> summary text. High-signal — deliberate section headers in non-linear documents. Index as separate "outline" tokens.
Spike update · 2026-05-11 · spike-walker measured scraper (html5ever-backed) extraction over a 104-file synthetic blow-up of the canon corpus: parse μs/file mean = 159, p50 = 155, p95 = 294; total wallclock 17.55 ms. That's ~17× under the 5 ms-per-file budget and ~57× under the 1 s-for-100-files target — extraction is essentially free, and adding more fields has no perf cost worth worrying about. Gotcha: "first <p>" returned None for fullscreen-viz.html (SVG-only body, no top-level <p>). Production extractor should add a body_text_excerpt field via a depth-first walk that skips <script>/<style> and concatenates the first ~400 chars of visible text — that's the reliable body-excerpt for SVG-heavy and non-prose artifacts. Field-distribution on the 8 canon artifacts (1/8 SVG, 1/8 <details>, 8/8 <script>) is corpus-specific — production should resample against the user's ≥50-artifact curated corpus before making density-based claims. Full context: docs/spike-findings.md.

Missing across the reference set (kb mandates)

  • <meta name="description"> — 0/20. Should be required in kb's output prompt.
  • <meta name="keywords"> — 0/20. Optional but cheap.
  • OG / Twitter — 0/20. Out of scope unless kb publishes.

Facets to surface

  • has_svg, svg_count; has_details, details_count; has_form; has_drag; has_animation; has_canvas, has_math (future-proof); has_prompt (true when <template id="kb-prompt"> is present — gates the regen flow); prompt_size_bytes (for the size-cap rule in §D below).
  • js_loc bucketed: static (0), light (1–50), interactive (51–200), rich (200+).
  • css_loc same bucketing.
  • kb_category from <meta name="kb-category">: Exploration / Code-Review / Design / Diagram / Report / Research / Deck / Editor.
  • size_kb.

Thumbnails

  1. Synthetic icon collage. Compose a small SVG from facets. Cheap; informative for kind, poor for content.
  2. Real screenshot via headless Chromium. True fidelity, but 100 ms+ per artifact, 100 KB+ PNGs.
  3. DOM-painted thumbnail. html2canvas in a tiny iframe.

Recommendation: ship (1) as fallback; (2) as default — cache at write-time, free at read-time. Thariq's 20 are visually distinct enough that screenshots dominate.

E. The kb-prompt embedding convention

<template id="kb-prompt"> + <meta> tags

Embedding option comparison

Recommendation: <template> for the prompt body, <meta> tags for the structured fields.

<head>
  <title>Consistent hashing — an interactive explainer</title>
  <meta name="kb-id" content="01J9X4..."> <!-- ULID -->
  <meta name="kb-model" content="claude-opus-4-7">
  <meta name="kb-model-version" content="2026-04-15">
  <meta name="kb-temperature" content="1.0">
  <meta name="kb-created" content="2026-05-10T14:32:11Z">
  <meta name="kb-category" content="research">
  <meta name="kb-tags" content="distributed-systems,hashing,explainer">
  <meta name="kb-sandbox" content="allow-scripts"> <!-- optional override -->
</head>
<body>
  <!-- artifact content -->
  <template id="kb-prompt">
Explain consistent hashing as an interactive explainer.
Include a live ring the reader can add and remove nodes from,
a comparison table vs. modulo hashing, and a hover-linked glossary.
  </template>
</body>

Why this shape

  • <template> content is parsed but not rendered, accessible programmatically as document.getElementById('kb-prompt').content.textContent. Long prose prompts retain newlines without escaping.
  • Structured fields go in <meta> — single-line, easy to extract, survives any HTML minifier.
  • The kb-sandbox meta is the per-artifact escape hatch from section C.
  • A ULID-style kb-id makes kb regen <id> unambiguous and is monotonic — handy for chronological listing without a separate timestamp index.

Privacy: scrub-before-embed pass

The prompt may contain the system prompt (often considered confidential), pasted file contents the user didn't realise were sensitive, API keys, customer data. kb must scrub before writing:

  1. Strip the system prompt by default. Store only user turns. Add <meta name="kb-prompt-system-included" content="false">.
  2. Pattern-redact: AWS keys (AKIA[0-9A-Z]{16}), GitHub PATs (ghp_[A-Za-z0-9]{36}), Anthropic keys (sk-ant-[...]), JWT-looking strings, generic high-entropy 32+ char tokens. Replace with <redacted:type>.
  3. Path scrub: replace /Users/<name>/... and /home/<name>/... with ~/....
  4. Confirmation gate: if prompt > 1000 chars, prompt the user once: "Embed full prompt? (y/n/edit)". Default n for shared/published artifacts.
  5. Audit hook: every regenerate writes the new prompt's diff to ~/.kb/audit.log.

Reproducibility fields

Beyond kb-prompt: kb-model, kb-model-version, kb-temperature, kb-top-p, kb-max-tokens, kb-skill (e.g. "html-artifacts" + version), kb-tool-version (kb itself), kb-source-files (input file SHAs for "regenerate the PR review when the diff changes" flows).

Prior art for prompt embedding

There is no industry convention. Claude Artifacts: no inline metadata, prompt lives only in the conversation. ChatGPT Canvas: same. v0.app: prompt in the web UI, not the file. Simon Willison's tools.simonwillison.net: prompt in the GitHub commit message. kb's <template> + <meta> pattern is novel-but-cheap.

F. Regenerate flow

In scope for v0.0.1, trivial when prompt is inline

$ kb regen 01J9X4HZP2  # ULID from kb-id meta
  ↳ extracted prompt (134 tokens)
  ↳ original model: claude-opus-4-7 (2026-04-15)
  ↳ regenerate with: [Enter for same / number to pick]
        1) claude-opus-4-7
        2) claude-opus-5
  > 2
  ↳ generating...
  ↳ wrote: 15-research-concept-explainer.html (was 13.6 KB, now 14.2 KB)
  ↳ previous version saved: .kb/history/01J9X4HZP2/2026-05-10T14-32.html

Versioning policy

  • Default: keep prior version under .kb/history/<id>/<timestamp>.html. Disk is cheap; lost-work pain real. GC older than N (kb config history.keep=5).
  • --replace: don't keep history.
  • --diff: show unified diff of rendered text content (DOM-walk minus scripts/styles), not raw HTML.
  • --keep-prompt: regenerate but force the new artifact to embed the original prompt verbatim (model upgrade A/B).

Edge case: if the original prompt was scrubbed (secrets redacted), the regenerated artifact will be missing context. Surface: warning: prompt contains 2 redacted tokens, regen may diverge.

G. Compete check

No one has built kb itself

  • Simon Willison has been adjacent for a year — Dec 2025 Useful patterns for building HTML tools treats single-file HTML as natural LLM-tool format, but framed as user-built tools with LLM help, not LLM-as-author. After Thariq, Simon explicitly updates: "this has caused me to reconsider, especially for output."
  • Claude Artifacts (2024–2026) ships exactly this technique — sandboxed HTML/React produced by an LLM. But Anthropic never argued the thesis publicly; Thariq's contribution is the articulation.
  • v0.app ships HTML/React from prompts but pitches as "AI app builder," not "richer-than-markdown artifact medium."
  • dogum/html-artifacts is the first packaged operationalisation — recognition heuristic, 9 categories, "matching-your-style" anti-AI-aesthetic ruleset. Generation-side only. kb should ship a fork-or-reference.
  • tools.simonwillison.net is browse-and-host for one author's manually-curated tools. Closest existing thing to kb but materially different scope.
  • claude-artifact-runner: takes Claude Artifacts and turns them into Vite apps — orthogonal: deploy, not gallery.

No project framed as "html-artifact gallery for LLM outputs with regenerate-from-prompt." This is open territory.

Open questions
  • Whether to ship a kb-skill meta value taxonomy (canonical names like html-artifacts, code-review) or treat it as free-form.
  • Whether to fork dogum/html-artifacts as kb/html-artifacts with kb-specific generation rules (mandatory kb-* metas), or maintain a separate addendum.
