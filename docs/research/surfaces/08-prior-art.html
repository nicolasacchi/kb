Decisions reinforced · 2026-05-11 (clusters 1–4)

Each of the four cluster outcomes strengthens the daemon-path verdict. The plugin/extension alternatives in §G remain rejected with stronger evidence:

  • Cluster 1 (iframe + DNS): per-artifact subdomain serving (<id>.artifacts.localhost) requires a daemon with HTTP virtual-host routing. Obsidian/Karakeep-fork/TiddlyWiki can't do this — they're single-process Electron or static apps.
  • Cluster 2 (HTTP API): 28 endpoints across five groups (topic 11). The CSRF Origin allowlist + async 202 + run id pattern + SSE firehose are exactly the surface plugins can't provide.
  • Cluster 3 (storage + embeddings): lance + sqlite split + multi-model embeddings (kb model {list,download,set,rm}). No alternative in the matrix approaches this stack.
  • Cluster 4 (multi-daemon): federation from v0.1 (~/.config/kb/daemons.toml + GET /api/identity). Obsidian is single-instance Electron — fundamentally incompatible with kb's multi-machine team-mode roadmap.

HTML-as-primary-unit canon is now concretely backed by topic 07's extended canon — Thariq's 20 + kb-research's 5 sample artifacts (sample-artifacts/). The bespoke daemon is the right path with higher confidence than at original write time.

Resolved by cluster 4: v0.0.1 indexer-only vs full-architecture-upfront — cluster 4 committed to TUI + SPA + multi-daemon together in v0.1 ("cluster 4 ambition"). Open question retired.

TL;DR

The gap is real and narrow. Each kb property exists somewhere — daemon (Tailscale, Syncthing), HTML-as-unit (TiddlyWiki, simonw/tools), AI-tagged self-host (Karakeep), prompt-aware (Claude Artifacts). Never combined. Three plugin / extension reframings were considered and rejected — kb-as-Obsidian-plugin, kb-as-Karakeep-fork, kb-as-TiddlyWiki-extension. Each fails on at least one load-bearing requirement: observability (TUI live-watching SSE during indexing/generation), programmatic agent ingest (HTTP API hit by other Claude Code sessions), headless server-side use (self-host with thin clients hitting kb remotely), and HTML-as-primary-unit (one self-contained .html per artifact, not markdown-with-html-guest or capture-snapshot or single-file-quine). A. Bookmark / read-later / curation

Self-hosted is the lesson; HTML-as-snapshot is the gap

  1. are.na — Hosted SaaS. Channel-as-collection model is the philosophical match. No self-host, no executable HTML.
  2. raindrop.io — SaaS bookmark manager. AI suggestions in Pro tier. Not self-hostable; HTML is a static snapshot.
  3. instapaper — Hosted distraction-free reader. Picked up Kobo's Pocket-replacement slot in 2025. Reading prose, not running interactive HTML.
  4. Pocket (RIP) — Mozilla shut down 2025-07-08; API and data deletion finalised 2025-11-12. Strongest argument anywhere for kb's self-hosted, files-on-disk premise.
  5. Omnivore — Open source AGPL, shut down 2024-11-15 after acquihire by ElevenLabs. The omnivore.work fork provides simplified Docker self-host but is functionally cold.
  6. readeck — AGPL-3.0, single Go binary, single Docker container. ~512 MB RAM, ~200 MB disk. Singled out in 2025 as the post-Omnivore default. Treats HTML as readable prose, no LLM-prompt awareness, no daemon-with-multiple-clients.
  7. wallabag — MIT, PHP/Symfony, mature. Heavier than readeck.
  8. Karakeep (formerly Hoarder) — AGPL-3.0, highest-momentum project post-Pocket. Next.js + Drizzle + Meilisearch + Puppeteer; AI auto-tagging via OpenAI or local Ollama; full-page HTML archive; OCR; yt-dlp; mobile + browser extensions. Closest in form. But: archived pages are captured snapshots (input from the web), not first-class authored artifacts (output from an LLM); no prompt linkage; no SSE observability.
  9. archivebox — Self-hosted internet archive (Python, Django, Docker). HTML/PDF/PNG/WARC/media. Designed around capturing the web.
  10. shiori — Go single binary, "simple Pocket clone." URL-centric.
  11. linkding — Django, minimalist. No content archiving by default.
B. LLM-artifact tools

The gap. No first-class tool.

  • Claude Artifacts — Live preview pane in chat. Share/Publish links require viewer login on claude.ai. April-2026 "Live Artifacts" can refresh against MCP-connected data. Artifacts cannot be deployed, hosted, or shared as real apps outside Claude's ecosystem; no native export to a personal archive.
  • ChatGPT Canvas — Same shape. No public gallery, no export-to-personal-archive primitive.
  • v0.app, bolt.new, Lovable — Generators (prompt → app), not galleries. Public community feeds, no per-user "everything I've made" surface.

Self-hosted attempts

  • CrazyDubya/Claude-Artifacts — Closest match by stated intent: "Render Artifacts locally." Single-developer hobby project; embedder, not gallery.
  • Nutlope/llamacoder — Generator (Llama on Together.ai), not gallery.
  • madewithclaude / claudeartifacts.com / awesome-claude-artifacts — Public showcases. Show others' work; no private inbox for your own.
  • Simon Willison's simonw/tools — Most realistic personal precedent. ~200+ standalone single-file HTML tools served via GitHub Pages. Each commit links to the LLM transcript. Design rules: single file, no React/build, CDN deps only. Essentially "kb v0 done in public on GitHub Pages with no daemon." Validates the artifact-as-single-file primitive; leaves untouched everything kb proposes about local search, observability, prompt linkage, daemon architecture.

Verdict: No one has built kb. The space is defined by either walled-garden chat-side previews (Claude/ChatGPT/v0) or one influential dev's GitHub-Pages folder convention.

C. Note apps (overlap risk)

Markdown-shaped, not HTML-shaped

  • Obsidian — Local-first, Markdown vault, plugin-rich. AI plugins (Smart Connections, Cortex). Bases shipped 2025. Considered as plugin host; see section G — rejected because plugin API can't expose HTTP for agent ingest, can't run headless on a self-host server, and the markdown-vault model fights HTML-as-primary-unit.
  • Logseq — Outliner, blocks-as-units. Same shape for our purposes.
  • Bear / Joplin / AppFlowy — Markdown notes apps. Off-axis.
  • Notion — Block-based, hosted, closed.
  • Foam / Dendron — VS-Code markdown wikis.
  • TiddlyWiki (5.3.8, August 2025) — Genuinely interesting precedent. Single self-contained HTML file containing CSS+JS+content; a quine that can save itself. Demonstrates HTML-first PKM is not absurd. But: tiddlers ≠ artifacts. No "this came from prompt X" concept.
  • HedgeDoc / Outline — Multi-user collaborative; off-axis.
F. Closest analogues, ranked

Substance vs form — none combine both

  1. simonw/tools — closest in substance (single-file HTML, LLM-authored, individually addressable, transcript-linked), furthest in form (no daemon, no local index, public GitHub Pages, no observability).
  2. Karakeep — closest in form (self-hosted, AI-tagged, FTS-indexed, full-page archive, multi-client surfaces), furthest in substance (input is "save URL from web," not "ingest LLM output").
  3. Readeck — clean Go-binary baseline for "minimal self-hosted + FTS + Docker." Simpler than Karakeep, same form objection.
  4. TiddlyWiki — only real precedent for HTML-as-primary-unit PKM. Quine-as-app architecture incompatible with kb's daemon ambition.
  5. ArchiveBox — closest adjacent tool: captures HTML at scale, daemon-friendly. Wrong direction (web → archive vs prompt → artifact).

G. The differentiation case

kb's wedge — alternatives considered and rejected

What no one else does: treat LLM-emitted HTML artifacts as the primary unit of storage, ingested via a local daemon that exposes the same data to multiple thin clients (CLI, TUI, SPA over HTTP/SSE) with first-class prompt/transcript linkage and semantic search over the artifacts themselves. Each existing tool gets one or two of those properties; none combine them.

"Generative tools have made it cheap to produce a small interactive HTML artifact for a given thought, but every popular surface for keeping those artifacts is shaped wrong."

Bookmark managers want URLs from the public web. Note apps want markdown blocks. Chat tools refuse to let the artifact leave their walls. Personal-tool collections like simonw/tools live as a public folder with no index or observability. kb is the local daemon that closes that loop — every artifact lands on disk, gets indexed lexically and semantically, served by a single process to whichever surface you want.

Three alternative paths considered — all rejected

Before committing to a bespoke daemon, three "use existing tools instead" reframings were evaluated. Each fails on at least one load-bearing requirement.

  1. kb-as-Obsidian-plugin — rejected. A plugin treating .html as first-class, rendering in a sandboxed iframe pane, with YAML-frontmatter prompt metadata + Smart Connections vector search, would inherit Obsidian's vault, mobile clients, plugin ecosystem. Fails on: (a) observability — Obsidian doesn't expose a streaming surface for an external dashboard to live-watch indexing/generation; (b) programmatic agent ingest — Obsidian plugins can't cleanly expose an HTTP API for other Claude Code sessions to hit; (c) headless server-side use — Obsidian is bound to its Electron UI; a remote self-host with thin browser/CLI clients is not the model; (d) HTML-as-primary-unit — Obsidian treats markdown as the host and HTML as a guest, the inverse of kb's design.
  2. kb-as-Karakeep-fork — rejected. Karakeep already has self-host, AI tagging, FTS, multi-client surfaces. Forking it to add an "artifact ingest" endpoint that accepts inline HTML + prompt would be faster to a working v1. Fails on: (a) HTML-as-primary-unit — Karakeep's data model is "URL + captured snapshot," not "authored artifact + prompt"; reshaping the schema is invasive; (b) observability — no SSE event stream for a TUI to subscribe to; (c) fork maintenance burden — diverging from upstream Karakeep means owning the merge conflicts forever, for a feature set that is decisively not theirs.
  3. kb-as-TiddlyWiki-extension — rejected. TiddlyWiki takes "everything in HTML" seriously and a plugin could treat each artifact as a tiddler. Fails on: (a) quine architecture — TiddlyWiki bundles content + app into one self-modifying file; kb wants one .html per artifact, ingested by an external indexer; (b) no daemon, no thin-client surface — TiddlyWiki is the entire stack in one file; observability + agent ingest + remote thin clients have no place in that model.

Decision: each alternative fails on at least one load-bearing requirement (observability, agent-ingest HTTP API, headless self-host, HTML-as-primary-unit). The bespoke Rust daemon — single binary, multiple thin clients over HTTP+SSE, files-on-disk as source of truth — is the right path. The plugin / extension reframings are documented here as "considered, rejected" for future readers; they should not be reopened without new information that one of these load-bearing requirements has changed.

H. Architecture precedent

Daemon + thin clients is well-trodden

Daemon + REST/SSE + multiple clients

  • Tailscale (tailscaled) — Long-running daemon owns WireGuard + control-plane state, exposes a LocalAPI; same binary acts as CLI when invoked under a different name. Limitation: only one daemon instance can run at a time.
  • Syncthing — Go daemon with REST + WebSocket event API, ships built-in web UI, with multiple third-party CLI / TUI / mobile clients. Almost a textbook reference for kb's intended shape.
  • Jellyfin / Plex — Long-running media server, REST API, multiple thin clients. Same pattern, different content.
  • bitcoind — Daemon + RPC + many third-party clients. The OG of this pattern in OSS.
  • Prometheus + Thanos + Grafana — Separate services rather than one daemon, but the analog: kb daemon as time-series-style store, third-party UIs as the read/visualise layer.

The pattern is so common that kb's choice of it raises no eyebrows. Syncthing is the best reference shape (one Rust daemon, REST + SSE, CLI + Ratatui TUI + browser SPA against the same API). kb's own concrete instantiation lives in topic 11 (28-endpoint HTTP contract) and topic 10 (browser SPA spec). The multi-daemon-from-v0.1 commitment in cluster 4 means kb actually goes further than Syncthing's single-process assumption — federation between user-configured daemons via GET /api/identity.

Ratatui dashboards over SSE

Ratatui is rendering-only; events delegated to backend. Crossterm 0.29+ ships async EventStream. Idiomatic SSE-driven dashboard:

tokio::mpsc channel
  ├─ task A: crossterm EventStream (keyboard / resize)
  ├─ task B: reqwest + eventsource-stream (SSE from daemon)
  └─ main loop: select!, update state, terminal.draw()

The Ratatui FAQ recommends the async-template repo as the starting point. Real-world precedent: Netflix's bpftop, OpenAI's codex CLI both use Ratatui. I found no public end-to-end tutorial specifically gluing SSE + Ratatui — meaning kb is on solid but lightly-trodden ground.

HTML files as primary data unit

  • TiddlyWiki (since 2004) — single self-contained HTML file is the whole app and store via the quine pattern.
  • ArchiveBox — stores HTML alongside PDF, PNG, WARC; HTML is one of the units.
  • simonw/tools — a directory of single-file HTMLs as the unit of distribution.
  • WARC archives, archive.today — HTML-centric but as captured snapshots.

kb's "HTML files as primary data unit, one file per artifact, everything else is metadata" is a defensible and lightly-claimed niche. TiddlyWiki and simonw/tools are the only real prior art and neither overlaps kb's daemon / index / observability surface.

Recommendation Confidence · HIGH

Daemon path confirmed. kb is built as a single Rust binary exposing an HTTP+SSE API to thin clients (CLI, TUI, browser SPA). The plugin / extension alternatives evaluated in section G all fail on at least one of four load-bearing requirements:

  1. Observability surface — Ratatui TUI live-watching SSE during indexing/generation is part of the product, not a nice-to-have.
  2. Programmatic agent ingest — other Claude Code sessions hit kb's HTTP API directly. Plugins can't expose HTTP cleanly; their host app's UI is the integration surface.
  3. Headless server-side use — kb may be self-hosted on a personal server with thin browser/CLI/TUI clients hitting it remotely. Plugins are bound to their host app's process and UI.
  4. HTML files on disk as primary unit — Karakeep treats HTML as a captured web snapshot, Obsidian treats it as a guest in a markdown vault, TiddlyWiki bundles everything into one quine. None match the design.

Each requirement is non-negotiable per the briefing's HIGH-confidence stance on "one daemon + thin clients." The fact that all four exist together is the wedge that justifies the bespoke daemon. The plugin / extension alternatives stay documented in section G as "considered, rejected" for future readers — they shouldn't be reopened without new evidence that one of these requirements has changed.
