Topic 09 · Commenting feature · Confidence MED-HIGH (v1 manual; SPA-aligned)

v1 of commentsTalking while reading.
Manually exported. Auto-resolved on regen.

A small feature that changes the writing loop: instead of editing artifacts, the operator annotates them — selections, sections, chapters, whole files — and exports those annotations to Claude Code, which addresses each comment in the next regen. The UX target is "linear and easy" — like talking to someone while reading. v1 is manual: copy-paste from the web UI, or kb comments export <id> from CLI. Future versions push comments to Claude Code in real time; out of scope here.

Upgrade · v1 → v2 (Web Gallery design integrated 2026-05-11)

The Web Gallery handoff (topic 10) supersedes this page's v1 export-only model with a richer v2. What changed:

  • Threaded replies — comments now have a replies array with author: you|claude. Round-trip is bi-directional: Claude's reply lands back in the JSON and renders inline with a sparkle mark.
  • Schema name — kb-comments/1. See topic 10 §I for the full shape.
  • Three exports — Claude prompt (self-contained instruction), kb JSON (the file Claude reads), Markdown (humans). All three available from one modal with copy + download.
  • Daemon path — kb/{kb}/.review/{id}.json is the canonical persistence location. Resolved by topic 11 §B (post deep-review correction): GET + POST /api/kb/{kb}/review/{id}; topic 10 §M-4 is the concern (resolved), topic 11 §B is the endpoint spec.
  • In-iframe annotator — original design proposes parent-side injection into the iframe's contentDocument. With topic 06's cluster-1 amended sandbox (keep allow-same-origin but iframe is cross-origin from parent), direct DOM access from the parent is blocked. Topic 10 §M-10 specifies the serve-time injection of /_kb/annotate.js. CLI export is deprecated in v2 — the SPA modal owns export.

The technical core of this page — anchor scopes (§B) and fuzzy-match regen stability (§C) — stays load-bearing. Superseded: §D (kb-comments.js shim mechanism) → see topic 10 §I serve-time injection; §E HTTP API table → see topic 11 §B; §H v2-as-MCP roadmap → v2 is now "topic 10 §I + topic 11 §B.3 round-trip" (MCP wrapper deferred separately to v0.3+).

A. Goal & UX target

Like Hypothesis / Google Docs marginalia, on artifacts the operator owns

The writing loop today: read an LLM-generated artifact → notice something to change → edit the artifact, breaking its regen-from-prompt invariant. The commenting loop: read → annotate → continue reading → export annotations → Claude Code regenerates the artifact addressing all annotations at once. The artifact's source of truth stays the prompt + model; the operator's notes accumulate alongside without contaminating either.

Frictionless inline commentary

  • Anchored popover near the selection (Hypothesis / Google Docs pattern). Inline, not modal.
  • Sidebar list of all comments on the current artifact, grouped by scope.
  • Single-keystroke comment entry (c on current selection); single-keystroke export (e); j/k through sidebar; r to mark resolved; ? for help overlay.
  • Status indicators: open (accent), exported (muted), resolved (low-contrast). Stale anchors get a "needs review" pill.

Constraints

  • Comments never modify the artifact HTML directly. That violates topic 07's "artifact is regen-able from prompt" invariant. Comments live in the kb store; the SPA paints them over the artifact iframe at render time.
  • Artifact iframe is sandboxed per topic 06 (post deep-review amended): per-artifact subdomain serving with allow-same-origin — the iframe has a real isolated origin but is cross-origin from the parent SPA, so parent-side DOM access is blocked by Same-Origin Policy. Selection events fire inside the iframe; the v2 mechanism is serve-time-injected /_kb/annotate.js (topic 06 Decisions + topic 10 §M-10), not the v1 wrapper-page shim §D describes.
  • v1 is manual. Per the operator's stated preference: keep the export trigger explicit. Real-time auto-feed to Claude Code is v3 territory.

Not a wiki. Not a discussion forum. (v2 update: replies have author: you|claude — Claude is now also an author of inline replies, per topic 10 §I.) The artifact is the medium.

B. Anchor scopes

Four scopes, ranked by stability across regen

Anchor scopes · representation & stability
ScopeAnchor representationStability across regenUX surface
Fileartifact id (ULID)Highest — survives any regen"Comment on this artifact" button in chrome
Chapterheading-text path (e.g. Tuning > Virtual nodes)High — kb-prompt convention encourages stable headingsButton beside each heading in the artifact-outline sidebar
Section<section> id or data-kb-id attribute if present; fallback to heading + nth-of-typeMediumSame as chapter, finer-grained
Selection{range start/end CSS path + offset} + ~200 char surrounding contextLowest — fragile on regenInline popover at selection

The UI surfaces the scope's stability at create-time: a small label next to the comment input — "file-scope, stable" or "selection, may not survive regen" — so the operator chooses the right scope for the right comment. A "what does this even mean across regens?" comment belongs at file-scope; "fix this typo" belongs at selection-scope.

Convention to encourage: the kb-prompt skill (referenced in topic 07) should add data-kb-id="stable-slug" to top-level <section>s in generated artifacts. This makes section-scope anchors as stable as chapter-scope, and gives the regen path a deterministic re-anchor target.

C. Anchor stability across regens

Auto-fuzzy-match + needs-review for low confidence

The hard problem: kb regen <id> writes a new HTML body. Comment anchors may move, change shape, or disappear. The recipe:

  1. On regen complete, kb walks each open / exported comment for that artifact_id:
    • File scope: unchanged.
    • Chapter scope: exact match on heading-text path → re-anchor automatically. Fuzzy match (Jaro-Winkler / token-sort > threshold) → re-anchor with anchor_state='reanchored'. Otherwise → anchor_state='stale'.
    • Section scope: data-kb-id match if present; fallback to heading + nth-of-type. Same confidence buckets.
    • Selection scope: fuzzy-match the surrounding 200-char context window against the new body. Above threshold → re-anchor with new range path; below → anchor_state='stale'.
  2. Stale comments emit comment.anchor_stale SSE and surface in the SPA sidebar with a needs review badge.
  3. The operator can re-anchor manually (drag-and-drop selection → POST /api/comments/:id/reanchor) or close the comment.

Tunables

  • KB_COMMENT_FUZZY_THRESHOLD — default 0.85 (Jaro-Winkler similarity).
  • KB_COMMENT_CONTEXT_CHARS — default 200 (surrounding window for selection-scope re-anchor).

Auto-resolve on regen. Per the user-confirmed flat threading: any comment with status open or exported moves to resolved when its artifact is regenerated, with resolved_by='regen'. The operator can re-open if the regen didn't address the comment. The auto-resolve fires independent of the anchor re-pinning — a stale-anchor resolved comment is still resolved; the stale-anchor signal is a future-readability hint, not a workflow gate.

D. Iframe boundary — postMessage shim (SUPERSEDED · see topic 10 §I)

Selection inside the artifact iframe → bridge to the parent SPA

Superseded (deep-review 2026-05-11). The original "wrapper page bundles kb-comments.js" mechanism described below is replaced by serve-time injection of /_kb/annotate.js per topic 06 Decisions + topic 10 §M-10. When the SPA toggles annotate mode, it requests the artifact with ?cm=on; the daemon rewrites the response to inject the script before </body>. The script runs in the artifact's own origin (subdomain) with full DOM access via allow-same-origin; communication with the host uses postMessage with direction-aware targetOrigin. postMessage protocol: cm:add, cm:flash, cm:refresh, cm:mode. The §D content below is preserved as v1 design history.

Per topic 06, artifacts run in a sandboxed iframe on a per-artifact subdomain (<id>.artifacts.localhost) without parent-DOM access. The kb SPA can't observe text selections inside the iframe directly. The pattern reuses topic 06's existing postMessage RPC bridge:

Shim inside the artifact iframe

kb's existing artifact-wrapper page (the one that loads the raw artifact body — see topic 06's recipe) is extended to include a small kb-comments.js shim. Bundled with the wrapper, ~150 LOC minified. Behaviour:

// kb-comments.js (running inside the artifact iframe)

document.addEventListener('selectionchange', () => {
  const sel = window.getSelection();
  if (!sel || sel.isCollapsed) return;
  const range = sel.getRangeAt(0);
  const anchor = serialiseRange(range); // { startPath, startOffset, endPath, endOffset }
  const text = sel.toString();
  const context = surroundingChars(range, 200);
  const rect = range.getBoundingClientRect();
  parent.postMessage({
    type: 'kb.selection',
    anchor, text, context, rect
  }, '*');
});

window.addEventListener('message', (e) => {
  if (e.source !== window.parent) return;
  if (e.data.type === 'kb.comments.list') paintHighlights(e.data.comments);
  if (e.data.type === 'kb.comment.scrollto') scrollToAnchor(e.data.anchor);
});

Parent SPA

  • On kb.selection: render an inline "Comment ⌘C" popover at the iframe-relative position (translate the iframe-local rect into parent viewport coordinates).
  • On comment submit: POST /api/artifacts/:id/comments with { anchor_kind:'selection', anchor_payload, anchor_context, body }.
  • For section / chapter / file scope: the SPA chrome owns the affordance — buttons beside each heading in the artifact-outline sidebar; "comment on this artifact" button in the chrome. No shim involvement needed for these.
  • Highlight rendering: parent posts kb.comments.list with the array of comments after fetching GET /api/artifacts/:id/comments; shim paints translucent overlay <div>s at each anchor's bounding rect (clickable, post back kb.comment.focus).

Why this stays inside the topic-06 sandbox model

The shim runs with allow-scripts only. It uses no storage APIs (the comment payload goes to the parent via postMessage). It cannot read the parent SPA's cookies or storage. The artifact subdomain remains opaque from the parent's perspective. The sandbox properties from topic 06 are preserved.

E. Storage + HTTP API + SSE events (SUPERSEDED · see topic 11 §B + topic 04 canonical taxonomy)

The engineering surface

Superseded (deep-review 2026-05-11). v2 stores comments as kb-comments/1 JSON files at kb/{kb}/.review/{id}.json (not sqlite). HTTP API is GET/POST /api/kb/{kb}/review/{id} per topic 11 §B. SSE events are comment.created / comment.exported / comment.resolved / comment.anchor_stale per topic 04 canonical taxonomy. The §E sqlite-and-CRUD content below is v1 design history.

SQLite addition

Comments live in kb's existing relational store (per topic 01's lance + sqlite split). Schema:

CREATE TABLE comments (
  id TEXT PRIMARY KEY,                 -- ULID
  artifact_id TEXT NOT NULL,           -- ref to docs.id
  anchor_kind TEXT NOT NULL,           -- 'selection' | 'section' | 'chapter' | 'file'
  anchor_payload TEXT NOT NULL,        -- JSON, scope-specific (heading path / range / id)
  anchor_context TEXT,                 -- ~200 chars surrounding (selection scope)
  anchor_state TEXT NOT NULL DEFAULT 'fresh',
                                       -- 'fresh' | 'reanchored' | 'stale'
  body TEXT NOT NULL,                  -- comment text (markdown)
  status TEXT NOT NULL DEFAULT 'open', -- 'open' | 'exported' | 'resolved'
  created_at INTEGER NOT NULL,
  exported_at INTEGER,
  resolved_at INTEGER,
  resolved_by TEXT                     -- 'regen' | 'manual'
);

CREATE INDEX comments_by_artifact ON comments(artifact_id, status, created_at);

SSE event types

Extends the schema from topic 04. Same envelope {v, id, type, ts, payload}; new comment.* namespace:

  • comment.created — payload {id, artifact_id, anchor_kind, body_excerpt}. TUI shows in Activity tab.
  • comment.exported — payload {artifact_id, count}.
  • comment.resolved — payload {id, resolved_by}; fires on regen-auto-resolve OR manual close.
  • comment.anchor_stale — payload {id, artifact_id, anchor_kind, prev_context, fuzzy_score}. Surfaces in TUI Errors tab and SPA sidebar with "needs review."

Per challenge #4, author per-type JSON Schema files alongside the existing event types — these are part of the v1 contract, version with v=1 from day one.

F. Web UI behaviour

Inline popover · sidebar · cross-artifact view

Inline popover

  • Appears at the right margin of the iframe near the selection. Vertical alignment to selection top.
  • Auto-dismiss on click-outside, esc, or successful submit.
  • Header shows the scope label ("selection" / "section: Tuning / Virtual nodes" etc.) so the operator can promote the scope before submitting.
  • Body is a small markdown textarea (tui-textarea-equivalent — actual SPA component is React/Svelte, but same UX).
  • Submit posts to POST /api/artifacts/:id/comments, optimistically appends to sidebar, server response confirms or rolls back.

Sidebar (per-artifact comments pane)

  • Right-hand pane in the artifact view, toggleable. Shows all comments on the current artifact.
  • Grouped by scope: file → chapter → section → selection.
  • Each card: anchor preview (heading path or text excerpt) + body excerpt (first ~120 chars) + status badge + actions (edit / resolve / delete).
  • Click a card → scroll iframe to the anchor (parent posts kb.comment.scrollto to shim) → flash highlight.
  • Stale anchors get a yellow border + "needs review" pill; clicking opens the manual re-anchor flow.

Cross-artifact view

  • kb chrome top-nav has a "Comments" surface listing all open comments across all artifacts.
  • Filterable by status (open / exported / resolved), scope, kb (multi-kb future).
  • Clicking jumps to the artifact + scrolls to the anchor.
  • Bulk-export: select N comments → "Export" button → same modal as per-artifact export, multi-artifact bundle.

Keyboard shortcuts (per topic 05's vim-like convention)

  • c — start a comment on current selection
  • e — open export modal for current artifact's comments
  • j / k — navigate the sidebar list
  • r — mark current sidebar comment resolved
  • x — delete current sidebar comment (with confirm)
  • ? — help overlay
G. Export & Claude Code integration (v1 manual) (SUPERSEDED · see topic 10 §I three-export modal)

Two paths, both manual-trigger

Path 1: copy-paste from web UI

Click "Export comments" in the chrome → modal shows formatted text → copy → paste into Claude Code. Default format is plaintext-block (paste-friendly):

## Comments on artifact 01J9X4HZP2 (consistent-hashing-explainer.html)

[c1] CHAPTER · "Tuning > Virtual nodes"
> 100 virtual nodes per physical node
COMMENT (operator, 2026-05-10):
Why 100? Cite the original paper.

[c2] SELECTION · in section "Ring construction"
> nodes are placed by hashing their identifier
COMMENT (operator, 2026-05-10):
Skips over jump consistent hashing as an alternative — add a brief comparison.

— end of comments —

Markdown and JSON formats are toggleable in the modal. Submit marks each comment status='exported', exported_at=now, fires comment.exported SSE.

Path 2: CLI / Claude Code shell

Same data, CLI surface. Claude Code can shell-call this directly during a session:

$ kb comments export 01J9X4HZP2 --format=text
[same output as above, written to stdout]

$ kb comments export 01J9X4HZP2 --format=json
{ "artifact": "01J9X4HZP2", "comments": [...] }

$ kb comments list --status=open
01J9X4HZP2 · selection · "Skips over jump…" · 2026-05-10
01JABCDE   · chapter   · "Tuning > Virtual nodes" · 2026-05-09
…

$ kb comments resolve c1            # manual close (resolved_by='manual')
$ kb comments add 01J9X4HZP2 --file --body "Replace with v0.4"

Claude Code workflow

kb's CLAUDE.md (or a kb-specific skill) instructs:

"Before regenerating an artifact, run kb comments export <id>. Address each comment in the new generation. After writing the new artifact, kb auto-resolves the comments."

The skill / CLAUDE.md addition is a small recipe, not a kb-internal feature. The operator authors it once per project that uses kb.

Auto-resolve on regen

kb regen <id> writes the new artifact, then for every comment on that artifact_id with status open or exported, sets status='resolved', resolved_at=now, resolved_by='regen'. Emits comment.resolved SSE for each. Anchor re-pinning runs concurrently per section C — independent of resolution.

If the regen didn't actually address the comment, the operator re-opens it (one-click in the sidebar). v2 could add an LLM-based "did this regen address comment X?" check; v1 trusts the operator's review.

H. v1 → future roadmap (SUPERSEDED · see v1→v2 callout above)

Three versions of comments, all on the same architecture

  1. v1 (with the SPA milestone) — manual. Web UI inline popover + sidebar. CLI kb comments {add, list, export, resolve, delete, reanchor}. HTTP API. SQLite schema. SSE events comment.{created, exported, resolved, anchor_stale}. Auto-resolve on regen with anchor fuzzy-match. This page designs v1.
  2. v2 — MCP wrapper. Builds on challenge #7's MCP-deferral. Expose tools kb_comments_for_artifact(id), kb_resolve_comment(id, reason), kb_list_open_comments(). Claude Code (and Cursor / Cline / Aider / Windsurf) can read and resolve comments programmatically without copy-paste. ~150 LOC of tokio + serde_json; daemon stays unchanged.
  3. v3 — real-time push. Claude Code subscribes to comment.created SSE via the MCP bridge. New comments trigger a Claude Code skill that proposes a regen automatically. The operator approves (or edits) the proposal. The "talking to someone" UX becomes "while writing alongside someone."

The architecture supports all three. v1 wires only the manual surfaces; v2 and v3 are additive shims over the same data model. No re-architecture between versions — that's the test for a good v1.

Recommendation Confidence · HIGH (for v1, given SPA exists) SUPERSEDED by v2 — see callout at top + topic 10 §I + topic 11 §B.3

Ship v1 with the SPA milestone. The architecture changes are modest and additive:

  1. Add the comments sqlite table + 7 HTTP routes + 4 SSE event types. ~300 LOC of axum + sqlx.
  2. Extend the topic-06 artifact-wrapper page with the kb-comments.js shim. ~150 LOC vanilla JS.
  3. SPA components: inline popover, per-artifact sidebar, cross-artifact view, export modal. The bulk of the UX work — defer detailed design to the SPA implementation phase.
  4. CLI subcommands kb comments {add, list, export, resolve, delete, reanchor}. Thin wrappers over the HTTP API.
  5. Per-event JSON Schemas alongside the existing event taxonomy.

Anchor stability via auto-fuzzy-match with anchor_stale callout (Jaro-Winkler ≥ 0.85, 200-char context window, both configurable). Auto-resolve on regen — flat threading per the operator's confirmed v1 stance. Export defaults to plaintext for paste-into-Claude-Code; markdown and JSON behind toggles. Treat the SSE event additions as a v1 contract — version with the existing events.schema.json.

v2 (MCP wrapper) and v3 (real-time push) are roadmap, not v1 scope. The architecture supports them without changes; design when there's pressure to add them.

Open questions
  • Cross-kb comments? Multi-kb is namespaced (briefing, HIGH confidence). Comments live per-kb by default — cleaner mental model, simpler queries. Cross-kb roll-up view in the SPA "Comments" surface is achievable later via ?kb=* filter.
  • Comment privacy on export. A comment may include the operator's private thinking. Apply the same scrub policy as the kb-prompt embedding (topic 07) before export — opt-in default for shared exports, opt-out for personal. v1 default: no scrub (single-user, local-only).
  • Material restructure on regen. If the regen removes the chapter the comment was anchored to, fuzzy-match fails. Surface as anchor_stale with the original context preserved; the user re-anchors manually or closes the comment. v2 could surface "the chapter you commented on no longer exists — was the comment addressed?" as an LLM-evaluated prompt.
  • Threading. Decided: flat in v1 (operator confirmed). Schema migration for v2 threading adds a nullable parent_comment_id column.
  • Mobile / small-screen UX. SPA is desktop-first; comment popover layout on phone is deferred.
  • Auto-resolve correctness check. Should auto-resolve fire only if the regen actually addressed the comment, or unconditionally? V1 unconditional (operator can re-open). V2 could attempt LLM-based "did the regen address this?" check.
  • Comment-on-the-prompt-itself. If the operator wants to comment on the kb-prompt embedded in the artifact (the meta tags, not the body), is that a file-scope comment with a special anchor, or out of scope? Default: file-scope; the regen flow incorporates it as prompt feedback.
  • Conflict resolution on simultaneous regen + comment. Operator adds comment c5; Claude Code regen completes; c5 was added after the prompt was sent. Should c5 auto-resolve? Default: no — only comments that existed at regen-start are auto-resolved. Track a regen_started_at timestamp on each regen.
