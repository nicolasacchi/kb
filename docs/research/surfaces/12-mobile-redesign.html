Topic 12 · SPA chrome on narrow viewports · Design review · 2026-05-19

Phase 1: tablet ≥768px (CSS-only).
Phase 2: phone ≥375px (FloatingPill → bottom sheet).

The SPA's FloatingPill + popover + comments panel were designed at desktop widths. Tablet works mostly accidentally; phone breaks: the pill overflows, the popover clips outside the viewport, the comments panel can't share screen with the iframe, and atlas is unusable. The iframe content stays the author's responsibility — this doc only redesigns the SPA chrome around it.

Target widths

Three breakpoints, chosen against real devices that surface in the access logs:

BucketWidthReal-world devicesPhase
Phone375 – 599 pxiPhone SE/12/15, Pixel 7, most Android in portraitP2
Tablet portrait600 – 899 pxiPad Mini portrait, foldable inner, narrow laptop windowP1
Tablet landscape / desktop≥900 pxiPad landscape, MacBook Air, monitorshipped

P1 is CSS-only — media queries, layout reflow, no JS or component restructuring. P2 is a real redesign because the FloatingPill+popover pattern doesn't translate cleanly to phone-native idiom; the pre-design assumption is bottom-sheet drawers replace popovers.

What breaks today

Concrete failures observed at narrow widths:

  • FloatingPill horizontal overflow. At <600 px the inner row (kb pill, source path pill, nav arrows, comments toggle, sibling popover trigger) wraps awkwardly or clips. The pill itself has min-width: ~520px implied by its child content.
  • Popover positioning. The G3/G4 sibling popover opens with a fixed width anchored to the trigger. At phone widths the popover hangs off the right edge of the viewport with no reflow fallback.
  • CommentsPanel + iframe split. On ?cm=on the SPA renders a side-by-side flex: iframe on the left, comments panel ~360px on the right. At <1024 px the iframe gets squeezed to unusable. At <768 px there's nothing usable.
  • Gallery card grid. The CSS grid auto-fits to ~280px columns; at 375px we get one column but with too-tight gutters and the card chrome (tags, glyphs, footer) gets cramped.
  • Atlas view. The 600×360 SVG is rendered as-is. At 375 px screen-width, points overlap; tap-targets are sub-12px; nobody can use this.
  • IndexHero featured block. Renders fine at all widths but its margins assume desktop-class horizontal padding.

Phase 1 — tablet (≥768 px, CSS-only)

Goal: nothing visually broken at iPad portrait. Each fix is a CSS file edit; no component refactors.

ComponentP1 change
FloatingPillAt <900px wrap the source-path pill onto a second row inside the pill (CSS flex-wrap on the inner container).
Sibling popoverAt <900px: max-width: calc(100vw - 32px), anchor-shift to clamp inside the viewport with a 16px gutter.
CommentsPanelAt <1024px: stack vertically (iframe on top, panel below). Panel max-height 40vh + scroll.
Gallery cardsAdd explicit breakpoint at 768px: 2 columns at 768–1023, 3+ at ≥1024 (auto-fit). Tighter inner padding at narrow widths.
AtlasViewIf window.innerWidth < 800, render a placeholder: "Atlas needs ≥800 px width — try landscape or a larger screen." Plain divs, no SVG.
IndexHeroReduce horizontal padding to 16px at <900px.

Estimated effort: 1-2 days. No new components, no JS, no new Playwright specs (the existing visual flow holds; we'd want a single new spec asserting the atlas placeholder + popover clamp).

Phase 2 — phone (≥375 px, FloatingPill rebuild)

The redesign:

  1. Collapsed state on phone — single floating button (FAB), bottom-right corner with safe-area padding. Contains the kb glyph + an unread-comments badge.
  2. Expanded state — tap the FAB → bottom-sheet drawer slides up, takes 50-60% of viewport height. Drawer hosts: kb name, source path, nav arrows, comments toggle, all the popover content (folder/sort/recent/siblings) inline as accordion sections.
  3. CommentsPanel on phone — full-screen overlay (modal sheet), accessed via the comments toggle in the drawer. Not side-by-side; phone doesn't have the pixels for split.
  4. Gallery cards on phone — single column, edge-to-edge with 12px gutters. Card chrome strips tags+glyphs to a single line ("3 tags · longread"). Filename + age + first-tag color band.
  5. Atlas on phone — placeholder div from P1, no point in trying.
  6. kb-switcher on phone — tap-and-hold the FAB → bottom sheet for kb picker. Or move to a dedicated route /kbs.
  7. Detail iframe — full-bleed (100vw × calc(100vh - safe-area-bottom - FAB height)). The FAB floats on top so the iframe content stays maximised.

Open decisions

Seven open-points the implementation round needs to resolve. Marked with my lean; flag any pushback.

  1. FAB position — bottom-right (standard) vs bottom-center (thumb-reachable). Lean: bottom-right with safe-area-inset-right.
  2. FAB content — kb glyph + unread badge, vs minimal "kb" wordmark, vs hamburger icon. Lean: kb name (truncated to 2 chars) + unread dot. Hamburger feels generic.
  3. Drawer dismiss gesture — tap outside, swipe down, or explicit close button. Lean: all three; the close button is the AT-accessible path.
  4. Sibling popover content on phone — inline accordion sections in the drawer (folder/sort/recent as collapsible blocks), vs nested sub-sheets. Lean: accordion sections; nested sheets are confusing.
  5. Comments composer on phone — full-screen modal, vs bottom sheet, vs inline-in-iframe (re-using annotate.ts's dialog). Lean: full-screen modal — annotate.ts's showModal() is the right primitive but it lives in the iframe, not the parent; the SPA path is a modal route /a/:kb/:id/cm/:cid.
  6. kb-switcher gesture — tap-and-hold the FAB, vs a dedicated route, vs a separate persistent UI element. Lean: dedicated /kbs route, accessed from the drawer footer. Hold-gesture is undiscoverable.
  7. Back-to-gallery on phone — browser back, vs swipe-right, vs explicit button in the drawer. Lean: explicit button in the drawer + browser back (both work). Swipe gestures fight the iframe scroll.

Risks & what to watch

  • Phase 2's CommentsPanel modal route — adds a URL state for the composer that didn't exist before. Touching the router config can drift the existing /a/:kb/:id/* splat semantics. Mitigation: use search-param state (?cm=<cid>) instead of a path segment.
  • iframe full-bleed on phone — the artifact content is desktop-authored; many will have horizontal scroll or 1000px-wide layouts that overflow the viewport. SPA can't fix this; document the expectation in authoring-artifacts.md (a phone-friendly <meta viewport> snippet, fluid widths).
  • Drawer focus trap — must keep keyboard nav and screen-reader announcements correct. Reuse the <dialog>.showModal() pattern (annotate.ts already uses it).
  • safe-area-inset on iOS notch / dynamic-island devices — FAB position + drawer corners must respect env(safe-area-inset-*).

Non-goals

  • Native mobile app. The PWA route (install-to-home-screen, offline cache, push notifications) is a separate decision; not in scope here.
  • Touch gestures beyond tap + standard scroll. Swipe-to-dismiss is the only optional gesture; if drag-handling fights the iframe scroll, drop it.
  • Reflowing artifact content. The iframe stays at the author's chosen layout; the SPA chrome adapts around it.
  • Phone landscape. ≥600px width hits the tablet bucket; the FAB shape stays mobile but the gallery grid expands.
