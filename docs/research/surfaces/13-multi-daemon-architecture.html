Topic 13 · D7 — SPA against ≥1 daemon · Design review · 2026-05-19

One active daemon at a time, picked by URL.
B2 (true multi-origin) baseline; B1 (federation) as Traefik-only optimisation.

The SPA today is base = "" — every fetch is same-origin against the daemon that served it. With co-located peers (sibling kbB.example.com hosts) and remote peers (laptop, work machine), B1 alone isn't enough — federation only works when daemons trust each other inside one Traefik. This doc commits to B2 as the architectural baseline and uses B1 as a Traefik-config optimisation for peers that happen to be co-located.

Problem statement

The fleet TUI already addresses multi-daemon for the terminal. The SPA hasn't — three pieces are hardcoded same-origin today:

  • web/src/api/client.ts — REST surface (fetchDoc, fetchDocs, fetchReview, fetchAtlasEdges, ...).
  • web/src/api/history.ts — history POST family (recordOpen, recordScroll, recordSearch, fetchHistory).
  • web/src/api/sse.ts — SSE consumer. Already daemon-aware (state.url per daemon); the fleet TUI's per-daemon-SSE pattern was lifted here too. No change needed for D7.

D7-prep (commit on this round) extracted the base URL into web/src/api/base.ts with a getter/setter; client.ts and history.ts now read it on every call. Forward-compatible with whichever pattern lands.

Three patterns

Recap of the options surfaced in the deep-review residue discussion:

B2True multi-originPer-daemon base, CORS preflight, per-daemon authCORS response headers; cross-daemon Origin allowlist3-5d

Why B2 as the baseline: B1 requires the daemons to be co-located behind a shared trust boundary (one Traefik, same Authelia chain). A laptop offline kb can't proxy through the production hub — it'd need a public endpoint and reverse-tunnel. The fleet promise is "see everything from one SPA" regardless of where the daemons live; B2 is the only pattern that delivers that.

Why B1 stays around: when two daemons are co-located, B1 is cheaper (no CORS dance, single Authelia session). Implementation: a Traefik rule + a [server.federation] kb.toml block, no SPA changes. Ship as a follow-up optimisation, not a Round 8 commitment.

Mental model — one active daemon

The TUI shows multiple daemons side-by-side (OVERVIEW rolls them up; TRAFFIC overlays req/sec). The SPA does not attempt that — there's no useful "unified gallery across daemons" on a small canvas. Instead: one daemon active at a time, identified by URL.

https://kb.example.com/?daemon=production       (default — kb.example.com itself)
https://kb.example.com/?daemon=laptop           (proxied via B1 or remote-CORS via B2)
https://kb.example.com/?daemon=remote-server    (only via B2)

The SPA loads at kb.example.com (the "host" origin). The ?daemon= query param picks which daemon answers data requests; the host origin still serves the JS/CSS bundle. Switching daemons in the SPA mutates the URL (history.pushState) so deep links work.

Why not daemon.kb.example.com subdomain?

Each daemon already owns a subdomain space for its artifact iframes (*.artifacts.kb.example.com, *.artifacts.kb-laptop.local). Putting the SPA itself on a daemon-specific subdomain doubles the namespace and forces the SPA bundle to be rebuilt per-daemon. Single-host SPA with query-param selection is cheaper.

B2 architecture (baseline)

SPA side

  1. Daemon list source. A new /api/daemons endpoint on the host daemon returns the configured fleet (or just [{name, base_url}]). The SPA fetches it once at boot; populates a daemon picker. Same source the TUI's daemons.toml uses, but served via HTTP so the SPA doesn't need filesystem access.
  2. Boot path wiring. App.tsx reads ?daemon= from useUrl(); calls setDaemonBase(daemon.base_url) from api/base.ts before any data fetch fires.
  3. Daemon switch UI. New <DaemonPicker> component in the LeftRail (or a dedicated header dropdown). Selecting a daemon mutates the URL; SSE reconnects via the existing sse module (which already takes a per-daemon URL).
  4. Per-daemon bearer auth. Today the SPA relies on Authelia's session cookie + Traefik's kb-inject-bearer middleware. Cross-origin destroys that — cookies are per-domain. The SPA must explicitly carry a per-daemon bearer. New api/bearer.ts module mirrors kb-tui's set_bearer: the daemon picker UI prompts for / stores tokens per daemon. Local-only daemons can omit (they bypass on loopback).
  5. iframe artifact-host. Today useArtifactHostSuffix() reads /api/identity and gets ".artifacts.kb.example.com". With per-daemon base, this query now returns the suffix matching the active daemon. The iframe loads from <id>.artifacts.<active-daemon-suffix>.
  6. postMessage origin checks. web/src/lib/artifactHost.ts's isArtifactOrigin needs to compare against the active daemon's suffix (not a single hardcoded value). Already parameterised — D7 just threads the active suffix through.

Daemon side

  1. CORS preflight on /api/*. Today every cross-origin POST fails preflight (no CORS response). Need to respond to OPTIONS with Access-Control-Allow-Origin matching the requesting SPA's origin iff it's on the cross-daemon allowlist.
  2. Cross-daemon Origin allowlist. A new [server] cross_daemon_origins = ["https://kb.example.com", "http://kb-laptop.local:4000"] in kb.toml. Origin-allowlist middleware accepts any origin in this list in addition to the configured parent_origin.
  3. Bearer-per-daemon. Already done — each daemon's auth.token is its own. The SPA carries the right one because it stored them per daemon.
  4. `/api/identity` includes artifact host suffix. Already does — the field exists. D7 just makes the SPA use it as the source of truth (today some code paths hardcode .artifacts.localhost as a fallback).
  5. `/api/daemons` endpoint on the host. Returns the fleet list (name, base_url, status). For a singleton deploy, returns just self. For a multi-daemon deploy, returns the union of daemons.toml + self.

B1 as a Traefik-only optimisation

When two daemons sit behind the same Traefik (sibling hostnames kbA.example.com + kbB.example.com), the cross-origin dance is unnecessary — Traefik can proxy. Ship as a config recipe, not as SPA code:

# docker-compose.yml — add a second kb service:
kbB:
  build: { context: ~/project/kbB }
  image: kb:local
  labels:
    - "traefik.http.routers.kbB-api.rule=Host(`kbB.example.com`)"
    - "traefik.http.routers.kbB-api.middlewares=authelia@docker,kbB-inject-bearer"

Then the SPA loaded from kb.example.com opens ?daemon=kbB → base URL https://kbB.example.com → Traefik routes to the kbB container, same Authelia session applies, CORS preflight succeeds because both origins share Authelia's SameSite=Lax cookie. No SPA code change — B2 already handles this transparently. B1 is then a deployment recipe documented in docs/self-host.md.

iframe artifact-host coordination

The trickiest cross-cutting concern. Each daemon has its own artifact subdomain space (*.artifacts.kb.example.com, *.artifacts.kb-laptop.local). When the SPA active daemon switches:

  • The iframe URL must re-target — new suffix, possibly new id space.
  • postMessage origin checks must update — pre-D7 the parent uses one hardcoded suffix; post-D7 it reads the active daemon's suffix from useArtifactHostSuffix() (already an SSE-subscribed hook).
  • The runtime injection (routes/artifact.rs::runtime_js) hardcodes postmessage_target from parent_origin — each daemon needs to set this to https://kb.example.com (the host SPA), regardless of which daemon serves the artifact.

Net result: every daemon in the fleet must configure parent_origin = "https://kb.example.com" (or whichever single origin hosts the SPA). The SPA's host origin is the canonical parent for every daemon's iframes. Document this in self-host.md.

SSE strategy — one active daemon

The fleet TUI subscribes to every daemon's SSE simultaneously and aggregates in traffic/events tabs. The SPA does not: only the active daemon's SSE is open. Rationale:

  • SSE consumers run in the browser; each connection is a long-lived TCP socket. Browsers cap ~6 connections per origin; multi-daemon would burn through that fast.
  • The SPA's reactive UI updates (gallery refresh on artifact.indexed, history bump on history.recorded) only make sense for the daemon the user is currently looking at.
  • Daemon-switch in the picker tears down the old SSE + opens the new one. The existing sse.ts module's add(url) / remove(url) already supports this — the active daemon swap is a remove-old + add-new.

If "see live activity across the fleet" is wanted later, the TUI is the right surface — it's already designed for it.

URL scheme

Decision: query param, not path segment.

?daemon=production               (default; can omit)
?daemon=laptop
/a/kb/<id>?daemon=laptop          (deep link to artifact on a specific daemon)

Why not /d/<daemon>/a/<kb>/<id>? It's nicer but doubles the route table. Query param is one router rule.

Default selection: the URL the SPA was served from. If kb.example.com serves the SPA, ?daemon= default is kb.example.com. Avoids "what's my home?" ambiguity.

Open decisions

  1. Daemon-list source format. Just {name, base_url}, or include artifact_host_suffix + auth_required: bool so the SPA pre-knows what to ask for? Lean: include both; chatty but stable.
  2. Bearer storage. Per-daemon token in localStorage (durable, cross-tab) vs sessionStorage (transient). Lean: localStorage; the SPA's bearer-show route can clear on demand.
  3. Token entry UX. Prompt at first cross-daemon switch, vs a Settings tab, vs assume Authelia/SSO carries it. Lean: settings tab + first-switch prompt as a one-off.
  4. Cross-daemon Origin allowlist. Static config in kb.toml, vs runtime API /api/peers readable by the operator. Lean: static cross_daemon_origins array in kb.toml; runtime config is a future-feature.
  5. Daemon picker placement. Header dropdown next to KB picker, vs a dedicated /daemons route, vs a global D hotkey (mirror of TUI). Lean: header dropdown; the TUI's D overlay is too modal for browser muscle memory.
  6. OPTIONS handler for CORS. Per-route axum config, vs a tower middleware that handles preflight generically, vs tower-http::cors. Lean: tower-http::cors — well-tested, configurable, matches the trusted-proxy allowlist.
  7. What happens if a peer is unreachable. Hide from the picker, vs grey-out with "offline since <timestamp>", vs error toast. Lean: grey-out; the picker is the operator's view of the fleet's health.

Risks & what to watch

  • CORS preflight cost — every state-changing POST gains an OPTIONS round-trip. For history/scroll (debounced 1s) that's 1 extra request per active reading session, negligible. For batched comment writes it could matter; if so, Access-Control-Max-Age caches the preflight for 24h.
  • SSE behind CORS — EventSource supports CORS but only when the daemon sets the headers correctly AND the SPA opens the stream with the right URL (no withCredentials mismatch). Same trap that bit the early SPA on Chrome's stricter SSE preflight.
  • Bearer leak — per-daemon tokens in localStorage are accessible to any JS in the SPA origin. The SPA is small + first-party, but any XSS (e.g. S1 if we'd missed it in Round 1) leaks every daemon token. Watch for new XSS surface; the comment-body escape (commit a4aa6c5) stays load-bearing.
  • Daemon-switch mid-flight — what if the user switches daemons while a history POST is in flight? AbortController on every fetch should handle this. Was extended in Round 7 (commit 9860fd0); D7 amplifies the test surface.
  • iframe re-mount on switch — the parent iframe's origin changes; the artifact reloads. Document this in the SPA's daemon-switch path (the user expects a flash).
  • artifact_host_suffix mismatch — if a peer daemon's parent_origin isn't set to the SPA's host, postMessage rejects from the parent side. The host-SPA prints a clear warning on mismatch (banner like the pre-existing identity check).

Non-goals

  • Unified gallery across daemons. The fleet TUI is the surface for fleet-level views. The SPA is single-daemon-at-a-time.
  • Cross-daemon search. Search queries hit the active daemon's lance only. Fan-out is a future feature, probably API-level rather than SPA-level.
  • Cross-daemon comments / review file portability. Comments live in <state>/<kb>/.review/<id>.json per-daemon. The SPA shows the active daemon's comments only.
  • P2P daemon discovery. mDNS already exists for LAN; over-the-internet discovery is out of scope. The operator lists peers in kb.toml.
