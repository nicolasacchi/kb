Typo tolerance in keyword search: a spike, a regression, and a fix

kb's BM25 arm has never tolerated a typo — a single dropped or transposed letter in a search query returns nothing, even though lance's own inverted-index implementation ships fuzzy full-text matching out of the box. This spike wires that capability up behind a new, default-off [kb.<name>.search] typo_tolerance flag — but the straightforward, "just enable it" version measurably wrecked quality on ordinary, typo-free queries in the repo's own bench. What shipped instead is a narrower fallback design that the bench confirms is quality-neutral.

Headline A blanket rewrite — fuzzing every query term unconditionally via FullTextSearchQuery::new_fuzzy — dropped Recall@1 from 0.150 to 0.000 and MRR from 0.378 to 0.076 on the repo's own 20-query keyword-mode gold set, with zero typos in any of those queries. Fuzzy matching floods the ranked set with weakly-related noise even when an exact hit already exists. The shipped design instead runs the exact query first, unchanged, and only falls back to a fuzzy pass when the exact arm returns nothing — which bench-measures byte-identical quality to the flag being off, for a genuine typo-tolerance win on the queries that would otherwise return nothing at all.

What's actually under the keyword arm

Storage::bm25_query (crates/kb-core/src/storage/lance.rs) drives lance's inverted-index FTS over five text columns (FTS_COLUMNS = [title, body, headings, code, prompt]), each with its own lance Index::FTS built by ensure_fts_index. This is not a hand-rolled postings list: lance-index 4.0.0 ships a real tantivy-style inverted index — a term dictionary backed by an fst::Map (a finite-state transducer), postings lists, and a BM25 scorer (lance_index::scalar::inverted). Crucially, that same crate already exposes fuzzy matching natively: MatchQuery (a leaf FTS query) carries a fuzziness: Option<u32> field, and when it's set, the executor runs a genuine fst::automaton::Levenshtein walk over the index's own term dictionary to find every term within the given edit distance — no separate term-dictionary structure to build or keep in sync ourselves. This changed the shape of the spike entirely: the question was never "can we cheaply derive a term dictionary from the existing index" (we can — it's already there, and lance already walks it for us) but "does turning this existing capability on actually help."

Attempt one: turn it on, unconditionally

The obvious first cut: when typo_tolerance is set, swap the exact FullTextSearchQuery::new(q) for a fuzzy one and always use it. Two library quirks surfaced immediately:

  1. None ("auto" fuzziness) is a no-op. MatchQuery::auto_fuzziness (0 for tokens ≤2 chars, 1 for 3–5, 2 for longer) reads as the natural "smart default," but the executor's own is_fuzzy gate (fts.rs/index.rs) is matches!(fuzziness, Some(n) if n != 0) — which None never satisfies. Asking for "auto" silently falls back to an exact match. A fixed distance (we used Some(1), matching this spike's own "edit-distance-1" framing) sidesteps the gate entirely.
  2. Fuzziness doesn't survive lance's own multi-column auto-fill. A MatchQuery with no explicit column gets expanded, at execution time, by fill_fts_query_column — and for >1 indexed columns (title+body alone already qualifies) that function rebuilds a fresh MatchQuery::new(...) per column via MultiMatchQuery::try_new, discarding the original's fuzziness entirely. A naive FullTextSearchQuery::new_fuzzy(q, Some(1)) against any real, multi-column-indexed kb therefore silently degrades back to an exact match — the opposite of what the flag promises.

Once fuzzy_query was fixed to build the compound multi-column query itself (reading which of FTS_COLUMNS currently have a live FTS index via lancedb's Table::list_indices, then setting fuzziness on each per-column leaf directly), the mechanism worked exactly as advertised: a single-letter typo against a single-document fixture now matched. But the bench told a different story at real-corpus scale.

The bench regression

Evidence gate: kb bench run --modes keyword against docs/research (146 docs) with the repo's own 20-query gold set (bench/queries/kb-docs.jsonl) — ordinary, well-formed natural-language queries, no typos anywhere in the set. Two throwaway daemons, one config difference ([kb.kb-docs.search] typo_tolerance = true):

Every quality metric collapsed — Recall@1 to zero. The mechanism itself was working correctly (fuzziness really was reaching every column); the problem is what fuzzy expansion does to ranking once it's live for every term. MatchQuery's default Operator::Or means a document counts as a hit if any expanded token from any query term matches — so a query like "embedding bake-off recall comparison between bge small base and large" now also weakly matches every document sharing an edit-distance-1 neighbor of any of those (very common) words. BM25's IDF weighting can't fully compensate: the ranked set is diluted with enough marginal matches that the genuinely relevant document's rank-position moves down or off the page entirely. Fuzzing a term that already has a perfect exact match earns you nothing and costs you precision.

The fix: fallback, not rewrite

The shipped design in bm25_query runs the ordinary exact query first, always, unchanged. Only if that comes back completely empty — and only when typo_tolerance is on — does a second, fuzzy pass run and supply the result instead. This has three properties that matter:

  • Every query the exact arm already answers is untouched. No dilution risk for the overwhelming majority of searches, because the fuzzy query never runs for them at all.
  • The flag only ever changes the outcome of a query that would otherwise return nothing — which is precisely kb's existing "corpus-gap signal" territory (the zero-hit query tracking shipped in GC-B3): a zero-hit search is already a notable event, not a routine one, so spending an extra query round-trip there is the right place to pay for typo recovery.
  • Determinism (GC-B1) is untouched either way. false issues the exact same single query as before this flag existed, byte-for-byte. true is identical to false whenever the exact arm finds anything — and when it doesn't, the fuzzy arm still goes through the same rank_sort id tie-break as every other search path.

Quality is bit-for-bit identical (every query in this gold set already has an exact hit, so the fuzzy arm never engages); the latency delta is within normal run-to-run noise on shared hardware — if anything, marginally faster on this run, not slower. A unit test (bm25_typo_tolerance_on_does_not_alter_results_when_exact_arm_already_hits) pins this property directly so a future change can't silently reintroduce the blanket-fuzzy regression. A second pair of unit tests exercises the actual value proposition: bm25_typo_tolerance_off_misses_a_single_letter_typo confirms the exact arm alone finds nothing for a one-letter-dropped query against a single fixture doc, and bm25_typo_tolerance_on_finds_the_single_letter_typo confirms the same query with the flag on recovers the document via the fuzzy fallback.

Recommendations

  1. Ship as opt-in, default off — done. An operator turns it on per kb via [kb.<name>.search] typo_tolerance = true; nothing changes for anyone who doesn't.
  2. Don't extend fuzzy matching to the hybrid arm's BM25 half beyond this fallback shape — it's already wired the same way (same bm25_query call, same fallback semantics), so no separate work needed, but any future change to widen fuzzy matching (e.g. applying it to partial-hit queries, not just zero-hit ones) needs its own bench pass first — this spike's regression shows the failure mode is real and easy to reintroduce.
  3. Memory recall and kb recollect stay exact-only — both call sites pass typo_tolerance=false explicitly. Recall's ranking is root invariant #10 (deterministic, LLM-free, rank-position × salience × decay); introducing a fuzzy fallback there is a separate design question this spike didn't investigate, not an oversight.
Method

Bench harness: a throwaway loopback daemon per variant (isolated KB_HOME, disable_embedder_fallback = true so no embedder/ONNX is ever spawned — BM25-only, per this repo's own scripts/bench-nightly.sh pattern), indexing docs/research (146 docs including this artifact's siblings) and driving kb bench run --modes keyword against the committed 20-query gold set. kb --version at test time: kb 0.22-74-gcd2782de-dirty, matching worktree HEAD. Reports are warm-cache end-to-end wall-time (the query set runs once untimed first); quality metrics are computed by kb bench itself from the gold set's labelled relevant ids, not hand-graded.
