Design · sessions subsystem

Workflow sessions inside kb — collecting, digesting, visualizing, and searching multi-agent work (2026-07)

2026-07-06 · grounded in the session-memory deep review (defect B3 + portfolio P4) and direct inspection of the on-disk workflow structures · implementation prompt: M2 in the next-prompts playbook

Thesis

Multi-agent workflows became the dominant unit of serious work in July 2026 — 7 of the last 12 kb sessions are ultracode orchestrations — and they are precisely what kb records worst: 79–94% of their tokens, tool calls, file touches, and failures are invisible to the digest (defect B3), because everything interesting happens in sidechain transcripts the capture pipeline never reads. Meanwhile the durable raw material is already sitting on disk, structured, deterministic, and richer than anyone is using: every workflow persists a journal with each agent's full structured result, every agent's complete transcript, its meta, and the orchestration script itself.

The design goal is therefore not new instrumentation — it is promotion: lift what already exists into kb's episodic model as first-class, queryable, visualizable records, under the same rulings that govern sessions (deterministic digest, pull-only retrieval, LLM-free daemon, newest-capture scoping). A workflow is to a session what a chapter is to a book — never a free-floating entity.

The perishability asymmetry The richest per-agent metadata (labels like verify:B7, phase assignment, per-agent token counts) lives only in /tmp task outputs. Two consequences shape the design: (1) capture must grab it opportunistically at Stop time while it may still exist; (2) the durable schema must tolerate its absence — label/phase/model become nullable, with the agent's first user message (always durable in its sidechain) as the fallback identity. Long-term fix is upstream: Claude Code writing label/phase into agent-*.meta.json would make this lossless — worth filing.

Resolved positions

D1 — Workflows are children of sessions, not a new top-level entity. A workflow row always hangs off a session (its spawning turn); the sessions surface stays the anchor for navigation, capture, and multi-capture scoping. No new nav section, no separate corpus. Direct Agent-tool spawns are modeled as a degenerate workflow (wf_id = NULL group) so one attribution path serves both.

D2 — Three-layer collection ladder, each layer independently shippable. L1 parses what the main transcript already contains (usage blocks — zero new I/O); L2 captures the journal + script (small, structured, the workflow's real output); L3 extracts tool-lines from sidechains (attribution). Each layer is deterministic, additive, and degrades gracefully when its source is missing. No layer blocks another.

D3 — Extract, never index raw. Sidechain transcripts never enter lance verbatim (the feasibility judge's bloat warning: 14–25 MB per big session would swamp the index and bury recollect). Bulk payloads embedded in the capture HTML ride inside <template class="kb-wf-raw"> blocks — the parser already excludes template content from BM25/embedding (parser.rs:498, the same mechanism that protects kb-prompt), while enrichment still reads it from raw_source. What gets indexed is a compact deterministic digest section; what gets stored in sqlite is structured rows.

D4 — Search surface = names and labels, not transcripts. Workflow name, description, phase titles, and agent labels join the session digest text (meaning-dense, tiny — "kb-code-craft-review · Review · Verify · verify:quarantine.rs" is exactly what a future query matches). Per-agent results are pull-only drill-down via CLI/HTTP, consistent with R0's exclusion of raw transcripts from default search.

D5 — Attribution rows carry provenance. Files/commits/research extracted from sidechains land in the existing session_files/session_commits/session_research tables with two new nullable columns: wf_id, agent_ref (label if known, else agentId). They are excluded from main-thread counters (message_count, token_total stay main-thread-truthful) but included in files/commits listings and kb why — which finally answers "who touched this file" for delegated work: "edited by verify:B7 in wf_1c23d6c7 (session 90086c87)".

D6 — Visualization is post-hoc archaeology, not live monitoring. The SPA renders completed workflow records. No live fleet view (the TUI is the frozen fleet monitor; live orchestration UI is Claude Code's job, and a half-live view would demand SSE plumbing invariant #24 doesn't owe it). The one live concession: the session card refreshes on the next Stop capture like everything else.

D7 — Invariant #11 absorbs workflows; the budget stays at 35. Workflow rows key on (session artifact, wf_id) and every read scopes to the newest capture exactly like sibling tables. The invariant's text gains one sentence ("workflow/agent rows are digest-derived, extraction-only — raw sidechains never indexed") rather than minting invariant #36.

Notes: everything nullable-by-design where the source is perishable (D2's graceful degradation); journal_layer records how much was captured so the UI can say "counters only — sidechains were gone" honestly instead of rendering emptiness as absence of work (the exact dishonesty B3 taught us to avoid). This schema lands via the versioned-migration framework the coverage-gap analysis already demands — the two efforts should share one migration.

Collection — the three-layer ladder

L1 — usage blocks (small effort; fixes the lying counters)

Parse task-notification blocks in the main transcript inside parse_session_activity (it currently discards them): extract <usage> fields, the workflow name from the summary line, wf_id/runId from the result text, status from agents_error + the notification status. Persist as session_workflows rows (agent rows absent at this layer). Zero new file I/O; existing captures self-heal on reindex because the blocks are already inside stored transcripts. This layer is P4-layer-1 in the repair portfolio and ships with the truthful-sessions milestone.

L2 — journal + script (the workflow's true output becomes durable)

In kb-capture.sh, after reading the main transcript, glob the session's workflow dirs and embed two things per workflow into the capture HTML:

  1. workflows/scripts/<name>-<wfid>.js — verbatim (10–30 KB, carries name/description/phases in its meta block);
  2. subagents/workflows/wf_*/journal.jsonl — with each result value capped (~2 KB per agent) at embed time; full results stay in the filesystem journal, whose path is recorded.

Both go inside <template class="kb-wf-raw" data-wf="<wfid>"> so they are enrichment-visible but index-invisible (D3). At Stop time the hook also checks whether the /tmp task-output file still exists (its path appears in the task-notification) and, if so, harvests the per-agent progress records (label/phase/model/tokens) into a compact JSON block — opportunistic, best-effort, nullable downstream. Enrichment then populates session_workflow_agents by joining journal (agent_id → result) + script meta (phases) + harvested progress (labels) + meta.json (spawn_depth).

L3 — sidechain tool-line extraction (attribution, not archiving)

Stream each agent-*.jsonl once at capture time and keep only:

  • the first user message head (~300 chars — the agent's durable identity),
  • tool_use lines for Edit/Write/Read (file paths), Bash (git + kb CLI commands), WebSearch/WebFetch (queries/URLs),
  • paired error tool_results,
  • the final assistant text tail (~500 chars).

Everything else is discarded. Extracted lines feed the existing extraction passes (files → session_files, commits → session_commits, searches/skills → session_research) with wf_id/agent_ref stamped (D5). Per-agent extraction is capped (~8 KB); a 65-agent workflow yields ≤ 0.5 MB of extract versus 14 MB raw. Sidechains are perishable (Claude Code may prune them), which is the argument for running L3 at capture time, not lazily at query time.

Digest changes (the indexed surface)

The deterministic session_digest gains one section per workflow — compact, meaning-dense, truncation-resistant (placed before the files line, like the planned outcome field):

workflows:
  kb-code-craft-review (wf_57bfcaac) — 140 agents / 4 phases
    (Survey · Grade · Verify · Synthesize), 12.8M tok, 2 failed
    failed: grade:storage-actor (retry cap), lens:security (spend limit)
    wrote: docs/research/kb-code-craft-review-2026-07.html (via synthesize:final)

What enters the embedded/BM25 text: workflow name, description, phase titles, agent labels, failure labels, deliverable paths. What stays out: prompts, results, transcripts (D4). This single change makes queries like "security audit workflow", "code craft review", or even "verify quarantine" land on the right session — today they land nowhere.

SPA — visualizing a fleet after the fact

Three additions, all inside the existing sessions route master-detail (no new nav, D1; mobile renders everything read-only, per the mobile-is-a-reader refusal; server state rides TanStack Query + SSE invalidation per invariant #23 — one ["workflow", wfId] query, invalidated by the same session.captured event as the detail rail).

1 · The workflow card (session detail rail)

⚙ kb-code-craft-review wf_57bfcaac ████████████░ Survey 42 · Grade 42 · Verify 51 · Synth 5 140 agents · 138 done · 2 failed 12.8M tok · 71 min ⚠ grade:storage-actor (retry cap) · lens:security (spend limit) → wrote kb-code-craft-review-2026-07.html [open ▸]

Phase segments are proportional to agent counts; failures always named (never just a count — B3's lesson is that hidden failures cost the most); the deliverable line links to the artifact when L3 attribution found one. Card collapsed by default under the existing effort stats; absent entirely for workflow-less sessions.

2 · The drill-down (expands in the main pane)

Agent rows sort errors-first, then tokens. Clicking an agent opens its detail: prompt_head, pretty-printed journal result (client-side JSON.parse attempt, fall back to text), files it touched (L3), its model/duration when known. When labels are null (perishable source lost), rows show prompt_head — honest degradation, visibly flagged by journal_layer.

3 · The concurrency strip (progressive enhancement)

When per-agent startedAt/durationMs survived harvesting, render a deterministic horizontal strip — one thin bar per agent, colored by phase, laid on the workflow's time axis — showing the fan-out/barrier shape at a glance (16-wide waves are instantly visible). When timing data is absent: omit the strip entirely. Never interpolate; a fabricated timeline is worse than none. This satisfies the long-deferred "timeline view" ask in the one place a timeline has dense data.

Also: sessions list rows gain a small ⚙ N badge when workflows exist — the list is where "which session was the big fleet run?" gets asked first.

Size math, retention, risks

  • Lance bloat (the killer risk): naive sidechain embedding would add 14–25 MB per big session to the index. D3's extraction ladder bounds capture growth to ~0.3–0.8 MB per big session, and the <template> trick keeps even that out of the embedded/BM25 surface. Budget check in acceptance: sessions-corpus lance size grows < 5% after reindexing all 138 captures with W2+W3.
  • Retention: kb copies extracts at capture; raw sidechains remain Claude Code's property (prunable). An optional kb sessions archive-raw <sid> tars the full wf dirs into the kb state dir for sessions worth preserving verbatim — explicit, per-session, never default.
  • Dedup across multi-capture: workflow/agent rows key on (artifact_id, wf_id[, agent_id]) and reads scope to newest capture (D7). A workflow captured mid-run at one Stop and complete at the next simply has a fuller newest row.
  • Nesting: spawn_depth > 1 (subagent-spawned agents) renders indented in the drill-down; totals roll up to the workflow, not double-counted (usage blocks already aggregate).
  • Cross-session resume: resumeFromRunId lets a later session resume an earlier session's workflow. Model as a new workflow row carrying resumed_from (wf_id) — a breadcrumb, not a merge; threads already group the sessions temporally.
  • Schema migration: two new tables + six columns — must ride the versioned-migration framework (coverage gap "schema-migration path"), not another CREATE TABLE IF NOT EXISTS accretion.

Open questions

  • Upstream label durability: the clean fix for the perishable label/phase metadata is Claude Code writing them into agent-*.meta.json. File the request; design assumes it never lands.
  • Result size policy: 2 KB per-agent result_head is a guess; the deep review's verifier results averaged ~1.4 KB of JSON and truncated acceptably. Revisit after W2 with real distribution data.
  • Direct Agent-tool spawns without workflows: the NULL-group modeling works, but their usage totals have no <usage> block — L3 extraction is their only counter source. Accept partial totals, flag them, or leave them un-totaled? (Current lean: flag.)
  • Should kb sessions resume quote the workflow result? A resuming agent probably wants the last workflow's return value verbatim (it is the state). Leaning yes, capped — belongs to the Resume-v2 program either way.
