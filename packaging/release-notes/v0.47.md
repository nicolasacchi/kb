## kb v0.47 — segmented omp capture, kb-code finding anchors, sticky diff headers

### Before you upgrade

- **kb-code migration V0046** adds one nullable column
  (`review_findings.reanchor_json`) and moves the kb-code schema epoch to 46.
  It is additive and fast, but it is not a gated epoch, so no automatic
  pre-migration snapshot is taken: back up the kb-code state first. After the
  upgrade an older kb-code refuses the volume (`refuse_if_volume_ahead`);
  rollback means restoring that backup. The kb daemon has no migration in this
  release (schema stays 45).
- **Segmented omp capture is off by default.** Turn it on for running omp
  sessions without a restart by creating
  `${XDG_CONFIG_HOME:-~/.config}/kb/capture-segments` (or start omp with
  `KB_CAPTURE_SEGMENTS=1`; `KB_CAPTURE_SEGMENTS=0` forces it off). It needs a
  `kb` CLI that has `kb sessions segment-plan` (v0.46) and
  `kb sessions drop-part` (this release) on the PATH the hooks use.

### New

- **Segmented omp capture** (behind the flag above). An omp session whose
  translation outgrows the 16 MiB part target is captured as an ordered chain
  of ordinary sessions (part 1 under the session id, parts 2+ under
  `<id>-pNN`, read side from v0.46). Each pass lands the live tail first and
  freezes up to four older parts, so a turn costs the tail only (synthetic
  152 MiB session: 11.2 s per turn with the single capture, 1.0 s per turn
  segmented after a one-time 10 s catch-up; peak RSS 427 -> 69 MiB). A part
  counts as landed only when its write succeeded; a part whose translation
  would exceed 40 MiB is re-planned smaller, never truncated; `/clear` or a
  rewind behind a frozen part drops the superseded parts through
  `kb sessions drop-part`, which verifies the file's embedded ids and never
  touches anything else.
- **`kb-code review findings reanchor <review> <slug> --path P --lines A[-B]`**
  and `POST /api/reviews/{id}/findings/{slug}/reanchor`: move a finding's
  anchor explicitly. Refused with 409 and a named reason unless the new anchor
  resolves exactly; same admission as dispositions; emits
  `review.changed` (`finding.reanchored`); records who, when and from where;
  a later re-import never overwrites it.
- **kb-code review diff:** the current file's header stays pinned under the
  toolbar while you scroll a long file, so "viewed" is always one click away
  (map open or closed).

### Fixes

- **kb-code findings no longer go orphaned after a re-import with corrected
  lines.** A finding's anchor is re-derived from its claimed location when the
  location changed, the anchor is missing, or the stored anchor no longer
  resolves (orphaned) or resolves only approximately to the claimed lines. An
  anchor that still resolves to OTHER lines than the claim is kept and the
  import reports `claim_disagrees_with_anchor` (with its confidence) instead
  of silently trusting either side. Citations that cannot be anchored (path
  absent, file too large or unreadable, line past the end) are reported per
  finding in `anchor_warnings[]` and never stored as an empty anchor. Non-UTF-8
  files are read with one lossy decoding on both the anchor and the resolve
  path, long non-ASCII lines resolve correctly, and an orphaned finding now
  says why (`resolution.orphan_reason`).

### Known issues

- After a SIGKILL of a capture's owner, orphan cleanup is load-dependent
  (about 2.4 s measured idle); a few constant-size reads in the omp capture
  still run in command substitutions, so only an IO stall there could delay a
  TERM.
- With segmented capture on and a `kb` older than this release, superseded
  parts cannot be dropped: the session re-runs its (cheap) pass on every
  trigger and repeats a warning until `kb` is upgraded.
